## 核心概念 / 本质机制

### 1. 寄存器是什么

寄存器是硬件提供给软件的控制接口：

1. 每个 外设控制器有一组寄存器，映射到 SoC 地址空间的固定位置。
2. 软件通过读写这些地址来控制硬件行为。
3. 寄存器宽度通常是 32 位（ARM）或 8/16/64 位（取决于硬件）。

典型寄存器分类：

| 类型 | 作用 | 例子 |
| --- | --- | --- |
| 控制寄存器 | 配置硬件工作模式 | CTRL、CFG、MODE |
| 状态寄存器 | 反映硬件当前状态 | STATUS、SR、ISR |
| 数据寄存器 | 读写数据 | DR、FIFO、RBR/TBR |
| 地址寄存器 | 指定操作地址 | SRC_ADDR、DST_ADDR |

### 2. SoC 地址空间

SoC 把所有外设控制器的寄存器映射到一个统一的物理地址空间：

```text
0x0000_0000 - 0x0FFF_FFFF: ROM / Boot Flash
0x1000_0000 - 0x1FFF_FFFF: SRAM
0x2000_0000 - 0x2FFF_FFFF: 外设寄存器区1（GPIO、UART、SPI...）
0x3000_0000 - 0x3FFF_FFFF: 外设寄存器区2（I2C、ADC、Timer...）
0x4000_0000 - 0x4FFF_FFFF: DMA 控制器
0x5000_0000 - 0x5FFF_FFFF: USB 控制器
0x6000_0000 - ...           : DDR 内存控制器
```

每个外设的寄存器在这个空间里占一段连续地址，这段地址叫做"基地址 + 偏移"。

例如 UART0 的基地址是 `0x2000_0000`，它的寄存器：

```text
0x2000_0000: RBR/THR (数据寄存器)
0x2000_0004: IER    (中断使能)
0x2000_0008: IIR/FCR(中断标识/FIFO控制)
0x2000_000C: LCR    (线路控制)
0x2000_0010: MCR    (Modem控制)
0x2000_0014: LSR    (线路状态)
```

### 3. 物理地址 vs 虚拟地址

```text
物理地址: 硬件总线上的真实地址，CPU 引脚上出现的地址信号
虚拟地址: CPU 指令中使用的地址，经过 MMU 翻译后变成物理地址
```

它们的关系：

```text
CPU 指令使用虚拟地址
  |
  V
MMU 查页表
  |
  V
翻译成物理地址
  |
  V
硬件总线访问
```

### 4. MMU 和页表

MMU（Memory Management Unit）是 CPU 内部负责地址翻译的硬件：

1. MMU 把虚拟地址按"页"（通常 4KB）为单位翻译成物理地址。
2. 翻译规则存储在"页表"里，页表本身放在内存中。
3. 每次虚拟地址访问，MMU 自动查页表完成翻译。
4. 如果页表里没有对应映射，触发"缺页异常"（Page Fault）。

简化版翻译过程：

```text
虚拟地址 = [页号] + [页内偏移]
  |
  V
页号查页表 → 得到物理页帧号
  |
  V
物理地址 = [物理页帧号] + [页内偏移]
```

### 5. 裸机 vs Linux 的地址访问

#### 裸机（无 MMU 或 MMU 直映射）

```c
#define UART0_BASE  0x20000000
#define UART0_DR    (*(volatile uint32_t *)(UART0_BASE + 0x00))

void uart_send(uint8_t ch) {
    UART0_DR = ch;  /* 直接写物理地址 */
}
```

裸机里虚拟地址等于物理地址（或 MMU 配置了 1:1 映射），所以可以直接用物理地址访问寄存器。

#### Linux（MMU 启用，虚拟地址空间隔离）

```c
void __iomem *base = ioremap(0x20000000, 0x1000);
if (!base) return -ENOMEM;

writel(ch, base + 0x00);      /* 通过虚拟地址访问 */
```

Linux 里不能直接用物理地址，必须先 `ioremap` 建立映射。

### 6. `ioremap` 做了什么

`ioremap` 的核心工作：

1. 在内核虚拟地址空间找到一段空闲区域。
2. 建立页表映射：虚拟地址 → 物理地址。
3. 标记这段映射为"设备内存"（Device Memory），禁止缓存和推测访问。
4. 返回虚拟地址指针。

为什么必须标记为"设备内存"：

1. 寄存器访问有副作用，不能被 CPU 缓存。
2. 寄存器访问顺序必须跟代码顺序一致，不能被 CPU 重排。
3. 不能做推测性读取（Speculative Read），否则会触发硬件状态变化。

### 7. `readl` / `writel` 为什么必须用

```c
/* 错误写法 */
uint32_t val = *(volatile uint32_t *)(base + REG_STATUS);

/* 正确写法 */
uint32_t val = readl(base + REG_STATUS);
```

`readl` / `writel` 做了三件普通指针读写不做的事：

1. **保证访问宽度**：确保是 32 位访问，不会被编译器拆成两次 16 位访问。
2. **内存屏障**：保证访问顺序，不会被 CPU 重排。
3. **编译器屏障**：防止编译器把多次访问优化掉或重排。

### 8. 不同宽度的访问函数

| 函数 | 宽度 | 用途 |
| --- | --- | --- |
| `readb` / `writeb` | 8 位 | 单字节寄存器 |
| `readw` / `writew` | 16 位 | 半字寄存器 |
| `readl` / `writel` | 32 位 | 字寄存器（最常用） |
| `readq` / `writeq` | 64 位 | 双字寄存器（64 位 SoC） |
| `readl_relaxed` / `writel_relaxed` | 32 位 | 无屏障版本（性能优化） |

### 9. 地址空间划分

```text
ARM 32 位 Linux 地址空间（典型）:

0x0000_0000 - 0xBFFF_FFFF: 用户态虚拟地址空间（3GB）
0xC000_0000 - 0xFFFF_FFFF: 内核虚拟地址空间（1GB）

内核空间细分:
0xC000_0000 - 0xF7FF_FFFF: 内核直接映射区（线性映射物理内存）
0xF800_0000 - 0xFBFF_FFFF: vmalloc 区（动态映射）
0xFC00_0000 - 0xFCFF_FFFF: ioremap 区（设备寄存器映射）
0xFD00_0000 - 0xFFFF_FFFF: 固定映射区和高端内存
```

`ioremap` 返回的地址通常落在 `0xFC00_0000 - 0xFCFF_FFFF` 这个区域。

### 10. 总线地址

DMA 硬件使用的地址叫做"总线地址"，它跟物理地址可能不同：

1. 在简单 SoC 上，总线地址 = 物理地址。
2. 在有 IOMMU 的 SoC 上，总线地址需要通过 IOMMU 翻译。
3. `dma_map_single` 返回的就是总线地址，给 DMA 硬件用。

```text
CPU 视角: 虚拟地址 → (MMU) → 物理地址
DMA 视角: 总线地址 → (IOMMU) → 物理地址
```

### 11. 设备树里的 `reg` 属性

```dts
uart0: serial@20000000 {
    compatible = "vendor,uart";
    reg = <0x20000000 0x1000>;  /* 基地址 0x20000000, 大小 0x1000 */
    interrupts = <0 25 4>;
};
```

`reg` 属性描述的是物理地址，驱动里需要 `ioremap` 后才能访问。

```text
  |

```

## 核心概念 / 本质机制

### 1. 地址空间到底是什么

从 CPU 视角看，系统里很多对象都通过地址访问：

1. RAM
2. Flash
3. 外设寄存器
4. 某些控制器窗口

这些地址组合起来，就是地址空间。

对 SoC 来说，常见做法是：

1. 某一段地址映射到内存。
2. 某一段地址映射到外设控制器。
3. 某一段地址保留不用。

所以当你看到一张 memory map，本质上是在看“CPU 访问不同地址时，背后到底连到了谁”。

### 2. 什么叫 MMIO

MMIO 是 `Memory-Mapped I/O`，也就是“把外设寄存器映射到内存地址空间”。

它的意义是：

1. CPU 不需要单独的特殊 I/O 指令。
2. 读写某些特定地址，就等于在和外设对话。

比如：

1. `0x40010000` 可能是 GPIO 控制器基地址。
2. `0x40010004` 可能是输出数据寄存器。
3. `0x40010008` 可能是输入状态寄存器。

这就是为什么“访问寄存器”和“访问地址”在代码层面看起来很像。

### 3. 基地址和偏移量怎么理解

最常见的寄存器组织方式是：

1. 一个外设有一个基地址。
2. 外设内部不同寄存器通过固定偏移排列。

例如：

```text
GPIO_BASE       = 0x40010000
GPIO_DIR_OFFSET = 0x00
GPIO_OUT_OFFSET = 0x04
GPIO_IN_OFFSET  = 0x08
```

则：

1. 方向寄存器地址 = `GPIO_BASE + 0x00`
2. 输出寄存器地址 = `GPIO_BASE + 0x04`
3. 输入寄存器地址 = `GPIO_BASE + 0x08`

理解了这一层，就不会把“外设地址”和“寄存器地址”混成一个概念。

### 4. 寄存器常见访问语义不能只按普通变量理解

寄存器最常见的语义包括：

1. `RO`：只读。
2. `WO`：只写。
3. `RW`：可读可写。
4. `W1C`：写 1 清零。
5. `W1S`：写 1 置位。
6. `RC`：读取后清除。

这意味着：

1. 不是所有寄存器都能“先读出来改一位再写回去”。
2. 某些状态寄存器读一下就变了。
3. 某些 pending 位必须写 1 才能清，不是写 0。

这类细节往往正是硬件联调最容易翻车的地方。

### 5. 为什么寄存器访问通常要 `volatile`

因为寄存器值可能在软件看不见的地方发生变化：

1. 硬件状态机在变。
2. 中断事件会改状态位。
3. DMA 或其他总线主设备会更新数据。

如果不用 `volatile`，编译器可能会：

1. 把多次读取优化成一次。
2. 认为某个值不会自己变化。
3. 重排访问顺序。

但要注意：

1. `volatile` 解决的是“不要把访问优化掉”。
2. 它不等于原子性。
3. 它也不自动解决并发同步和内存屏障问题。

### 6. 为什么读改写很常见，但又很危险

很多控制寄存器会这样操作：

1. 先读原值。
2. 改其中几位。
3. 再写回去。

这就是读改写，简称 RMW。

它的风险在于：

1. 某些位可能是写 1 清零语义，读回再写可能误清状态。
2. 某些位可能由硬件同时更新，读改写期间值已经变了。
3. 多个上下文同时操作同一寄存器时会丢位。

所以看到寄存器操作时，一定先问：

1. 这个寄存器是纯控制寄存器，还是混合了状态位？
2. 能不能安全读回？
3. 是否需要专门的 set/clear 寄存器代替 RMW？

### 7. 位域才是寄存器真正的控制粒度

寄存器一般是 8/16/32/64 位宽，但你真正关心的通常是其中某几位。

常见概念包括：

1. bit：单个位。
2. field：连续几位组成的字段。
3. mask：位掩码。
4. shift：左移或右移到目标位置。

例如某寄存器：

1. bit 0 控制使能。
2. bit 1 表示 ready。
3. bit 7:4 表示时钟分频值。

软件真正做的是：

1. 用掩码选中目标位。
2. 清旧值。
3. 写入新值。

### 8. 为什么访问宽度和对齐也会出问题

不是所有寄存器都能随意用 `char`、`short`、`int` 访问。

需要看手册明确：

1. 寄存器宽度是多少。
2. 是否支持字节访问。
3. 是否要求 32 位对齐访问。

如果访问宽度不对，可能出现：

1. 写了没效果。
2. 写错其他位。
3. 总线错误。
4. 只在某些架构上出问题。

### 9. 为什么设备树、驱动、裸机代码最后都会落到地址映射

看起来它们很不一样，但最终都要解决：

1. 这个设备的寄存器窗口在哪。
2. 中断号是多少。
3. 时钟、复位和电源怎么接。
4. 哪些地址要映射进 CPU 可访问空间。

所以你看到：

1. 裸机里是手写宏访问地址。
2. Linux 里是 `ioremap()` 或 `devm_platform_ioremap_resource()`。
3. 设备树里是 `reg = <...>`。

它们本质上都在表达同一件事：硬件寄存器空间如何被软件正确访问。

## 数据流 / 控制流 / 时序关系

下面用“打开 GPIO 时钟并配置输出”为例，看一次寄存器访问真正经历了什么：

```text
CPU 执行写寄存器代码
-> 总线把写请求送到时钟控制器寄存器窗口
-> 时钟控制器置位 GPIO 时钟使能位
-> GPIO 模块获得时钟
-> CPU 再写 GPIO 方向寄存器
-> GPIO 输出能力被配置
-> CPU 写 GPIO 输出数据寄存器
-> 外部引脚电平变化
```

这条链里任何一环有问题，最终都会表现成“GPIO 没反应”：

1. 地址写错。
2. 时钟没真正打开。
3. 寄存器位意义理解错。
4. 引脚没复用到 GPIO。
5. 外部电路把引脚拉住了。

## 代码解读

### 1. 为什么裸机用 `volatile` 而 Linux 用 `readl`/`writel`

裸机没有 MMU，虚拟地址等于物理地址，`volatile` 防止编译器优化就够了。Linux 有 MMU 和缓存，`readl`/`writel` 除了防止优化，还保证访问顺序和宽度。

### 2. 为什么 `devm_ioremap_resource` 比 `ioremap` 更推荐

`devm_ioremap_resource` 做了三件事：

1. 检查资源冲突（两个驱动映射同一块地址）。
2. 自动在设备移除时取消映射。
3. 失败时返回 `ERR_PTR`，方便错误处理。

### 3. 为什么 `void __iomem *` 是特殊指针类型

`__iomem` 是一个 Sparse 注解，告诉静态分析工具"这个指针指向 IO 内存，不是普通内存"。用 `Sparse` 检查代码时，如果对 `__iomem` 指针用普通指针操作会报警。

### 4. 为什么 `readl_relaxed` 存在

某些场景下访问顺序已经被其他同步机制保证，不需要额外的内存屏障。`readl_relaxed` 省掉屏障开销，在热路径上性能更好。但使用时必须确保顺序正确。

## 代码解读

### 1. 为什么先写 `RCC_AHBENR`

因为很多外设在没有时钟时：

1. 寄存器读写看起来无效。
2. 模块状态机根本不运行。

所以先开时钟是寄存器访问能生效的重要前提。

### 2. 为什么 `GPIOA_MODER` 要先清再写

因为每个引脚模式通常占两位或多位。

如果只盲目 `OR` 一个值：

1. 旧模式位可能还在。
2. 最终组合成错误模式。

“先清目标字段，再写新值”是字段型寄存器最常见也最稳的写法。

### 3. 为什么宏里用了 `volatile`

因为这些地址背后不是普通 RAM，而是硬件窗口。

不用 `volatile` 时：

1. 编译器可能把某些读写优化掉。
2. 调试看到的寄存器访问次数可能和代码不一致。

## 边界条件与适用范围

1. `ioremap` 映射的地址空间有限，大量映射可能耗尽 vmalloc 区。
2. 不是所有物理地址都能 `ioremap`，只有 SoC 地址空间里定义的设备区域才可以。
