# 硬件-原理图阅读方法

## 原始问题

软件工程师拿到一块板子的原理图，不知道从哪里看起，看不懂符号、网络名、电源域和信号流向，更不知道怎么把原理图上的信息跟设备树、驱动代码、调试现象对应起来。原理图到底该怎么读？

## 先给结论

读原理图不是从左上角看到右下角，而是带着问题、按层级读：

1. 先看电源：芯片有没有供电，电压域对不对。
2. 再看时钟和复位：晶振有没有，复位电路怎么接。
3. 再看核心 SoC：引脚分配、电源域、启动配置。
4. 再看外设连接：每个外设连了哪些引脚、怎么供电、上下拉怎么配。
5. 最后把原理图信息跟设备树、驱动代码、调试日志串起来验证。

如果拿到原理图只会找芯片型号，但不会追踪网络名、不会看电源域、不会确认上下拉、不会把原理图信息跟软件配置对应，就还没有真正掌握原理图阅读能力。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 拿到原理图不知道从哪里看起，看了半天找不到关键信息。
2. 看不懂原理图上的符号、网络名、器件编号规则。
3. 不知道怎么确认某个引脚的上下拉、供电域、复用功能。
4. 驱动调不通时，不知道怎么回到原理图验证硬件连接。
5. 设备树配置不知道怎么跟原理图对应。

它在 AI 时代依然重要，因为 AI 能帮你写设备树和驱动代码，但它不知道你板子上的实际连线。只有你能从原理图上确认：这个 GPIO 有没有外部上拉、这个 I2C 设备地址是多少、这个电源域是不是 3.3V。原理图阅读能力是校验 AI 输出是否物理正确的关键。

## 核心概念 / 本质机制

### 1. 原理图是什么

原理图（Schematic）是用标准符号表示电路连接关系的图纸：

1. 它不反映物理布局（那是 PCB 图的事）。
2. 它反映的是"谁和谁连在一起"的逻辑关系。
3. 同一张原理图上，同一个网络名（Net Name）的所有引脚在物理上是连通的。

### 2. 原理图的基本组成

| 组成元素 | 作用 | 例子 |
| --- | --- | --- |
| 器件符号 | 表示芯片、电阻、电容等 | U1、R3、C5 |
| 网络名 / 标号 | 表示连接关系 | I2C1_SDA、VCC_3V3 |
| 电源符号 | 表示供电网络 | VCC、GND、VDD_IO |
| 总线 | 一组信号用粗线表示 | DATA[7:0]、ADDR[15:0] |
| 跨页连接符 | 不同页面间的信号连接 | off-page connector |
| Note / 标注 | 设计说明和注意事项 | "1K pull-up" |

### 3. 器件编号规则

```text
U  - 集成电路（IC）
R  - 电阻
C  - 电容
L  - 电感
D  - 二极管
Q  - 晶体管
J  - 连接器 / 排针
Y  / X - 晶振
FB - 磁珠
TP - 测试点
SW - 开关 / 按键
LED - 发光二极管
```

编号后面的数字是序号：U1 是第一个 IC，R3 是第三个电阻。

### 4. 网络名是读原理图的关键

网络名（Net Name / Net Label）是原理图里最重要的信息之一：

1. 同一张图上，相同网络名的所有引脚物理连通。
2. 网络名通常体现信号功能：`I2C1_SDA`、`UART0_TX`、`SPI2_CLK`。
3. 电源网络名通常体现电压：`VCC_3V3`、`VDD_1V8`、`VDDQ_DDR`。

读图时追踪一个信号的方法：从一个引脚出发，沿着网络名找到所有连接点。

### 5. 电源域的读法

电源域是原理图里最优先确认的信息：

```text
典型 SoC 电源域:

VDD_CORE   - CPU 核心电压（通常 0.8V~1.2V）
VDD_IO     - IO 电压（通常 3.3V 或 1.8V）
VDD_DDR    - DDR 供电（通常 1.2V 或 1.35V）
VDD_PHY    - PHY 供电（USB/ETH 等）
VDD_ANA    - 模拟供电（ADC/DAC 等）
```

读电源域时重点看：

1. 每个电源域的电压值是多少。
2. 电源从哪来（LDO、DCDC、PMIC）。
3. 去耦电容是否足够（通常每个电源引脚旁都有 100nF）。
4. 不同电源域之间有没有电平转换芯片。

### 6. SoC 部分的读法

SoC 是原理图的核心，通常占好几页。读 SoC 部分时重点看：

1. **电源引脚**：VDD、VSS、VDDIO 是否都接了正确的电源。
2. **启动配置引脚**：BOOT_MODE、SYS_CFG 等，决定芯片从哪里启动。
3. **晶振和时钟**：主晶振频率、RTC 晶振、时钟输入引脚。
4. **复位电路**：复位引脚（RESET_N / POR_N）的上拉和电容。
5. **JTAG / SWD**：调试接口引脚。
6. **GPIO 分配**：哪些引脚分配给了哪些功能。

### 7. 外设连接的读法

每个外设模块通常有独立的原理图页面，读法：

```text
1. 找到外设芯片符号
2. 看它的供电引脚和电源域
3. 看它的通信接口（I2C/SPI/UART 地址和引脚）
4. 看它的中断引脚连到 SoC 的哪个 GPIO
5. 看它的控制引脚（使能、复位、片选）
6. 看上下拉配置
7. 看去耦电容
```

### 8. I2C 设备的典型读法

```text
I2C 传感器（例：加速度计）

U5 (BMA250)
  |
  +-- VDD -> VCC_3V3 (供电)
  +-- GND -> GND
  +-- SDA -> I2C1_SDA (连到 SoC 的 I2C1_SDA)
  +-- SCL -> I2C1_SCL (连到 SoC 的 I2C1_SCL)
  +-- INT1 -> GPIO3_A7 (中断引脚)
  +-- INT2 -> NC (未连接)
  +-- SDO -> GND (地址选择：接地 = 0x18)
  +-- CSB -> VCC_3V3 (SPI 片选拉高 = 禁用 SPI 模式)
```

关键信息提取：

1. I2C 地址：SDO 接 GND → 地址 0x18；SDO 接 VCC → 地址 0x19。
2. 中断引脚：INT1 连到 GPIO3_A7，设备树里要配这个 GPIO。
3. 上下拉：I2C 总线的 SDA/SCL 上拉电阻在哪一页。

### 9. 跨页追踪信号

原理图通常分很多页，信号经常跨页连接。追踪方法：

1. 找到信号的网络名。
2. 在其他页面搜索相同网络名。
3. 或者用 off-page connector（跨页连接符）追踪。

很多 EDA 工具支持"高亮网络"功能，点击网络名后所有连接点都会高亮。

### 10. 从原理图到设备树的映射

```text
原理图信息              设备树属性
-----------------      ----------------
I2C1_SDA/SCL          i2c1 节点
传感器地址 0x18        reg = <0x18>
INT1 -> GPIO3_A7      interrupts-extended = <&gpio3 7 ...>
VCC_3V3 供电           无直接对应（但影响 IO 电平）
SDO -> GND             无直接对应（但决定地址）
```

## 数据流 / 控制流 / 时序关系

### 读原理图的推荐顺序

```text
第 1 步: 找到电源页面
  - 确认所有电源域和电压值
  - 确认 PMIC / LDO / DCDC 输出
  |
  V
第 2 步: 找到 SoC 主页面
  - 确认供电、晶振、复位、启动配置
  - 确认 JTAG/SWD 调试接口
  |
  V
第 3 步: 找到目标外设页面
  - 确认供电和电源域
  - 确认通信接口和引脚
  - 确认中断、使能、复位引脚
  - 确认上下拉和地址配置
  |
  V
第 4 步: 追踪关键信号
  - 从 SoC 引脚出发，追踪到外设
  - 确认中间有没有电平转换、缓冲器、多路复用器
  |
  V
第 5 步: 跟设备树和驱动代码对照
  - 确认设备树配置和原理图一致
  - 确认驱动使用的引脚和原理图一致
```

### 排障时的读图顺序

```text
设备不工作
  |
  V
先看电源: 供电是否正常？电压对不对？
  |
  V
再看时钟和复位: 晶振有没有？复位电路对不对？
  |
  V
再看连接: 引脚有没有接对？有没有虚焊？
  |
  V
再看上下拉: I2C 有没有上拉？地址脚电平对不对？
  |
  V
再看电平: 两边 IO 电压是否兼容？
  |
  V
最后看软件: 设备树和驱动配置是否跟原理图一致？
```

## 最小可运行示例

### 从原理图提取 I2C 设备信息并写设备树

假设原理图上有这样一个 I2C 温度传感器：

```text
U3 (TMP102)
  V+  -> VCC_3V3
  GND -> GND
  SDA -> I2C1_SDA (SoC 引脚 GPIO0_A3)
  SCL -> I2C1_SCL (SoC 引脚 GPIO0_A4)
  ALERT -> GPIO1_B2
  A0 -> GND
  A1 -> GND
```

从原理图提取的信息：

1. 挂在 I2C1 总线上。
2. A0=A1=GND → 地址 = 0x48（查 TMP102 数据手册）。
3. ALERT 引脚连到 GPIO1_B2。
4. 供电 3.3V。

对应设备树：

```dts
&i2c1 {
    status = "okay";

    temperature-sensor@48 {
        compatible = "ti,tmp102";
        reg = <0x48>;
        interrupt-parent = <&gpio1>;
        interrupts = <10 IRQ_TYPE_LEVEL_LOW>;
    };
};
```

### 从原理图提取 SPI Flash 信息

```text
U8 (W25Q128)
  VCC -> VCC_3V3
  GND -> GND
  CS#  -> SPI0_CS0 (SoC 引脚 GPIO2_A0)
  DO   -> SPI0_MISO (SoC 引脚 GPIO2_A1)
  WP#  -> VCC_3V3 (写保护禁用)
  DI   -> SPI0_MOSI (SoC 引脚 GPIO2_A2)
  CLK  -> SPI0_CLK (SoC 引脚 GPIO2_A3)
  HOLD# -> VCC_3V3 (HOLD 禁用)
```

对应设备树：

```dts
&spi0 {
    status = "okay";

    flash@0 {
        compatible = "winbond,w25q128";
        reg = <0>;
        spi-max-frequency = <50000000>;
    };
};
```

## 代码解读

### 1. 为什么 I2C 地址要查数据手册而不是猜

I2C 地址由芯片的地址引脚（A0/A1/A2 或 SDO/CSB）决定。不同芯片的地址映射不同，必须查数据手册确认。原理图上只告诉你地址引脚接了什么电平，但地址计算规则在数据手册里。

### 2. 为什么 ALERT 中断的触发类型要确认

TMP102 的 ALERT 引脚是开漏输出、低电平有效。所以设备树里配 `IRQ_TYPE_LEVEL_LOW`。如果配成边沿触发，可能因为电平持续低而重复进中断，或者因为信号太短而丢中断。

### 3. 为什么 SPI Flash 的 WP# 和 HOLD# 要拉高

WP#（写保护）和 HOLD#（暂停）都是低有效。拉高表示禁用这两个功能，让 Flash 可以正常写入和连续传输。如果这两个引脚悬空或被拉低，Flash 可能写不进数据或传输异常。

## 正确写法 vs 常见错误写法

| 场景 | 正确做法 | 常见错误 | 为什么错 |
| --- | --- | --- | --- |
| 读 I2C 地址 | 查数据手册 + 看地址引脚电平 | 直接用常见默认地址 | 地址引脚不同电平对应不同地址 |
| 确认上下拉 | 在原理图上找电阻位置 | 假设芯片内部有上拉 | 很多 I2C 设备需要外部上拉 |
| 确认 IO 电平 | 看电源域和电平转换芯片 | 假设所有 IO 都是 3.3V | 很多 SoC 有多个 IO 域 |
| 确认中断极性 | 看 ALERT/INT 引脚的极性说明 | 默认高电平有效 | 很多传感器中断是低有效 / 开漏 |
| 设备树引脚号 | 从原理图追踪到 SoC 引脚号 | 猜测或照搬参考板 | 不同板子引脚分配可能不同 |
| 确认启动方式 | 看 BOOT_MODE 引脚的上下拉 | 假设默认从 eMMC 启动 | 不同配置启动源不同 |

## 边界条件与适用范围

1. 这篇笔记面向软件工程师读原理图，不是硬件工程师画原理图。
2. 不同公司的原理图风格和命名规范可能不同，但基本元素和读法是通用的。
3. 有些原理图信息可能不完整（比如内部上拉没有标出），需要结合数据手册确认。
4. 高速信号（DDR、USB、PCIe）的原理图还需要关注阻抗匹配、等长、差分对等，这篇不深入。
5. 原理图只反映设计意图，实际 PCB 可能有意外的短路、断路或焊接问题。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| I2C 设备探测不到 | 地址错；没上拉；供电不对 | 万用表量 SDA/SCL 电平 |
| SPI 数据错乱 | 片选错；模式错；WP/HOLD 脚没拉高 | 示波器看 CS 和时钟 |
| 中断不进 | 极性配反；引脚号错；上下拉不对 | 示波器看中断引脚电平 |
| 设备树配了但没效果 | 引脚号跟原理图不对应 | 逐个对照原理图和设备树 |
| 两个设备地址冲突 | I2C 地址引脚配重了 | 查原理图地址引脚电平 |
| GPIO 方向不对 | 原理图上引脚功能理解错 | 看 SoC 手册的 pinmux 表 |

### 推荐排查顺序

1. 先在原理图上找到目标器件。
2. 确认供电引脚和电压值。
3. 追踪通信接口引脚到 SoC。
4. 确认上下拉、地址配置、极性。
5. 跟设备树和驱动代码逐项对照。
6. 用万用表或示波器验证实际电平。

## 工程落地建议

### 1. 建立原理图信息提取模板

每次拿到新板子，按模板提取关键信息：

```text
板卡名称:
SoC 型号:
电源域:
  - VDD_CORE: ___V
  - VDD_IO: ___V
  - VDD_DDR: ___V

启动配置:
  - BOOT_MODE[1:0]: ___

I2C 总线:
  - I2C0: SDA=___, SCL=___, 设备列表=___
  - I2C1: SDA=___, SCL=___, 设备列表=___

SPI 总线:
  - SPI0: CS=___, CLK=___, MOSI=___, MISO=___, 设备列表=___

UART:
  - UART0: TX=___, RX=___, 用途=___(调试串口)

关键 GPIO:
  - LED: ___
  - 按键: ___
  - 复位: ___
```

### 2. 用 EDA 工具的搜索和高亮功能

大多数 EDA 工具（Altium、KiCad、Cadence）支持：

1. 按网络名搜索。
2. 高亮整个网络。
3. 从引脚跳转到连接的另一个引脚。
4. 生成网络表（Netlist），方便批量检查。

### 3. 把原理图信息写进代码注释

```c
/* TMP102 温度传感器，I2C1 总线，地址 0x48
 * ALERT -> GPIO1_B2 (低电平有效，开漏输出)
 * 原理图: U3, 第 5 页
 */
```

### 4. 原理图和设备树做交叉索引

在设备树注释里标注原理图页码和器件编号：

```dts
/* U3 on schematic page 5 */
temperature-sensor@48 {
    compatible = "ti,tmp102";
    reg = <0x48>;
};
```

## 性能、稳定性、可维护性影响

1. 原理图阅读能力直接影响 bring-up 速度：能快速确认硬件连接，减少"猜问题"的时间。
2. 设备树和驱动配置如果跟原理图不一致，会带来隐蔽的稳定性问题。
3. 把原理图信息提取成文档和代码注释，能显著降低后续维护成本。
4. 不会读原理图的工程师，遇到硬件相关问题时只能依赖硬件同事，响应速度慢。

## 面试 / 问答怎么讲

### 30 秒版本

读原理图的核心是带着问题、按层级读：先看电源域和电压，再看 SoC 供电和启动配置，再看外设连接和引脚分配，最后跟设备树和驱动代码对照。关键是追踪网络名，同一个网络名的所有引脚物理连通。

### 3 分钟版本

可以从一个具体外设讲起：比如 I2C 温度传感器。先在原理图上找到器件，确认供电和电压域，追踪 SDA/SCL 到 SoC 的引脚，确认地址引脚电平计算地址，确认中断引脚和极性，确认上下拉。然后说明这些信息怎么映射到设备树的 reg、interrupts、pinctrl 属性。最后强调排障时也要回到原理图验证。

### 10 分钟版本

可以系统展开：先讲原理图的基本元素（器件符号、网络名、电源符号、跨页连接），再讲读图顺序（电源→SoC→外设→信号追踪），再讲从原理图到设备树的映射方法，再讲排障时怎么用原理图定位问题。然后举两个完整例子：一个 I2C 设备、一个 SPI 设备，从原理图提取信息到写设备树。最后讲常见坑点：地址引脚、上下拉、IO 电平、中断极性。

## 实战练习

1. 找一份真实开发板原理图，按"电源→SoC→外设"的顺序读，提取所有 I2C 设备的地址和引脚信息。
2. 对照原理图检查一个 Linux 设备树文件，确认每个设备的 reg、interrupts、gpios 属性是否正确。
3. 在原理图上追踪一个中断信号，从外设引脚到 SoC GPIO，确认极性和上下拉。
4. 用万用表测量板子上一个 I2C 总线的 SDA/SCL 静态电平，验证是否有上拉。
5. 画一张"原理图信息→设备树属性→驱动代码"的对应表，至少覆盖 3 个外设。

## 关键要点

1. 读原理图按层级：电源→SoC→外设→信号追踪→设备树对照。
2. 网络名是核心：相同网络名的所有引脚物理连通。
3. I2C 地址由地址引脚电平决定，必须查数据手册确认。
4. 上下拉、IO 电平、中断极性是高频坑点，必须从原理图确认。
5. 原理图信息必须跟设备树和驱动代码逐项对照，不能想当然。
6. 建立信息提取模板和交叉索引，能显著降低 bring-up 和维护成本。
7. 排障时先回到原理图验证硬件连接，再怀疑软件逻辑。
