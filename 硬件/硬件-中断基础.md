# 硬件-中断基础

## 原始问题

中断到底是怎么从硬件信号变成软件函数调用的？中断控制器做了什么？向量表是什么？为什么裸机中断和 Linux 中断处理方式差别这么大？FIQ 和 IRQ 有什么区别？中断优先级怎么决定谁先执行？中断嵌套和中断屏蔽的规则是什么？

## 先给结论

中断的本质是"硬件主动通知 CPU 有事件需要处理"，整条链路是：

1. 外设产生中断信号（电平或边沿）。
2. 中断控制器（GIC / NVIC / IOAPIC）收集、仲裁、优先级排序。
3. 中断控制器向 CPU 发送中断请求。
4. CPU 响应中断，查向量表找到入口地址。
5. CPU 保存现场，跳转到中断服务程序（ISR）执行。
6. ISR 处理完毕，清中断源，恢复现场，返回被中断的代码。

如果只知道"中断就是注册一个回调函数"，但讲不清信号怎么传到 CPU、向量表怎么查、优先级怎么仲裁、为什么要清中断源，就还没有真正理解中断的硬件本质。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 不理解中断从硬件信号到软件函数的完整路径。
2. 分不清中断控制器、向量表、ISR、中断号的关系。
3. 不知道电平触发和边沿触发的区别，选错触发方式导致中断丢失或重复。
4. 不理解中断优先级和嵌套的硬件规则。
5. 面试时被问"中断响应流程"，只能说出"硬件通知软件"。

它在 AI 时代依然重要，因为 AI 生成驱动代码时经常搞错触发类型、忘记清中断源、忽略优先级配置。理解中断的硬件机制后，你才能判断 AI 给的中断处理代码是否正确、是否会丢中断或死锁。

## 核心概念 / 本质机制

### 1. 中断信号的产生

外设通过一根中断线（IRQ line）向中断控制器发信号：

```text
外设内部事件发生（数据就绪 / FIFO 满 / 按键按下 / 定时器溢出）
  |
  V
外设中断状态寄存器置位（pending）
  |
  V
外设中断使能寄存器已使能
  |
  V
中断线电平变化或产生边沿
  |
  V
中断控制器检测到信号
```

关键点：外设中断信号的产生需要两个条件——事件发生了（pending 位）且中断使能了（enable 位）。

### 2. 中断控制器

中断控制器是 CPU 和外设之间的"中断调度中心"：

| 架构 | 中断控制器 | 典型场景 |
| --- | --- | --- |
| ARM Cortex-M | NVIC | STM32、单片机 |
| ARM Cortex-A | GIC (v2/v3/v4) | i.MX、RK、QCOM 等 SoC |
| x86 | IOAPIC + LAPIC | PC、服务器 |

中断控制器的核心职责：

1. **收集**：接收多个外设的中断请求。
2. **仲裁**：多个中断同时发生时，按优先级决定谁先上报。
3. **屏蔽**：根据配置屏蔽某些中断。
4. **上报**：向 CPU 发送中断信号，附带中断号。
5. **状态管理**：维护 pending、active、masked 等状态。

### 3. NVIC（ARM Cortex-M）

NVIC 是 Cortex-M 系列的中断控制器，特点：

1. 支持 1~240 个中断源（具体数量由芯片厂商决定）。
2. 每个中断有独立优先级（4~8 位优先级，实际位数由厂商配置）。
3. 支持中断嵌套（高优先级可以抢占低优先级）。
4. 向量表直接存放在内存中，可运行时修改。
5. 支持 SysTick、PendSV、SVCall 等系统异常。

NVIC 寄存器概览：

| 寄存器 | 作用 |
| --- | --- |
| ISER | 中断使能（写 1 使能） |
| ICER | 中断禁能（写 1 禁能） |
| ISPR | 中断挂起（写 1 挂起） |
| ICPR | 中断解挂（写 1 清挂起） |
| IPR[0..59] | 中断优先级配置 |
| IABR | 中断活跃状态（只读） |

### 4. GIC（ARM Cortex-A）

GIC 是 Cortex-A 系列的中断控制器，比 NVIC 复杂得多：

```text
GIC 结构:

外设中断线 --> Distributor --> CPU Interface --> CPU
                  |                |
                  |                +-- 只转发给目标 CPU
                  +-- 优先级仲裁、屏蔽、状态管理
```

GIC 的中断分类：

| 类型 | 缩写 | 说明 |
| --- | --- | --- |
| 外设中断 | SPI | 共享外设中断，可路由到任意 CPU |
| 私有外设中断 | PPI | 每个 CPU 独有的中断（定时器等） |
| 软件生成中断 | SGI | CPU 间通信用的软件中断 |

GIC 的中断状态机：

```text
Inactive -> Pending -> Active -> Inactive
                  \-> Active & Pending -> Inactive
```

- Inactive：空闲，没有中断请求。
- Pending：中断已请求，等待 CPU 处理。
- Active：CPU 正在处理该中断。
- Active & Pending：正在处理中，又来了一个同号中断。

### 5. 中断向量表

向量表是一个存放中断入口地址的数组，CPU 响应中断时自动查表跳转：

```text
Cortex-M 向量表布局:

偏移     内容
0x00     初始 MSP 值
0x04     Reset 入口
0x08     NMI 入口
0x0C     HardFault 入口
0x10     MemManage 入口
0x14     BusFault 入口
0x18     UsageFault 入口
...
0x3C     SVCall 入口
0x40     Debug Monitor 入口
...
0x4C     PendSV 入口
0x50     SysTick 入口
0x54     IRQ0 入口
0x58     IRQ1 入口
...
```

Cortex-M 的向量表可以重定位（修改 VTOR 寄存器），这在 Bootloader 跳转 APP 时很关键。

Cortex-A 的向量表位置由 VBAR 寄存器指定，异常模式比 Cortex-M 更复杂（有 IRQ/FIQ/SVC/ABORT/UNDEF 等多种模式）。

### 6. 电平触发 vs 边沿触发

| 触发方式 | 原理 | 特点 | 适用场景 |
| --- | --- | --- | --- |
| 电平触发 | 中断线保持高电平就持续请求 | 如果不清源，中断会反复进 | 共享中断线、简单外设 |
| 边沿触发 | 检测到上升沿或下降沿时请求一次 | 不会自动重复，但可能丢中断 | 高速外设、独占中断线 |

电平触发的关键：ISR 里必须清中断源（让电平变回无效），否则 ISR 返回后中断会立即再次进入。

边沿触发的关键：如果 ISR 处理太慢，新的边沿可能在旧中断还没处理完时就来了，导致丢失。

### 7. FIQ vs IRQ

ARM 架构有两个外部中断输入：

| 特性 | IRQ | FIQ |
| --- | --- | --- |
| 优先级 | 较低 | 较高（FIQ 可以打断 IRQ） |
| 向量位置 | 0x18 | 0x1C |
| 独立寄存器 | 无 | 有（r8_fiq ~ r12_fiq） |
| 典型用途 | 通用外设中断 | 极低延迟关键中断 |

FIQ 的设计目标是"最快响应"：

1. FIQ 在向量表末尾，ISR 可以直接从向量地址开始写，省掉跳转指令。
2. FIQ 有独立的影子寄存器，不需要保存/恢复 r8~r12，减少上下文切换开销。
3. FIQ 优先级高于 IRQ，不会被 IRQ 抢占。

实际项目中 FIQ 用得越来越少，大多数系统只用 IRQ + 优先级来管理中断。

### 8. 中断优先级

优先级决定两个核心问题：

1. 多个中断同时 pending，谁先被处理。
2. 正在处理某个中断时，新来的中断能不能抢占。

Cortex-M 优先级规则：

1. 优先级数值越小，优先级越高。
2. 优先级分为抢占优先级（Preemption）和子优先级（Sub-priority），通过 PRIGROUP 配置分组。
3. 抢占优先级高的可以打断低的（嵌套）。
4. 抢占优先级相同时，子优先级高的先处理，但不能嵌套。

GIC 优先级规则：

1. 优先级数值越小，优先级越高（与 Cortex-M 一致）。
2. 优先级掩码（PMR）可以屏蔽低于某个阈值的所有中断。
3. Binary Point 寄存器决定优先级分组方式。

### 9. 中断屏蔽

中断屏蔽分多个层级：

```text
CPU 层面:
  - CPSR.I 位: 屏蔽所有 IRQ
  - CPSR.F 位: 屏蔽所有 FIQ
  - ARM64: DAIF 寄存器的 I/F 位

中断控制器层面:
  - GIC: 每个中断可以单独 enable/disable
  - NVIC: ISER/ICER 寄存器

外设层面:
  - 外设自己的中断使能寄存器
```

Linux 驱动中的屏蔽：

1. `local_irq_disable()` / `local_irq_enable()`：屏蔽/开启当前 CPU 所有中断。
2. `spin_lock_irqsave()` / `spin_lock_irqrestore()`：加锁同时屏蔽中断。
3. `disable_irq()` / `enable_irq()`：屏蔽/开启指定中断线。

### 10. 中断处理的完整流程

```text
1. 外设产生中断信号
2. 中断控制器检测并仲裁
3. 中断控制器向 CPU 发送中断请求
4. CPU 完成当前指令
5. CPU 保存关键寄存器（PC、CPSR 等）到栈
6. CPU 查向量表，获取 ISR 入口地址
7. CPU 跳转到 ISR 执行
8. ISR 保存额外上下文（callee-saved 寄存器）
9. ISR 识别中断源（读中断控制器或外设状态寄存器）
10. ISR 处理中断（读数据、清标志等）
11. ISR 清中断源（关键步骤！）
12. ISR 恢复上下文
13. CPU 执行中断返回指令（ARM: eret / msp; x86: iret）
14. CPU 恢复被中断的代码继续执行
```

## 数据流 / 控制流 / 时序关系

### Cortex-M 中断响应时序

```text
外设信号变化
  |
  V  (几个时钟周期)
NVIC 检测到中断，置 pending
  |
  V  (等待当前指令完成 + 响应周期)
CPU 进入中断响应:
  - 自动压栈: xPSR, PC, LR, R12, R3~R0
  - 从向量表读取 ISR 地址
  - 设置 LR 为 EXC_RETURN
  |
  V  (12 个时钟周期，Cortex-M3/M4)
ISR 第一条指令执行
  |
  V
ISR 处理逻辑
  |
  V
清中断源
  |
  V
ISR 返回 (BX LR / POP {PC})
  |
  V  (自动出栈)
被中断代码恢复执行
```

### Linux 中断响应路径

```text
外设中断信号
  |
  V
GIC 仲裁并上报
  |
  V
CPU 响应，进入 IRQ 异常模式
  |
  V
Linux 异常向量入口 (vector_irq)
  |
  V
保存上下文 (pt_regs)
  |
  V
irq_handler (中断控制器驱动处理)
  |
  V
generic_handle_irq
  |
  V
handle_irq (高层处理)
  |
  V
action->handler (驱动注册的 ISR)
  |
  V
ISR 返回，检查是否需要调度
  |
  V
恢复上下文或调度到其他任务
```

## 最小可运行示例

### 裸机 Cortex-M 中断（STM32 风格）

```c
#include <stdint.h>

#define NVIC_ISER0   (*(volatile uint32_t *)0xE000E100)
#define NVIC_ICER0   (*(volatile uint32_t *)0xE000E180)
#define NVIC_ICPR0   (*(volatile uint32_t *)0xE000E280)
#define NVIC_IPR0    (*(volatile uint32_t *)0xE000E400)

#define EXTI_BASE    0x40010400
#define EXTI_IMR     (*(volatile uint32_t *)(EXTI_BASE + 0x00))
#define EXTI_RTSR    (*(volatile uint32_t *)(EXTI_BASE + 0x08))
#define EXTI_PR      (*(volatile uint32_t *)(EXTI_BASE + 0x14))

#define SYSCFG_EXTICR1 (*(volatile uint32_t *)0x40013808)

#define IRQ_EXTI0    6

volatile uint32_t g_key_pressed = 0;

void EXTI0_IRQHandler(void)
{
    if (EXTI_PR & (1 << 0)) {
        EXTI_PR = (1 << 0);
        g_key_pressed = 1;
    }
}

static void exti0_init(void)
{
    SYSCFG_EXTICR1 = (SYSCFG_EXTICR1 & ~0x000F) | 0x0000;

    EXTI_IMR  |= (1 << 0);
    EXTI_RTSR |= (1 << 0);

    NVIC_IPR0 = (NVIC_IPR0 & ~(0xFF << 8)) | (0x10 << 8);

    NVIC_ISER0 = (1 << IRQ_EXTI0);
}

int main(void)
{
    exti0_init();

    while (1) {
        if (g_key_pressed) {
            g_key_pressed = 0;
        }
    }
}
```

### Linux 驱动中断注册

```c
#include <linux/interrupt.h>
#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/of.h>

struct mydev_priv {
    int irq;
    void __iomem *base;
};

#define REG_STATUS  0x04
#define STATUS_IRQ  BIT(0)

static irqreturn_t my_irq_handler(int irq, void *dev_id)
{
    struct mydev_priv *priv = dev_id;
    u32 status;

    status = readl(priv->base + REG_STATUS);
    if (!(status & STATUS_IRQ))
        return IRQ_NONE;

    writel(STATUS_IRQ, priv->base + REG_STATUS);

    return IRQ_HANDLED;
}

static int my_probe(struct platform_device *pdev)
{
    struct mydev_priv *priv;
    int ret;

    priv = devm_kzalloc(&pdev->dev, sizeof(*priv), GFP_KERNEL);
    if (!priv)
        return -ENOMEM;

    priv->irq = platform_get_irq(pdev, 0);
    if (priv->irq < 0)
        return priv->irq;

    priv->base = devm_platform_ioremap_resource(pdev, 0);
    if (IS_ERR(priv->base))
        return PTR_ERR(priv->base);

    ret = devm_request_irq(&pdev->dev, priv->irq, my_irq_handler,
                           IRQF_TRIGGER_RISING, "mydev-irq", priv);
    if (ret)
        return ret;

    platform_set_drvdata(pdev, priv);
    return 0;
}

static const struct of_device_id my_match[] = {
    { .compatible = "vendor,mydev" },
    {}
};
MODULE_DEVICE_TABLE(of, my_match);

static struct platform_driver my_driver = {
    .probe  = my_probe,
    .driver = {
        .name = "mydev-irq",
        .of_match_table = my_match,
    },
};
module_platform_driver(my_driver);

MODULE_LICENSE("GPL");
```

## 代码解读

### 1. 为什么裸机 ISR 里必须清 EXTI_PR

`EXTI_PR` 是"写 1 清零"（W1C）寄存器。如果不清，中断控制器会认为中断仍然 pending，ISR 返回后立刻再次进入，形成死循环。写 `EXTI_PR = (1 << 0)` 就是告诉硬件"这个中断我已经处理了"。

### 2. 为什么 Linux 驱动用 `devm_request_irq` 而不是 `request_irq`

`devm_request_irq` 在设备移除时自动释放中断，避免忘记 `free_irq` 导致中断泄漏。同时它还自动处理 `IRQF_SHARED` 的 dev_id 匹配。

### 3. 为什么 ISR 返回值是 `IRQ_HANDLED` / `IRQ_NONE`

Linux 用这个返回值做中断检测：

1. `IRQ_HANDLED`：确认处理了中断。
2. `IRQ_NONE`：这不是我的中断（共享中断线场景）。
3. 如果连续多次返回 `IRQ_NONE`，内核会认为中断线出了问题，自动禁用该中断。

### 4. 为什么 `IRQF_TRIGGER_RISING` 要在注册时指定

触发类型决定了中断控制器怎么检测信号。注册时指定可以让内核统一配置中断控制器，而不是让驱动自己去配硬件。

### 5. 为什么裸机向量表可以放任意位置（VTOR）

Cortex-M 的 VTOR 寄存器可以重定位向量表。Bootloader 跳转 APP 时，APP 需要把 VTOR 指向自己的向量表，否则中断还是跳到 Bootloader 的 ISR。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 清中断源 | ISR 里先清外设 pending 再返回 | 只做处理不清 pending | 电平触发会死循环进中断 |
| 触发类型 | 根据硬件信号选电平/边沿 | 全部默认电平触发 | 边沿信号可能丢中断 |
| 中断使能 | 先配外设再使能中断 | 先使能中断再配外设 | 配置过程中可能误触发 |
| 共享中断 | 检查是否是自己的中断再处理 | 直接处理不判断 | 可能处理了别人的中断 |
| ISR 返回值 | 处理了返回 IRQ_HANDLED | 全部返回 IRQ_HANDLED | 共享中断时内核无法检测异常 |
| 上下文保护 | ISR 里不用可能睡眠的函数 | ISR 里调用 kmalloc/mutex | 会导致死锁或崩溃 |
| 裸机 VTOR | APP 启动时重设 VTOR | 不设 VTOR | 中断跳到 Bootloader 的 ISR |

## 边界条件与适用范围

1. 中断延迟不是零：从信号产生到 ISR 执行，至少有十几个时钟周期的硬件响应时间。
2. 中断嵌套深度有限：实际项目中通常只允许 2~3 层嵌套，太深会栈溢出。
3. 中断优先级数量有限：NVIC 优先级位数由芯片厂商决定，可能是 4 位（16 级）或更少。
4. 不是所有中断都能共享：某些中断线只支持独占模式，不能设 `IRQF_SHARED`。
5. FIQ 在现代 Linux 系统中几乎不用，多数场景用 IRQ + 高优先级替代。
6. Cortex-A 的中断处理比 Cortex-M 复杂得多，涉及异常级别（EL0~EL3）和多种异常模式。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 中断完全不进 | 中断控制器没使能；触发类型错；中断线没连 | 查 NVIC/GIC 寄存器、示波器看信号 |
| 中断反复进（死循环） | 没清中断源；电平触发但源没拉低 | 检查 ISR 是否清了 pending |
| 中断丢失 | 边沿触发但处理太慢；中断被屏蔽 | 查中断控制器 pending 计数 |
| 中断进错 ISR | 向量表配置错；VTOR 没设 | 检查向量表内容和 VTOR |
| 中断延迟大 | 优先级低；ISR 里做了太多事 | 用 GPIO 翻转 + 示波器量延迟 |
| 共享中断只响应一个 | ISR 返回值不对；dev_id 不匹配 | 检查 IRQ_HANDLED/IRQ_NONE |
| 中断里死锁 | ISR 里调了可能睡眠的函数 | 检查 ISR 里是否用了 mutex/sleep |
| APP 中断跳到 Bootloader | VTOR 没重设 | 检查 VTOR 寄存器值 |

### 推荐排查顺序

1. 先确认中断信号是否真的产生了（示波器 / 逻辑分析仪）。
2. 再确认中断控制器是否检测到了（查 pending / active 寄存器）。
3. 再确认中断是否使能了（查 enable 寄存器）。
4. 再确认向量表是否正确（查入口地址）。
5. 再确认 ISR 是否执行了（加 GPIO 翻转或打印）。
6. 最后确认 ISR 是否正确清了中断源。

## 工程落地建议

### 1. ISR 里只做最少必要的事

```c
static irqreturn_t my_irq_handler(int irq, void *dev_id)
{
    struct mydev_priv *priv = dev_id;
    u32 status = readl(priv->base + REG_STATUS);

    if (status & STATUS_RX_READY) {
        u32 data = readl(priv->base + REG_DATA);
        priv->rx_buf[priv->rx_len++] = data;
    }

    writel(status, priv->base + REG_STATUS);
    return IRQ_HANDLED;
}
```

ISR 里只做：读数据、清中断、设标志。耗时操作放到线程或下半部。

### 2. 用 GPIO 翻转测量中断延迟

```c
static irqreturn_t my_irq_handler(int irq, void *dev_id)
{
    gpiod_set_value(priv->debug_gpio, 1);
    /* ... 处理逻辑 ... */
    gpiod_set_value(priv->debug_gpio, 0);

```

用示波器同时看中断信号和 debug GPIO，就能量出响应延迟。

### 3. 裸机向量表重定位模板

```c
#define VTOR (*(volatile uint32_t *)0xE000ED08)

void app_init_vector_table(void)
{
    extern uint32_t _vector_table_start;
    VTOR = (uint32_t)&_vector_table_start;
    __DSB();
    __ISB();
}
```

### 4. Linux 驱动中优先用 threaded IRQ

```c
ret = devm_request_threaded_irq(&pdev->dev, priv->irq,
                                my_hard_irq, my_thread_fn,
                                IRQF_TRIGGER_RISING,
                                "mydev-irq", priv);
```

threaded IRQ 把硬中断和线程处理分开，硬中断里只做最少操作，线程里做耗时处理，避免在中断上下文里调用可能睡眠的函数。

## 性能、稳定性、可维护性影响

1. ISR 执行时间直接影响系统响应性：ISR 越短，其他中断延迟越低。
2. 中断嵌套深度影响栈使用：每层嵌套都需要栈空间，深度过大可能栈溢出。
3. 不清中断源是系统不稳定的高频根因：电平触发下会死循环，边沿触发下可能丢失后续中断。
4. 优先级配置不当会导致低优先级中断被饿死。
5. 良好的中断分层（硬中断 + 线程 / 下半部）能同时保证响应性和处理完整性。

## 面试 / 问答怎么讲

### 30 秒版本

中断是硬件主动通知 CPU 的机制。外设产生信号，中断控制器仲裁优先级后上报 CPU，CPU 查向量表跳转到 ISR 执行。ISR 里必须清中断源，否则电平触发会死循环。触发方式分电平和边沿，选择不当会丢中断或重复进中断。

### 3 分钟版本

从信号产生讲起：外设事件发生 → 中断线信号变化 → 中断控制器收集仲裁 → CPU 响应 → 查向量表 → 跳转 ISR → 清中断源 → 返回。然后说明电平触发和边沿触发的区别、优先级和嵌套规则、FIQ 和 IRQ 的差异。最后强调 ISR 要短、要清中断源、不能睡眠。

### 10 分钟版本

可以结合 Cortex-M 和 Cortex-A 两种架构展开。先讲 NVIC 的寄存器操作和向量表布局，再讲 GIC 的 Distributor + CPU Interface 架构和 SPI/PPI/SGI 分类。然后详细说明中断状态机（Inactive → Pending → Active → Inactive）。再对比裸机和 Linux 的中断处理差异：裸机直接在 ISR 里处理，Linux 分硬中断和软中断/threaded IRQ。最后讨论中断调试方法：GPIO 翻转测延迟、/proc/interrupts 看统计、ftrace 跟踪中断路径。

## 实战练习

1. 在 Cortex-M 裸机上配置一个 GPIO 外部中断，用按键触发，ISR 里翻转 LED，用示波器测量中断响应延迟。
2. 故意在 ISR 里不清中断源，观察电平触发下的死循环现象。
3. 在 Linux 驱动里用 `devm_request_threaded_irq` 注册中断，硬中断里只读数据，线程里做打印和后处理。
4. 用 `/proc/interrupts` 和 `/sys/kernel/debug/tracing` 观察中断统计和路径。
5. 在 Bootloader + APP 场景下，验证 APP 不设 VTOR 时中断会跳到哪里。

## 关键要点

1. 中断链路：外设信号 → 中断控制器仲裁 → CPU 响应 → 向量表 → ISR → 清中断源 → 返回。
2. 中断控制器是 CPU 和外设之间的调度中心，负责收集、仲裁、屏蔽和上报。
3. 向量表存放 ISR 入口地址，CPU 响应中断时自动查表跳转。
4. 电平触发不清源会死循环，边沿触发处理太慢会丢中断。
5. ISR 必须短、必须清中断源、不能调用可能睡眠的函数。
6. 优先级数值越小优先级越高（ARM 系列统一规则）。
7. FIQ 比 IRQ 优先级高、有独立寄存器、响应更快，但现代系统很少使用。
8. 裸机 APP 启动时必须重设 VTOR，否则中断跳到 Bootloader 的 ISR。
