# RTOS-任务间通信

## 原始问题

多个任务同时跑起来以后，它们之间到底该怎么传数据、传事件、做同步？为什么有的场景该用队列，有的该用信号量，有的又更适合事件组，而不是一律用全局变量？

## 先给结论

任务间通信的本质，是在并发系统里安全地传递数据、事件和资源拥有权。

先记住下面几个结论：

1. 任务间通信不只是“把值传过去”，还包括同步、时序和所有权。
2. 队列更适合传数据，信号量更适合同步，互斥锁更适合保护共享资源，事件组更适合组合条件。
3. 用全局变量临时凑合最容易导致竞态、覆盖和调试困难。
4. 任务通信设计不好，最常见现象不是立刻崩，而是偶发错、偶发卡、偶发丢。
5. AI 能生成 RTOS 通信代码，但只有你理解数据语义和同步语义，才能决定到底该选哪种机制。

## 这个知识解决什么问题

1. 不知道队列、信号量、互斥锁和事件组各自适合什么场景。
2. 多个任务共享数据后，系统开始偶发错乱。
3. 面试和工作中经常会被问到“队列和信号量有什么区别”。

## 核心概念 / 本质机制

### 1. 任务间通信到底在解决什么

主要解决三类问题：

1. 传数据。
2. 通知事件。
3. 保护共享资源。

如果这三件事混着做，代码很快就会乱。

### 2. 队列适合传数据

队列的核心特点是：

1. 有序。
2. 带缓存。
3. 可以阻塞等待。

典型场景：

1. UART 接收任务把字节交给协议解析任务。
2. 采样任务把数据交给处理任务。

### 3. 信号量适合同步

信号量更像“你可以开始了”的通知。

典型场景：

1. 中断通知任务有数据来了。
2. 一个任务等待另一个任务完成某步骤。

### 4. 互斥锁适合保护共享资源

它的重点不是传事件，而是保证同一时刻只有一个任务操作共享对象。

典型场景：

1. 多任务共享同一个 I2C 总线。
2. 多任务共享同一个日志输出接口。

### 5. 事件组适合组合条件

如果你关心的是“多个事件是否都发生了”，事件组会更方便。

典型场景：

1. 等待网络就绪和设备初始化都完成。
2. 等待多个子模块准备完成再进入下一阶段。

## 数据流 / 控制流 / 时序关系

```text
UART 中断收到数据
-> 中断把字节写入队列
-> 解析任务从队列阻塞接收
-> 解析完成后给业务任务发事件或消息
-> 业务任务再根据事件更新状态机
```

## 最小可运行示例

```c
static QueueHandle_t sensor_queue;
static SemaphoreHandle_t ready_sem;

static void sample_task(void *arg)
{
    int sample;

    (void)arg;

    for (;;) {
        sample = adc_read();
        xQueueSend(sensor_queue, &sample, portMAX_DELAY);
        vTaskDelay(pdMS_TO_TICKS(10));
    }
}

static void process_task(void *arg)
{
    int sample;

    (void)arg;

    xSemaphoreTake(ready_sem, portMAX_DELAY);

    for (;;) {
        if (xQueueReceive(sensor_queue, &sample, portMAX_DELAY) == pdPASS)
            process_sample(sample);
    }
}
```

## 代码解读

### 1. 为什么队列和信号量一起出现

因为它们解决的问题不同：

1. `ready_sem` 表示“系统初始化完成，可以开始工作”。
2. `sensor_queue` 表示“这里有一批采样数据”。

### 2. 为什么不建议直接共享 `sample`

直接共享全局变量最容易出现：

1. 覆盖旧值。
2. 读到半更新数据。
3. 丢失时间顺序。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 传数据 | 队列 | 只用全局变量 | 容易覆盖和乱序 |
| 通知事件 | 信号量 / 事件组 | 轮询标志位 | CPU 浪费且时序差 |
| 保护共享资源 | 互斥锁 | 多任务直接同时访问 | 竞态和数据破坏 |
| 组合条件 | 事件组 | 手工拼一堆 flag | 可读性和维护性差 |

## 边界条件与适用范围

1. 不同 RTOS 名称和 API 可能不同，但“队列传数据、信号量做同步、互斥锁保资源”的主线基本一致。
2. 某些场景可以多种机制都能做，但应优先选语义最贴切的一种。
3. ISR 和任务上下文使用 API 时要区分普通版本和 ISR 版本。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 偶发丢数据 | 队列长度太小；发送过快 | 看队列深度和满队列日志 |
| 任务一直等不到 | 信号量没释放；事件没置位 | 查发送点和等待点 |
| 共享资源偶发错乱 | 没加互斥锁；锁范围不对 | 查并发访问路径 |
| 系统卡死 | 锁顺序错；死锁 | 查所有加锁路径 |

## 工程落地建议

1. 先分清是传数据、发通知还是保护资源。
2. 设计通信机制时顺手设计超时和错误日志。
3. 通信对象命名尽量体现语义，比如 `rx_queue`、`ready_sem`、`bus_mutex`。

## 性能、稳定性、可维护性影响

1. 任务间通信设计是否清楚，直接影响系统稳定性。
2. 用错机制通常不会立刻报错，但会显著增加偶发问题。
3. 语义清晰的同步对象能大幅降低维护成本。

## 面试 / 问答怎么讲

### 30 秒版本

任务间通信主要解决三类问题：传数据、通知事件、保护共享资源。队列更适合传数据，信号量更适合同步，互斥锁更适合保护资源，事件组更适合组合条件。

### 3 分钟版本

可以结合一个采样任务和处理任务的例子，说明为什么采样数据用队列、系统准备完成用信号量、共享总线用互斥锁。这样比只背 API 更能体现理解。

### 10 分钟版本

可以再进一步讲并发风险、ISR 与任务配合、超时处理和死锁排查，说明为什么任务间通信的关键不是“能跑通”，而是语义清楚、异常路径清楚、调试路径清楚。

## 实战练习

1. 用队列实现一次 UART 数据从接收任务到解析任务的传递。
2. 用信号量实现一次“初始化完成后再开始业务任务”的同步。
3. 用互斥锁保护一个共享 I2C 总线接口。

## 关键要点

1. 队列传数据，信号量做同步，互斥锁保资源，事件组管组合条件。
2. 先分清通信语义，再选 RTOS 机制。
3. 全局变量直连是最容易埋坑的做法。
4. 并发问题往往是偶发型，设计阶段比事后补救更重要。
