# 项目与架构-错误处理与日志策略

## 原始问题

为什么很多嵌入式项目刚开始看起来功能都能跑，但一到联调、异常场景、量产和维护阶段，就开始出现“错了不知道谁先错”“日志太多看不出根因”“出问题只能加更多打印”的情况？错误处理和日志策略到底该怎么设计，才能真正服务工程交付？

## 先给结论

错误处理与日志策略的本质，是让系统在异常发生时能够被尽早发现、被准确传播、被有效定位，并在需要时安全恢复。

先记住下面几个结论：

1. 错误处理不只是“返回一个错误码”，而是“定义谁发现、谁上报、谁恢复、谁记录上下文”。
2. 日志不只是“多打一点打印”，而是“在关键边界留下足够的信息，让你能还原问题链”。
3. 大多数难排障项目的问题，不是没有日志，而是错误传播链混乱、日志重复、上下文缺失、严重级别失真。
4. 好的策略通常是：底层返回可判断的错误，上层决定是否降级、重试、告警或终止，同时在合适边界打一次高价值日志。
5. AI 可以帮你生成错误码枚举和日志宏，但它不知道你的系统里哪些错误该重试、哪些错误必须停机、哪些日志应该限频，真正决定工程质量的是你的策略设计。

如果只能说“失败就打印一下然后返回 -1”，却讲不清错误如何分类、日志应该打在哪里、为什么不能层层重复打印同一个失败、如何防止日志淹没根因，就说明这部分还没有真正掌握。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 模块之间错误传播混乱，调用方拿到失败却不知道上下文。
2. 代码里到处 `printf`，但一出故障仍然无法快速定位根因。
3. 面试和工作中经常被问到“你怎么做错误处理和日志设计”，却只能回答“打日志、返回错误码”。
4. 项目从 demo 走向交付时，需要把“能跑”升级成“异常时也可维护、可排障、可复盘”的系统。

它在 AI 时代仍然重要，因为 AI 非常擅长生成“看起来规范”的 `LOG_ERROR()` 和 `enum err`，但它不会自动知道你这个错误应该在驱动层吞掉、在服务层升级告警，还是在系统层触发保护动作；也不会自动知道哪些日志是根因、哪些只是链式失败。真正稀缺的，是你对系统边界和失败语义的判断。

## 核心概念 / 本质机制

### 1. 错误处理到底在处理什么

至少包含四件事：

1. 发现错误。
2. 表达错误。
3. 传播错误。
4. 处理错误。

如果只做了第一步和第二步，例如“发现失败并返回 `-1`”，但没有设计后两步，系统就会变成：

1. 失败消息到处飞。
2. 上层不知道该怎么做。
3. 日志里重复出现同一个现象，却没人真正接住它。

### 2. 为什么要先区分错误类型

不是所有错误都应该一样对待。

常见划分方式包括：

1. 可恢复错误：例如暂时超时、资源忙、网络短时波动。
2. 不可恢复错误：例如配置非法、硬件缺失、关键数据损坏。
3. 输入错误：例如参数非法、状态不允许。
4. 环境错误：例如外设没响应、电源没起、依赖服务未就绪。
5. 编程错误：例如违反接口约束、状态机不变量被打破。

如果不分类，系统很容易：

1. 对致命错误也盲目重试。
2. 对暂时错误却直接崩溃。
3. 对调用者输入错误和底层硬件错误都返回同一个 `-1`。

### 3. 为什么错误码只是载体，不是策略本身

错误码解决的是“怎么表达失败结果”，例如：

1. `0` 表示成功，负值表示失败。
2. `enum` 区分具体错误原因。
3. `errno` 风格统一部分语义。

但真正更关键的是：

1. 谁负责解释这个错误。
2. 哪一层决定是否重试、降级、告警、上报。
3. 哪一层负责最终日志。

所以错误码只是信号，策略才是工程能力。

### 4. 为什么日志不能层层重复打印

这是非常常见的坏味道：

1. 底层函数失败打印一遍。
2. 中间层收到失败又打印一遍。
3. 上层再打印一遍。
4. 最后日志里出现三条几乎相同的错误。

问题在于：

1. 噪声变大。
2. 根因被淹没。
3. 你看到的是“三次同一个失败”，不是“三个独立问题”。

更稳的做法通常是：

1. 底层返回清晰错误码。
2. 在真正跨边界、需要补上下文的地方打一条高价值日志。
3. 上层只在策略变化点打印，例如“决定重试”“进入降级模式”“准备复位系统”。

### 5. 什么叫“高价值日志”

高价值日志至少应该回答这些问题：

1. 谁出错了。
2. 当时在做什么。
3. 错误码或状态是什么。
4. 影响范围是什么。
5. 系统准备怎么处理。

例如：

1. “I2C read failed” 价值不够。
2. “sensor init: read chip id failed, addr=0x48, ret=-ETIMEDOUT, retry=2/3” 价值就高得多。

### 6. 为什么日志级别必须有语义

常见级别可以这样理解：

1. `ERROR`：当前功能失败或系统异常，需要关注。
2. `WARN`：偏离正常路径，但系统还能继续运行。
3. `INFO`：关键生命周期事件，例如初始化完成、模式切换。
4. `DEBUG`：联调期细节，不应长期大流量开启。

如果级别乱用，常见后果是：

1. 正常事件刷成 ERROR，告警疲劳。
2. 真正根因只打成 DEBUG，现场看不到。
3. 所有东西都打 INFO，日志没有重点。

### 7. 为什么“在边界打日志”比“到处打日志”更重要

常见高价值边界包括：

1. 驱动初始化边界。
2. 模块接口边界。
3. 状态切换边界。
4. 重试和降级边界。
5. 错误即将跨模块传播的边界。

因为这些位置最适合补足上下文：

1. 当前模块是谁。
2. 输入条件是什么。
3. 下一步决定是什么。

反而在深层函数里到处打日志，很容易只剩碎片。

### 8. 为什么错误处理必须和恢复策略一起设计

错误发生后常见动作包括：

1. 直接返回。
2. 重试。
3. 回滚。
4. 降级。
5. 复位模块。
6. 上报并停止服务。

没有恢复策略的错误处理，往往只是“把失败往上扔”。

但真正工程里更重要的问题是：

1. 这个失败能不能靠重试解决。
2. 重试几次才合理。
3. 失败后还能不能继续提供部分能力。
4. 什么时候必须进入安全状态。

## 数据流 / 控制流 / 时序关系

下面用一个“传感器初始化失败”的典型链路来理解：

```text
app_start()
-> sensor_service_init()
-> sensor_driver_init()
-> i2c_read_chip_id() 失败
-> driver 返回明确错误码
-> service 记录一次带上下文的日志
-> service 根据策略决定重试 3 次
-> 仍失败
-> service 进入降级模式并上报“传感器不可用”
-> app 根据能力矩阵关闭相关功能
```

这里面每层都应该做自己该做的事：

1. 底层负责发现和表达错误。
2. 服务层负责策略决定。
3. 应用层负责用户可见影响和最终降级动作。

## 最小可运行示例

下面给一个适合嵌入式工程的最小错误处理闭环：

```c
#include <stdio.h>

typedef enum {
    APP_OK = 0,
    APP_ERR_PARAM = -1,
    APP_ERR_IO = -2,
    APP_ERR_TIMEOUT = -3,
    APP_ERR_NOT_READY = -4,
} app_err_t;

typedef struct {
    int retries;
    int online;
} sensor_ctx_t;

static app_err_t sensor_read_chip_id(unsigned char *id)
{
    if (i2c_bus_not_ready())
        return APP_ERR_NOT_READY;

    if (i2c_read_reg(0x00, id) != 0)
        return APP_ERR_TIMEOUT;

    return APP_OK;
}

static app_err_t sensor_service_init(sensor_ctx_t *ctx)
{
    unsigned char chip_id = 0;
    app_err_t ret;

    if (ctx == NULL)
        return APP_ERR_PARAM;

    for (ctx->retries = 0; ctx->retries < 3; ++ctx->retries) {
        ret = sensor_read_chip_id(&chip_id);
        if (ret == APP_OK) {
            ctx->online = 1;
            printf("[INFO] sensor init ok, chip_id=0x%02X\n", chip_id);
            return APP_OK;
        }

        printf("[WARN] sensor init retry=%d ret=%d\n",
               ctx->retries + 1, ret);
    }

    ctx->online = 0;
    printf("[ERROR] sensor init failed after retries, degraded mode\n");
    return APP_ERR_IO;
}
```

这个示例体现了几件关键事：

1. 底层函数返回明确错误码，而不是只返回真假。
2. 中间层补充上下文并决定是否重试。
3. 成功、重试、失败三类事件使用了不同级别的日志。
4. 最终失败后明确进入降级模式，而不是“打印一下就算了”。

## 代码解读

### 1. 为什么 `sensor_read_chip_id()` 不直接打印日志

因为它属于较底层函数。

如果这里一失败就打印，而上层初始化流程也打印，很快就会重复。

更稳的做法是：

1. 底层尽量返回清晰错误。
2. 由更靠近业务边界的一层决定是否打印和怎么打印。

### 2. 为什么重试逻辑放在 `sensor_service_init()`

因为“是否值得重试”通常是策略问题，不是底层驱动语义本身。

底层函数最清楚“发生了什么错误”，但服务层更清楚：

1. 当前功能是否关键。
2. 重试几次可以接受。
3. 失败后是否允许降级。

### 3. 为什么日志里要带 `retry` 和 `ret`

因为这决定了你后面能否快速判断：

1. 是一次偶发失败，还是持续失败。
2. 重试机制是否真的在运行。
3. 失败类型是否稳定一致。

### 4. 为什么最终失败后要显式设置 `online = 0`

因为错误处理不只是打印日志，还要让系统状态和现实一致。

如果日志说失败了，但内部状态还像成功一样，后面只会产生更多次生问题。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 错误表达 | 返回有区分度的错误码 | 所有失败都返回 `-1` | 上层没法制定策略 |
| 日志边界 | 在跨模块边界补充上下文打印 | 每层都打一遍一样的错 | 日志噪声大 |
| 恢复策略 | 根据错误类型决定重试/降级/终止 | 一律无限重试或一律直接退出 | 既不稳也不可控 |
| 日志级别 | `ERROR/WARN/INFO/DEBUG` 有明确含义 | 所有日志都用同一级别 | 重点丢失 |
| 状态同步 | 错误处理后同步更新系统状态 | 打完日志但状态没变 | 容易引发次生故障 |
| 限频控制 | 高频错误加计数或限频 | 每次失败都狂刷日志 | 根因被日志洪水淹没 |

## 边界条件与适用范围

1. 这篇笔记更偏嵌入式和系统工程视角，不展开所有桌面服务或分布式日志体系细节。
2. 很底层、极高频路径可能不适合每次都打印日志，更适合计数器、trace 点或限频日志。
3. 不同项目对错误码和日志风格可以不同，但边界清晰、上下文充分、策略明确这三件事最好保持不变。
4. 对安全相关或强实时系统，某些错误处理策略会比普通产品更保守，例如直接进入安全态。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 日志很多但看不出根因 | 层层重复打印；缺少上下文 | 找第一条真正改变状态的日志 |
| 出错后系统状态越来越乱 | 失败后没更新状态；回滚不完整 | 查状态机和错误路径 |
| 现场日志刷爆串口 | 高频错误无节制打印 | 增加限频、计数、摘要日志 |
| 所有模块都返回 `-1` | 错误码体系太粗糙 | 重构错误分类 |
| 重试逻辑让系统更卡 | 对不可恢复错误也无限重试 | 按错误类型分流 |
| 调试期能定位，量产后定位不了 | 关键信息只在 DEBUG 级别 | 调整关键日志级别和字段 |

排查一条错误链时，推荐先问这几个问题：

1. 第一处失败在哪一层发生。
2. 哪一条日志真正补充了上下文。
3. 哪一层决定了重试或降级。
4. 最终系统状态有没有和失败结果保持一致。

## 工程落地建议

1. 先统一错误码和日志级别的基本语义，再写模块代码。
2. 约定“谁负责最终打印”，避免层层重复。
3. 对初始化、状态切换、重试和降级这些关键边界打高价值日志。
4. 高频错误默认考虑限频、计数器和摘要输出。
5. 错误处理路径要和正常路径一样做最小验证，不要只测 happy path。

## 性能、稳定性、可维护性影响

1. 错误策略清晰后，系统在异常情况下更可控，不容易失控扩散。
2. 高价值日志能显著缩短排障时间，尤其是在联调和现场问题里。
3. 日志洪水和重复错误处理会直接拖垮实时性、串口带宽和维护体验。
4. 把错误处理设计成系统能力的一部分，是从 demo 走向交付的重要分水岭。

## 面试 / 问答怎么讲

### 30 秒版本

错误处理与日志策略的核心，不是简单返回错误码和多打日志，而是明确错误分类、传播边界和恢复动作。底层返回清晰失败，上层决定重试或降级，并在关键边界打一条有上下文的高价值日志，这样系统才真正可维护。

### 3 分钟版本

可以先讲错误处理四步：发现、表达、传播、处理。然后讲为什么要区分可恢复和不可恢复错误，为什么不能层层重复打印，为什么日志级别要有语义。最后补一个实际例子，比如传感器初始化失败时，底层返回错误码，服务层决定重试和降级，并记录一次带上下文的日志。

### 10 分钟版本

可以进一步结合项目经验展开：哪些错误在驱动层记录，哪些在业务层记录；什么时候用错误码、什么时候用断言；高频路径为什么要限频；为什么“打印一下就返回”不等于错误处理；如何把错误和状态机、重试、回滚、告警串起来。再补一个“现场日志很多却定位不到根因”的反例，会很有说服力。

## 实战练习

1. 选一个现有模块，把所有裸 `-1` 返回值重构成有语义的错误码。
2. 选一条初始化链路，重构成“底层返回错误，上层决定重试和降级，只在边界打日志”的结构。
3. 给一个高频失败场景增加限频日志和失败计数，并验证日志量变化。
4. 故意制造一个设备不可用场景，检查日志、状态变量和上层降级行为是否一致。

## 关键要点

1. 错误处理的重点是策略，不只是返回值。
2. 日志的重点是上下文，不是数量。
3. 真正值钱的是“错误被准确传播并被系统接住”，而不是“到处都在打印失败”。
4. 错误处理和日志策略，是工程交付能力的重要组成部分。
