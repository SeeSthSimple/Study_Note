# 项目与架构-模块边界划分

## 原始问题

为什么很多嵌入式项目刚开始还能维护，做一段时间后就变成“改一个地方动全局”？模块边界到底该怎么划，为什么它比“先把功能做出来”更影响长期交付质量？

## 先给结论

模块边界划分的本质，是明确“谁负责什么、谁不该知道什么、谁通过什么接口协作”。

先记住下面几个结论：

1. 边界划分得好，系统会更容易改、测、查和交接。
2. 边界划分得差，最常见现象不是功能不能跑，而是改动风险越来越大。
3. 嵌入式项目特别容易因为硬件、协议、RTOS、驱动和业务层混在一起而失控。
4. 好的模块边界不是按文件数划，而是按职责、变化频率和依赖方向划。
5. AI 可以帮你重写函数，但如果边界本身混乱，它只会更快地产生“能跑但难维护”的代码。

## 这个知识解决什么问题

1. 功能越来越多后，代码开始出现跨层直接访问和全局变量蔓延。
2. 不知道一个模块应该封装到什么程度。
3. 面试和工作中经常被问到“你怎么拆模块、怎么设计边界”。

## 核心概念 / 本质机制

### 1. 模块边界到底在划什么

至少在划三件事：

1. 职责边界。
2. 数据边界。
3. 依赖边界。

一个模块最理想的状态是：

1. 它的职责清楚。
2. 它暴露的接口有限。
3. 它的内部细节不被外部随意依赖。

### 2. 为什么嵌入式项目特别容易边界失控

因为它天然跨层：

1. 硬件和寄存器。
2. 驱动和 RTOS。
3. 协议和业务逻辑。
4. 升级、日志、状态机和异常恢复。

如果没有刻意划边界，很容易出现：

1. 业务层直接改寄存器。
2. 协议层直接操作硬件。
3. 多个任务直接共享内部结构体。

### 3. 一个稳妥的划分思路是什么

常见好思路包括：

1. 按职责划分。
2. 按变化频率划分。
3. 按依赖方向划分。

例如传感器项目里可以拆成：

1. `bsp`：底层硬件访问。
2. `driver`：设备驱动封装。
3. `protocol`：通信协议。
4. `service`：业务逻辑。
5. `app`：应用流程。

### 4. 为什么接口数量越少通常越稳

因为接口一旦暴露出去，就会被依赖。

接口越散，问题越多：

1. 调用方越容易越层。
2. 修改内部实现越容易牵一大片。
3. 交接和阅读成本越高。

### 5. 为什么边界划分和错误处理强相关

如果边界不清楚，错误通常也会乱传。

例如：

1. 底层错误码随意往上漏。
2. 上层直接依赖底层寄存器状态。
3. 业务层不得不理解太多底层细节。

清晰边界能让错误在合适层次被转换和处理。

## 数据流 / 控制流 / 时序关系

下面给一个典型嵌入式应用分层：

```text
app
-> service
-> protocol
-> driver
-> bsp
-> hardware
```

理想依赖方向是从上到下单向流动，而不是层层交叉回调、全局互调。

## 最小可运行示例

下面给一个简单的模块边界例子：

```c
/* driver_sensor.h */
int sensor_init(void);
int sensor_read_temperature(int *temp);

/* service_monitor.c */
int monitor_sample_once(void)
{
    int temp;
    int ret;

    ret = sensor_read_temperature(&temp);
    if (ret < 0)
        return ret;

    return alarm_check_temp(temp);
}
```

这个例子表达的是：

1. `service_monitor` 只依赖传感器驱动提供的接口。
2. 它不需要知道 I2C 细节、寄存器地址或 GPIO 时序。
3. 以后底层从 I2C 改成 SPI，只要驱动接口稳定，上层基本不用动。

## 代码解读

### 1. 为什么 `service` 不该直接碰寄存器

因为这会让业务层直接依赖底层细节。

一旦底层实现变化：

1. 上层跟着改。
2. 维护范围扩大。
3. 测试和回归成本上升。

### 2. 为什么“封装”不是把所有函数都藏起来

封装的目标不是神秘，而是控制依赖面。

真正需要暴露的应该是：

1. 稳定接口。
2. 语义清楚的能力。

而不是所有内部步骤。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 业务调用 | 调用驱动接口 | 直接改底层寄存器 | 越层依赖严重 |
| 模块职责 | 一个模块围绕单一主责任 | 一个模块什么都做 | 难维护 |
| 依赖方向 | 尽量单向 | 层层双向调用 | 结构越来越乱 |
| 数据暴露 | 暴露必要结果 | 公开大量内部结构体 | 修改代价高 |

## 边界条件与适用范围

1. 不是所有项目都要追求复杂分层，小项目可以简单，但边界思路依然要有。
2. 边界过细也会带来不必要复杂度，所以要结合项目规模权衡。
3. 真正重要的是职责和依赖是否清晰，不是目录名字是否漂亮。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 改一个模块全项目回归 | 边界不清；接口面过大 | 画依赖图，看改动波及范围 |
| 业务逻辑难测 | 业务层依赖太多底层细节 | 查是否能做接口替身 |
| 新人接手困难 | 层次混乱；入口过多 | 看模块职责是否一眼可见 |
| 错误处理乱 | 错误在错误层次泄漏 | 查错误码和日志在哪层转换 |

## 工程落地建议

1. 写模块前先回答：这个模块负责什么，不负责什么。
2. 先设计接口，再填内部实现。
3. 画一张简单依赖图，确认依赖方向是否大致单向。
4. 交接时优先讲模块边界，而不是先讲函数细节。

## 性能、稳定性、可维护性影响

1. 模块边界本身通常不直接决定性能，但强烈决定维护成本和回归风险。
2. 边界清楚，重构和适配新板卡会轻松很多。
3. 边界混乱时，项目越做越怕改，这会直接放大工作压力。

## 面试 / 问答怎么讲

### 30 秒版本

模块边界划分的核心是明确职责、数据和依赖边界，让每层只知道自己该知道的东西。嵌入式项目里如果业务层、协议层和驱动层混在一起，短期能跑，长期一定难维护。

### 3 分钟版本

可以从一个传感器项目讲起：底层 `bsp` 负责硬件访问，驱动层封装寄存器读写，协议层处理通信格式，业务层只关心温度值和告警逻辑。这样换板、换总线或换协议时，影响范围就更可控。

### 10 分钟版本

可以进一步讲变化频率和依赖方向：把经常变化的板级实现隔离在底层，把稳定业务接口留给上层；错误码和日志在合适层转换；通过状态机和服务层收敛复杂流程。这种讲法更接近真实工程架构能力。

## 实战练习

1. 选一个现有小项目，画出当前模块依赖图。
2. 找出一个“业务层越过驱动层直接碰底层”的例子，重构成清晰边界。
3. 为一个传感器模块设计最小稳定接口，并说明哪些实现细节不应暴露。

## 关键要点

1. 模块边界划的是职责、数据和依赖。
2. 嵌入式项目越跨层，越需要刻意控制边界。
3. 好边界能显著降低维护压力和回归风险。
4. 先设计接口，再写实现，通常更稳。
