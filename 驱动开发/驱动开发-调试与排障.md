# 驱动开发-调试与排障

## 原始问题

驱动写完了但 `probe` 不进、中断不触发、数据不对、系统崩溃，到底怎么查？`dmesg` 里那些信息怎么看？`dev_dbg` 和 `pr_debug` 有什么区别？`ftrace` 和 `dynamic_debug` 怎么用？驱动排障有没有系统化的方法论？

## 先给结论

驱动排障的核心不是"到处加 print"，而是"按层级定位、用工具验证、缩小怀疑范围"：

1. 排障的第一步永远是"确认现象"，而不是"猜测原因"。
2. 驱动问题按层级排查：模块加载 → 设备匹配 → probe → 资源申请 → 中断 → 数据流。
3. `dmesg` 是驱动排障的第一站，`dev_dbg` / `dynamic_debug` 是精确控制日志的工具。
4. `ftrace` 可以跟踪函数调用链，`debugfs` 可以查看内核内部状态。
5. 崩溃分析从 `oops` 日志入手，定位出错指令和调用栈。

如果只能背"加 print 调试"，但讲不清排障方法论、日志工具使用和崩溃分析，就还没有真正掌握驱动调试。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 驱动 `probe` 不进，不知道是匹配问题还是资源问题。
2. 中断不触发或数据不对，不知道从哪里开始查。
3. 系统崩溃后只有一屏 `oops` 信息，不知道怎么分析。
4. 不知道 `dynamic_debug`、`ftrace`、`debugfs` 这些工具怎么用。
5. 面试时被问"你怎么调试驱动"，只能说"加 print"。

它在AI时代依然重要，因为AI生成代码后，验证和排障仍然必须靠人。调试能力是"AI 不可替代"的核心工程能力之一。

## 核心概念 / 本质机制

### 1. 驱动排障的系统化方法论

```text
第1步：确认现象
  -> 到底出了什么问题？不工作？偶发错误？崩溃？

第2步：缩小范围
  -> 是驱动问题还是硬件问题？
  -> 是 probe 阶段还是运行阶段？
  -> 是配置问题还是逻辑问题？

第3步：建立怀疑链
  -> 列出所有可能的原因，按可能性排序

第4步：逐个验证
  -> 用工具确认或排除每个怀疑

第5步：定位根因
  -> 找到最小可复现条件

第6步：修复并验证
  -> 修复后确认问题确实解决，不是偶然消失
```

### 2. 按层级排查驱动问题

| 层级 | 检查内容 | 工具 |
| --- | --- | --- |
| 模块加载 | `insmod` 是否成功 | `lsmod`、`dmesg` |
| 设备匹配 | 设备树和驱动是否匹配 | `/sys/bus/platform/drivers/` |
| probe | probe 是否被调用、返回什么 | `dmesg`、`dev_info` |
| 资源申请 | 内存、IO、IRQ、时钟是否成功 | `dmesg`、`/proc/iomem` |
| 中断 | 中断是否触发、handler 是否被调用 | `/proc/interrupts` |
| 数据流 | 数据是否正确流转 | `dev_dbg`、逻辑分析仪 |
| 并发 | 是否有竞态、死锁 | `lockdep`、`ftrace` |

### 3. 日志系统

#### `printk` 和日志级别

```c
pr_emerg("system is unusable\n");   /* 0, 最高 */
pr_alert("action must be taken\n"); /* 1 */
pr_crit("critical conditions\n");   /* 2 */
pr_err("error conditions\n");       /* 3 */
pr_warn("warning conditions\n");    /* 4 */
pr_notice("normal but significant\n"); /* 5 */
pr_info("informational\n");         /* 6 */
pr_debug("debug-level messages\n"); /* 7, 最低 */
```

查看日志：

```bash
dmesg                      # 查看内核日志
dmesg -w                   # 实时跟踪
dmesg -l err,warn          # 只看错误和警告
dmesg | grep mydev         # 过滤特定驱动
```

日志级别控制：

```bash
echo 8 > /proc/sys/kernel/printk   # 所有级别都输出到控制台
```

#### `dev_dbg` 和 `dynamic_debug`

`dev_dbg` 是设备相关的调试日志，可以在运行时动态开关：

```c
dev_dbg(&pdev->dev, "irq=%d, status=0x%x\n", irq, status);
```

运行时控制：

```bash
# 开启所有 mydev 的调试日志
echo "file mydev.c +p" > /sys/kernel/debug/dynamic_debug/control

# 开启特定函数的调试日志
echo "file mydev.c func my_probe +p" > /sys/kernel/debug/dynamic_debug/control

# 关闭
echo "file mydev.c -p" > /sys/kernel/debug/dynamic_debug/control

# 查看当前所有调试开关
cat /sys/kernel/debug/dynamic_debug/control | grep mydev
```

`dynamic_debug` 的优势：

1. 不需要重新编译内核或模块。
2. 可以按文件、函数、行号精确控制。
3. 生产环境可以关闭所有调试日志，零开销。

### 4. `/sys` 和 `/proc` 文件系统

#### `/proc/interrupts`

```bash
cat /proc/interrupts
```

查看内容：

1. 每个 IRQ 号的触发次数。
2. 绑定到哪个 CPU。
3. 注册的驱动名称。
4. 中断类型（Edge/Level）。

#### `/proc/iomem`

```bash
cat /proc/iomem
```

查看物理内存区域分配情况，确认 IO 映射是否正确。

#### `/sys/bus/`

```bash
# 查看已注册的 platform 设备
ls /sys/bus/platform/devices/

# 查看已注册的驱动
ls /sys/bus/platform/drivers/

# 查看设备绑定状态
cat /sys/bus/platform/devices/mydev/driver/module
```

#### `/sys/kernel/debug/`

```bash
# GPIO 状态
cat /sys/kernel/debug/gpio

# pinctrl 状态
cat /sys/kernel/debug/pinctrl/pinctrl-maps

# regulator 状态
cat /sys/kernel/debug/regulator/regulator_summary

# clk 状态
cat /sys/kernel/debug/clk/clk_summary
```

### 5. ftrace：函数跟踪

```bash
# 查看可用的跟踪器
cat /sys/kernel/debug/tracing/available_tracers

# 使用 function 跟踪器
echo function > /sys/kernel/debug/tracing/current_tracer

# 只跟踪特定函数
echo my_probe > /sys/kernel/debug/tracing/set_ftrace_filter

# 启动跟踪
echo 1 > /sys/kernel/debug/tracing/tracing_on

# 触发操作后查看结果
cat /sys/kernel/debug/tracing/trace

# 停止跟踪
echo 0 > /sys/kernel/debug/tracing/tracing_on
```

`function_graph` 跟踪器可以显示函数调用关系：

```bash
echo function_graph > /sys/kernel/debug/tracing/current_tracer
echo 1 > /sys/kernel/debug/tracing/tracing_on
# 触发操作
cat /sys/kernel/debug/tracing/trace
```

### 6. 崩溃分析

#### oops 日志解读

```text
Unable to handle kernel NULL pointer dereference at virtual address 00000000
pgd = c0004000
[00000000] *pgd=00000000
Internal error: Oops: 5 [#1] SMP ARM
Modules linked in: mydev(+) ...
CPU: 0 PID: 123 Comm: insmod
PC is at my_probe+0x34/0x100 [mydev]
LR is at platform_drv_probe+0x48/0xa0
...
Call trace:
[<bf000034>] my_probe+0x34/0x100 [mydev]
[<c0123456>] platform_drv_probe+0x48/0xa0
[<c0125678>] driver_probe_device+0x88/0x120
```

关键信息：

1. **出错类型**：NULL pointer dereference（空指针解引用）。
2. **出错地址**：`00000000`（访问了空指针）。
3. **出错位置**：`my_probe+0x34`（在 `my_probe` 函数偏移 0x34 处）。
4. **调用栈**：从 `my_probe` 到 `driver_probe_device`。

定位方法：

1. 用 `addr2line` 把偏移转成源码行号：

```bash
arm-linux-gnueabihf-addr2line -e mydev.ko 0x34
```

2. 用 `gdb` 查看反汇编：

```bash
arm-linux-gnueabihf-gdb mydev.ko
(gdb) disassemble my_probe
```

#### 常见崩溃类型

| 崩溃类型 | 典型原因 | 排查方向 |
| --- | --- | --- |
| NULL pointer dereference | 指针未初始化或函数返回 NULL 未检查 | 检查返回值 |
| Unable to handle paging request | 访问了未映射的地址 | 检查 ioremap |
| BUG: scheduling while atomic | 在原子上下文调用了可能睡眠的函数 | 检查中断上下文 |
| spinlock lockup | 自旋锁死锁 | 检查锁顺序 |
| kernel stack overflow | 栈溢出 | 减少栈上大数组 |

### 7. lockdep：锁依赖检测

```bash
# 启用 lockdep
echo 1 > /proc/sys/kernel/lockdep
```

lockdep 能检测：

1. 潜在的死锁（ABBA 锁顺序）。
2. 在中断上下文使用了可能睡眠的锁。
3. 重复加锁。

### 8. 常见驱动问题的排查模板

#### probe 不进

```bash
# 1. 模块是否加载
lsmod | grep mydev

# 2. 设备树节点是否存在
ls /sys/bus/platform/devices/ | grep mydev

# 3. 驱动是否注册
ls /sys/bus/platform/drivers/ | grep mydev

# 4. 匹配是否成功
cat /sys/bus/platform/devices/mydev/driver/module 2>&1

# 5. dmesg 看错误
dmesg | grep -i "mydev\|probe\|match"
```

#### 中断不触发

```bash
# 1. 中断是否注册成功
dmesg | grep "irq"

# 2. 中断计数是否增加
cat /proc/interrupts | grep mydev

# 3. 中断触发类型是否正确
cat /proc/interrupts

# 4. 硬件是否真的产生中断
# 用示波器量中断引脚
```

#### 数据不对

```bash
# 1. 寄存器值是否正确
dev_dbg(&pdev->dev, "reg=0x%x\n", readl(base + REG));

# 2. DMA 缓冲区内容
dev_dbg(&pdev->dev, "buf[0]=0x%x\n", buf[0]);

# 3. 用逻辑分析仪抓总线数据
```

## 数据流 / 控制流 / 时序关系

排障的典型流程：

```text
发现问题
-> 确认现象（不工作？偶发？崩溃？）
-> 缩小范围（哪一层？哪个阶段？）
-> 建立怀疑链（列出可能原因）
-> 逐个验证（用工具确认或排除）
-> 定位根因（最小可复现条件）
-> 修复
-> 验证修复（确认不是偶然消失）
-> 防止复发（加日志、加检查、加测试）
```

## 最小可运行示例

以下是一个带完整调试日志的驱动框架：

```c
#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/io.h>
#include <linux/interrupt.h>

struct mydev_priv {
    void __iomem *base;
    int irq;
};

#define REG_CTRL   0x00
#define REG_STATUS 0x04

static irqreturn_t my_irq_handler(int irq, void *dev_id)
{
    struct mydev_priv *priv = dev_id;
    u32 status;

    status = readl(priv->base + REG_STATUS);
    dev_dbg(NULL, "irq=%d, status=0x%x\n", irq, status);

    if (!(status & BIT(0)))
        return IRQ_NONE;

    writel(BIT(0), priv->base + REG_STATUS);
    return IRQ_HANDLED;
}

static int my_probe(struct platform_device *pdev)
{
    struct mydev_priv *priv;
    struct resource *res;
    int ret, irq;

    dev_info(&pdev->dev, "probe start\n");

    priv = devm_kzalloc(&pdev->dev, sizeof(*priv), GFP_KERNEL);
    if (!priv) {
        dev_err(&pdev->dev, "kzalloc failed\n");
        return -ENOMEM;
    }

    res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
    if (!res) {
        dev_err(&pdev->dev, "get mem resource failed\n");
        return -ENODEV;
    }
    dev_dbg(&pdev->dev, "mem: 0x%pa-0x%pa\n", &res->start, &res->end);

    priv->base = devm_ioremap_resource(&pdev->dev, res);
    if (IS_ERR(priv->base)) {
        dev_err(&pdev->dev, "ioremap failed: %ld\n", PTR_ERR(priv->base));
        return PTR_ERR(priv->base);
    }

    irq = platform_get_irq(pdev, 0);
    if (irq < 0) {
        dev_err(&pdev->dev, "get irq failed: %d\n", irq);
        return irq;
    }
    dev_dbg(&pdev->dev, "irq=%d\n", irq);
    priv->irq = irq;

    ret = devm_request_irq(&pdev->dev, irq, my_irq_handler, 0,
                           dev_name(&pdev->dev), priv);
    if (ret) {
        dev_err(&pdev->dev, "request_irq failed: %d\n", ret);
        return ret;
    }

    platform_set_drvdata(pdev, priv);
    dev_info(&pdev->dev, "probe success\n");
    return 0;
}

static int my_remove(struct platform_device *pdev)
{
    dev_info(&pdev->dev, "remove\n");
    return 0;
}

static const struct of_device_id my_match[] = {
    { .compatible = "vendor,mydev" },
    {}
};
MODULE_DEVICE_TABLE(of, my_match);

static struct platform_driver my_driver = {
    .probe  = my_probe,
    .remove = my_remove,
    .driver = {
        .name = "mydev-debug",
        .of_match_table = my_match,
    },
};
module_platform_driver(my_driver);

MODULE_LICENSE("GPL");
```

## 代码解读

### 1. 为什么每一步都加 `dev_err` / `dev_dbg`

这是驱动排障的基本习惯：每一步失败都有明确的错误日志，可以快速定位失败位置。

### 2. 为什么用 `dev_dbg` 而不是 `dev_info` 记录调试信息

`dev_dbg` 默认不输出，只有通过 `dynamic_debug` 开启后才输出。生产环境零开销，开发时可以精确控制。

### 3. 为什么 `ioremap` 失败时打印 `PTR_ERR`

`PTR_ERR` 把错误指针转成错误码，可以知道具体是什么错误。

### 4. 为什么 `dev_name(&pdev->dev)` 作为中断名称

这样 `/proc/interrupts` 里能看到设备名，方便识别。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 调试日志 | `dev_dbg` + `dynamic_debug` | 到处 `printk` | 生产环境无法关闭 |
| 错误日志 | 每步失败都 `dev_err` | 只在最后返回错误 | 不知道哪一步失败 |
| 崩溃分析 | `addr2line` 定位源码行 | 凭猜测改代码 | 浪费时间 |
| 排障顺序 | 按层级逐步排查 | 随机猜测 | 效率低 |
| 并发问题 | `lockdep` 检测 | 靠运气发现 | 死锁可能很久才出现 |
| 日志级别 | `pr_err`/`pr_warn`/`pr_info`/`pr_debug` 分级 | 全用 `printk` | 无法过滤 |

## 边界条件与适用范围

1. `dynamic_debug` 需要内核配置 `CONFIG_DYNAMIC_DEBUG`。
2. `ftrace` 需要内核配置 `CONFIG_FUNCTION_TRACER`。
3. `lockdep` 有性能开销，生产环境通常关闭。
4. `debugfs` 需要挂载：`mount -t debugfs none /sys/kernel/debug`。
5. 崩溃日志可能不完整，严重时系统直接死机没有任何输出。
6. 某些时序相关的 bug 加了日志就不复现（Heisenbug），需要用非侵入式工具。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| probe 不进 | compatible 不匹配 | `ls /sys/bus/platform/devices/` |
| 中断不触发 | IRQ 号错或触发类型错 | `cat /proc/interrupts` |
| 加日志后 bug 消失 | 时序相关 bug | 用 `ftrace` 或示波器 |
| oops 信息不完整 | 日志级别太低 | `echo 8 > /proc/sys/kernel/printk` |
| lockdep 误报 | 复杂锁场景 | 仔细分析锁依赖图 |

## 工程落地建议

### 1. 驱动开发时默认加完整日志

1. `probe` 每一步加 `dev_err`（失败路径）和 `dev_dbg`（成功路径）。
2. 中断 handler 加 `dev_dbg` 记录触发。
3. 关键数据流加 `dev_dbg` 记录值。

### 2. 提交代码前关闭调试日志

用 `dynamic_debug` 控制，不要删除 `dev_dbg` 语句。以后出问题时可以随时开启。

### 3. 建立排障检查清单

每次遇到驱动问题时，按清单逐项检查：

1. 模块是否加载？
2. 设备树是否正确？
3. 匹配是否成功？
4. probe 是否被调用？
5. 资源申请是否成功？
6. 中断是否触发？
7. 数据流是否正确？

### 4. 用版本控制跟踪问题

每次修改都提交，方便回退和对比。

## 性能、稳定性、可维护性影响

1. `dev_dbg` 在关闭时零开销，不影响性能。
2. `ftrace` 有一定开销，但通常可以接受。
3. `lockdep` 开销较大，只在开发阶段开启。
4. 完整的日志体系让排障效率大幅提升，长期收益远大于开发成本。
5. 排障能力是独立做项目的关键能力，比写代码本身更重要。

## 面试 / 问答怎么讲

### 30 秒版本

驱动排障按层级定位：模块加载 → 设备匹配 → probe → 资源 → 中断 → 数据流。`dmesg` 是第一站，`dev_dbg` + `dynamic_debug` 精确控制日志，`ftrace` 跟踪函数调用，`/proc/interrupts` 查中断状态，`addr2line` 分析崩溃位置。

### 3 分钟版本

可以从排障方法论讲起：确认现象 → 缩小范围 → 建立怀疑链 → 逐个验证。然后说明按层级排查的思路，每层用什么工具。再举一个"probe 不进"的完整排查过程：`lsmod` → `/sys/bus/` → `dmesg`。最后补充崩溃分析的基本方法：读 oops 日志 → `addr2line` 定位。

### 10 分钟版本

可以结合一个真实排障案例展开：驱动 probe 成功但中断不触发。先用 `cat /proc/interrupts` 确认中断计数，发现为 0。再用示波器量中断引脚，确认硬件有信号。然后用 `dynamic_debug` 开启中断 handler 日志，发现 handler 没被调用。最后发现是 `request_irq` 时触发类型配置错误。这种讲法展示了完整的排障思维链。

## 实战练习

1. 故意写一个 compatible 不匹配的驱动，观察 probe 不进的现象，用 `/sys/bus/` 排查。
2. 在驱动里加 `dev_dbg` 日志，用 `dynamic_debug` 运行时开关。
3. 用 `ftrace` 跟踪一个驱动的 probe 函数调用链。
4. 故意写一个空指针解引用，分析 oops 日志并用 `addr2line` 定位。
5. 用 `lockdep` 检测一个故意制造的 ABBA 死锁。

## 关键要点

1. 排障方法论：确认现象 → 缩小范围 → 建立怀疑链 → 逐个验证。
2. 按层级排查：模块 → 匹配 → probe → 资源 → 中断 → 数据流。
3. `dmesg` 是第一站，`dev_dbg` + `dynamic_debug` 精确控制日志。
4. `/proc/interrupts`、`/sys/bus/`、`/sys/kernel/debug/` 是核心信息源。
5. `ftrace` 跟踪函数调用，`addr2line` 分析崩溃位置。
6. `lockdep` 检测锁问题，`dynamic_debug` 零开销开关日志。
7. 排障能力是独立做项目的关键，比写代码本身更重要。
