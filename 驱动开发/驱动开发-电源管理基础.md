# 驱动开发-电源管理基础

## 原始问题

为什么嵌入式 Linux 设备需要休眠和唤醒？驱动里 `suspend` 和 `resume` 回调到底怎么写？`runtime PM` 和 `system PM` 有什么区别？设备休眠后中断还能用吗？`pm_runtime_put` 和 `pm_runtime_get` 怎么配对使用？

## 先给结论

Linux 电源管理分两个层面：

1. **System PM（系统级电源管理）**：整个系统进入休眠状态（suspend-to-RAM、suspend-to-idle），所有驱动需要配合保存和恢复状态。通过 `suspend`/`resume` 回调实现。
2. **Runtime PM（运行时电源管理）**：系统运行时，空闲设备自动进入低功耗状态，需要时自动恢复。通过 `pm_runtime_get`/`pm_runtime_put` 引用计数实现。
3. 驱动需要做两件事：保存/恢复硬件状态，正确处理唤醒事件。
4. Runtime PM 的核心是引用计数：`get` 加 1 表示"我在用"，`put` 减 1 表示"我不用了"，计数归零时设备自动进入低功耗。
5. 休眠时中断不可用，唤醒依赖外部中断（如按键、RTC、网络唤醒）。

如果只能背"有 suspend 和 resume"，但讲不清 System PM 和 Runtime PM 的区别、引用计数机制、状态保存恢复和唤醒源配置，就还没有真正掌握驱动电源管理。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 系统休眠后唤醒，外设不工作了，不知道怎么在驱动里恢复状态。
2. 不理解 Runtime PM 的引用计数机制，`get`/`put` 不配对导致设备无法休眠。
3. 不知道怎么配置唤醒源，系统休眠后无法被唤醒。
4. 驱动里没有实现电源管理，设备功耗过高。
5. 面试时被问"你怎么做低功耗"，只能说出"关时钟"。

它在AI时代依然重要，因为AI生成驱动代码时经常忽略电源管理，导致设备无法进入低功耗状态。理解电源管理后，你才能让AI生成的代码满足实际产品的功耗要求。

## 核心概念 / 本质机制

### 1. System PM vs Runtime PM

| 特性 | System PM | Runtime PM |
| --- | --- | --- |
| 触发方式 | 用户态写 `/sys/power/state` | 驱动主动调用 `pm_runtime_put` |
| 影响范围 | 整个系统 | 单个设备 |
| 状态 | 系统级休眠（RAM/IDLE/STANDBY） | 设备级低功耗（active/idle/suspended） |
| 驱动回调 | `suspend`/`resume` | `runtime_suspend`/`runtime_resume` |
| 中断 | 不可用（除唤醒源外） | 可用 |
| 恢复方式 | 唤醒源触发 | `pm_runtime_get` 触发 |

### 2. System PM：休眠和唤醒

#### 休眠流程

```text
用户态: echo mem > /sys/power/state
  |
  V
内核 PM 核心: 冻结用户态进程
  |
  V
总线 PM: 调用总线下的设备 suspend 回调
  |
  V
驱动 suspend: 保存硬件状态、关闭时钟、禁用中断
  |
  V
CPU 进入低功耗模式
```

#### 唤醒流程

```text
唤醒源触发（按键、RTC、网络）
  |
  V
CPU 退出低功耗模式
  |
  V
内核 PM 核心: 恢复用户态进程
  |
  V
总线 PM: 调用设备 resume 回调
  |
  V
驱动 resume: 恢复硬件状态、开启时钟、使能中断
```

#### 驱动实现

```c
static int my_suspend(struct device *dev)
{
    struct mydev_priv *priv = dev_get_drvdata(dev);

    /* 保存硬件状态 */
    priv->saved_ctrl = readl(priv->base + REG_CTRL);
    priv->saved_cfg = readl(priv->base + REG_CFG);

    /* 关闭硬件 */
    writel(0, priv->base + REG_CTRL);

    /* 关闭时钟 */
    clk_disable_unprepare(priv->clk);

    dev_info(dev, "suspended\n");
    return 0;
}

static int my_resume(struct device *dev)
{
    struct mydev_priv *priv = dev_get_drvdata(dev);
    int ret;

    /* 开启时钟 */
    ret = clk_prepare_enable(priv->clk);
    if (ret) return ret;

    /* 恢复硬件状态 */
    writel(priv->saved_cfg, priv->base + REG_CFG);
    writel(priv->saved_ctrl, priv->base + REG_CTRL);

    dev_info(dev, "resumed\n");
    return 0;
}

static const struct dev_pm_ops my_pm_ops = {
    .suspend    = my_suspend,
    .resume     = my_resume,
    .runtime_suspend = my_runtime_suspend,
    .runtime_resume  = my_runtime_resume,
};
```

### 3. Runtime PM：运行时电源管理

#### 引用计数机制

```text
pm_runtime_get(dev)   -> 计数 +1，设备变为 active
pm_runtime_put(dev)   -> 计数 -1，计数为 0 时设备自动进入 suspended

pm_runtime_get_sync(dev)  -> 同步版本，等设备恢复完成
pm_runtime_put_sync(dev)  -> 同步版本，等设备进入低功耗完成
```

#### 驱动实现

```c
static int my_runtime_suspend(struct device *dev)
{
    struct mydev_priv *priv = dev_get_drvdata(dev);

    /* 关闭时钟 */
    clk_disable_unprepare(priv->clk);

    dev_dbg(dev, "runtime suspended\n");
    return 0;
}

static int my_runtime_resume(struct device *dev)
{
    struct mydev_priv *priv = dev_get_drvdata(dev);
    int ret;

    /* 开启时钟 */
    ret = clk_prepare_enable(priv->clk);
    if (ret) return ret;

    /* 恢复硬件状态（时钟关闭后寄存器可能丢失） */
    writel(priv->saved_cfg, priv->base + REG_CFG);
    writel(priv->saved_ctrl, priv->base + REG_CTRL);

    dev_dbg(dev, "runtime resumed\n");
    return 0;
}
```

#### 使用模式

```c
/* 打开设备时 */
static int my_open(struct inode *inode, struct file *filp)
{
    struct mydev_priv *priv = ...;
    pm_runtime_get_sync(priv->dev);
    return 0;
}

/* 关闭设备时 */
static int my_release(struct inode *inode, struct file *filp)
{
    struct mydev_priv *priv = ...;
    pm_runtime_put(priv->dev);
    return 0;
}

/* 中断处理时 */
static irqreturn_t my_irq_handler(int irq, void *dev_id)
{
    struct mydev_priv *priv = dev_id;

    /* 中断可能在设备 runtime suspended 时触发 */
    /* 如果配置了 wakeup，需要先 resume */
    pm_runtime_get_sync(priv->dev);

    /* 处理中断 */
    ...

    pm_runtime_put(priv->dev);
    return IRQ_HANDLED;
}
```

### 4. probe 里的 Runtime PM 初始化

```c
static int my_probe(struct platform_device *pdev)
{
    ...

    /* 初始化 Runtime PM */
    pm_runtime_enable(&pdev->dev);

    /* 初始状态设为 active */
    pm_runtime_get_sync(&pdev->dev);

    /* probe 完成后 put，允许设备空闲时自动休眠 */
    pm_runtime_put(&pdev->dev);

    return 0;
}

static int my_remove(struct platform_device *pdev)
{
    /* 确保设备 active 再移除 */
    pm_runtime_get_sync(&pdev->dev);

    /* 禁用 Runtime PM */
    pm_runtime_disable(&pdev->dev);

    return 0;
}
```

### 5. 唤醒源配置

设备休眠后，只有配置为唤醒源的中断才能唤醒系统。

#### 设备树配置

```dts
mydev@10000000 {
    compatible = "vendor,mydev";
    interrupts = <0 25 4>;
    wakeup-source;           /* 标记为唤醒源 */
};
```

#### 驱动里设置

```c
/* 在 probe 里 */
device_set_wakeup_capable(&pdev->dev, true);
device_wakeup_enable(&pdev->dev);

/* 在 suspend 里使能唤醒中断 */
enable_irq_wake(priv->irq);

/* 在 resume 里禁用唤醒中断 */
disable_irq_wake(priv->irq);
```

`enable_irq_wake` 的作用：

1. 告诉中断控制器：这个中断在休眠状态下也要能触发。
2. 休眠时这个中断不会走正常处理流程，而是触发系统唤醒。
3. 唤醒后 `resume` 回调执行，中断恢复正常处理。

### 6. 休眠状态

| 状态 | 描述 | 功耗 | 唤醒速度 |
| --- | --- | --- | --- |
| `freeze` (Suspend-to-Idle) | 冻结用户态，CPU 进入 idle | 最低 | 最快 |
| `standby` (Power-On Suspend) | CPU 断电，RAM 保持 | 较低 | 较快 |
| `mem` (Suspend-to-RAM) | CPU 和大部分外设断电，RAM 保持 | 很低 | 较慢 |
| `disk` (Suspend-to-Disk) | 内存内容写入磁盘，全系统断电 | 最低 | 最慢 |

嵌入式最常用的是 `mem`（Suspend-to-RAM）。

### 7. autosleep：自动休眠

Runtime PM 支持"设备空闲一段时间后自动进入低功耗"：

```c
/* 设备空闲 2 秒后自动 runtime suspend */
pm_runtime_set_autosuspend_delay(&pdev->dev, 2000);
pm_runtime_use_autosuspend(&pdev->dev);
pm_runtime_put_autosuspend(&pdev->dev);
```

`pm_runtime_put_autosuspend` 的行为：

1. 计数减 1。
2. 如果计数为 0，启动一个定时器。
3. 定时器到期后调用 `runtime_suspend`。
4. 如果在定时器到期前有 `get` 调用，取消定时器。

### 8. 电源管理中的常见问题

#### 问题1：`get`/`put` 不配对

```c
pm_runtime_get(dev);   // 计数 1
pm_runtime_get(dev);   // 计数 2
pm_runtime_put(dev);   // 计数 1
// 忘了第二次 put，设备永远不会 runtime suspend
```

#### 问题2：runtime suspend 后寄存器丢失

某些硬件在时钟关闭后寄存器值会丢失，`runtime_resume` 时必须重新配置。

#### 问题3：中断在 runtime suspended 时触发

如果设备配置了 `wakeup-source`，中断可能在设备 suspended 时触发。需要在 handler 里先 `pm_runtime_get_sync` 再处理。

#### 问题4：suspend 期间设备还在工作

System PM 的 `suspend` 回调必须确保设备完全停止工作，否则系统可能无法进入低功耗。

## 数据流 / 控制流 / 时序关系

### System PM 时序

```text
echo mem > /sys/power/state
-> 冻结用户态进程
-> 按设备树顺序调用各驱动的 suspend
-> 每个驱动保存状态、关闭时钟
-> CPU 进入低功耗
-> 唤醒源中断触发
-> CPU 退出低功耗
-> 按反序调用各驱动的 resume
-> 每个驱动恢复状态、开启时钟
-> 解冻用户态进程
```

### Runtime PM 时序

```text
pm_runtime_get(dev)
-> 计数 +1
-> 如果设备 suspended，调用 runtime_resume
-> 设备变为 active

... 使用设备 ...

pm_runtime_put(dev)
-> 计数 -1
-> 如果计数为 0，调用 runtime_suspend
-> 设备变为 suspended
```

## 最小可运行示例

```c
#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/pm_runtime.h>
#include <linux/io.h>
#include <linux/clk.h>

struct mydev_priv {
    struct device *dev;
    void __iomem *base;
    struct clk *clk;
    u32 saved_ctrl;
    u32 saved_cfg;
};

#define REG_CTRL 0x00
#define REG_CFG  0x04

static int my_runtime_suspend(struct device *dev)
{
    struct mydev_priv *priv = dev_get_drvdata(dev);
    priv->saved_ctrl = readl(priv->base + REG_CTRL);
    priv->saved_cfg = readl(priv->base + REG_CFG);
    clk_disable_unprepare(priv->clk);
    dev_dbg(dev, "runtime suspend\n");
    return 0;
}

static int my_runtime_resume(struct device *dev)
{
    struct mydev_priv *priv = dev_get_drvdata(dev);
    int ret = clk_prepare_enable(priv->clk);
    if (ret) return ret;
    writel(priv->saved_cfg, priv->base + REG_CFG);
    writel(priv->saved_ctrl, priv->base + REG_CTRL);
    dev_dbg(dev, "runtime resume\n");
    return 0;
}

static int my_suspend(struct device *dev)
{
    struct mydev_priv *priv = dev_get_drvdata(dev);
    priv->saved_ctrl = readl(priv->base + REG_CTRL);
    priv->saved_cfg = readl(priv->base + REG_CFG);
    writel(0, priv->base + REG_CTRL);
    clk_disable_unprepare(priv->clk);
    dev_info(dev, "system suspend\n");
    return 0;
}

static int my_resume(struct device *dev)
{
    struct mydev_priv *priv = dev_get_drvdata(dev);
    int ret = clk_prepare_enable(priv->clk);
    if (ret) return ret;
    writel(priv->saved_cfg, priv->base + REG_CFG);
    writel(priv->saved_ctrl, priv->base + REG_CTRL);
    dev_info(dev, "system resume\n");
    return 0;
}

static const struct dev_pm_ops my_pm_ops = {
    .suspend         = my_suspend,
    .resume          = my_resume,
    .runtime_suspend = my_runtime_suspend,
    .runtime_resume  = my_runtime_resume,
};

static int my_probe(struct platform_device *pdev)
{
    struct mydev_priv *priv;
    struct resource *res;

    priv = devm_kzalloc(&pdev->dev, sizeof(*priv), GFP_KERNEL);
    if (!priv) return -ENOMEM;

    res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
    priv->base = devm_ioremap_resource(&pdev->dev, res);
    if (IS_ERR(priv->base)) return PTR_ERR(priv->base);

    priv->clk = devm_clk_get(&pdev->dev, NULL);
    if (IS_ERR(priv->clk)) return PTR_ERR(priv->clk);

    priv->dev = &pdev->dev;
    platform_set_drvdata(pdev, priv);

    pm_runtime_enable(&pdev->dev);
    pm_runtime_get_sync(&pdev->dev);

    writel(0x01, priv->base + REG_CTRL);

    pm_runtime_put(&pdev->dev);

    device_set_wakeup_capable(&pdev->dev, true);

    dev_info(&pdev->dev, "probed\n");
    return 0;
}

static int my_remove(struct platform_device *pdev)
{
    pm_runtime_get_sync(&pdev->dev);
    pm_runtime_disable(&pdev->dev);
    return 0;
}

static const struct of_device_id my_match[] = {
    { .compatible = "vendor,mydev" },
    {}
};
MODULE_DEVICE_TABLE(of, my_match);

static struct platform_driver my_driver = {
    .probe  = my_probe,
    .remove = my_remove,
    .driver = {
        .name = "mydev-pm",
        .of_match_table = my_match,
        .pm = &my_pm_ops,
    },
};
module_platform_driver(my_driver);

MODULE_LICENSE("GPL");
```

## 代码解读

### 1. 为什么 `suspend` 和 `runtime_suspend` 都要保存状态

因为两种场景都会关闭时钟，寄存器值可能丢失。恢复时都需要重新写入。

### 2. 为什么 `probe` 里先 `get_sync` 再 `put`

`get_sync` 确保设备在 active 状态下完成初始化。`put` 允许设备在空闲时自动进入低功耗。

### 3. 为什么 `remove` 里先 `get_sync` 再 `disable`

确保设备在 active 状态下安全移除，避免在 suspended 状态下访问硬件。

### 4. 为什么 `.pm = &my_pm_ops` 放在 `driver` 结构体里

这是 Linux PM 框架的标准注册方式。PM 核心通过这个指针找到驱动的电源管理回调。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| Runtime PM 初始化 | probe 里 `pm_runtime_enable` + `get_sync` | 不初始化直接用 | 设备状态不确定 |
| get/put 配对 | 每个 get 对应一个 put | 只 get 不 put | 设备永远不休眠 |
| 状态保存 | suspend 前保存寄存器 | 不保存直接关时钟 | resume 后状态丢失 |
| 唤醒源 | `enable_irq_wake` + `wakeup-source` | 不配置唤醒源 | 系统无法唤醒 |
| autosuspend | `pm_runtime_put_autosuspend` | `pm_runtime_put` | 频繁唤醒反而更耗电 |
| remove 清理 | `get_sync` + `disable` | 直接 `disable` | 可能在 suspended 状态移除 |

## 边界条件与适用范围

1. 不是所有设备都需要 Runtime PM，简单设备可以不实现。
2. `pm_runtime_get_sync` 可能睡眠，不能在原子上下文使用。
3. System PM 的 `suspend` 回调必须确保设备完全停止，否则系统无法进入低功耗。
4. 某些硬件在时钟关闭后寄存器不会丢失，可以不保存状态。
5. 唤醒源的数量有限，不是所有中断都能配置为唤醒源。
6. Runtime PM 和 System PM 可能交互：系统休眠时需要先 resume 所有 runtime suspended 的设备。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- | 
| 唤醒后外设不工作 | resume 没恢复寄存器 | 检查 resume 是否重新配置硬件 |
| 设备从不休眠 | get/put 不配对 | 检查 `pm_runtime_get` 计数 |
| 系统无法休眠 | 驱动 suspend 返回错误 | `dmesg` 看哪个驱动失败 |
| 系统无法唤醒 | 没配置唤醒源 | 检查 `wakeup-source` 和 `enable_irq_wake` |
| 功耗比预期高 | Runtime PM 未启用 | `cat /sys/devices/.../power/runtime_status` |

### 推荐排查顺序

1. 先确认 Runtime PM 是否启用：`cat /sys/devices/.../power/runtime_status`。
2. 再确认 get/put 是否配对：`cat /sys/devices/.../power/runtime_usage`。
3. 再确认 System PM 是否成功：`dmesg | grep suspend`。
4. 再确认唤醒源是否配置：`cat /sys/kernel/debug/wakeup_sources`。
5. 最后用电流表测量实际功耗。

## 工程落地建议

### 1. 新驱动默认实现 Runtime PM

即使当前不需要低功耗，也预留接口，以后加功耗优化时不需要大改。

### 2. 用 autosuspend 减少频繁唤醒

```c
pm_runtime_set_autosuspend_delay(dev, 2000);
pm_runtime_use_autosuspend(dev);
```

设备空闲 2 秒后才进入低功耗，避免频繁开关时钟。

### 3. 唤醒源在设备树里标记

```dts
wakeup-source;
```

比驱动里硬编码更灵活。

### 4. 测试休眠唤醒

```bash
echo mem > /sys/power/state
# 等待唤醒
dmesg | tail -20
```

## 性能、稳定性、可维护性影响

1. Runtime PM 能显著降低空闲设备的功耗，延长电池续航。
2. 频繁的 get/put 有一定开销，autosuspend 可以缓解。
3. 状态保存恢复如果遗漏，会导致唤醒后外设异常。
4. 电源管理是嵌入式产品的硬性需求，不做 PM 的驱动无法用于量产。
5. 良好的 PM 实现让产品在功耗和响应速度之间取得平衡。

## 面试 / 问答怎么讲

### 30 秒版本

Linux 电源管理分 System PM 和 Runtime PM。System PM 是系统级休眠唤醒，驱动通过 `suspend`/`resume` 保存恢复状态。Runtime PM 是运行时设备级低功耗，通过 `pm_runtime_get`/`put` 引用计数控制。唤醒需要配置 `wakeup-source` 和 `enable_irq_wake`。

### 3 分钟版本

可以从两个层面讲起：System PM 解决"整个系统休眠"的问题，驱动在 `suspend` 里保存状态、关时钟，在 `resume` 里恢复状态、开时钟。Runtime PM 解决"设备空闲时省电"的问题，通过引用计数自动管理。然后说明 `get`/`put` 必须配对，否则设备永远不休眠。再补充唤醒源配置和 autosuspend 机制。

### 10 分钟版本

可以结合一个完整驱动展开：probe 里初始化 Runtime PM，open 时 get、close 时 put，中断 handler 里也做 get/put 保护。然后说明 System PM 的 suspend/resume 实现，包括寄存器保存和时钟控制。再讨论唤醒源配置、autosuspend 延迟设置、以及"唤醒后外设不工作"的典型排障过程。最后说明功耗测试方法。

## 实战练习

1. 给一个已有驱动加 Runtime PM 支持，用 `cat /sys/.../power/runtime_status` 验证状态切换。
2. 实现 `suspend`/`resume` 回调，用 `echo mem > /sys/power/state` 测试休眠唤醒。
3. 配置一个 GPIO 按键作为唤醒源，测试系统休眠后按键唤醒。
4. 用 `pm_runtime_put_autosuspend` 替代 `pm_runtime_put`，观察设备空闲多久后才进入低功耗。
5. 故意在 `resume` 里不恢复寄存器，观察唤醒后外设行为异常。

## 关键要点

1. System PM 管系统级休眠，Runtime PM 管设备级低功耗。
2. `suspend`/`resume` 保存恢复硬件状态，`runtime_suspend`/`runtime_resume` 同理。
3. Runtime PM 核心是引用计数：`get` 加 1，`put` 减 1，归零自动休眠。
4. `get`/`put` 必须配对，否则设备永远不进入低功耗。
5. 唤醒需要配置 `wakeup-source` 和 `enable_irq_wake`。
6. autosuspend 延迟避免频繁开关，适合间歇性使用的设备。
7. 电源管理是嵌入式产品的硬性需求，不做 PM 的驱动无法量产。
