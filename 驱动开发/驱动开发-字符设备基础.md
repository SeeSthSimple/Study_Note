# 驱动开发-字符设备基础

## 原始问题

Linux 里用户态程序怎么访问硬件？为什么写驱动要先注册字符设备？`file_operations` 里的那些回调到底怎么跟 `open`、`read`、`write`、`close` 对应？字符设备驱动从注册到用户态访问的完整链路是什么？

## 先给结论

字符设备是 Linux 里最基础的设备抽象，它的核心是"像文件一样访问硬件"：

1. 字符设备按字节流访问，不可寻址，大多数简单外设驱动都是字符设备。
2. 驱动通过 `register_chrdev` 或 `cdev_add` 注册，获得主设备号。
3. 用户态通过 `/dev/xxx` 节点，用 `open`/`read`/`write`/`close`/`ioctl` 访问。
4. `file_operations` 是驱动和内核 VFS 之间的接口表，每个系统调用对应一个回调。
5. `ioctl` 是用户态和驱动之间传递自定义命令的标准通道。

如果只能背"字符设备就是 file_operations"，但讲不清注册流程、设备节点创建、用户态到内核态的调用链路和并发保护，就还没有真正掌握字符设备驱动。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 知道要写驱动，但不知道从注册到用户态访问的完整链路怎么串起来。
2. 不理解 `file_operations` 里每个回调什么时候被调用、参数含义是什么。
3. 不知道 `ioctl` 怎么设计命令、怎么传参数、怎么保证安全。
4. 多个进程同时 `open` 同一个设备时，不知道怎么保护共享状态。
5. 面试时知道"字符设备"这个词，但讲不清注册、节点、VFS 和并发的完整关系。

它在AI时代依然重要，因为AI能快速生成一个 `file_operations` 模板，但经常忽略并发保护、`ioctl` 命令设计规范、错误路径和设备节点创建时机。理解字符设备完整链路后，你才能判断AI给的驱动代码是否工程可用。

## 核心概念 / 本质机制

### 1. 字符设备在 Linux 里的位置

```text
用户态:  open("/dev/mydev", O_RDWR)
  |
  V
VFS 层:  根据设备号查找对应的 file_operations
  |
  V
驱动层:  调用驱动注册的 open 回调
```

字符设备的核心抽象是：**把硬件操作封装成文件操作**。

用户态程序不需要知道硬件细节，只需要用标准文件 API 就能访问设备。

### 2. 字符设备 vs 块设备 vs 网络设备

| 类型 | 访问方式 | 典型例子 |
| --- | --- | --- |
| 字符设备 | 字节流，顺序访问 | UART、GPIO、LED、按键 |
| 块设备 | 按块随机访问，有缓存 | 硬盘、eMMC、NAND |
| 网络设备 | 包收发 | 以太网、WiFi |

嵌入式里最常写的是字符设备驱动。

### 3. 注册字符设备的两种方式

#### 方式1：`register_chrdev`（旧接口，简单）

```c
int major = register_chrdev(0, "mydev", &my_fops);
if (major < 0) {
    pr_err("register_chrdev failed\n");
    return major;
}
```

特点：

1. 自动分配主设备号（传0）或指定主设备号。
2. 注册后所有次设备号都归这个驱动。
3. 接口简单，但不灵活。

#### 方式2：`cdev_add`（新接口，推荐）

```c
dev_t dev;
struct cdev my_cdev;

int ret = alloc_chrdev_region(&dev, 0, 1, "mydev");
if (ret < 0) return ret;

cdev_init(&my_cdev, &my_fops);
my_cdev.owner = THIS_MODULE;

ret = cdev_add(&my_cdev, dev, 1);
if (ret < 0) {
    unregister_chrdev_region(dev, 1);
    return ret;
}
```

特点：

1. 可以精确控制主设备号和次设备号范围。
2. 更灵活，支持多个设备实例。
3. 是现代驱动的推荐方式。

### 4. 设备节点创建

注册字符设备后，还需要在 `/dev/` 下创建节点，用户态才能访问。

#### 手动创建

```bash
mknod /dev/mydev c 240 0
chmod 666 /dev/mydev
```

#### 自动创建（udev/mdev）

驱动里通过 `class_create` 和 `device_create` 自动触发 udev 创建节点：

```c
struct class *my_class = class_create(THIS_MODULE, "mydev_class");
struct device *my_device = device_create(my_class, NULL, dev, NULL, "mydev");
```

这样 `/dev/mydev` 会自动出现。

### 5. `file_operations` 核心回调

```c
static const struct file_operations my_fops = {
    .owner   = THIS_MODULE,
    .open    = my_open,
    .release = my_release,
    .read    = my_read,
    .write   = my_write,
    .unlocked_ioctl = my_ioctl,
};
```

各回调的调用时机：

| 回调 | 用户态调用 | 作用 |
| --- | --- | --- |
| `open` | `open("/dev/mydev", ...)` | 初始化设备状态，分配私有数据 |
| `release` | `close(fd)` | 释放资源，最后一个关闭时清理 |
| `read` | `read(fd, buf, count)` | 从设备读取数据到用户态 |
| `write` | `write(fd, buf, count)` | 从用户态写入数据到设备 |
| `unlocked_ioctl` | `ioctl(fd, cmd, arg)` | 自定义命令通道 |

### 6. `read` 和 `write` 的关键细节

```c
static ssize_t my_read(struct file *filp, char __user *buf,
                       size_t count, loff_t *f_pos)
{
    unsigned char data[64];
    int data_len;

    data_len = hardware_read(data, sizeof(data));
    if (data_len < 0) return data_len;

    if (data_len > count) data_len = count;

    if (copy_to_user(buf, data, data_len))
        return -EFAULT;

    return data_len;
}

static ssize_t my_write(struct file *filp, const char __user *buf,
                        size_t count, loff_t *f_pos)
{
    unsigned char data[64];
    int len = count;

    if (len > sizeof(data)) len = sizeof(data);

    if (copy_from_user(data, buf, len))
        return -EFAULT;

    int ret = hardware_write(data, len);
    if (ret < 0) return ret;

    return len;
}
```

关键点：

1. 用户态指针必须用 `copy_to_user` / `copy_from_user` 访问，不能直接读写。
2. 返回值是实际读写的字节数，负数表示错误。
3. `count` 是用户态请求的大小，驱动要自己做边界检查。

### 7. `ioctl` 的设计规范

`ioctl` 是用户态和驱动之间传递自定义命令的标准通道。

命令编码规范：

```c
#include <linux/ioctl.h>

#define MYDEV_MAGIC 'M'

#define MYDEV_CMD_RESET    _IO(MYDEV_MAGIC, 0)
#define MYDEV_CMD_SET_MODE _IOW(MYDEV_MAGIC, 1, int)
#define MYDEV_CMD_GET_MODE _IOR(MYDEV_MAGIC, 2, int)
#define MYDEV_CMD_XFER     _IOWR(MYDEV_MAGIC, 3, struct mydev_xfer)
```

宏的含义：

1. `_IO(type, nr)`：无参数命令。
2. `_IOW(type, nr, datatype)`：从用户态写（传入参数）。
3. `_IOR(type, nr, datatype)`：从用户态读（传出参数）。
4. `_IOWR(type, nr, datatype)`：双向传参。

ioctl 实现：

```c
static long my_ioctl(struct file *filp, unsigned int cmd, unsigned long arg)
{
    switch (cmd) {
    case MYDEV_CMD_RESET:
        hardware_reset();
        break;
    case MYDEV_CMD_SET_MODE: {
        int mode;
        if (copy_from_user(&mode, (int __user *)arg, sizeof(mode)))
            return -EFAULT;
        hardware_set_mode(mode);
        break;
    }
    case MYDEV_CMD_GET_MODE: {
        int mode = hardware_get_mode();
        if (copy_to_user((int __user *)arg, &mode, sizeof(mode)))
            return -EFAULT;
        break;
    }
    default:
        return -ENOTTY;
    }
    return 0;
}
```

### 8. 私有数据和并发保护

多个进程可能同时 `open` 同一个设备，需要保护共享状态。

```c
struct mydev_priv {
    struct cdev cdev;
    struct mutex lock;
    int open_count;
    /* 其他设备状态 */
};

static int my_open(struct inode *inode, struct file *filp)
{
    struct mydev_priv *priv = container_of(inode->i_cdev,
                                           struct mydev_priv, cdev);
    filp->private_data = priv;

    mutex_lock(&priv->lock);
    priv->open_count++;
    mutex_unlock(&priv->lock);

    return 0;
}

static int my_release(struct inode *inode, struct file *filp)
{
    struct mydev_priv *priv = filp->private_data;

    mutex_lock(&priv->lock);
    priv->open_count--;
    mutex_unlock(&priv->lock);

    return 0;
}
```

关键点：

1. `filp->private_data` 是驱动保存 per-open 状态的标准位置。
2. 共享状态必须用锁保护。
3. `container_of` 从 `cdev` 反推出私有数据结构。

## 数据流 / 控制流 / 时序关系

字符设备从注册到访问的完整链路：

```text
模块加载 (init)
-> alloc_chrdev_region() 分配设备号
-> cdev_init() + cdev_add() 注册字符设备
-> class_create() + device_create() 创建设备节点
-> /dev/mydev 出现

用户态访问:
-> open("/dev/mydev") -> VFS 查找 -> 驱动 .open 回调
-> read(fd, buf, n)  -> VFS 转发 -> 驱动 .read 回调 -> copy_to_user
-> ioctl(fd, cmd)    -> VFS 转发 -> 驱动 .unlocked_ioctl 回调
-> write(fd, buf, n) -> VFS 转发 -> 驱动 .write 回调 -> copy_from_user
-> close(fd)         -> VFS 转发 -> 驱动 .release 回调

模块卸载 (exit)
-> device_destroy() + class_destroy() 删除节点
-> cdev_del() 注销字符设备
-> unregister_chrdev_region() 释放设备号
```

## 最小可运行示例

```c
#include <linux/module.h>
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/device.h>
#include <linux/uaccess.h>
#include <linux/mutex.h>

#define DEVICE_NAME "mydev"
#define CLASS_NAME  "mydev_class"
#define BUF_SIZE    64

static int major_num;
static struct class *my_class = NULL;
static struct device *my_device = NULL;

struct mydev_priv {
    struct cdev cdev;
    struct mutex lock;
    char buf[BUF_SIZE];
    int buf_len;
};

static struct mydev_priv priv;

static int my_open(struct inode *inode, struct file *filp)
{
    filp->private_data = &priv;
    pr_info("mydev: open\n");
    return 0;
}

static int my_release(struct inode *inode, struct file *filp)
{
    pr_info("mydev: release\n");
    return 0;
}

static ssize_t my_read(struct file *filp, char __user *buf,
                       size_t count, loff_t *f_pos)
{
    struct mydev_priv *p = filp->private_data;
    int len;

    mutex_lock(&p->lock);
    len = p->buf_len;
    if (len == 0) {
        mutex_unlock(&p->lock);
        return 0;
    }
    if (len > count) len = count;

    if (copy_to_user(buf, p->buf, len)) {
        mutex_unlock(&p->lock);
        return -EFAULT;
    }

    p->buf_len = 0;
    mutex_unlock(&p->lock);

    return len;
}

static ssize_t my_write(struct file *filp, const char __user *buf,
                        size_t count, loff_t *f_pos)
{
    struct mydev_priv *p = filp->private_data;
    int len = count;

    if (len > BUF_SIZE) len = BUF_SIZE;

    mutex_lock(&p->lock);
    if (copy_from_user(p->buf, buf, len)) {
        mutex_unlock(&p->lock);
        return -EFAULT;
    }
    p->buf_len = len;
    mutex_unlock(&p->lock);

    return len;
}

static const struct file_operations my_fops = {
    .owner   = THIS_MODULE,
    .open    = my_open,
    .release = my_release,
    .read    = my_read,
    .write   = my_write,
};

static int __init my_init(void)
{
    dev_t dev;
    int ret;

    ret = alloc_chrdev_region(&dev, 0, 1, DEVICE_NAME);
    if (ret < 0) return ret;
    major_num = MAJOR(dev);

    cdev_init(&priv.cdev, &my_fops);
    priv.cdev.owner = THIS_MODULE;
    mutex_init(&priv.lock);

    ret = cdev_add(&priv.cdev, dev, 1);
    if (ret < 0) goto fail_cdev;

    my_class = class_create(THIS_MODULE, CLASS_NAME);
    if (IS_ERR(my_class)) { ret = PTR_ERR(my_class); goto fail_class; }

    my_device = device_create(my_class, NULL, dev, NULL, DEVICE_NAME);
    if (IS_ERR(my_device)) { ret = PTR_ERR(my_device); goto fail_device; }

    pr_info("mydev: registered major=%d\n", major_num);
    return 0;

fail_device:
    class_destroy(my_class);
fail_class:
    cdev_del(&priv.cdev);
fail_cdev:
    unregister_chrdev_region(dev, 1);
    return ret;
}

static void __exit my_exit(void)
{
    device_destroy(my_class, MKDEV(major_num, 0));
    class_destroy(my_class);
    cdev_del(&priv.cdev);
    unregister_chrdev_region(MKDEV(major_num, 0), 1);
    pr_info("mydev: unregistered\n");
}

module_init(my_init);
module_exit(my_exit);
MODULE_LICENSE("GPL");
MODULE_AUTHOR("demo");
```

用户态测试程序：

```c
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>

int main(void) {
    int fd = open("/dev/mydev", O_RDWR);
    if (fd < 0) {
        perror("open");
        return 1;
    }

    const char *msg = "hello from user";
    write(fd, msg, strlen(msg));

    char buf[64] = {0};
    int n = read(fd, buf, sizeof(buf));
    if (n > 0) {
        buf[n] = '\0';
        printf("read: %s\n", buf);
    }

    close(fd);
    return 0;
}
```

## 代码解读

### 1. 为什么 `alloc_chrdev_region` 传 0

传 0 表示让内核自动分配主设备号，避免跟已有设备冲突。

### 2. 为什么 `copy_to_user` 和 `copy_from_user` 不能省

用户态指针不能在内核态直接访问，必须用这两个函数。它们会做安全性检查，防止用户态传入非法地址导致内核崩溃。

### 3. 为什么 `read` 里要清空 `buf_len`

这是一个简单的"读后清空"语义：数据读走后就没了。实际驱动里可能需要环形缓冲区或阻塞等待。

### 4. 为什么 `mutex` 保护的是 `buf` 和 `buf_len`

因为多个进程可能同时 `read` 或 `write`，如果不加锁，`buf_len` 和 `buf` 的状态可能不一致。

### 5. 为什么 `init` 里的错误路径要逐步回滚

每一步都可能失败，失败后必须把之前成功申请的资源全部释放，否则会泄漏。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 用户态数据访问 | `copy_to_user` / `copy_from_user` | 直接读写用户态指针 | 内核崩溃或安全漏洞 |
| ioctl 命令定义 | `_IO` / `_IOW` / `_IOR` 宏 | 随便定义数字 | 命令冲突，无法跨平台 |
| 共享状态保护 | `mutex_lock` / `mutex_unlock` | 不加锁 | 多进程并发时数据不一致 |
| 设备节点创建 | `class_create` + `device_create` | 手动 `mknod` | 重启后丢失，不适合生产 |
| 错误路径 | 逐步回滚已申请资源 | 只返回错误码不释放 | 资源泄漏 |
| 返回值 | 实际读写字节数 | 总是返回 `count` | 用户态无法判断真实传输量 |

## 边界条件与适用范围

1. 字符设备适合按字节流访问的外设，不适合需要随机寻址的存储设备。
2. `copy_to_user` / `copy_from_user` 可能因为缺页而睡眠，不能在原子上下文使用。
3. `ioctl` 命令编码要遵循规范，避免跟其他驱动冲突。
4. 设备节点权限要合理设置，避免非特权用户误操作硬件。
5. 驱动里的 `read` 如果没有数据，可以返回 0（非阻塞）或阻塞等待。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| `open` 返回 -ENODEV | 设备节点不存在或设备号不匹配 | `ls -la /dev/mydev`，`cat /proc/devices` |
| `read` 返回 -EFAULT | `copy_to_user` 失败 | 检查用户态缓冲区是否合法 |
| `ioctl` 返回 -ENOTTY | 命令号不匹配 | 检查命令编码是否一致 |
| 数据偶发错乱 | 缺少并发保护 | 加锁保护共享状态 |
| 模块加载失败 | 设备号冲突或资源申请失败 | `dmesg` 看内核日志 |
| 设备节点不出现 | `class_create` 或 `device_create` 失败 | `dmesg` 检查返回值 |

### 推荐排查顺序

1. 先确认模块是否加载成功：`lsmod`。
2. 再确认设备号是否注册：`cat /proc/devices`。
3. 再确认设备节点是否存在：`ls -la /dev/mydev`。
4. 再确认 `open` 是否成功：用户态程序打印 `fd`。
5. 再确认 `read`/`write`/`ioctl` 的返回值。
6. 最后看 `dmesg` 里的内核日志。

## 工程落地建议

### 1. 驱动代码的标准目录结构

```text
mydev_driver/
├── Makefile
├── mydev.c       # 驱动主文件
├── mydev.h       # ioctl 命令定义和共享头文件
└── test_mydev.c  # 用户态测试程序
```

### 2. ioctl 命令定义放在共享头文件里

驱动和用户态测试程序都要包含同一个头文件，确保命令编码一致。

### 3. 给驱动加日志

1. `pr_info`：正常流程日志。
2. `pr_warn`：异常但不致命。
3. `pr_err`：错误。
4. `pr_debug`：调试日志，可通过 `dynamic_debug` 控制。

### 4. 考虑使用 `miscdevice` 简化注册

如果只需要一个次设备号，可以用 `miscdevice` 简化：

```c
static struct miscdevice my_misc = {
    .minor = MISC_DYNAMIC_MINOR,
    .name = "mydev",
    .fops = &my_fops,
};

misc_register(&my_misc);   // init
misc_deregister(&my_misc); // exit
```

`miscdevice` 内部自动处理设备号分配和节点创建。

## 性能、稳定性、可维护性影响

1. 字符设备驱动的性能瓶颈通常在硬件本身，而不是 VFS 层开销。
2. `copy_to_user` / `copy_from_user` 有一定开销，大数据量时考虑 `mmap` 或 DMA。
3. 锁粒度影响并发性能，临界区要尽可能小。
4. `ioctl` 命令设计要考虑向后兼容，新增命令不能破坏旧版用户态程序。
5. 驱动的错误路径必须完整，否则长期运行可能泄漏资源。

## 面试 / 问答怎么讲

### 30 秒版本

字符设备是 Linux 里最基础的设备抽象，用户态通过 `/dev/xxx` 用文件 API 访问硬件。驱动通过 `cdev_add` 注册，提供 `file_operations` 回调。`read`/`write` 用 `copy_to_user`/`copy_from_user` 传数据，`ioctl` 传自定义命令。共享状态必须加锁保护。

### 3 分钟版本

可以从注册流程讲起：`alloc_chrdev_region` 分配设备号、`cdev_init` + `cdev_add` 注册字符设备、`class_create` + `device_create` 创建节点。然后说明 `file_operations` 各回调的调用时机和参数含义。再补充 `ioctl` 命令编码规范（`_IO`/`_IOW`/`_IOR` 宏）。最后强调并发保护和错误路径的重要性。

### 10 分钟版本

可以结合一个完整驱动展开：从模块 `init` 到 `exit` 的完整生命周期，包括错误路径的逐步回滚。然后展示用户态测试程序如何调用 `open`/`write`/`read`/`ioctl`/`close`。再讨论 `miscdevice` 简化方案、`mmap` 替代 `read`/`write` 的场景、DMA 的大数据量传输。最后说明排障主线：模块加载 → 设备号 → 节点 → open → read/write → dmesg。

## 实战练习

1. 写一个最简字符设备驱动，`write` 存数据、`read` 取数据，用 `insmod` 加载后用 `echo` 和 `cat` 测试。
2. 给驱动加一个 `ioctl` 命令，实现"清空缓冲区"功能。
3. 写一个用户态程序，用 `ioctl` 设置设备模式并用 `read`/`write` 验证。
4. 故意去掉 `mutex` 保护，用两个进程同时 `write` 观察数据错乱。
5. 把 `cdev` 注册改成 `miscdevice`，对比代码复杂度。

## 关键要点

1. 字符设备的核心是"像文件一样访问硬件"，通过 `file_operations` 连接 VFS 和驱动。
2. 注册流程：分配设备号 → `cdev_add` → 创建节点。
3. `copy_to_user` / `copy_from_user` 是内核态和用户态之间安全传数据的唯一方式。
4. `ioctl` 命令必须用 `_IO`/`_IOW`/`_IOR` 宏编码，避免冲突。
5. 共享状态必须加锁，`filp->private_data` 保存 per-open 状态。
6. 错误路径必须逐步回滚已申请资源。
7. `miscdevice` 是单设备场景的简化方案。
