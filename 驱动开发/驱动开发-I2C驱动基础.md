# 驱动开发-I2C驱动基础

## 原始问题

Linux 里的 I2C 驱动到底和 platform 驱动有什么不同？为什么 I2C 设备已经挂在总线上了，驱动却还需要 `id_table`、`of_match_table`、`probe` 这些结构？真正写一个 I2C 驱动时，主线应该怎么抓？

## 先给结论

I2C 驱动的本质，是让一个挂在 I2C 总线上的从设备通过标准总线模型接入内核。

先记住下面几个结论：

1. I2C 设备不是固定 MMIO 设备，它依赖 I2C 控制器和总线模型存在。
2. I2C 驱动的匹配通常依赖设备树 `compatible`、ACPI 或传统 `i2c_device_id`。
3. `probe` 的核心不是“实现算法”，而是确认设备存在、初始化寄存器、申请依赖资源并注册对外能力。
4. I2C 驱动排障主线通常是：控制器是否工作 -> 从设备是否 ACK -> 设备是否被枚举 / 创建 -> 驱动是否匹配 -> 寄存器初始化是否正确。
5. AI 可以生成 I2C 驱动模板，但只有你理解总线层、设备层和寄存器层的边界，才能把它变成真驱动。

## 这个知识解决什么问题

1. 不知道 I2C 驱动和 platform 驱动的边界。
2. 设备在线但驱动不匹配，或者驱动 `probe` 了但设备功能不对。
3. 面试和工作中经常被问到 Linux I2C 驱动怎么写，缺少稳定主线。

## 核心概念 / 本质机制

### 1. I2C 驱动和 platform 驱动的本质区别

platform 驱动常面对固定地址的 MMIO 设备。

I2C 驱动面对的是：

1. 已经挂在某个 I2C 控制器下面的从设备。
2. 通过总线事务访问寄存器，而不是直接 MMIO。

所以 I2C 驱动的资源主线更像：

1. I2C 适配器。
2. I2C client。
3. I2C 读写事务。

### 2. 内核里一个 I2C 设备是如何表示的

典型对象是 `struct i2c_client`。

它至少表达：

1. 该设备挂在哪个 adapter 上。
2. 它的从地址是什么。
3. 它关联了哪个设备对象。

驱动进入 `probe` 时，拿到的核心入口就是 `i2c_client`。

### 3. I2C 驱动的 `probe` 在做什么

常见动作包括：

1. 分配私有数据。
2. 读取芯片 ID 或版本寄存器，确认设备真实存在。
3. 初始化配置寄存器。
4. 申请 GPIO、中断、regulator 等额外资源。
5. 注册子系统接口，比如 input、hwmon、iio 等。

### 4. 为什么很多 I2C 驱动会先读 chip ID

因为 I2C 总线层能匹配到驱动，不代表一定就是目标芯片。

先读一个固定 ID 或版本寄存器，有几个好处：

1. 确认设备真的在线。
2. 确认地址没冲突。
3. 确认当前是预期型号。

### 5. 为什么总线通了不代表驱动就对了

I2C 调试常分两层：

1. 总线层：ACK、地址、波形、读写事务是否正常。
2. 设备层：寄存器地址、初始化顺序、数据格式是否正确。

很多驱动问题其实卡在第二层。

## 数据流 / 控制流 / 时序关系

```text
I2C 控制器工作正常
-> 设备树或板级代码创建 i2c_client
-> I2C 驱动注册
-> 匹配成功进入 probe
-> 驱动通过 i2c_smbus_* 或 i2c_transfer 访问寄存器
-> 确认 chip ID / 初始化设备
-> 注册对外接口
```

## 最小可运行示例

```c
#include <linux/i2c.h>
#include <linux/module.h>
#include <linux/slab.h>

struct demo_priv {
    struct i2c_client *client;
};

static int demo_probe(struct i2c_client *client)
{
    struct demo_priv *priv;
    int chip_id;

    priv = devm_kzalloc(&client->dev, sizeof(*priv), GFP_KERNEL);
    if (!priv)
        return -ENOMEM;

    priv->client = client;

    chip_id = i2c_smbus_read_byte_data(client, 0x00);
    if (chip_id < 0)
        return chip_id;

    dev_info(&client->dev, "chip id = 0x%x\n", chip_id);
    i2c_set_clientdata(client, priv);
    return 0;
}

static const struct of_device_id demo_of_match[] = {
    { .compatible = "demo,my-i2c-dev" },
    { }
};
MODULE_DEVICE_TABLE(of, demo_of_match);

static struct i2c_driver demo_driver = {
    .probe = demo_probe,
    .driver = {
        .name = "demo_i2c_dev",
        .of_match_table = demo_of_match,
    },
};
module_i2c_driver(demo_driver);

MODULE_LICENSE("GPL");
```

## 代码解读

### 1. 为什么示例用 `i2c_smbus_read_byte_data`

因为很多寄存器型设备最小闭环就是“读一个寄存器值”。

这一步非常适合拿来：

1. 确认总线和地址没问题。
2. 确认设备真实在线。
3. 确认最基本的寄存器访问工作正常。

### 2. 为什么 `i2c_client` 比设备地址更重要

因为它不只是地址，还包含设备对象和所属总线上下文。

驱动不是在真空中操作一个地址，而是在操作内核模型里的设备实例。

### 3. 为什么这只是最小 I2C 驱动闭环

真实项目里通常还要继续补：

1. 多字节寄存器读写。
2. 中断。
3. 电源管理。
4. 缓存与同步。
5. 子系统注册。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 驱动入口 | 通过 `i2c_client` 和总线模型访问 | 把 I2C 设备当成平台 MMIO 设备写 | 模型不对 |
| 设备确认 | 先读固定寄存器确认芯片 | 匹配成功就盲信设备存在 | 后续问题难定位 |
| 排障路径 | 先看总线 ACK，再看寄存器初始化 | 一上来只改驱动逻辑 | 容易漏掉链路层问题 |
| 私有数据 | `devm_kzalloc` + `i2c_set_clientdata` | 到处用全局变量 | 多实例和维护都差 |

## 边界条件与适用范围

1. 这篇笔记聚焦典型寄存器型 I2C 设备驱动，不覆盖所有复杂子系统。
2. 不同设备寄存器宽度、地址位宽、读写时序差异很大，要结合手册。
3. 某些设备更适合走现成子系统框架，如 hwmon、iio、input、rtc，不应只写裸读写。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| `probe` 不进 | 节点没创建设备；匹配失败 | 查设备树和匹配表 |
| 读寄存器失败 | 地址错；设备没 ACK；时序不对 | 先看总线波形和 ACK |
| 能通信但值不对 | 寄存器地址错；大小端错；初始化顺序错 | 查手册和事务流程 |
| 某些板子能跑某些不行 | GPIO、中断、电源依赖未建模 | 查板级资源和设备树 |

## 工程落地建议

1. 先完成“读 chip ID”这类最小闭环，再扩展功能。
2. 把总线层问题和设备寄存器层问题分开排查。
3. 对外接口尽量接入对应内核子系统，不要所有东西都自造轮子。

## 性能、稳定性、可维护性影响

1. I2C 驱动稳定性高度依赖总线事务正确性和设备初始化顺序。
2. 清晰的最小验证闭环能显著降低联调成本。
3. 走标准子系统和标准资源管理，长期维护成本会低很多。

## 面试 / 问答怎么讲

### 30 秒版本

Linux I2C 驱动的核心是通过 I2C 总线模型接管一个 `i2c_client` 设备，在 `probe` 里先确认芯片存在，再初始化寄存器并注册上层接口。排障时要先分清是总线层问题还是设备寄存器层问题。

### 3 分钟版本

可以先讲 I2C 驱动和 platform 驱动的区别：前者通过总线事务访问从设备，后者更多是 MMIO 固定设备。然后讲 `i2c_client`、匹配、`probe` 和读 chip ID 的最小闭环，再补波形、ACK 和子系统接入。

### 10 分钟版本

可以进一步结合一个传感器驱动展开：设备树创建 client，驱动匹配进入 `probe`，先读 chip ID，再配置寄存器，最后注册到 IIO 或 input 等子系统。排障时同时看设备树、总线波形、寄存器读写和依赖资源。这种讲法很贴近真实工作。

## 实战练习

1. 写一个最小 I2C 驱动，只读出 chip ID 并打印。
2. 用逻辑分析仪抓一次读寄存器事务，对照驱动代码理解地址和数据流。
3. 给 I2C 驱动补一个 GPIO 中断依赖，并设计排障路径。

## 关键要点

1. I2C 驱动建立在总线模型之上，不是简单地址读写。
2. 最小闭环通常是匹配成功后读出固定寄存器。
3. 排障时先分总线层，再分设备层。
4. 走标准内核子系统会更稳。
