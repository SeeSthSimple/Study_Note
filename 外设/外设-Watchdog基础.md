# 外设-Watchdog基础

## 原始问题

Watchdog（看门狗）到底是什么？为什么它看起来只是“定时喂狗防复位”，但一到真实项目里就会遇到误复位、喂狗点选错、异常卡死却没复位、上线后偶发重启定位困难这些问题？真正做项目时，应该怎样系统掌握 Watchdog，而不是只会调用一次 `feed()`？

## 先给结论

Watchdog 的本质是“用硬件超时机制监督系统是否按预期前进”，它不是为了“避免复位”，而是为了“在系统失控时强制恢复”。

先记住下面几个结论：

1. Watchdog 的核心目标是故障恢复，不是正常路径装饰。
2. 喂狗点设计比“会不会喂狗 API”更关键，喂错位置会掩盖真实故障。
3. 看门狗超时时间必须结合最坏执行路径和调度抖动来定，不是越长越好。
4. 真实工程通常要配合复位原因记录、故障快照和启动自检，形成可追溯闭环。
5. 独立看门狗（IWDG）与窗口看门狗（WWDG）适用场景不同，选型错误会导致稳定性问题。

如果只能背“定期喂狗防止复位”，却讲不清为什么主循环喂狗可能掩盖任务死锁、为什么窗口看门狗能发现“喂得太早”的异常、为什么调试阶段要处理暂停行为，就说明这部分还没有真正掌握。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 项目里开了看门狗却依然出现卡死，或者反过来出现误复位，不知道根因在哪。
2. 不清楚喂狗应该放在中断、主循环还是任务健康检查点。
3. 上线后设备偶发重启，但没有形成有效追溯链路。
4. 面试时会说“看门狗防死机”，但讲不清独立看门狗和窗口看门狗差异。

它在 AI 时代仍然重要，因为 AI 可以生成一段看门狗初始化和喂狗代码，但它不知道你的系统最长阻塞路径、RTOS 任务优先级关系、现场供电波动和调试流程。Watchdog 理解越扎实，越能把“自动恢复”变成“可控恢复”。

## 核心概念 / 本质机制

### 1. Watchdog 在监督什么

Watchdog 监督的是“系统是否持续前进”，不是“某段代码是否执行过一次”。

最常见机制：

1. 看门狗计数器持续递减。
2. 软件在规定时间内喂狗（重装计数）。
3. 若超时未喂狗，触发系统复位或中断。

所以它本质上是硬件层面的最后保险。

### 2. 独立看门狗（IWDG）

典型特点：

1. 常由独立低速时钟驱动，抗主时钟异常能力更强。
2. 一旦开启通常不易关闭（依芯片而定）。
3. 适合做系统级兜底恢复。

工程意义：即使主时钟或部分外设异常，IWDG 仍可能继续计时并触发复位。

### 3. 窗口看门狗（WWDG）

典型特点：

1. 喂狗必须发生在“允许窗口”内。
2. 太晚喂会复位，太早喂也可能触发异常。
3. 更适合检测程序节奏异常（跑飞或异常快循环）。

工程意义：WWDG 不只检查“有没有活着”，还检查“活着节奏是否合理”。

### 4. 喂狗点为什么是成败关键

高频错误是把喂狗放在“总能执行到”的路径，比如空转主循环。

风险是：

1. 某关键任务已死锁，但主循环还能喂狗，故障被掩盖。
2. 通信线程卡死但后台空闲线程持续喂狗，系统表现“假健康”。

更稳做法通常是：

1. 汇总关键任务心跳。
2. 只有所有关键健康条件满足才喂狗。

### 5. 超时参数怎么定

看门狗超时不是拍脑袋选。

常见设计步骤：

1. 统计最坏执行时间（任务、ISR、临界区、IO 阻塞）。
2. 叠加调度抖动和异常恢复余量。
3. 再确定超时阈值和喂狗周期。

太短会误复位，太长会失去故障恢复价值。

### 6. 调试阶段的特殊处理

调试时常见断点会让 CPU 停住，若看门狗仍在跑，会导致反复复位。

常见策略：

1. 使用芯片支持的“调试暂停看门狗”功能。
2. 调试版本放宽超时或临时策略化处理。
3. 明确区分 Debug 配置与 Release 配置。

### 7. 复位原因记录是排障关键证据

只有“复位了”没有价值，关键是“为什么复位”。

建议最小闭环：

1. 启动读取复位原因寄存器。
2. 持久化关键状态（错误码、任务心跳、计数器）。
3. 上报或日志记录，支持现场回溯。

## 数据流 / 控制流 / 时序关系

下面用“RTOS 多任务健康检查喂狗”串主线：

```text
系统启动
-> 初始化 Watchdog 超时参数
-> 各关键任务周期上报心跳
-> 监控模块汇总健康状态
-> 仅在全部关键条件满足时喂狗
-> 若任务卡死/调度异常导致未喂狗
-> Watchdog 超时触发复位
-> 启动后读取复位原因并记录
```

这条链上每一步都可能出问题：

1. 心跳设计不覆盖关键路径，导致假健康。
2. 喂狗窗口与任务节拍不匹配，出现误复位。
3. 复位后不记录原因，现场问题无法追溯。
4. 调试配置污染发布配置，引入隐藏风险。

## 最小可运行示例

下面给一个简化寄存器级示例，目标：

1. 初始化独立看门狗。
2. 在主循环周期喂狗。

```c
#define WDG_BASE            0x40003000
#define WDG_KR              (*(volatile unsigned int *)(WDG_BASE + 0x00))
#define WDG_PR              (*(volatile unsigned int *)(WDG_BASE + 0x04))
#define WDG_RLR             (*(volatile unsigned int *)(WDG_BASE + 0x08))
#define WDG_SR              (*(volatile unsigned int *)(WDG_BASE + 0x0C))

#define WDG_KR_UNLOCK       0x5555U
#define WDG_KR_RELOAD       0xAAAAU
#define WDG_KR_START        0xCCCCU

static void wdg_init(void)
{
    WDG_KR = WDG_KR_UNLOCK;

    /* 示例：分频和重装值按芯片手册换算到目标超时时间 */
    WDG_PR = 3U;
    WDG_RLR = 999U;

    while (WDG_SR)
        ;

    WDG_KR = WDG_KR_RELOAD;
    WDG_KR = WDG_KR_START;
}

static void wdg_feed(void)
{
    WDG_KR = WDG_KR_RELOAD;
}

int main(void)
{
    wdg_init();

    while (1) {
        /* 真实工程里应替换为关键健康条件判断 */
        wdg_feed();

        for (volatile unsigned int i = 0; i < 80000; i++)
            ;
    }
}
```

这个示例里假设：

1. 看门狗时钟源稳定可用。
2. `PR/RLR` 换算符合芯片手册定义。
3. 主循环执行周期远小于看门狗超时。

如果你的系统是 RTOS、多核或含长阻塞外设流程，喂狗策略必须升级为“健康检查后喂狗”，不能照搬主循环喂狗。

## 代码解读

### 1. 为什么这个示例仍然有价值

它先跑通了“初始化 -> 超时计数 -> 周期喂狗”的最小闭环，能快速验证硬件链路是否正常。

### 2. 为什么主循环喂狗仅适合演示

主循环喂狗不能代表系统健康，只适合最小验证。

真实项目应把喂狗绑定到关键任务健康状态，不然容易掩盖故障。

### 3. 为什么要等待状态寄存器更新完成

某些芯片写入分频或重装值后需要等待同步完成，直接继续可能导致配置未生效。

### 4. 为什么这个示例不能直接量产

量产级通常还要补：

1. 复位原因持久化。
2. 关键任务心跳聚合。
3. 喂狗异常计数与故障码上报。
4. Debug/Release 差异配置管理。
5. 启动阶段和升级阶段的特例处理。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 喂狗策略 | 关键健康条件满足后喂狗 | 在空循环无条件喂狗 | 容易掩盖任务死锁 |
| 超时配置 | 基于最坏执行路径定超时 | 凭经验随便给一个值 | 易误复位或失去保护 |
| 复位追溯 | 启动即记录复位原因 | 复位后不留证据 | 现场问题难定位 |
| 调试行为 | 配置断点场景下的策略 | 调试时忽略看门狗影响 | 反复复位影响定位 |
| 系统分层 | 喂狗与业务逻辑解耦 | 到处散落喂狗调用 | 维护困难且风险高 |
| 上线验证 | 故障注入验证复位链路 | 只测正常路径 | 无法确认兜底有效 |

## 边界条件与适用范围

1. 这篇笔记面向 MCU/SoC 常见硬件看门狗基础，不绑定具体厂商寄存器定义。
2. 不同芯片在时钟源、可否关闭、窗口机制、复位域影响范围上差异较大。
3. Watchdog 解决的是“失控恢复”，不替代正确的软件并发设计和异常处理。
4. 对安全关键系统，通常还需配合外部看门狗、掉电监测和故障安全策略。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 设备频繁重启 | 超时太短；喂狗窗口不匹配 | 记录重启周期、核对超时与任务节拍 |
| 明明卡死却不复位 | 喂狗点放错；非关键路径持续喂狗 | 审计喂狗调用链和健康条件 |
| 调试时反复复位 | 断点暂停导致超时 | 检查调试暂停配置 |
| 上线后偶发复位 | 长尾阻塞未计入超时预算 | 抓最长路径耗时和调度抖动 |
| 复位后无证据 | 未保存复位原因与现场数据 | 启动早期读取并持久化状态 |
| 升级阶段失败复位 | 升级流程阻塞过久未喂狗 | 为升级流程设计专用策略 |
| 多任务系统误判健康 | 心跳指标不完整 | 扩充关键任务与关键资源健康检查 |

### 推荐排查顺序

1. 先确认复位原因是否确实来自看门狗。
2. 再核对超时参数与最坏执行路径是否匹配。
3. 再审计喂狗点是否真正代表系统健康。
4. 再验证调试/升级等特殊场景策略。
5. 最后做故障注入验证恢复闭环是否可靠。

### 常用验证方式

1. 故意阻塞关键任务，验证能否按预期复位。
2. 故意让任务跑飞，验证窗口喂狗策略是否能抓到。
3. 统计复位计数和原因分布，做长期稳定性观察。
4. 在不同温度、电压、负载下验证超时裕量。
5. 验证复位后日志链路是否完整可追溯。

## 工程落地建议

### 1. 先定义“健康”再定义“喂狗”

先明确系统健康判据（任务、通信、内存、关键外设状态），再决定何时喂狗。

这样能避免“喂狗成功但系统已坏”的假象。

### 2. 用监控模块统一管理喂狗

建议集中一个 watchdog manager：

1. 收集关键任务心跳。
2. 统一判定健康。
3. 单点执行喂狗。

这样比在各处散落 `feed()` 更可控。

### 3. 把复位追溯做成标准动作

建议每次启动都执行：

1. 读取复位原因。
2. 记录故障上下文。
3. 上报统计。

长期看这比“临时抓日志”更有效。

### 4. 把故障注入纳入回归

不仅测正常路径，还要定期测：

1. 任务卡死。
2. 调度阻塞。
3. 通信超时。

看门狗机制只有在故障注入中通过，才算真正可用。

## 性能、稳定性、可维护性影响

1. Watchdog 本身开销很低，但喂狗策略设计会直接影响系统稳定性。
2. 复位追溯链路缺失会显著拉高线上故障定位成本。
3. 集中化健康监控和喂狗管理可降低维护复杂度与误用风险。
4. 将看门狗验证流程化，能明显提升长期可靠性。

## 面试 / 问答怎么讲

### 30 秒版本

看门狗是硬件超时监督机制，用于系统失控时强制恢复。关键不在“会喂狗”，而在“喂狗是否基于真实健康状态”，并且要配合复位原因记录形成可追溯闭环。

### 3 分钟版本

可以先讲 IWDG 和 WWDG 的差异，再讲超时参数如何按最坏路径设定。然后强调喂狗点设计：不能只在主循环喂，要基于关键任务心跳。最后补充工程落地要点：复位原因记录、故障注入测试、Debug/Release 策略分离。

### 10 分钟版本

结合一个线上偶发重启案例展开：先通过复位原因确认看门狗触发，再排查超时预算和喂狗点，发现某关键任务卡死但主循环仍喂狗。重构为监控模块统一喂狗后，再做故障注入和长期统计，最终把不可复现问题转成可追溯、可验证的恢复机制。

## 实战练习

1. 在裸机工程中实现 IWDG 初始化和周期喂狗最小闭环。
2. 把主循环喂狗改成“两个关键任务心跳都正常才喂狗”。
3. 设计一个复位原因记录结构，重启后串口打印上次复位来源。
4. 做一次故障注入：故意卡死任务，验证看门狗复位和日志链路。
5. 对比不同超时配置下的误复位率与故障恢复时延。

## 关键要点

1. Watchdog 的目标是故障恢复，不是避免复位。
2. 喂狗点必须绑定真实健康条件，不能放在无条件路径。
3. 超时参数要基于最坏执行路径和抖动预算。
4. 复位原因记录与故障注入验证是工程落地关键。
5. IWDG/WWDG 选型和调试策略会直接影响稳定性。
