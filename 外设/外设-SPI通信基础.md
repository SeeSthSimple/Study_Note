# 外设-SPI通信基础

## 原始问题

SPI 看起来只是 `SCLK / MOSI / MISO / CS` 几根线配起来就能通信，但为什么真正做项目时总是反复遇到模式不对、片选时序不对、读回全 `0xFF`、收发错位、频率一拉高就不稳定这些问题？如果不想只会调用库函数，应该怎样系统理解 SPI？

## 先给结论

SPI 的本质，是一种由主设备提供时钟、按位同步移位、通常以片选信号划分一次事务边界的同步串行通信方式。

先记住下面几个结论：

1. SPI 不是“带地址的总线协议”，它通常没有像 I2C 那样统一的地址和应答机制，通信能不能成立主要取决于片选、时钟模式、位宽、位序和频率是否匹配。
2. SPI 的高频问题往往不在“发没发出去”，而在“对方是在哪个边沿采样、片选什么时候拉低拉高、一次事务到底从哪里开始到哪里结束”。
3. SPI 是全双工位交换机制，哪怕你只是想“读”，主机也必须继续送时钟，通常还要发 dummy 字节。
4. 同样叫 SPI，不同芯片和器件的“命令格式、寄存器地址长度、dummy 周期、CS 约束、最大时钟频率”可能完全不同，真正起决定作用的是器件手册，不是 SPI 这个名字本身。
5. 学 SPI 不能只记四种模式和四根线，还要建立一条稳定主线：引脚与电气 -> 时钟模式 -> 事务边界 -> 数据帧组织 -> 驱动实现 -> 波形排障。

如果只能背“SPI 是同步全双工串行通信”，却讲不清为什么读操作也要发数据、为什么 CPOL/CPHA 一错就会错位、为什么有时必须在片选拉低后延时再发时钟，就说明这部分还没有真正掌握。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 知道 SPI 有四根线，但不知道每根线在一次事务里到底起什么作用。
2. 能调通某一个 SPI 设备，但换一个 Flash、ADC、屏幕或传感器后就不稳定。
3. 面试或工作里会背 `Mode 0 ~ Mode 3`，但讲不清 `CPOL / CPHA` 真正影响的是什么。
4. 项目中遇到“写得进去，读不回来”“低速正常，高速异常”“逻辑分析仪看着有波形但数据不对”时，没有稳定排查路径。
5. 后续学习 `SPI Flash`、`Linux SPI 驱动`、`DMA 收发`、`显示屏驱动` 时，缺一篇能打底的外设视角笔记。

它在 AI 时代仍然重要，因为 AI 可以快速生成 SPI 初始化代码和读写函数，但它不知道目标器件要求哪种时钟模式，不知道你的片选是不是手动控制，不知道读数据前是否需要 dummy 周期，也不知道高速下板级走线和采样边沿是否还能稳定。SPI 理解越扎实，你越能分辨 AI 生成的是“语法正确”，还是“波形一上板就错”。

## 核心概念 / 本质机制

### 1. SPI 的基本信号线

最常见的四线 SPI 包括：

1. `SCLK`：时钟线，由主设备输出。
2. `MOSI`：`Master Out Slave In`，主发从收。
3. `MISO`：`Master In Slave Out`，主收从发。
4. `CS` / `NSS`：片选线，通常低有效，用来选中当前从设备。

理解 SPI 的第一步，不是记缩写，而是记住谁控制节奏：

1. 主设备决定什么时候开始通信。
2. 主设备决定时钟频率。
3. 主设备决定当前选中哪个从设备。
4. 只有被片选命中的从设备才应该响应当前事务。

### 2. SPI 是同步通信，不是异步通信

SPI 和 UART 的核心区别之一是：SPI 有独立时钟线。

这意味着：

1. 每来一个时钟周期，双方就交换一位数据。
2. 接收方不需要像 UART 那样靠波特率估计采样点，而是跟着时钟边沿采样。
3. 只要时钟模式、建立保持时间满足要求，SPI 通常能做到更高速度、更稳定采样。

但这不意味着 SPI 一定“更简单”，因为它把复杂度转移到了：

1. 时钟极性和相位。
2. 片选边界。
3. 事务格式。
4. 高速下的信号完整性。

### 3. SPI 的本质是“移位寄存器交换”

可以把 SPI 理解成主从两边各有一个移位寄存器。

每来一个时钟：

1. 主设备在一侧推出一位。
2. 从设备在另一侧推出一位。
3. 双方在约定的边沿采样对方送来的位。

所以 SPI 从物理行为上天然是全双工的。

这带来两个非常重要的工程结论：

1. 你发送一个字节的同时，也一定会接收到一个字节。
2. 你想从从机“读”一个字节，本质上仍然要靠主机继续送时钟，把对方的数据移出来。

很多“为什么读 SPI 还要写一个 `0xFF` 或 `0x00`”的问题，根本原因就在这里。

### 4. SPI 不天然定义地址、应答和消息边界

SPI 只规定“怎么按时钟交换位”，通常不规定：

1. 第一字节是不是命令。
2. 后面几字节是不是地址。
3. 读之前是否要先写寄存器地址。
4. 错误怎么表示。
5. 一帧什么时候结束。

这些通常由具体器件协议决定。

例如：

1. 某些传感器要求第一字节是寄存器地址，高位还带读写标志。
2. 某些 Flash 先发命令，再发 3 字节地址，再发 dummy，再读数据。
3. 某些 ADC 在上一个事务准备数据，下一个事务才真正读出结果。

所以“SPI 会不会”只是入口，“这个 SPI 设备怎么定义事务”才是关键。

### 5. `CPOL` 和 `CPHA` 决定时钟模式

SPI 最常见的高频考点就是四种模式。

1. `CPOL` 决定时钟空闲电平。
2. `CPHA` 决定在第几个边沿采样数据。

常见模式如下：

| 模式 | CPOL | CPHA | 空闲电平 | 常用理解 |
|------|------|------|----------|----------|
| Mode 0 | 0 | 0 | 空闲低 | 第一个边沿采样 |
| Mode 1 | 0 | 1 | 空闲低 | 第二个边沿采样 |
| Mode 2 | 1 | 0 | 空闲高 | 第一个边沿采样 |
| Mode 3 | 1 | 1 | 空闲高 | 第二个边沿采样 |

实际工程里最重要的不是死背表，而是知道模式错了会发生什么：

1. 采样边沿错了，数据整体左移或右移一位。
2. 某些位看起来随机错，尤其是高频时更明显。
3. 逻辑分析仪上“像是有数据”，但寄存器值始终不对。

### 6. 片选 `CS` 往往决定一次事务边界

很多器件会把 `CS` 拉低到拉高之间视为一次完整事务。

这意味着：

1. `CS` 拉低后，器件开始接收命令。
2. 中间如果误拉高，器件可能把事务直接终止。
3. 某些器件要求在 `CS` 拉低后先等待几个纳秒再开始时钟。
4. 某些器件要求一条命令和后续数据必须保持在同一次 `CS` 低电平窗口内完成。

因此 SPI 排障时一定要同时看：

1. 数据对不对。
2. `CS` 时序对不对。
3. 一次 API 调用有没有把本该连在一起的事务拆开。

### 7. 位序、位宽和时钟频率同样关键

除了模式，SPI 还常见下面几个配置项：

1. 位序：`MSB first` 还是 `LSB first`。
2. 位宽：`8-bit`、`16-bit`，有些控制器支持更宽。
3. 时钟频率：由主设备分频决定。

常见问题包括：

1. 设备要求 `MSB first`，结果控制器配成了 `LSB first`。
2. 寄存器是按 8 位协议设计的，却用了 16 位帧，导致从机按错边界解析。
3. 低速调通后直接拉高到上限频率，忽略了器件手册中的最大时钟和板级信号质量。

### 8. 多从设备共享总线时，共享的是时钟和数据线，不共享事务语义

SPI 常见拓扑是：

1. `SCLK / MOSI / MISO` 多个从设备共享。
2. 每个从设备单独一根 `CS`。

它的好处是实现简单，但要注意：

1. 任意时刻只能片选一个从设备。
2. 未被选中的从设备必须正确释放 `MISO`，否则会总线冲突。
3. 不同从设备可能要求不同模式和频率，切换设备时要同步切换配置。

很多“同一条总线上 A 正常、B 不正常”的问题，不是连线坏了，而是没有在切换从设备时同步切换模式和速率。

## 数据流 / 控制流 / 时序关系

### 1. 主机写寄存器的典型过程

下面是一个常见的写事务思路：

```text
主机拉低 CS
-> 发送写命令 / 寄存器地址
-> 发送待写数据
-> 等最后一位时钟完成
-> 主机拉高 CS
```

如果把它展开成线上的动作，可以理解为：

```text
CS:   ________----------------------________
SCLK:         _-_-_-_-_-_-_-_-_-_-_
MOSI:         [cmd/addr][data]
MISO:         [无意义/状态][无意义/状态]
```

这里常见认知误区是：

1. 写操作时 `MISO` 就“完全没用”。
2. 其实很多器件会在写事务中顺带返回状态位，或者至少会有移位出来的旧值。

### 2. 主机读寄存器的典型过程

很多 SPI 从机不是“主机一拉低片选，从机就自动把数据送出来”，而是要先告诉它“我要读哪个寄存器”。

典型流程如下：

```text
主机拉低 CS
-> 发送读命令 / 寄存器地址
-> 继续发送 1 个或多个 dummy 字节以产生时钟
-> 从机在 MISO 上返回目标数据
-> 主机拉高 CS
```

可以把它画成：

```text
CS:   ________------------------------------________
SCLK:         _-_-_-_-_-_-_-_-_-_-_-_-_-_-_
MOSI:         [read cmd][dummy][dummy]
MISO:         [status? ][data0][data1]
```

关键点在于：

1. 读数据靠的是时钟，不是“主机静静等着从机自己说话”。
2. 某些器件在命令和真实数据之间需要固定 dummy 周期。
3. 如果 dummy 发少了，读出来的数据通常会错位。

### 3. 模式错误时，波形“看起来正常”但数据会错

模式错时经常出现下面这种情况：

```text
主机以为：上升沿采样
从机要求：下降沿采样
结果：数据在采样瞬间还没稳定，或者刚被更新
```

现象通常是：

1. 每次读到的值都固定错误。
2. 某些位始终翻转。
3. 降低频率后“偶尔能用”，提高频率后彻底错误。

这类问题只看 API 往往很难发现，抓波形会更直接。

## 最小可运行示例

下面给一个简化的 SPI 主机轮询收发示例，用来说明 SPI 的最小闭环思路。寄存器地址是示意性质，不对应具体芯片。

```c
#define SPI_BASE        0x40013000U
#define SPI_CR1         (*(volatile unsigned int *)(SPI_BASE + 0x00))
#define SPI_SR          (*(volatile unsigned int *)(SPI_BASE + 0x08))
#define SPI_DR          (*(volatile unsigned int *)(SPI_BASE + 0x0C))

#define SPI_CR1_SPE     (1U << 6)
#define SPI_SR_RXNE     (1U << 0)
#define SPI_SR_TXE      (1U << 1)
#define SPI_SR_BSY      (1U << 7)

static void spi_init(void)
{
    /* 省略 pinmux、时钟和模式配置，只强调最小使能流程 */
    SPI_CR1 |= SPI_CR1_SPE;
}

static unsigned char spi_transfer_byte(unsigned char tx)
{
    while (!(SPI_SR & SPI_SR_TXE))
        ;

    SPI_DR = tx;

    while (!(SPI_SR & SPI_SR_RXNE))
        ;

    return (unsigned char)SPI_DR;
}

static void spi_wait_idle(void)
{
    while (SPI_SR & SPI_SR_BSY)
        ;
}

static void cs_low(void)
{
    /* 这里假设 CS 用 GPIO 手动控制 */
}

static void cs_high(void)
{
}

static unsigned char spi_read_reg(unsigned char reg)
{
    unsigned char value;

    cs_low();

    spi_transfer_byte(reg | 0x80U);
    value = spi_transfer_byte(0xFFU);

    spi_wait_idle();
    cs_high();

    return value;
}

int main(void)
{
    unsigned char id;

    spi_init();

    id = spi_read_reg(0x0FU);

    (void)id;

    for (;;)
        ;
}
```

这个示例完成的事情很简单：

1. 初始化 SPI 控制器。
2. 手动拉低片选。
3. 先发寄存器地址和读标志。
4. 再发一个 dummy 字节，把从机数据时钟出来。
5. 等总线空闲后释放片选。

虽然它不完整，但已经能帮助你理解 SPI 读操作最核心的事务结构。

## 代码解读

### 1. 为什么 `spi_transfer_byte()` 同时有发送和接收

因为 SPI 物理层就是双向移位交换。

所以一次字节传输里：

1. 你写入 `SPI_DR`，表示准备发送。
2. 硬件在时钟作用下把这一个字节移出去。
3. 与此同时，对方也会回传一个字节。
4. 收到的字节进入接收寄存器，等软件去读。

这也是为什么很多控制器要求“每发一次都要把接收寄存器读干净”，否则后续可能溢出。

### 2. 为什么读寄存器时要先发地址再发 dummy

因为大部分 SPI 器件需要先知道你想访问哪里。

第一字节往往承担的是：

1. 读写标志。
2. 寄存器地址。
3. 连续读写标志。

真正有意义的数据通常会在后一个或后几个字节阶段返回。所以 `dummy` 的作用不是“随便发点什么”，而是“继续提供时钟，把目标数据移出来”。

### 3. 为什么释放 `CS` 前要等 `BSY` 清零

很多控制器 `TXE` 置位只表示发送寄存器空了，不一定表示线上的最后一个 bit 已经发完。

如果这时提前拉高 `CS`，就可能导致：

1. 最后几个时钟没有完成。
2. 从机把事务判定为异常中止。
3. 写命令偶发失效，或读回数据少一个 bit。

所以很多平台上都需要在事务结束时额外等待 `BSY` 清零。

## 正确写法 vs 常见错误写法

### 1. 读操作时持续送时钟

正确思路：

```c
cs_low();
spi_transfer_byte(READ_CMD);
value = spi_transfer_byte(0xFF);
cs_high();
```

错误思路：

```c
cs_low();
spi_transfer_byte(READ_CMD);
/* 以为从机会自己把数据“吐出来” */
value = spi_receive_only();
cs_high();
```

问题在于很多主机控制器如果不继续发送，就不会继续出时钟，从机的数据也就出不来。

### 2. 保持一次完整事务的 `CS` 连续性

正确思路：

1. 一条命令、地址和对应数据保持在同一次 `CS` 低电平期间完成。

常见错误：

1. 发完地址就先拉高 `CS`。
2. 再重新拉低 `CS` 去读数据。

除非器件手册明确允许，否则这种拆分常常会让从机重新解释后续字节，导致读写失败。

### 3. 按器件手册配置模式和位序

正确思路：

1. 以器件手册为准配置 `CPOL / CPHA / bit order / frame size / max frequency`。

常见错误：

1. 直接沿用另一个设备的 SPI 配置。
2. 觉得“有波形就说明模式对了”。
3. 不切换配置就把同一总线接到不同从设备上。

## 边界条件与适用范围

SPI 很强，但它也有明确边界：

1. SPI 适合板内、短距离、高速、主从明确的同步通信。
2. SPI 不擅长长距离传输，也不适合像 CAN 那样做复杂仲裁。
3. SPI 协议层很自由，灵活性高，但互操作性差，同样叫 SPI 的设备事务格式可能完全不同。
4. 当从设备很多时，片选线会迅速增多，GPIO 资源会被占用。
5. 高速 SPI 对走线长度、阻抗、地参考和串扰更敏感，不能只看软件。

实际工程里通常这样理解：

1. 要简单点对点高速板内通信，SPI 很常用。
2. 要多设备共享且协议统一，I2C 往往更省线。
3. 要日志、调试或跨模块串口协议，UART 往往更直接。

## 常见坑与排查

### 1. 读回全 `0xFF`

高频原因包括：

1. 从机没被真正选中，`CS` 极性或引脚接错。
2. `MISO` 悬空或上拉，未选中时一直表现为高。
3. 读命令格式不对，器件没有开始输出数据。
4. dummy 周期不够，读到的是空转数据。

### 2. 读回全 `0x00`

常见原因包括：

1. `MISO` 被拉低或短路。
2. 模式不对，采样到的都是无效低位。
3. 从机仍在复位或未完成初始化。

### 3. 低速正常，高速异常

优先检查：

1. 频率是否超过器件规格。
2. `CPOL / CPHA` 边沿裕量是否太小。
3. 板级走线是否过长、回流路径是否差、串扰是否明显。
4. 上升沿下降沿是否过慢或过冲严重。

### 4. 某个设备正常，换另一个设备就不正常

优先检查：

1. 是否为不同设备切换了模式。
2. 是否切换了位宽和位序。
3. 是否每个设备都用了独立 `CS`。
4. 未选中的设备是否真的释放了 `MISO`。

### 5. 波形看着像对，寄存器值却不对

优先排查：

1. 地址字节是否需要带读写位。
2. 连续读写位是否需要置位。
3. 事务中是否缺少 dummy。
4. `CS` 是否被驱动层在中途自动拉高。
5. 接收缓冲是否读晚了，导致旧值残留。

### 6. 推荐排查顺序

遇到 SPI 问题时，尽量按这条主线排：

1. 电源、地、引脚连接和电平是否正确。
2. `CS / SCLK / MOSI / MISO` 是否接对。
3. `CS` 极性和事务边界是否符合手册。
4. 模式、位序、位宽、频率是否匹配。
5. 命令格式、地址长度、dummy 周期是否正确。
6. 用逻辑分析仪对照 datasheet 看每一字节是否符合预期。

## 工程落地建议

1. 先用最低稳定频率把命令格式调通，再逐步提速，不要一开始就跑上限。
2. 把“设备协议层”和“控制器传输层”分开，前者负责组包，后者只负责一段 SPI 事务。
3. 尽量把 `CS` 管理、模式切换、事务边界封装清楚，避免上层业务代码随意拼接。
4. 如果同一总线挂多个设备，给每个设备保留独立配置，不要偷懒共用一个默认模式。
5. 抓波形时不要只看 `MOSI`，一定要同时看 `CS`、`SCLK`、`MISO`，否则很容易漏掉根因。
6. 对读写寄存器接口，尽量把命令格式、地址位定义和 dummy 个数写成明确常量，不要散落在业务代码里。

## 性能、稳定性、可维护性影响

从工程视角看，SPI 的几个关键取舍如下：

1. 轮询实现最直观，但 CPU 占用高，适合初始化和低频控制路径。
2. 中断适合中等吞吐场景，但事务边界、缓冲和状态机要设计清楚。
3. DMA 适合大块连续传输，比如屏幕刷新、Flash 搬运、音频流，但也更依赖缓存一致性、缓冲区生命周期和错误恢复设计。
4. 提高时钟频率可以提升吞吐，但会放大边沿裕量、板级布线和驱动时序问题。
5. 如果 SPI 层没有明确抽象，很容易出现“每个设备都能用一点，但谁都不好维护”的问题。

所以一个好用的 SPI 驱动，不只是“能发能收”，还要做到：

1. 设备配置清晰。
2. 事务边界稳定。
3. 错误可观察。
4. 波形可验证。
5. 上层协议不被底层细节污染。

## 面试 / 问答怎么讲

如果面试官问“SPI 是什么”，可以按下面这条主线讲：

1. SPI 是一种主从式同步串行通信方式，主机提供时钟，常见线有 `SCLK / MOSI / MISO / CS`。
2. 它的物理层本质是移位寄存器按时钟交换数据，所以天然全双工。
3. SPI 本身通常不规定地址和应答，具体事务格式由器件协议定义，很多设备会用 `CS` 低电平窗口表示一次事务。
4. 实际使用时最关键的配置是 `CPOL / CPHA`、位序、位宽和频率。
5. 常见问题包括模式错误、片选时序错误、dummy 周期不足和高速下信号完整性问题。

如果被追问“SPI 和 I2C 的区别”，可以这样答：

1. SPI 更偏高速、主从明确、协议灵活，但线多，通常每个从设备都要独立片选。
2. I2C 更省线、总线仲裁和地址机制更统一，但速度通常更低，对上拉和总线电容更敏感。
3. SPI 常用于 Flash、LCD、ADC、高速传感器；I2C 常用于配置类器件、低中速传感器、板级管理器件。

## 实战练习

1. 自己画出 `Mode 0` 和 `Mode 3` 的采样边沿区别，并解释为什么模式错会造成位错位。
2. 选一个常见 SPI 传感器数据手册，整理它的读寄存器事务格式，包括命令位、地址位、dummy 周期和 `CS` 约束。
3. 写一个最小 `spi_read_reg()` 和 `spi_write_reg()` 封装，把控制器传输和器件协议拆成两层。
4. 用逻辑分析仪抓一次真实 SPI 读事务，对照手册确认每一字节含义。
5. 故意把 `CPHA` 或 `CPOL` 改错，观察波形和读值会出现什么现象。

## 关键要点

1. SPI 的主线不是“四根线叫什么”，而是“主机给时钟、片选划边界、双方按边沿交换位”。
2. 读 SPI 数据必须继续送时钟，所以读操作往往离不开 dummy 字节。
3. `CPOL / CPHA`、位序、位宽、频率和 `CS` 时序共同决定通信是否成立。
4. SPI 只定义底层位交换，真正的命令格式、地址长度和 dummy 周期要看具体器件手册。
5. SPI 排障要同时看协议和波形，尤其是 `CS`、采样边沿和事务连续性。
