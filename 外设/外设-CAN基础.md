# 外设-CAN基础

## 原始问题

CAN 到底是什么？为什么它在车载和工业场景里这么常见，看起来只是“总线收发报文”，但真实项目里经常遇到仲裁丢帧、总线错误、波特率不匹配、节点掉线、收发正常却业务错乱等问题？应该怎样系统掌握 CAN，而不是只会发一帧 ID+数据？

## 先给结论

CAN 的本质是“多节点共享差分总线上的优先级仲裁通信机制”，它不是简单串口替代，而是一套带错误检测与自动恢复能力的实时总线协议。

先记住下面几个结论：

1. CAN 的核心竞争力是多主仲裁、抗干扰、错误处理与工程可靠性。
2. CAN 报文优先级由 ID 决定，ID 越小优先级通常越高。
3. CAN 成败不仅看协议栈，还高度依赖物理层：终端电阻、布线、共地、收发器电平。
4. 调试 CAN 必须同时看三层：物理波形、控制器状态、上层报文语义。
5. “能收发”不等于“系统正确”，周期、超时、丢帧策略和节点状态管理同样关键。

如果只能背“CAN 抗干扰强、两根线通信”，却讲不清仲裁为什么不会碰撞损坏数据、错误帧怎么触发、总线关闭（bus-off）后怎么恢复，就说明这部分还没有真正掌握。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. CAN 节点上线后偶发离线、重发很多、延迟变大，不知道从物理层还是协议层入手。
2. 多节点场景下报文优先级设计不当，关键消息被挤压。
3. 项目里有报文但业务状态异常，缺少“从帧到语义”的排查主线。
4. 面试时会背标准帧扩展帧，但讲不清错误状态机和工程落地。

它在 AI 时代仍然重要，因为 AI 可以生成 CAN 初始化和收发代码，但它不知道你的线束拓扑、终端匹配、节点负载率、实时性约束和故障策略。CAN 理解越扎实，越能把“代码可跑”变成“系统可用”。

## 核心概念 / 本质机制

### 1. CAN 的通信模型

CAN 是多主总线，多个节点都可发。

核心机制：

1. 总线空闲时任意节点可发起发送。
2. 发送期间通过位级仲裁决定谁继续发送。
3. 仲裁失败节点自动停止发送并等待重发。

关键点是仲裁过程中不会破坏获胜帧内容。

### 2. 报文结构与 ID 含义

常见报文类型：

1. 标准帧（11 位 ID）。
2. 扩展帧（29 位 ID）。

ID 不是地址，更多承载“消息优先级 + 语义类别”。

工程里通常要先定义报文矩阵：

1. 哪些 ID 属于周期状态。
2. 哪些 ID 属于事件上报。
3. 哪些 ID 属于诊断和控制。

### 3. 仲裁为什么可控

CAN 使用显性位/隐性位机制（dominant/recessive）。

常见理解：

1. 发送隐性位但读到显性位，说明仲裁失败。
2. 仲裁失败节点立即退让，不破坏总线。

所以高优先级报文能更稳定抢到总线时隙。

### 4. 错误检测与节点状态

CAN 具备多种错误检测：

1. 位错误。
2. 填充错误。
3. CRC 错误。
4. 格式错误。
5. 应答错误。

节点常见状态：

1. Error Active。
2. Error Passive。
3. Bus-Off。

工程要点：出现 bus-off 不只是“重启就好”，要记录原因、统计频率并设计恢复策略。

### 5. 位时序和波特率

CAN 波特率由时间量子与段参数共同决定（不同控制器命名略有差异）。

高频坑：

1. 两端标称都 500kbps，但采样点配置差异太大，导致边缘场景错误率升高。
2. 线长、节点数、拓扑与波特率不匹配。

### 6. 物理层基础约束

CANH/CANL 差分传输需要配套收发器和终端匹配。

常见工程约束：

1. 总线两端终端电阻（典型 120Ω）匹配。
2. 避免星型过长支线。
3. 共地和电源完整性处理。
4. 收发器选型和共模范围匹配。

很多“协议看起来没问题”的故障根因都在这里。

## 数据流 / 控制流 / 时序关系

下面用“节点 A 周期发送状态帧，节点 B 接收并超时监控”串主线：

```text
节点A周期组帧
-> CAN控制器发帧并参与仲裁
-> 总线传输
-> 节点B过滤并接收
-> 上层解析数据并刷新状态
-> 超时监控检查帧间隔
-> 超时则标记节点异常
```

这条链上每一步都可能出问题：

1. ID 设计不合理导致关键帧竞争失败。
2. 过滤器配置错误导致“总线有帧但收不到”。
3. 上层只看收到一次，不做超时监控。
4. 错误计数上升但未做状态管理。

## 最小可运行示例

```c
#define CAN_BASE            0x40006400
#define CAN_CR              (*(volatile unsigned int *)(CAN_BASE + 0x00))
#define CAN_SR              (*(volatile unsigned int *)(CAN_BASE + 0x04))
#define CAN_BTR             (*(volatile unsigned int *)(CAN_BASE + 0x08))
#define CAN_TIR             (*(volatile unsigned int *)(CAN_BASE + 0x10))
#define CAN_TDTR            (*(volatile unsigned int *)(CAN_BASE + 0x14))
#define CAN_TDLR            (*(volatile unsigned int *)(CAN_BASE + 0x18))
#define CAN_TDHR            (*(volatile unsigned int *)(CAN_BASE + 0x1C))

static void can_init(void)
{
    /* 示例：位时序参数按目标波特率和时钟实际计算 */
    CAN_BTR = 0x001c0003;
}

static int can_send_std(unsigned int id, const unsigned char *data, unsigned int len)
{
    if (len > 8)
        return -1;

    CAN_TIR = (id & 0x7ffU) << 21;
    CAN_TDTR = len & 0xfU;
    CAN_TDLR = (unsigned int)data[0] |
               ((unsigned int)data[1] << 8) |
               ((unsigned int)data[2] << 16) |
               ((unsigned int)data[3] << 24);
    CAN_TDHR = (unsigned int)data[4] |
               ((unsigned int)data[5] << 8) |
               ((unsigned int)data[6] << 16) |
               ((unsigned int)data[7] << 24);

    CAN_TIR |= 1U;
    return 0;
}
```

这个示例表达的是最小发帧闭环，真实工程还要补滤波器、接收中断、错误状态处理和 bus-off 恢复。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| ID 设计 | 按实时性做优先级规划 | 随机分配 ID | 关键帧可能长期被压制 |
| 物理层 | 先查终端与布线再查协议 | 一上来只改软件参数 | 根因可能在总线硬件 |
| 接收策略 | 过滤+超时监控+状态机 | 只要收到过一次就当正常 | 易漏检掉线 |
| 错误处理 | 跟踪错误计数和状态迁移 | 忽略 bus-off | 节点可能长期离线 |

## 边界条件与适用范围

1. 这篇笔记面向经典 CAN 基础，CAN FD 细节另开主题更合适。
2. 不同控制器寄存器布局、位时序计算方式有差异，不能照搬。
3. 高实时系统中，CAN 报文矩阵和调度策略比“单次收发 API”更关键。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 完全通信不上 | 波特率/采样点不匹配；终端错误 | 示波器看差分波形、核对位时序 |
| 偶发丢帧 | 总线负载高；优先级设计差 | 统计总线负载和各 ID 延迟 |
| 节点频繁 bus-off | 物理层噪声或收发器异常 | 读错误计数器、查电源地和布线 |
| 有帧但业务异常 | 报文语义/缩放/字节序错 | 对照协议矩阵逐字段校验 |

## 工程落地建议

1. 先做报文矩阵，再写驱动和应用。
2. 把复位计数、bus-off 次数、超时次数纳入健康监控。
3. 把“无总线/弱干扰/强干扰”作为三类回归场景。

## 面试 / 问答怎么讲

### 30 秒版本

CAN 是多主差分总线，靠位级仲裁保障高优先级报文实时发送，并内建错误检测和状态恢复机制。工程难点在物理层匹配、位时序和报文调度。

### 3 分钟版本

先讲 CAN 的仲裁机制和 ID 优先级，再讲错误状态机（active/passive/bus-off）和物理层约束（终端、布线、收发器）。最后补工程主线：报文矩阵、超时监控、故障追溯。

## 关键要点

1. CAN 核心是仲裁与错误恢复，不只是“能发能收”。
2. 物理层和协议层必须一起排查。
3. 报文优先级和超时策略决定系统可用性。
