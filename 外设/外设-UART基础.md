# 外设-UART基础

## 原始问题

UART 到底是什么？为什么串口看起来像是嵌入式里最简单的接口，但真正做项目时又经常遇到波特率、收发时序、中断接收、丢字节和协议解析问题？

## 先给结论

UART 的本质，是一种异步串行通信方式，它用最少的线把字节按约定时序一位一位发送出去。

先记住下面几个结论：

1. UART 是字节流接口，不天然提供消息边界。
2. 一条 UART 链路最核心的约定是波特率、数据位、校验位、停止位。
3. UART 的高频问题通常不在“会不会发一个字节”，而在“收发双方配置是否一致、接收是否稳定、数据边界怎么处理”。
4. 对 MCU 和 Linux 平台来说，UART 都是最常见的日志、调试、控制和设备通信入口。
5. 学 UART 时要同时看三层：硬件线、电气和时序；控制器配置；上层协议和缓冲机制。

如果只能背“UART 是异步串口”，却讲不清起始位和停止位的作用、为什么波特率不对会乱码、为什么 UART 适合承载协议但不等于协议本身，就说明这部分还没有真正掌握。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 刚接触嵌入式时，不知道 UART 到底靠什么完成收发。
2. 串口有输出但乱码、丢字节、错包时，不知道该先查配置、波形还是协议。
3. 面试和工作中常被问到 UART 和 SPI、I2C 的区别，但讲不清主线。
4. 后续学习串口协议、Bootloader 日志、驱动开发和板级调试时，缺一个外设视角的稳定入口。

它在 AI 时代仍然重要，因为 AI 可以很快给你生成一段串口初始化代码，但它不知道你的波特率是否匹配、FIFO 深度是否够、日志量是否会堵塞系统、协议是否应该用 DMA 或中断收发。UART 理解越扎实，越能把 AI 生成代码变成真正稳定的工程方案。

## 核心概念 / 本质机制

### 1. UART 是怎么传输一个字节的

UART 是异步通信，不共享独立时钟线。

它依赖双方事先约定好的波特率，然后通过每一位持续时间来对齐采样。

一个典型 UART 帧通常包括：

1. 起始位。
2. 数据位。
3. 可选校验位。
4. 停止位。

接收方看到起始位后开始按约定节拍采样后面的数据位。

### 2. 为什么 UART 叫异步

因为它不像 SPI 那样有一根独立的时钟线同步收发。

它依赖的是：

1. 双方对波特率的预先约定。
2. 起始位提供一帧开始的同步点。

所以 UART 最大的前提是双方配置一致，否则就容易乱码。

### 3. 最常见的配置项是什么

常见 UART 配置通常写成：

```text
115200 8N1
```

它的意思是：

1. 波特率 `115200`
2. 数据位 `8`
3. 无校验 `N`
4. 停止位 `1`

收发双方只要其中任一项不一致，都可能出现：

1. 完全收不到。
2. 收到乱码。
3. 偶发错字节。

### 4. UART 为什么常被拿来做日志和协议

因为它有几个明显优点：

1. 线少，通常只要 TX、RX、GND。
2. 硬件简单，成本低。
3. 调试方便，逻辑分析仪和串口工具都容易接入。

但它的局限也很明显：

1. 没有天然消息边界。
2. 没有总线仲裁能力。
3. 一般是点对点，不像 I2C 能天然多从设备共享。

### 5. 轮询、中断和 DMA 收发各自适合什么场景

UART 收发常见三类方式：

1. 轮询。
2. 中断。
3. DMA。

大致思路是：

1. 数据量小、逻辑简单时，轮询最容易理解。
2. 普通实时收发场景，中断最常见。
3. 大吞吐、连续收发、CPU 想省事时，更常用 DMA。

真正的工程取舍通常不在“哪个最高级”，而在：

1. 数据量多大。
2. 响应实时性要求多高。
3. CPU 是否忙。
4. 缓冲区和协议复杂度如何。

### 6. UART 是字节流，不是协议

这点特别重要。

UART 控制器帮你做的是“把字节发出去、把字节收进来”。

它不帮你做：

1. 一帧从哪开始到哪结束。
2. 这一帧是什么命令。
3. 校验怎么做。
4. 超时和重发怎么做。

这些属于上层协议设计，所以 UART 基础和串口协议设计要分开理解。

## 数据流 / 控制流 / 时序关系

下面给一个典型 UART 接收链路：

```text
发送方输出起始位 + 数据位 + 停止位
-> 接收方 UART 控制器检测起始位
-> 按波特率节拍采样各数据位
-> 硬件拼成 1 个字节放入接收寄存器 / FIFO
-> 中断或 DMA 通知软件
-> 软件从缓冲区取字节并交给协议解析层
```

这条链路里常见问题包括：

1. 波特率不一致，采样点偏掉。
2. 软件取数据不及时，FIFO 溢出。
3. 上层把 UART 字节流误当成完整帧。

## 最小可运行示例

下面给一个简化的 UART 轮询发送和接收示例：

```c
#define UART_BASE        0x40000000
#define UART_DR          (*(volatile unsigned int *)(UART_BASE + 0x00))
#define UART_SR          (*(volatile unsigned int *)(UART_BASE + 0x04))
#define UART_TX_EMPTY    (1U << 7)
#define UART_RX_READY    (1U << 0)

static void uart_putc(char ch)
{
    while (!(UART_SR & UART_TX_EMPTY))
        ;

    UART_DR = (unsigned int)ch;
}

static char uart_getc(void)
{
    while (!(UART_SR & UART_RX_READY))
        ;

    return (char)UART_DR;
}

static void uart_puts(const char *s)
{
    while (*s)
        uart_putc(*s++);
}

int main(void)
{
    char ch;

    uart_puts("uart demo start\r\n");

    for (;;) {
        ch = uart_getc();
        uart_putc(ch);
    }
}
```

这个示例完成的是最小回环逻辑：

1. 串口打印启动信息。
2. 收到一个字节。
3. 立即原样回发。

它虽然简单，但已经能帮助你验证：

1. 基本收发是否工作。
2. 波特率和串口配置是否一致。
3. TX、RX 线路是否接对。

## 代码解读

### 1. 为什么轮询示例仍然有价值

因为它把 UART 主线压缩到了最小闭环。

你至少可以先确认：

1. 控制器寄存器访问是否正常。
2. 串口引脚是否配对。
3. 波特率配置是否正确。

如果这个最小示例都跑不通，就没必要急着上中断和 DMA。

### 2. 为什么 `uart_getc()` 会阻塞

因为它一直等到接收就绪位为真。

这在演示里很直观，但在真实项目里如果直接这么写，容易导致：

1. 整个主循环卡住。
2. 其他任务得不到运行机会。

所以工程里更常见的是中断或 DMA。

### 3. 为什么这个示例不能直接代表完整工程 UART

真实项目里还要继续考虑：

1. FIFO 和缓冲区。
2. 中断接收。
3. DMA 收发。
4. 错误位，比如帧错误、奇偶校验错误、溢出错误。
5. 协议解析和超时处理。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 配置理解 | 明确波特率、数据位、校验位、停止位 | 只改波特率不核对其他参数 | 双方配置不一致会出错 |
| 收发定位 | 先确认 UART 基本收发，再上协议 | 串口都没通就直接怀疑协议层 | 排障方向错 |
| 数据边界 | 把 UART 当字节流处理 | 假设一次收到的就是完整消息 | 上层解析容易错 |
| 工程收发 | 合理使用中断或 DMA | 长期使用阻塞轮询 | 容易拖慢系统 |
| 错误处理 | 检查溢出、帧错误、校验错误 | 只看有没有收到字节 | 异常字节根因难定位 |

## 边界条件与适用范围

1. UART 非常适合低到中速、点对点、调试友好的链路。
2. 如果需要多设备共享、严格同步或更高吞吐，I2C、SPI、CAN、USB 等可能更合适。
3. 某些板子会用 RS-232、RS-485 或 TTL 电平，电平标准不同，不能直接混接。
4. “串口乱码”不一定是软件配置问题，也可能是电平、接线、地线和波形质量问题。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 输出乱码 | 波特率不一致；校验位不一致；电平不兼容 | 核对配置、逻辑分析仪解码、示波器看电平 |
| 收不到数据 | TX/RX 接反；地没共地；引脚复用错 | 查原理图、测波形、查 pinmux |
| 偶发丢字节 | FIFO 溢出；中断处理不及时；缓冲区太小 | 看错误标志、接收节奏和缓冲区 |
| 日志卡系统 | 阻塞发送过多；高频打印 | 查任务耗时、串口发送方式 |
| 串口通了但协议总错 | 上层没分帧；半包处理差 | 查协议解析状态机 |

### 推荐排查顺序

1. 先确认电平标准、TX/RX 接线和共地。
2. 再确认波特率、数据位、校验位、停止位。
3. 再确认最小收发闭环是否跑通。
4. 再看中断 / DMA / 缓冲区是否稳定。
5. 最后再看上层协议解析。

## 工程落地建议

### 1. 区分“调试串口”和“业务串口”

很多项目里：

1. 一条 UART 主要用来打日志。
2. 另一条 UART 用来跑协议。

这两类用途的要求不完全一样，设计时要分清。

### 2. 日志量不要无节制

串口日志很方便，但大量阻塞打印会：

1. 拖慢任务调度。
2. 放大实时性问题。
3. 掩盖原本的时序 bug。

### 3. 协议设计要和 UART 层解耦

推荐分层：

1. UART 驱动负责收发字节。
2. 缓冲层负责搬运和缓存。
3. 协议层负责分帧、校验和命令处理。

这样后续从轮询切换到 DMA 时，上层逻辑不必全改。

## 性能、稳定性、可维护性影响

1. UART 本身不复杂，但它经常承担日志和设备通信双重职责，所以稳定性影响很大。
2. 如果 UART 收发和协议层没有解耦，后续改动成本会很高。
3. 合理的中断 / DMA / 缓冲设计，能显著降低丢字节和卡顿风险。

## 面试 / 问答怎么讲

### 30 秒版本

UART 是一种异步串行接口，靠双方预先约定的波特率和起始位、停止位完成字节收发。它擅长做日志和点对点通信，但它本身只是字节流接口，不等于协议。

### 3 分钟版本

可以先讲 UART 的基本帧结构：起始位、数据位、可选校验位、停止位，再讲 `115200 8N1` 这类配置。然后说明为什么 UART 只是字节流、为什么常见问题是波特率不一致和上层协议边界没处理好，最后再补轮询、中断和 DMA 三种收发方式的适用场景。

### 10 分钟版本

可以结合一个真实项目展开，比如一条 UART 用来打日志，另一条 UART 用来收发设备协议。先说明基本收发和电平配置，再说明中断 / DMA 接收与缓冲机制，最后把协议分帧、超时和调试手段串起来，体现你能把外设层和协议层一起讲清楚。

## 实战练习

1. 写一个 UART 最小回环程序，确认收发和波特率配置。
2. 把轮询接收改成中断接收，比较 CPU 占用和代码结构变化。
3. 用逻辑分析仪抓一次 UART 波形，验证 `115200 8N1` 的字节时序。
4. 结合一份串口协议，为 UART 接收层设计一个环形缓冲区。

## 关键要点

1. UART 是异步串行字节流接口，不是协议本身。
2. 波特率、数据位、校验位、停止位必须双方一致。
3. 工程里要同时关注硬件电平、控制器配置和上层缓冲 / 协议。
4. 先跑通最小收发闭环，再做中断、DMA 和协议扩展。
