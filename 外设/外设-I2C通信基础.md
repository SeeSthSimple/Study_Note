# 外设-I2C通信基础

## 原始问题

I2C 到底是什么？为什么它只用两根线就能挂很多设备，但项目里又经常遇到无 ACK、总线卡死、地址冲突和波形异常问题？

## 先给结论

I2C 的本质，是一条基于开漏和上拉的同步双线总线。

先记住下面几个结论：

1. I2C 最核心的不是“只有两根线”，而是时钟线 `SCL`、数据线 `SDA` 和总线仲裁规则。
2. I2C 依赖上拉电阻，没有上拉或者上拉不合适，总线很容易出问题。
3. I2C 设备通信的基本单位是“起始位 + 地址 + 读写位 + ACK/NACK + 数据 + 停止位”。
4. 很多 I2C 问题不是驱动 API 不会用，而是地址理解错、上拉不对、时序不稳或设备根本没上电。
5. AI 可以帮你写 I2C 读写代码，但它不知道你的总线电容、上拉、电压域和地址是否真实匹配。

## 这个知识解决什么问题

1. 不知道 I2C 为什么要开漏和上拉。
2. 传感器、EEPROM 等设备明明挂在总线上，却经常无 ACK。
3. 面试和工作里经常被问到 I2C 起始位、ACK、仲裁和时钟拉伸。
4. 后续做 I2C 驱动、设备树、协议和板级调试时，需要一篇外设视角主线笔记。

## 核心概念 / 本质机制

### 1. I2C 的两根线分别做什么

1. `SCL`：时钟线。
2. `SDA`：数据线。

主设备通常发起传输并提供时钟节拍，从设备按时钟节拍在 `SDA` 上传数据或采样数据。

### 2. 为什么 I2C 要开漏和上拉

I2C 总线不是推挽对推挽直接硬顶，而是：

1. 设备需要拉低时主动拉低。
2. 不拉低时释放总线，由上拉把线恢复为高。

这样做的好处是：

1. 多设备共享同一条线更安全。
2. 可以支持仲裁和 ACK 机制。

### 3. 一次最基本的 I2C 传输长什么样

```text
START
-> 7bit/10bit 地址
-> R/W 位
-> ACK
-> 数据字节
-> ACK/NACK
-> STOP
```

### 4. ACK 为什么关键

ACK 是总线是否真正握手成功的最直接信号之一。

常见情况：

1. 地址正确且设备在线，通常会有 ACK。
2. 地址错、设备没上电、总线异常时，常见现象就是无 ACK。

### 5. 什么是时钟拉伸

某些从设备准备数据较慢，会暂时拉低 `SCL`，告诉主设备“先等等”。

这就是时钟拉伸。

如果主设备或驱动没有正确支持，可能会出现：

1. 读写超时。
2. 波形看起来时钟异常。

## 数据流 / 控制流 / 时序关系

下面给一个典型“写寄存器地址后再读数据”的 I2C 链路：

```text
START
-> 发送从地址 + 写位
-> 从设备 ACK
-> 发送寄存器地址
-> 从设备 ACK
-> RESTART
-> 发送从地址 + 读位
-> 从设备 ACK
-> 读取数据字节
-> 主设备 ACK/NACK
-> STOP
```

这条链路是很多传感器、EEPROM、寄存器类设备的标准主线。

## 最小可运行示例

```c
static int sensor_read_reg(unsigned char reg, unsigned char *value)
{
    if (i2c_start() < 0)
        return -1;

    if (i2c_send_byte((SENSOR_ADDR << 1) | 0) < 0)
        return -1;

    if (i2c_send_byte(reg) < 0)
        return -1;

    if (i2c_restart() < 0)
        return -1;

    if (i2c_send_byte((SENSOR_ADDR << 1) | 1) < 0)
        return -1;

    *value = i2c_read_byte(I2C_NACK);
    i2c_stop();
    return 0;
}
```

## 代码解读

### 1. 为什么读寄存器前往往要先写寄存器地址

因为很多 I2C 外设内部有寄存器指针。

先写寄存器地址，是在告诉设备后续要从哪个寄存器开始读。

### 2. 为什么最后一个字节常用 `NACK`

因为主设备要通过最后一次 `NACK` 告诉从设备“我读完了，不再继续要数据”。

### 3. 为什么 `restart` 很常见

因为很多设备读取流程本质上是：

1. 先写寄存器地址。
2. 再切换成读模式读取数据。

中间用重复起始而不是彻底停止，是 I2C 常见标准时序。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 电气设计 | 明确上拉和电压域 | 忽略上拉直接连线 | 总线可能不稳定 |
| 地址理解 | 明确 7bit 地址和 R/W 位关系 | 把 8bit 地址当 7bit 地址直接用 | 易导致无 ACK |
| 读寄存器 | 先写寄存器地址再读 | 直接切到读模式 | 很多设备读不到目标寄存器 |
| 总线排障 | 先看 ACK 和波形 | 一上来只怪驱动 | 根因可能在硬件层 |

## 边界条件与适用范围

1. I2C 适合中低速、多器件共享和寄存器访问型设备。
2. 不同器件是否支持时钟拉伸、重复起始和多字节连续读，细节可能不同。
3. 7 位地址和 10 位地址要区分，资料中有时还会出现左移后的 8 位表示法，容易混。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 无 ACK | 地址错；设备没上电；上拉不对 | 核地址、供电和波形 |
| 总线一直拉低 | 某设备锁总线；上电异常；驱动中途中断 | 示波器看 SDA/SCL 静态电平 |
| 偶发读错 | 边沿太慢；干扰；时序不满足 | 示波器看波形质量 |
| 读值一直不变 | 寄存器地址错；没用重复起始 | 看协议流程和手册 |

## 工程落地建议

1. 优先把 7 位地址、寄存器地址和读写流程写清楚。
2. 硬件设计阶段就确认上拉、电压域和地址冲突。
3. 调试时一定结合逻辑分析仪或示波器看 ACK 和时序。

## 性能、稳定性、可维护性影响

1. I2C 不是高速总线，但它是高频基础总线，稳定性问题会拖累大量外设。
2. 地址、上拉和波形质量理解清楚后，调试效率会明显提升。
3. 把读写主线写清楚，比背 API 更有长期价值。

## 面试 / 问答怎么讲

### 30 秒版本

I2C 是一条基于开漏和上拉的同步双线总线，核心是 `SCL`、`SDA`、起始停止、地址、ACK 和共享总线规则。很多问题本质上都绕不开上拉、电压域和 ACK 时序。

### 3 分钟版本

可以先讲 I2C 为什么要开漏和上拉，再讲一次典型读寄存器流程：起始位、地址、ACK、寄存器地址、重复起始、读数据、停止位。然后补无 ACK、总线拉低和地址位宽混淆这些高频坑。

### 10 分钟版本

可以进一步展开波形和工程排障，比如如何用逻辑分析仪看 ACK，如何判断地址是不是用了错误表示法，为什么总线共享必须考虑上拉和电容，为什么某些设备读寄存器一定要用重复起始。这种讲法更贴近真实工作。

1. I2C 的核心是开漏、上拉、地址和 ACK。
2. 7 位地址和 8 位表示法要分清。
3. 很多 I2C 问题先看波形，再看代码。
4. 读寄存器流程通常是先写地址再读。
