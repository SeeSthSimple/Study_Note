# 外设-I2C通信基础

## 原始问题

I2C 通信在嵌入式开发中几乎无处不在，但为什么很多人只会调 API，遇到通信失败、时序不对、设备不响应时就没有稳定排查思路？真正做项目时，应该怎样理解 I2C，而不是只会背"起始 - 地址 - 读写 - 停止"？

## 先给结论

I2C 通信的本质，是用两根线（SDA 数据线、SCL 时钟线）在多个设备之间建立一种**主从同步半双工**的通信机制。

先记住下面几个结论：

1. I2C 通信成败不取决于"代码有没有调 API"，而取决于时序是否满足器件要求、总线电气特性是否可靠、地址和时序配置是否正确。
2. 绝大多数 I2C 问题的根因可以归结为：时序参数不对、上拉电阻不合适、地址错误、从机响应问题、总线竞争或干扰。
3. 学 I2C 时最重要的不是记住起始 / 停止条件怎么画，而是建立一条稳定主线：电气层 -> 时序层 -> 协议层 -> 驱动层 -> 排障层。
4. 硬件 I2C 和外设 I2C（GPIO 模拟）各有适用场景，理解它们的约束比盲目选择更重要。

如果只能画出时序图，却讲不清上拉电阻怎么选、时序参数怎么配、通信失败时从哪里切入排查，就说明这部分还没有真正掌握。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 单个 I2C 设备能通信，但总线上挂多个设备时就开始出问题。
2. 换了不同厂家的传感器，代码没改却不能通信。
3. 知道 I2C 时序长什么样，但遇到通信失败时没有稳定排查路径。
4. 面试时会背"起始条件、地址、应答、停止"，但讲不清上拉电阻、时序参数和电气约束。
5. 项目里遇到"偶尔通信失败""读回来的数据全是 0xFF""设备偶尔不响应"等问题时，不知道先查硬件还是先查软件。

它在 AI 时代仍然重要，因为 AI 可以帮你生成 I2C 初始化代码和读写函数，但它不知道你的上拉电阻是否匹配总线电容，不知道时序参数是否满足器件要求，也不知道多设备总线上是否存在地址冲突或电气问题。I2C 理解越扎实，你越能判断 AI 给出的代码是"能编译"，还是"上线后通信不稳定"。

## 核心概念 / 本质机制

### 1. I2C 的物理层约束

I2C 总线有两根线：

1. **SDA（Serial Data）**：双向数据线。
2. **SCL（Serial Clock）**：时钟线，由主机驱动。

关键特性：

1. **开漏输出**：SDA 和 SCL 通常都是开漏结构，需要外接上拉电阻。
2. **线与逻辑**：多个设备可以同时驱动总线为低电平，但无法同时驱动为高电平。
3. **主从架构**：主机发起通信、产生时钟；从机响应地址和数据。
4. **半双工**：同一时刻数据只能沿一个方向传输。

### 2. 上拉电阻的作用和选型

上拉电阻不是随便选的，它直接影响：

1. **上升沿速度**：电阻越大，RC 时间常数越大，上升沿越缓。
2. **功耗**：电阻越小，低电平时电流越大。
3. **驱动能力**：总线上设备越多，电容越大，需要更小的上拉电阻。

典型值范围：

- 标准模式（100kHz）：4.7kΩ - 10kΩ
- 快速模式（400kHz）：2.2kΩ - 4.7kΩ
- 高速模式（1MHz+）：1kΩ - 2.2kΩ

经验法则：

1. 总线电容大、速度快 → 选小电阻。
2. 功耗敏感、速度慢 → 选大电阻。
3. 多设备总线 → 先测波形，再调整电阻。

### 3. I2C 时序的核心参数

一次完整的 I2C 通信包含几个关键时序段：

```
空闲 -> 起始条件 -> 地址帧 -> 应答 -> 数据帧 -> 应答 -> ... -> 停止条件 -> 空闲
```

关键时序参数（以标准模式为例）：

1. **SCL 频率**：100kHz（标准）、400kHz（快速）、1MHz（高速）。
2. **建立时间（Setup Time）**：数据在 SCL 上升沿前必须稳定的时间。
3. **保持时间（Hold Time）**：数据在 SCL 上升沿后必须保持的时间。
4. **低电平时间 / 高电平时间**：SCL 一个周期的占空比约束。

不同器件对这些参数有不同要求， datasheet 里通常会给出最小值。

### 4. 起始条件和停止条件

**起始条件（START）**：

- SCL 为高时，SDA 从高变低。
- 表示一次通信开始，所有从机都会检测到。

**停止条件（STOP）**：

- SCL 为高时，SDA 从低变高。
- 表示通信结束，总线释放。

**重复起始条件（Repeated START）**：

- 不释放总线，直接发起新通信。
- 常用于"写地址 + 读数据"的原子操作。

### 5. 地址帧和数据帧

**地址帧**：

- 7 位地址 + 1 位读写位（R/W）。
- 例如：地址 0x50，写操作 = 0xA0，读操作 = 0xA1。
- 第 9 个时钟周期是从机的应答（ACK）。

**数据帧**：

- 8 位数据。
- 第 9 个时钟周期是接收方的应答（ACK）。
- 如果接收方不响应（NACK），表示通信结束或读操作完成。

### 6. 应答机制

I2C 的应答机制是通信成败的关键：

1. **ACK（应答）**：接收方在第 9 个时钟周期拉低 SDA。
2. **NACK（非应答）**：接收方不拉低 SDA，通常表示：
   - 地址没有匹配的设备。
   - 读操作已经完成。
   - 从机忙或出错。

绝大多数 I2C 通信失败，最终都表现为"没有收到应答"。

### 7. 硬件 I2C vs GPIO 模拟 I2C

| 特性 | 硬件 I2C | GPIO 模拟 I2C |
|------|---------|--------------|
| 时序精度 | 高，由硬件保证 | 依赖软件延时，易受中断影响 |
| CPU 占用 | 低，可中断 +DMA | 高，需要 CPU 持续控制 |
| 灵活性 | 受限于外设引脚 | 任意 GPIO 都可模拟 |
| 调试难度 | 需要查外设寄存器 | 可直接控制波形 |
| 适用场景 | 稳定通信、高速通信 | 引脚受限、低速、临时调试 |

工程建议：

1. 能上硬件 I2C 就优先用硬件 I2C。
2. GPIO 模拟适合低速、简单场景，不要指望它能稳定跑高速。
3. 如果模拟 I2C 出问题，优先检查延时函数和中断影响。

## 数据流 / 控制流 / 时序关系

### 1. 主机写数据到从机的完整流程

```
主机                      总线                      从机
 |                         |                         |
 |--START----------------->|                         |
 |                         |--地址+R/W=0------------>|
 |                         |                         |--地址匹配
 |                         |<--ACK--------------------|
 |                         |                         |
 |                         |--数据字节 1------------>|
 |                         |                         |--接收数据
 |                         |<--ACK--------------------|
 |                         |                         |
 |                         |--数据字节 2------------>|
 |                         |<--ACK--------------------|
 |                         |                         |
 |--STOP------------------>|                         |
```

### 2. 主机从从机读数据的完整流程

```
主机                      总线                      从机
 |                         |                         |
 |--START----------------->|                         |
 |                         |--地址+R/W=0------------>|
 |                         |<--ACK--------------------|
 |                         |                         |
 |                         |--寄存器地址------------>|
 |                         |<--ACK--------------------|
 |                         |                         |
 |--ReSTART---------------->                         |
 |                         |--地址+R/W=1------------>|
 |                         |<--ACK--------------------|
 |                         |                         |
 |<--数据字节 1------------|                         |
 |--ACK-------------------->                         |
 |                         |                         |
 |<--数据字节 2------------|                         |
 |--NACK------------------>|                         |
 |                         |                         |
 |--STOP------------------>|                         |
```

### 3. 常见问题时序

**没有应答的时序**：

```
主机发送地址后：
SCL: ____|‾‾‾‾|____|‾‾‾‾|____
              ↑
              第 9 个周期，SDA 应该被拉低但没有
SDA: ‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾
```

可能原因：

1. 从机地址错误。
2. 从机未供电或复位。
3. 总线电气问题。
4. 时序参数不满足要求。

## 最小可运行示例

### 1. 硬件 I2C 初始化示例（STM32 HAL）

```c
#include "stm32f4xx_hal.h"

static I2C_HandleTypeDef hi2c1;

void MX_I2C1_Init(void)
{
    hi2c1.Instance = I2C1;
    hi2c1.Init.ClockSpeed = 100000;        // 100kHz
    hi2c1.Init.DutyCycle = I2C_DUTYCYCLE_2;
    hi2c1.Init.OwnAddress1 = 0;            // 主机模式，自身地址设为 0
    hi2c1.Init.AddressingMode = I2C_ADDRESSINGMODE_7BIT;
    hi2c1.Init.DualAddressMode = I2C_DUALADDRESS_DISABLE;
    hi2c1.Init.OwnAddress2 = 0;
    hi2c1.Init.GeneralCallMode = I2C_GENERALCALL_DISABLE;
    hi2c1.Init.NoStretchMode = I2C_NOSTRETCH_DISABLE;

    if (HAL_I2C_Init(&hi2c1) != HAL_OK)
        Error_Handler();
}

void HAL_I2C_MspInit(I2C_HandleTypeDef *hi2c)
{
    GPIO_InitTypeDef GPIO_InitStruct;

    if (hi2c->Instance == I2C1) {
        // 使能时钟
        __HAL_RCC_I2C1_CLK_ENABLE();
        __HAL_RCC_GPIOB_CLK_ENABLE();

        // PB6 -> SCL, PB7 -> SDA
        GPIO_InitStruct.Pin = GPIO_PIN_6 | GPIO_PIN_7;
        GPIO_InitStruct.Mode = GPIO_MODE_AF_OD;        // 复用开漏
        GPIO_InitStruct.Pull = GPIO_NOPULL;            // 外部上拉
        GPIO_InitStruct.Speed = GPIO_SPEED_FREQ_HIGH;
        GPIO_InitStruct.Alternate = GPIO_AF4_I2C1;
        HAL_GPIO_Init(GPIOB, &GPIO_InitStruct);
    }
}
```

### 4. GPIO 模拟 I2C 示例（简化版）

```c
#define I2C_SDA_PIN     GPIO_PIN_0
#define I2C_SCL_PIN     GPIO_PIN_1
#define I2C_GPIO_PORT   GPIOA

static void i2c_delay(void)
{
    // 简单延时，实际应根据目标频率调整
    for (volatile int i = 0; i < 10; i++);
}

static void i2c_sda_high(void)
{
    HAL_GPIO_WritePin(I2C_GPIO_PORT, I2C_SDA_PIN, GPIO_PIN_SET);
}

static void i2c_sda_low(void)
{
    HAL_GPIO_WritePin(I2C_GPIO_PORT, I2C_SDA_PIN, GPIO_PIN_RESET);
}

static void i2c_scl_high(void)
{
    HAL_GPIO_WritePin(I2C_GPIO_PORT, I2C_SCL_PIN, GPIO_PIN_SET);
}

static void i2c_scl_low(void)
{
    HAL_GPIO_WritePin(I2C_GPIO_PORT, I2C_SCL_PIN, GPIO_PIN_RESET);
}

static void i2c_start(void)
{
    i2c_sda_high();
    i2c_scl_high();
    i2c_delay();
    i2c_sda_low();    // SCL 高时 SDA 下降沿 -> START
    i2c_delay();
    i2c_scl_low();
}

static void i2c_stop(void)
{
    i2c_sda_low();
    i2c_scl_low();
    i2c_delay();
    i2c_scl_high();
    i2c_delay();
    i2c_sda_high();   // SCL 高时 SDA 上升沿 -> STOP
    i2c_delay();
}

static uint8_t i2c_write_byte(uint8_t byte)
{
    uint8_t i;
    
    for (i = 0; i < 8; i++) {
        if (byte & 0x80)
            i2c_sda_high();
        else
            i2c_sda_low();
        
        i2c_scl_high();
        i2c_delay();
        i2c_scl_low();
        i2c_delay();
        byte <<= 1;
    }
    
    // 读取 ACK
    i2c_sda_high();
    i2c_scl_high();
    i2c_delay();
    
    uint8_t ack = HAL_GPIO_ReadPin(I2C_GPIO_PORT, I2C_SDA_PIN);
    i2c_scl_low();
    
    return (ack == GPIO_PIN_RESET) ? 1 : 0;  // 1=ACK, 0=NACK
}
```

## 代码解读

### 1. 为什么硬件 I2C 要配置为开漏模式

I2C 总线规范定义了开漏输出，这是为了支持：

1. 多主机仲裁。
2. 时钟拉伸（Clock Stretching）。
3. 不同电压器件共存。

如果配置成推挽输出，可能会损坏器件或导致总线竞争。

### 2. 为什么上拉电阻要外接

大多数 MCU 的 GPIO 内部上拉太弱（通常 20kΩ-50kΩ），无法满足：

1. 快速模式的上升沿要求。
2. 多设备总线的驱动需求。

工程上通常会外接 2.2kΩ-4.7kΩ 的上拉电阻。

### 3. 为什么读操作需要 ReSTART

很多 I2C 器件（如 EEPROM、传感器）要求：

1. 先写寄存器地址（写操作）。
2. 然后不释放总线，直接发起读操作。

如果中间释放了总线（STOP + START），从机可能丢失上下文，读回错误数据。

### 4. 为什么模拟 I2C 要关中断

模拟 I2C 的时序完全依赖软件延时精度。如果中途被中断打断：

1. SCL 高电平时间过长。
2. 数据建立 / 保持时间不满足要求。
3. 从机可能超时或出错。

关键路径上建议关中断或使用更高优先级。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
|------|---------|-------------|---------|
| 上拉电阻 | 根据总线电容和速度选 2.2kΩ-4.7kΩ | 随便用 10kΩ 或不用上拉 | 上升沿太缓或无法驱动高电平 |
| 引脚配置 | 配置为复用开漏 + 外部上拉 | 配置成推挽或内部上拉 | 违反 I2C 规范，可能损坏器件 |
| 时序延时 | 根据目标频率精确计算延时 | 随便写延时或不调延时 | 时序不满足器件要求 |
| 地址计算 | 7 位地址左移 1 位 + R/W 位 | 直接用 7 位地址当 8 位用 | 地址错误，从机不响应 |
| 读操作流程 | START+ 写地址+ReSTART+ 读数据 | START+ 写地址+STOP+START+ 读 | 从机可能丢失寄存器地址上下文 |
| 超时处理 | 加超时检测并复位 I2C 状态 | 死等标志位 | 总线异常时系统卡死 |
| 多设备总线 | 先扫描地址确认设备存在 | 直接通信，失败再查 | 无法快速定位是硬件还是软件问题 |

## 边界条件与适用范围

1. 这篇笔记讲的是标准 I2C 协议，不适用于 SMBus、PMBus 等衍生协议（虽然它们基于 I2C，但有额外约束）。
2. 不同 MCU 的硬件 I2C 外设实现差异很大，有些甚至存在硬件 bug，需要参考具体 errata。
3. 高速模式（1MHz、3.4MHz）对布线和电气要求更高，不能简单套用标准模式的参数。
4. 长距离通信（>20cm）需要考虑总线电容、干扰和电平转换问题。
5. 某些特殊器件（如某些触摸屏 IC）可能需要非标准时序或特殊流程。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
|------|---------|-------------|
| 从机不响应地址 | 地址错误；从机未供电；上拉缺失 | 用逻辑分析仪抓 START+ 地址波形 |
| 读回数据全 0xFF | 从机 NACK；总线未上拉；时序太快 | 看第 9 个周期是否有 ACK |
| 偶尔通信失败 | 时序边界太紧；干扰；接触不良 | 降低速度、测波形、加固连接 |
| 多设备时部分失败 | 地址冲突；总线电容过大 | 逐个设备测试，测上升沿时间 |
| 写成功读失败 | 缺少 ReSTART；寄存器地址没写入 | 抓完整时序，看是否有 STOP 插入 |
| 通信几次后卡死 | 未处理超时；从机时钟拉伸 | 加超时复位逻辑，查从机状态 |
| 模拟 I2C 不稳定 | 延时被中断打断 | 关键段关中断或提高优先级 |

### 推荐排查顺序

1. **先电气，后协议**：
   - 测 SDA、SCL 是否有上拉（空闲时应为高电平）。
   - 测上升沿是否陡峭（太缓说明上拉太弱或电容太大）。

2. **先单设备，后多设备**：
   - 总线上只留一个从机，排除地址冲突和电容问题。

3. **先低速，后高速**：
   - 把 I2C 速度降到 50kHz 以下，看是否稳定。

4. **先硬件 I2C，后模拟 I2C**：
   - 硬件 I2C 时序更可靠，先排除软件问题。

5. **必须抓波形**：
   - 逻辑分析仪或示波器是 I2C 排障的必备工具。
   - 重点看：START/STOP、地址、ACK、数据、时序参数。

## 工程落地建议

### 1. 上拉电阻先按 4.7kΩ 选，再调

工程上最稳妥的做法：

1. 先焊 4.7kΩ 上拉。
2. 测波形，看上升沿时间。
3. 如果太缓，换 2.2kΩ；如果功耗敏感且速度够，可以保留。

### 2. 时序参数留余量

如果器件 datasheet 要求最小建立时间 100ns：

1. 不要刚好按 100ns 配。
2. 建议留 2-3 倍余量，按 200-300ns 配。
3. 这样温度、电压波动时更稳定。

### 3. 必须加超时保护

```c
uint32_t timeout = 1000;
while (!__HAL_I2C_GET_FLAG(&hi2c1, I2C_FLAG_TXE)) {
    if (--timeout == 0) {
        // 超时，复位 I2C
        HAL_I2C_DeInit(&hi2c1);
        HAL_I2C_Init(&hi2c1);
        return HAL_ERROR;
    }
}
```

没有超时保护的 I2C 代码，上线后迟早卡死。

### 4. 多设备总线要先做地址扫描

```c
void i2c_scan(I2C_HandleTypeDef *hi2c)
{
    for (uint8_t addr = 0x08; addr < 0x78; addr++) {
        uint8_t dev_addr = addr << 1;
        HAL_StatusTypeDef status = HAL_I2C_IsDeviceReady(
            hi2c, dev_addr, 1, 10);
        
        if (status == HAL_OK)
            printf("Found device at 0x%02X\n", addr);
    }
}
```

这样能快速确认：

1. 哪些地址有设备响应。
2. 是否有地址冲突。
3. 总线电气是否可靠。

### 5. 关键通信要验证数据完整性

不要假设"通信成功 = 数据正确"。

建议做法：

1. 读器件 ID 寄存器确认通信对象正确。
2. 写 - 读回验证关键配置。
3. 对校验和敏感的器件要加校验。

## 性能、稳定性、可维护性影响

1. **时序参数设计**：
   - 太紧 → 稳定性差，环境变化时易失败。
   - 太松 → 通信效率低，但不影响可靠性。
   - 建议优先保稳定，再优化速度。

2. **上拉电阻选择**：
   - 直接影响信号完整性和功耗。
   - 多设备总线必须实测波形后调整。

3. **错误处理机制**：
   - 没有超时保护的 I2C 代码是定时炸弹。
   - 通信失败后必须能复位总线状态。

4. **可维护性**：
   - 硬件 I2C 比模拟 I2C 更易维护。
   - 封装良好的驱动层能让上层应用不关心底层细节。

## 面试 / 问答怎么讲

### 30 秒版本

I2C 是用 SDA 和 SCL 两根线实现的主从同步半双工通信。关键点是开漏输出需要上拉电阻、7 位地址 + 读写位、应答机制和时序参数。实际工程里上拉电阻选型、时序参数配置和超时处理比单纯背时序图更重要。

### 3 分钟版本

可以从物理层讲起：I2C 是开漏结构，需要外接上拉电阻；多设备共享总线，靠地址区分。然后讲协议层：起始条件、地址帧、数据帧、应答、停止条件。再结合读写流程说明为什么需要 ReSTART、为什么读操作最后要发 NACK。最后提一下硬件 I2C 和模拟 I2C 的区别，以及常见问题的排查思路。

### 10 分钟版本

可以进一步结合示波器波形展开：先展示正常通信的 SDA、SCL 波形，标出 START、地址、ACK、数据、STOP 各段。然后展示几种典型失败波形：没有 ACK、上升沿太缓、时序参数不满足要求。再说明上拉电阻怎么选、时序参数怎么根据器件 datasheet 配置、超时保护怎么写。最后结合多设备场景说明地址冲突和总线电容问题怎么排查。这种讲法既有理论又有工程实践。

## 实战练习

1. 用逻辑分析仪抓取一次完整的 I2C 读写时序，标出每一段的含义。
2. 故意把上拉电阻换成 10kΩ，观察上升沿变化和通信稳定性。
3. 写一个 I2C 地址扫描函数，扫描总线上所有可能的地址并记录响应设备。
4. 故意把地址配错，观察通信失败时的波形特征。
5. 用 GPIO 模拟 I2C 实现一个简单的 EEPROM 读写驱动，并和硬件 I2C 对比稳定性。
6. 设计一个带超时保护的 I2C 读写封装函数，并测试超时复位是否生效。

## 关键要点

1. I2C 成败不只在协议，更在电气层和时序层。
2. 上拉电阻不是随便选的，要根据总线电容和速度实测调整。
3. 读操作要用 ReSTART 保持原子性，不能中间释放总线。
4. 必须加超时保护，否则总线异常时系统会卡死。
5. 排障时先抓波形，从电气层到协议层逐段验证。
