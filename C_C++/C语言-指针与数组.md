# C语言-指针与数组

## 原始问题

为什么 C 里“数组名像指针、指针也能像数组一样下标访问”这件事总让人越学越乱？到底什么时候它们相同，什么时候完全不是一回事？为什么很多函数参数一旦写成数组，最后看起来又像指针？

## 先给结论

指针与数组是 C 里最容易混淆、也最影响后续代码阅读和排障的一组基础概念。

先记住这几个结论：

1. 指针是“保存地址的变量”，数组是“一整块连续对象”，它们不是同一个东西。
2. 数组名在很多表达式里会退化成指向首元素的指针，所以看起来很像，但数组本身并不会因此变成指针变量。
3. 指针运算的步长由“指向的类型”决定，不是简单按字节乱跳。
4. 把数组传给函数时，函数拿到的通常只是首元素地址，所以元素个数必须额外传入。
5. 真正危险的不是语法不会写，而是分不清对象边界、生命周期和可访问范围，最后导致越界、空指针、悬空指针或错误的 `sizeof` 判断。

如果只能背“数组名是地址”“指针就是数组”这种模糊说法，但讲不清数组退化、函数参数语义、指针运算边界和 `sizeof` 的差异，就还没有真正掌握 C 的指针与数组。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 写函数时不知道为什么 `int arr[]` 和 `int *arr` 在参数位置看起来一样。
2. 经常把 `sizeof(arr)` 和元素个数混为一谈，一进函数就算错长度。
3. 读嵌入式、驱动、协议或库代码时，被各种 `buf`、`ptr`、`*p++`、`arr[i]` 搞混。
4. 不知道为什么有些指针能走、有些一加一就越界，有些地址看着没报错却已经是未定义行为。

它在 AI 时代依然重要，因为 AI 很容易生成“看起来像对的”数组和指针代码，但经常把长度、边界、数组退化和对象生命周期处理错。你越理解这组概念，越能快速看出 AI 生成代码是否只是表面能编译，还是实际可维护、可验证、可排障。

## 核心概念 / 本质机制

### 1. 指针的本质

指针可以先理解成“保存某个对象地址的变量”，但这只是第一层。

更完整地说，它同时包含三层语义：

1. 它保存的是哪个地址。
2. 它声明为指向什么类型。
3. 它当前是否仍然指向一个有效对象。

例如：

```c
int value = 10;
int *p = &value;
```

这里 `p` 不只是“一个数字地址”，它还是“一个指向 `int` 的地址”。这会直接影响：

1. `*p` 按 `int` 解释内存。
2. `p + 1` 会跨过一个 `int` 的大小。
3. 编译器会按 `int *` 做类型检查和警告提示。

### 2. 数组的本质

数组是“一整块连续存放的同类型对象集合”。

例如：

```c
int arr[4] = {1, 2, 3, 4};
```

这里的 `arr` 是 4 个连续 `int` 组成的整体对象，不是一个普通指针变量。

它至少有这几个特征：

1. 大小在这个作用域里是固定可知的。
2. `sizeof(arr)` 得到的是整块数组总字节数。
3. 数组名本身不是左值变量，不能做 `arr = other_ptr` 这种赋值。

### 3. 为什么数组名看起来像指针

这是因为在很多表达式里，数组名会退化成指向首元素的指针。

例如：

```c
int arr[4] = {1, 2, 3, 4};
int *p = arr;
```

这里 `arr` 在赋值表达式里退化成 `&arr[0]`，所以可以赋给 `int *p`。

但要注意，这只是“在这个表达式里发生了退化”，不是说数组从此就等于指针。

最典型的反例是：

```c
sizeof(arr)
```

这里 `arr` 不会退化，得到的是整个数组大小，而不是指针大小。

### 4. 指针下标和数组下标为什么都能用

`arr[i]` 的本质可以理解成：

```c
*(arr + i)
```

所以只要你有一个“指向某类元素的地址”，就能写下标访问。

这也是为什么下面两种写法都能工作：

```c
arr[i]
p[i]
```

因为它们最后都会变成“基地址 + 偏移，再解引用”。

### 5. 指针运算为什么不是按字节乱加

指针运算的步长由它指向的类型决定。

例如：

```c
int *p;
char *c;
```

那么：

1. `p + 1` 表示跳过一个 `int` 的大小。
2. `c + 1` 表示跳过一个 `char` 的大小。

这就是为什么“同一个地址数值变化量”不能脱离类型单独理解。

### 6. 函数参数里的数组为什么最后都像指针

在函数参数位置，这几种写法本质上等价：

```c
void func(int arr[]);
void func(int arr[10]);
void func(int *arr);
```

函数拿到的都只是“首元素地址”，不会自动保留真实数组长度。

所以一进函数，下面这种写法通常就是错的：

```c
sizeof(arr) / sizeof(arr[0])
```

因为这里的 `arr` 已经不是原始数组对象，而是一个指针参数。

### 7. 指针正确与否，本质上是边界和生命周期问题

很多人把指针理解成“难在语法”，但真实工程里更难的是：

1. 它指向的对象还活着吗。
2. 它允许访问到哪里为止。
3. 它是不是空指针。
4. 它是不是已经越过了当前数组边界。

所以很多 bug 的根因不是 `*` 或 `[]` 写错，而是对象边界判断错了。

### 8. 一维数组和二维数组的陷阱不同

二维数组尤其容易误解。

例如：

```c
int matrix[2][3];
```

它退化后更接近“指向含 3 个 `int` 的数组”的指针，也就是：

```c
int (*p)[3] = matrix;
```

而不是：

```c
int **pp;
```

`int **` 和二维数组不是同一个东西，这在函数参数和接口设计里非常关键。

## 数据流 / 控制流 / 时序关系

数组传给函数时，通常会走这样一条主线：

```text
在调用者作用域里定义数组
-> 用 sizeof 计算元素个数
-> 把首元素地址和元素个数一起传给函数
-> 函数通过指针和长度遍历数据
-> 函数返回结果或状态码
-> 调用者继续持有原数组对象
```

这条链路里最容易出错的点有：

1. 调用者忘了传长度。
2. 函数里用 `sizeof` 误判元素个数。
3. 指针为空但函数直接解引用。
4. 遍历上界写错，访问越界。
5. 把局部数组地址返回出去，导致悬空指针。

## 最小可运行示例

下面给一个把数组传入函数、计算总和并做原地缩放的最小示例。

```c
#include <stdio.h>
#include <stddef.h>

static int sum_array(const int *arr, size_t len, int *out_sum)
{
    size_t i;
    int sum = 0;

    if (arr == NULL || out_sum == NULL || len == 0) {
        return -1;
    }

    for (i = 0; i < len; ++i) {
        sum += arr[i];
    }

    *out_sum = sum;
    return 0;
}

static int scale_array(int *arr, size_t len, int factor)
{
    size_t i;

    if (arr == NULL || len == 0) {
        return -1;
    }

    for (i = 0; i < len; ++i) {
        arr[i] *= factor;
    }

    return 0;
}

static void print_array(const int *arr, size_t len)
{
    size_t i;

    for (i = 0; i < len; ++i) {
        printf("%d ", arr[i]);
    }
    printf("\n");
}

int main(void)
{
    int data[] = {1, 2, 3, 4};
    size_t count = sizeof(data) / sizeof(data[0]);
    int sum = 0;

    if (sum_array(data, count, &sum) != 0) {
        fprintf(stderr, "sum_array failed\n");
        return 1;
    }

    printf("sum = %d\n", sum);

    if (scale_array(data, count, 10) != 0) {
        fprintf(stderr, "scale_array failed\n");
        return 1;
    }

    print_array(data, count);
    return 0;
}
```

编译和运行：

```bash
gcc -Wall -Wextra -Werror -std=c11 demo.c -o demo
./demo
```

预期输出：

```text
sum = 10
10 20 30 40
```

## 代码解读

### 1. 为什么元素个数要在调用者侧计算

因为 `data` 在 `main` 里仍然是完整数组对象，`sizeof(data)` 还能得到总字节数。

一旦传进 `sum_array` 或 `scale_array`，形参就只剩首元素地址，原始数组大小信息已经丢了。

### 2. 为什么 `sum_array` 用 `const int *arr`

这是在接口层明确说明“只读输入，不修改数组内容”。

`const` 的价值不只是语法限制，更是在帮助调用者和阅读者理解函数意图。

### 3. 为什么 `scale_array` 能直接修改 `data`

因为传进去的是首元素地址，函数通过这个地址访问的是调用者那块真实数组对象。

这仍然是值传递，只是传进去的值恰好是一个地址。

### 4. 为什么 `len == 0` 也要作为边界检查

空长度在有些接口里可以接受，但必须统一约定。

这里把它当作非法输入处理，是为了让示例里的边界更清晰，避免“传空数组但还以为成功处理了”的歧义。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 计算数组元素个数 | `sizeof(arr) / sizeof(arr[0])` 只在当前作用域的真实数组对象上使用 | 在函数参数里继续这样算 | 形参已经退化成指针 |
| 传数组给函数 | 同时传 `arr` 和 `len` | 只传 `arr`，让函数自己猜长度 | 指针不保存元素个数 |
| 只读访问 | `const int *arr` | 所有函数都收可写指针 | 容易误改输入数据 |
| 指针遍历 | 保证范围在同一数组对象内 | 指针无限加减，只要没崩就继续用 | 越界后属于未定义行为 |
| 二维数组参数 | `void f(int arr[][3])` 或 `void f(int (*arr)[3])` | 直接写成 `int **` | 类型和内存布局都不匹配 |
| 返回结果 | 通过输出参数或返回堆内存 | 返回局部数组地址 | 函数结束后对象已失效 |

## 边界条件与适用范围

1. 数组退化只发生在很多表达式场景里，不是所有地方都会退化，`sizeof` 和一元 `&` 就是常见例外。
2. 指针运算只有在同一数组对象内部或尾后位置才有定义，跨对象乱算地址即使暂时不崩，也不可靠。
3. “数组形参”和“指针形参”在函数参数位置等价，但这不意味着所有数组场景都能用指针完全替代。
4. 二维数组、数组指针、指针数组是三套不同概念，不能用“反正都是地址”糊过去。
5. 这篇笔记主要讲普通对象数组和指针的基础关系，不展开多级指针所有权和复杂动态二维结构。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 数组长度在函数里算错 | 把指针当数组算 `sizeof` | 打印 `sizeof(arr)` 和类型 |
| 程序偶发崩溃 | 指针为空；越界访问；悬空指针 | 看崩溃点，开 AddressSanitizer |
| 二维数组传参编译不过或行为异常 | 把二维数组写成 `int **` | 回到真实声明核对类型 |
| 函数修改结果没生效 | 传的是值而不是地址；或写错解引用 | 检查参数签名和调用方式 |
| 输出偶尔正确偶尔错误 | 局部数组地址被返回；越界破坏内存 | 查生命周期和访问上界 |

### 推荐排查顺序

1. 先确认当前拿到的是“真实数组对象”还是“指针参数”。
2. 再确认长度来自哪里，是否仍然可信。
3. 再确认指针是否为空、是否指向仍然有效的对象。
4. 再确认循环上界和指针运算有没有越过数组边界。
5. 最后再看更复杂的别名、类型转换或多级指针问题。

### 常用验证方式

```bash
gcc -Wall -Wextra -Werror -std=c11 demo.c -o demo
gcc -fsanitize=address -g demo.c -o demo
gdb ./demo
```

这些工具的价值分别是：

1. 编译警告能先帮你发现明显的类型和边界问题。
2. AddressSanitizer 很适合抓越界和 use-after-scope 一类错误。
3. `gdb` 适合看某个指针在崩溃时到底指向哪里。

## 工程落地建议

### 1. 默认把“指针 + 长度”当成一组一起传

在工程代码里，不要只传一个裸指针然后靠注释猜元素个数。

更稳妥的习惯是同时传：

1. 基地址。
2. 元素个数或总字节数。
3. 是否可写。

### 2. 接口命名要表达边界语义

例如：

1. `buf` 更像字节缓冲区。
2. `count` 表示元素个数。
3. `size_bytes` 表示总字节数。
4. `capacity` 表示可容纳上限。

这些命名能明显降低“把字节数当元素个数”的风险。

### 3. 看代码时优先抓三条线

1. 这是不是原始数组对象，还是已经退化后的指针。
2. 长度是如何得到的，是否和数据源保持一致。
3. 当前指针拥有的可访问范围到底到哪里。

## 性能、稳定性、可维护性影响

1. 指针和数组理解不清，往往不会在编译期立即暴露，而是在运行时变成越界、随机值、偶发崩溃和难复现问题。
2. 显式传长度和只读语义，会显著提高接口可维护性，因为调用者不用猜边界规则。
3. 用正确的类型表达二维数组、只读缓冲区和输出参数，比堆更多注释更可靠。
4. 真正高质量的 C 代码，不是“能把指针写过去”，而是让对象边界始终可推理、可验证。

## 面试 / 问答怎么讲

### 30 秒版本

指针是保存地址的变量，数组是一整块连续对象，它们不是同一个东西。数组名在很多表达式里会退化成首元素指针，所以看起来很像，但 `sizeof`、可赋值性和函数参数语义都能看出它们的区别。实际工程里最重要的是别把指针和长度拆开，更别在错误边界上做指针运算。

### 3 分钟版本

可以从 `int data[4]` 和 `int *p = data` 讲起：为什么 `data[i]` 和 `p[i]` 都能用，为什么数组传参后通常只剩首元素地址，所以函数里不能再靠 `sizeof` 算长度。接着补充指针运算按类型步长走、二维数组不是 `int **`、越界和悬空指针本质上是对象边界和生命周期问题，这样主线就很完整。

### 10 分钟版本

可以再结合一个最小示例展开：调用者先在本地用 `sizeof` 算元素个数，再把首元素地址和长度传给函数；函数里用 `const int *` 只读遍历，用 `int *` 原地修改。然后延伸到为什么函数里 `sizeof(arr)` 失效、为什么 `int matrix[2][3]` 不能当 `int **`、如何用 sanitizer 和调试器查数组越界。这种讲法更接近真实工程能力。

## 实战练习

1. 写一个 `find_max(const int *arr, size_t len, int *out_max)`，要求保留完整参数检查。
2. 故意在函数参数里用 `sizeof(arr) / sizeof(arr[0])` 算长度，观察结果为什么不对。
3. 写一个二维数组求和函数，分别尝试 `int arr[][3]` 和 `int **`，解释为什么后一种不适合真实二维数组。
4. 写一个返回局部数组地址的错误示例，再解释它为什么属于生命周期错误。
5. 用 AddressSanitizer 运行一个故意越界的数组程序，观察报错并总结定位路径。

## 关键要点

1. 指针是地址变量，数组是连续对象，它们不是同一个东西。
2. 数组名在很多表达式里会退化成首元素指针，但 `sizeof` 等场景仍能看出差异。
3. 指针运算按元素类型步长前进，不是简单按字节乱加。
4. 数组传给函数后通常只剩首元素地址，所以长度必须额外传入。
5. 指针问题的本质通常不是语法，而是边界、生命周期和对象有效性。
6. 二维数组、数组指针、指针数组必须分开理解，不能一概而论。
