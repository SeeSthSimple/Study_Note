# C与C++-并发基础

## 原始问题

为什么嵌入式代码里经常出现"逻辑看起来对，但偶发性失效"的问题？为什么中断里改一个标志位，主循环就突然不响应了？为什么加了锁还是死锁或数据不一致？并发到底在C和C++里怎么理解，什么时候该用它，什么时候该避开它？

## 先给结论

并发最核心的问题不是"能不能同时跑"，而是"多个控制流访问同一个资源时，顺序和可见性能不能被控制住"：

1. 竞态条件是并发bug的根因，本质是"多个执行流对同一个共享资源的访问时序不确定"。
2. 互斥锁、原子操作、信号量都是解决竞态的工具，但每种都有适用边界和代价。
3. 死锁往往是锁顺序或锁范围错误导致的，比"数据竞争"更难排查。
4. 嵌入式里"中断与主循环"的配合，是裸机环境下最常见的并发问题来源。
5. C++的线程库和原子操作是比pthread更现代的选择，但并发问题的本质跟语言无关。

如果只能背"并发就是同时做几件事"，但讲不清竞态、临界区、原子性、可见性和死锁，就还没有真正掌握并发。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 代码加了锁但数据还是乱，不知道是锁粒度问题还是锁使用方式问题。
2. 中断里改了标志位，主循环却看不到变化，不确定是编译器优化还是硬件问题。
3. 多线程程序偶发崩溃或死锁，但每次复现路径都不一样。
4. 不知道什么时候该用互斥锁、什么时候该用原子变量、什么时候该用信号量。
5. 面试时能讲出"线程安全""竞态条件"这些词，但不知道怎么在实际代码里分析和设计。

它在AI时代依然重要，因为AI生成的嵌入式代码和驱动代码里，并发边界经常被忽略或处理错误。你越理解并发模型，越能判断AI生成代码是否在"并发安全"和"性能"之间做了合理取舍。

## 核心概念 / 本质机制

### 1. 并发的本质

并发指的是"多个控制流在同一时间段内交替执行"。

在单核CPU上，这是通过时间片轮转实现的；在多核CPU上，才是真正的并行执行。无论哪种情况，核心问题都是：**多个执行流可能同时访问同一个资源**。

嵌入式里常见的并发来源：

1. 主循环 + 多个中断服务程序
2. 多任务RTOS里的多个线程
3. 多核处理器上的多个核心

### 2. 竞态条件

竞态条件（Race Condition）是并发编程里最核心的问题。

它的定义是：多个执行流对共享资源的访问顺序依赖于执行时序，而这种时序依赖会导致结果不确定。

最经典的例子是两个线程同时执行 `counter++`：

```c
// 线程A和线程B各自执行 counter++
counter = counter + 1;
```

表面上看这是一个简单操作，但实际CPU执行时它分解为三步：

1. 读取 counter 当前值到寄存器
2. 寄存器值加 1
3. 写回 counter

如果两个线程的时序如下：

```text
线程A: 读(0) -> 加1 -> 写(1)
线程B:      读(1) -> 加1 -> 写(2)  // 正确
```

但也可能是：

```text
线程A: 读(0) -> 加1
线程B: 读(0) -> 加1 -> 写(1)
线程A:                       写(1)  // 覆盖了B的结果
```

两次 `counter++` 结果应该是2，但实际得到1。这就是竞态条件。

### 3. 临界区

临界区是访问共享资源的代码段，这个资源一次只能被一个执行流使用。

互斥锁、信号量、原子操作都是保护临界区的手段。

关键设计原则是：**把共享资源的访问尽可能缩小到最小临界区**，这样能减少锁竞争，提高并发性能。

### 4. 原子操作

原子操作是不可分割的操作，在执行过程中不会被其他线程或中断插入。

C++11 引入了标准原子类型：

```cpp
#include <atomic>

std::atomic<int> counter{0};
counter.fetch_add(1);  // 原子加1
```

对于简单的计数器、标志位，原子操作比互斥锁更轻量。

但要注意：

1. 原子操作不等于"安全" —— 需要先分析是不是所有共享访问都能用原子覆盖。
2. 原子操作也有"边界"，比如 `atomic<int>` 的递增是原子的，但"读取后判断再操作"不是原子的。

### 5. 互斥锁

互斥锁（Mutex）用于保护临界区，核心语义是：

1. 加锁后，其他试图加锁的线程会阻塞。
2. 解锁后，阻塞的线程之一获得锁。
3. 同一线程不能重复加锁（取决于实现），否则会死锁。

C++ 示例：

```cpp
#include <mutex>

std::mutex mtx;
int shared_data = 0;

void safe_increment() {
    std::lock_guard<std::mutex> lock(mtx);
    ++shared_data;  // 临界区
}
```

`std::lock_guard` 是 RAII 风格的锁管理，构造时加锁，析构时自动解锁。这能防止"加锁后忘记解锁"或"异常路径导致锁无法释放"。

### 6. 可见性问题

可见性是并发里特别容易被忽略的问题。

典型场景：

```c
volatile bool flag = false;

// 中断服务程序
void ISR(void) {
    flag = true;
}

// 主循环
while (!flag) {
    // 等待
}
```

这里 `flag` 变了，但主循环可能看不到，因为：

1. 编译器优化：可能把 `while(!flag)` 优化成只读一次寄存器。
2. CPU缓存：flag 可能还在缓存里，没刷到主存。
3. CPU重排：指令执行顺序可能跟代码顺序不一致。

解决方案：

1. `volatile`：告诉编译器"每次都要从内存读，不要优化"
2. 内存屏障（Memory Barrier）：强制刷新CPU缓存和指令顺序
3. C++11 原子类型：默认包含必要的内存序保证

### 7. 死锁

死锁是并发编程里最让人头疼的问题之一。

它通常有四个必要条件（Coffman 条件）：

1. 互斥：资源一次只能被一个执行流使用
2. 占有并等待：已经持有资源的执行流还在等待其他资源
3. 不可抢占：资源不能被强制剥夺
4. 循环等待：形成环形依赖链

常见死锁模式：

```c
// 线程A
lock(&mutex1);
lock(&mutex2);  // 等待B释放mutex2

// 线程B
lock(&mutex2);
lock(&mutex1);  // 等待A释放mutex1
```

死锁的排查难点在于：很多死锁不是100%复现，跟调度时序有关。

### 8. 嵌入式里的中断与主循环并发

这是嵌入式里最特殊的并发模型。

在裸机环境里，主要控制流是主循环（main loop），中断服务程序（ISR）会在任意时刻打断它。

典型共享场景：

```c
volatile bool data_ready = false;
uint32_t sensor_data = 0;

// 中断服务程序
void UART_ISR(void) {
    sensor_data = UART->DR;  // 读取数据
    data_ready = true;       // 置标志
}

// 主循环
int main(void) {
    while (1) {
        if (data_ready) {
            process(sensor_data);  // 使用数据
            data_ready = false;    // 清除标志
        }
    }
}
```

这个例子里有几个典型的并发边界：

1. `data_ready` 和 `sensor_data` 都不是原子变量，但它们之间有因果关系。
2. `data_ready = false` 写在主循环里，但如果中断在"判断后、清标志前"发生，标志会被覆盖。
3. 更好的做法是用原子操作或关中断来保护这个标志位。

### 9. C 风格的关中断保护

在裸机嵌入式里，最常用的同步手段不是互斥锁，而是关中断：

```c
uint32_t critical_enter(void) {
    uint32_t primask = __get_PRIMASK();
    __disable_irq();
    return primask;
}

void critical_exit(uint32_t primask) {
    __set_PRIMASK(primask);
}

// 使用
uint32_t mask = critical_enter();
shared_flag = true;
shared_value = 42;
critical_exit(mask);
```

关中断的特点：

1. 简单直接，不需要操作系统支持。
2. 保证原子性，因为中断被禁止了。
3. 但会影响实时性，关中断时间必须尽可能短。
4. 不能在关中断期间做耗时操作或调用可能阻塞的函数。

## 数据流 / 控制流 / 时序关系

并发问题的数据流和普通顺序代码完全不同：

```text
普通顺序代码:
  A -> B -> C -> D（每一步结果直接影响下一步）

并发代码:
  线程A: A1 -> A2 -> A3
  线程B:      B1 -> B2 -> B3
  结果依赖于 A1、A2、A3 和 B1、B2、B3 的交错顺序
```

理解这一点至关重要：**并发下的执行结果不是唯一确定的，而是取决于时序**。

这意味着：

1. 并发代码很难通过"多次运行看起来对"来证明正确性。
2. 必须从设计层面保证"无论时序如何交错，结果都是正确的"。
3. 这叫做"线程安全"或"并发安全"。

## 最小可运行示例

### C++ 多线程计数器示例

```cpp
#include <atomic>
#include <iostream>
#include <thread>
#include <vector>

std::atomic<int> counter{0};
const int ITERATIONS = 100000;

void increment(void) {
    for (int i = 0; i < ITERATIONS; ++i) {
        counter.fetch_add(1, std::memory_order_relaxed);
    }
}

int main(void) {
    const int num_threads = 4;
    std::vector<std::thread> threads;

    for (int i = 0; i < num_threads; ++i) {
        threads.emplace_back(increment);
    }

    for (auto &t : threads) {
        t.join();
    }

    std::cout << "counter = " << counter.load() << "\n";
    std::cout << "expected = " << num_threads * ITERATIONS << "\n";

    return 0;
}
```

编译和运行：

```bash
g++ -std=c++17 -pthread demo.cpp -o demo
./demo
```

预期输出（每次都应该一致）：

```text
counter = 400000
expected = 400000
```

如果把 `fetch_add` 换成普通 `++counter`，结果通常会小于 400000，因为存在数据竞争。

### C 风格中断与主循环示例

```c
#include <stdio.h>
#include <stdint.h>
#include <stdbool.h>

volatile bool data_ready = false;
volatile uint32_t shared_value = 0;

void simulate_isr(void) {
    shared_value = 42;
    data_ready = true;
}

int main(void) {
    simulate_isr();

    for (int i = 0; i < 10; ++i) {
        if (data_ready) {
            printf("value = %u\n", shared_value);
            data_ready = false;
            break;
        }
    }

    return 0;
}
```

这个示例演示了中断与主循环的配合模式，以及为什么 `volatile` 是必要的。

## 代码解读

### 1. 为什么 `std::atomic` 比普通变量更适合计数器

因为 `fetch_add` 保证"读取-修改-写回"是原子完成的，不会被其他线程的操作插断。

普通 `++counter` 在汇编层面是三条独立指令，多核环境下可以被其他线程插断。

### 2. 为什么 `volatile bool` 在嵌入式例子里是必要的

`volatile` 的作用是强制编译器每次都从内存读取，而不是使用寄存器中的缓存值。

在嵌入式例子里，如果没有 `volatile`，编译器可能把"读取 `data_ready`"优化成只读一次，然后进入死循环。

### 3. 为什么 `std::lock_guard` 更安全

它的构造和析构自动配对，不会出现"加锁后忘记解锁"或"异常路径跳过解锁"的问题。

这跟 RAII 管理文件句柄、内存的思路是一致的。

### 4. 什么是 `memory_order_relaxed`

这是 C++11 原子操作的一种内存序选项：

1. `memory_order_relaxed`：只保证原子性，不保证顺序。性能最高，但需要你自己确保不依赖顺序。
2. `memory_order_seq_cst`（默认）：完全顺序一致性，最安全但性能最低。

对于简单计数器，`relaxed` 通常够用；但如果你的代码依赖于"先读A再读B"这样的顺序，就不能用 `relaxed`。

### 5. 为什么关中断时间必须尽可能短

因为关中断期间，所有中断都被屏蔽，系统无法响应外部事件。如果关中断时间过长：

1. 可能丢失中断事件。
2. 影响实时性，违反时序约束。
3. 看门狗可能超时复位。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 多线程计数器 | `std::atomic<int>` 或互斥锁 | 普通 `int` 加 `++` | 非原子操作存在数据竞争 |
| 中断与主循环共享标志 | `volatile bool` 或原子变量 | 普通 `bool` | 编译器优化导致可见性问题 |
| 保护临界区 | `std::lock_guard<std::mutex>` | 只加锁不解锁，或忘记加锁 | 可能导致死锁或数据竞争 |
| 多把锁时 | 固定加锁顺序，所有线程一致 | 不同线程用不同顺序 | 容易形成循环等待导致死锁 |
| 原子变量组合使用 | 确认每一步都是原子 | 读后判断再操作 | "读-判断-写"本身不是原子 |
| 嵌入式临界区 | 关中断保护，时间尽可能短 | 关中断后做耗时操作 | 影响实时性，可能丢失中断 |
| 共享指针 | `std::atomic<std::shared_ptr<T>>` 或 `std::shared_ptr` + 锁 | 裸 `T*` 无保护 | 指针本身读写不是原子 |
| 避免死锁 | 用 RAII 锁管理，缩小临界区 | 在临界区里调用未知代码 | 可能导致锁二次获取或死锁 |

## 边界条件与适用范围

1. 原子操作不是万能的，只适合"单个变量的原子读写"场景。
2. 互斥锁不适合非常高频繁的共享访问，会成为性能瓶颈。
3. 嵌入式中断上下文里不能使用会导致阻塞的操作（如 `std::mutex`）。
4. `volatile` 不等于线程安全，它只解决编译器优化问题，不解决CPU缓存和指令重排问题。
5. 死锁不是"每次都出现"，偶发性死锁更难排查。
6. 并发代码的测试和验证比普通代码更复杂，不能只靠"多跑几次看看"。
7. RTOS 里的信号量和互斥量语义不同：信号量可以用于同步和资源计数，互斥量用于互斥且支持优先级继承。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 数据偶发不一致 | 存在数据竞争，缺少保护 | 加锁或改用原子操作，用 ThreadSanitizer |
| 标志位变了却看不到 | 编译器优化或CPU缓存问题 | 加 `volatile` 或用原子变量 |
| 加了锁还是出问题 | 锁粒度太大，或锁保护范围不对 | 分析临界区是否覆盖了所有共享访问 |
| 偶发死锁 | 锁顺序问题、多线程都等待对方 | 查加锁顺序、减少持锁时间、检查递归锁 |
| 程序hang住 | 死锁或所有线程都在等某个条件 | 看线程栈、查锁状态 |
| 性能急剧下降 | 锁竞争严重、临界区太大 | 缩小临界区、减少锁粒度、改用原子操作 |
| 中断丢失 | 关中断时间过长 | 缩短关中断区间，避免在临界区内做耗时操作 |

### 推荐排查顺序

1. 先确认是"数据不一致"还是"死锁"还是"性能问题"。
2. 如果是数据不一致，再确认哪些变量是共享的，是否都有适当保护。
3. 如果用了锁，确认锁是否覆盖了所有需要保护的路径。
4. 如果用原子操作，确认是否所有访问都是原子的，没有"读-判断-写"这样的复合操作。
5. 如果是死锁，查加锁顺序、是否有递归锁、持锁时间是否过长。
6. 最后考虑内存序问题（较罕见，但确实存在）。

### 常用验证方式

```bash
g++ -std=c++17 -pthread -fsanitize=thread demo.cpp -o demo
g++ -std=c++17 -pthread demo.cpp -o demo
```

ThreadSanitizer 能检测出数据竞争和死锁，是并发代码验证的重要工具。

## 工程落地建议

### 1. 先考虑"要不要用并发"

并发是为了解决真实需求，不是为了"让代码看起来更高效"。

需要并发的典型场景：

1. 同时处理多个外设事件（嵌入式）
2. 提升CPU密集任务的吞吐量（多核）
3. 分离关注点，比如同时做通信和计算

不需要并发的场景：

1. 单核CPU、事件串行处理就够了
2. 简单状态机，单线程就够了
3. 性能瓶颈不在并发而在算法本身

### 2. 共享数据的设计原则

1. 尽量减少共享数据：能用局部变量的就不用共享，能用消息传递的就不用共享内存。
2. 必须共享时，优先用原子操作。
3. 复杂共享用互斥锁，但要把临界区尽可能缩小。
4. 给锁约定一个命名规范或强制规则（比如 "mtx_" 前缀）。

### 3. 嵌入式中断与主循环的设计原则

1. ISR 里只做"置标志"和"读取数据"，不做复杂处理。
2. 主循环轮询标志位，收到标志后做具体处理。
3. 如果标志和数据需要组合使用，考虑用原子操作或关中断保护。
4. 避免在 ISR 里调用可能阻塞的代码。

### 4. 多线程程序的设计原则

1. 线程数量不是越多越好，通常跟 CPU 核数相关。
2. 线程间通信优先用消息队列、管道等结构化方式。
3. 共享数据访问路径要尽量少且清晰。
4. 用 RAII 管理锁，别手工加锁解锁。

### 5. 死锁预防策略

1. 固定加锁顺序：所有线程按同一顺序获取多把锁。
2. 缩小临界区：持锁时间越短，死锁概率越低。
3. 避免嵌套锁：尽量不要在持锁状态下再获取另一把锁。
4. 使用 `std::scoped_lock` 同时获取多把锁，避免部分获取。

## 性能、稳定性、可维护性影响

1. 并发代码的性能收益主要来自多核并行，但锁竞争和同步开销会抵消这部分收益。
2. 并发代码的稳定性高度依赖设计正确性，"看起来对"不等于"并发安全"。
3. 并发代码的维护成本通常高于普通代码，因为时序相关bug更难复现和定位。
4. 过度并发的代码，线程数量多、锁关系复杂，维护难度会急剧上升。
5. 真正好的并发设计，是让共享尽可能少、临界区尽可能小、锁尽可能短。

## 面试 / 问答怎么讲

### 30 秒版本

并发编程的核心问题是竞态条件，本质是多个执行流对同一个共享资源的访问时序不确定。解决方案包括原子操作、互斥锁、信号量等，但每种都有适用边界和性能代价。嵌入式里最常见的是中断与主循环的配合，需要注意可见性问题。

### 3 分钟版本

可以从竞态条件讲起：两个线程同时对同一个计数器执行 `++`，为什么结果会小于正确值。然后解释为什么需要原子操作或互斥锁来保护临界区。再补充可见性问题（编译器优化、CPU缓存、指令重排），以及 `volatile` 和内存屏障的作用。最后说明死锁的四个条件和常见死锁模式，以及嵌入式中关中断保护的使用方式。

### 10 分钟版本

可以结合一个嵌入式实际案例展开：主循环和中断共享一个标志位和数据，为什么需要 `volatile` 或原子变量。再扩展到多线程场景，分析多把锁时的死锁风险、如何用固定加锁顺序避免。然后说明 C++ 的 `std::atomic`、`std::mutex`、`std::lock_guard` 各自的适用场景，以及如何用 ThreadSanitizer 和锁分析工具验证并发安全性。最后讨论如何通过缩小临界区、减少锁粒度来提升性能。

## 实战练习

1. 用 `std::atomic` 实现一个多线程安全的消息队列，生产者和消费者各在独立线程。
2. 用 `std::mutex` 保护一个共享链表，实现插入和删除操作。
3. 写一个嵌入式场景：中断设置标志，主循环轮询处理，注意可见性问题。
4. 故意制造一个死锁：两把锁不同顺序加锁，然后用 ThreadSanitizer 检测出来。
5. 把一个"读-判断-写"复合操作改成真正的原子操作，观察 ThreadSanitizer 的输出变化。
6. 在裸机代码里用关中断保护一段共享数据操作，测量关中断时间。

## 关键要点

1. 并发问题的本质不是"同时执行"，而是"共享资源访问的时序不确定"。
2. 竞态条件是并发bug的根因，数据竞争是竞态的特殊形式。
3. 互斥锁、原子操作、信号量是三种主要同步手段，各有适用场景。
4. `volatile` 不等于线程安全，它只解决编译器优化问题。
5. 死锁比数据竞争更难排查，因为它不100%复现。
6. 嵌入式里"中断与主循环"是最常见的并发模型，需要注意标志位和数据的可见性。
7. 关中断是裸机环境下最常用的同步手段，但关中断时间必须尽可能短。
8. 并发代码的设计原则是：尽量减少共享，尽量缩小临界区，尽量缩短持锁时间。
