# C与C++-接口设计与错误处理

## 原始问题

为什么很多代码明明功能能跑，但一到多人协作、长期维护或异常输入就变得很脆弱？接口设计和错误处理到底应该怎么做，才能让模块不仅“能用”，还“好用、稳用、好查错”？

## 先给结论

真正能撑起工程项目的，不只是算法和语法，而是接口边界和失败边界：

1. 好接口要把输入、输出、所有权、约束和错误语义说清楚。
2. 错误处理要先保证状态一致和资源正确，再考虑如何上报。
3. C 项目通常更依赖返回码和显式 out 参数，C++ 则要结合值语义、异常和 RAII 做取舍。
4. 默认“静默失败”“返回魔法值”“出错还偷偷改半截状态”都是高风险设计。

最重要的工程结论是：

1. 参数校验、返回值检查和不变量维护是接口质量底线。
2. 接口要尽量让错误难以发生，让误用更容易被发现。
3. 错误上报方式要和调用场景匹配，不要把热路径、初始化路径和致命错误混成一种处理方式。
4. 日志、断言和错误码不是互斥关系，而是不同层级的工具。

如果只能背“接口要清晰”“要检查返回值”，但讲不清所有权、错误分层、参数约束和状态一致性，就还没有真正掌握这个主题。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 模块能跑，但调用者一旦传错参数就崩，或者错误很难定位。
2. 不知道该返回 `bool`、错误码、空指针，还是直接抛异常。
3. 函数失败后对象状态变得半新半旧，后续 bug 越来越难查。
4. 面试或工作中需要讲“怎么设计可维护 API”，但没有稳定判断标准。

它在 AI 时代依然重要，因为 AI 生成接口很快，但往往默认 happy path，忽略参数边界、错误语义和长期演进。真正可靠的系统，很多时候赢在接口收口，而不是算法花哨。

## 核心概念 / 本质机制

### 1. 好接口到底要说清什么

一个可维护接口，至少要让调用方明确知道：

1. 这个函数或类解决什么问题。
2. 输入参数是否合法，哪些可以为空，哪些不能。
3. 输出通过什么返回，成功和失败各意味着什么。
4. 谁拥有传入和传出的资源。
5. 失败后对象或模块会处于什么状态。

### 2. 错误处理的核心不是“怎么报”，而是“失败后系统还稳不稳”

很多人一提错误处理就只想返回值或异常，但真正关键的是：

1. 出错后资源有没有泄漏。
2. 状态有没有被改坏。
3. 调用者能不能继续安全使用对象或模块。

### 3. C 和 C++ 常见错误处理风格有什么差异

C 里更常见：

1. 返回状态码
2. 用 out 参数返回结果
3. 用日志补充现场

C++ 里常见两类：

1. 热路径或底层组件用状态值、`bool`、错误码等显式返回
2. 构造、配置加载、不可忽略失败场景，有时会结合异常和 RAII

关键不是教条站队，而是让错误语义和调用成本匹配。

### 4. 断言、日志、错误码分别适合什么

可以先这样区分：

1. 断言更适合开发期检查“本不该被违反”的内部不变量。
2. 错误码更适合预期内、需要调用者处理的失败。
3. 日志更适合保留现场和排障，不应替代返回语义。

### 5. 为什么接口要尽量“让误用更难发生”

稳定接口不是靠文档祈祷调用者不犯错，而是靠设计减少误用空间，例如：

1. 长度和指针成对出现。
2. 输入只读就用 `const`。
3. 返回值需要检查就加 `[[nodiscard]]` 或在文档里明确要求。
4. 一个函数不要同时承担太多职责。

## 数据流 / 控制流 / 时序关系

良好接口的典型调用链应尽量是：

```text
调用方准备输入
-> 接口做边界校验
-> 内部逻辑执行
-> 成功时返回结果并保持状态一致
-> 失败时返回明确错误并保持资源和状态可控
-> 调用方根据错误语义决定重试、回退或上报
```

这条链的核心不是“失败了告诉你一下”，而是“失败后系统仍然收得住”。

## 最小可运行示例

```c
#include <stddef.h>
#include <stdint.h>

typedef enum {
    FRAME_OK = 0,
    FRAME_EINVAL = -1,
    FRAME_ESHORT = -2,
    FRAME_ECHECK = -3
} FrameStatus;

typedef struct {
    const uint8_t *data;
    size_t len;
} ByteView;

typedef struct {
    uint8_t id;
    uint8_t value;
} Frame;

static FrameStatus frame_parse(ByteView input, Frame *out_frame)
{
    if (input.data == NULL || out_frame == NULL) {
        return FRAME_EINVAL;
    }

    if (input.len < 3) {
        return FRAME_ESHORT;
    }

    if ((uint8_t)(input.data[0] + input.data[1]) != input.data[2]) {
        return FRAME_ECHECK;
    }

    out_frame->id = input.data[0];
    out_frame->value = input.data[1];
    return FRAME_OK;
}
```

这个例子的重点不是协议本身，而是接口风格：

1. 输入和输出边界清晰。
2. 错误类型可区分。
3. 失败时不会把 `out_frame` 写成半截有效状态。

## 代码解读

### 1. 为什么先做参数校验

因为边界校验是接口第一道门。没有参数校验，很多错误会直接升级成崩溃或未定义行为。

### 2. 为什么返回错误码而不是 `bool`

因为这里失败原因有多种：参数非法、长度不够、校验失败。用错误码能让调用方做更细粒度处理。

### 3. 为什么在所有校验通过前不写 `out_frame`

这样能避免失败后输出对象处于半更新状态，这属于最基础的状态一致性设计。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 输入校验 | 一开始就检查空指针、长度和状态 | 直接默认输入合法 | 错误会升级成崩溃或脏数据 |
| 错误语义 | 可区分不同失败原因 | 统一返回 `-1` 或 `false` | 调用方无法有效处理 |
| 输出状态 | 成功前不写半截结果 | 失败时已部分修改输出对象 | 后续状态难以推理 |
| 所有权表达 | 写清谁申请、谁释放、谁借用 | 资源归属靠默契 | 泄漏和重复释放风险高 |
| 日志策略 | 用日志补现场，用返回语义表达失败 | 只打印日志不返回错误 | 调用方无法自动处理 |

## 边界条件与适用范围

1. 不是所有接口都要暴露非常细的错误码，但至少要让调用者区分“可以重试”和“输入本身有问题”。
2. 底层热路径不一定适合大量异常和重型错误对象，要考虑调用开销。
3. 断言更适合内部开发期不变量，不应替代用户输入校验。
4. C++ 是否用异常，要看团队风格、场景和边界，而不是只看语言支持。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 函数失败但外部状态也乱了 | 先改状态后校验 | 检查失败路径是否半更新 |
| 调用者总是误用接口 | 参数语义不清、命名含糊 | 回看函数签名和注释是否足够明确 |
| 排障困难 | 只有日志没有返回语义，或只有返回码没有日志 | 同时梳理调用链和现场信息 |
| 资源管理混乱 | 所有权没写清楚 | 检查申请、借用、释放边界 |

## 工程落地建议

### 1. 设计接口时默认检查这五件事

1. 输入是否合法
2. 输出如何表达
3. 谁拥有资源
4. 失败后状态如何保证
5. 调用者拿到错误后该怎么处理

### 2. 错误处理要分层

可以粗分为：

1. 参数或输入错误
2. 资源不足
3. 外部依赖失败
4. 逻辑不变量被破坏

不同层级，处理策略通常不同。

### 3. 给关键返回值加“必须看”的约束

在 C++ 里可以考虑 `[[nodiscard]]`，在 C 里至少要通过命名、文档和代码评审强调返回值不能忽略。

## 性能、稳定性、可维护性影响

1. 接口清晰，往往比局部微优化更能降低长期维护成本。
2. 错误语义设计得越好，排障速度越快，调用者误用概率越低。
3. 真正成熟的工程，不是“永不失败”，而是“失败时状态仍然受控，且能快速定位”。

## 面试 / 问答怎么讲

### 30 秒版本

接口设计和错误处理的核心，是把输入、输出、所有权和失败语义说清楚。好接口不仅让 happy path 顺，还能让误用更难发生、让失败更容易定位。C 常用返回码加 out 参数，C++ 则结合值语义、RAII 和场景选择异常或显式错误返回。

### 3 分钟版本

可以先讲一个解析接口例子：先校验参数和长度，再执行业务逻辑，成功才写输出，失败返回可区分错误码。然后补充所有权、日志、断言和状态一致性设计。最后说明错误处理不只是“怎么报错”，更关键是“失败后对象和资源是否仍然可控”。

### 10 分钟版本

可以进一步结合项目经验展开：哪些接口适合 `bool`，哪些适合错误码，哪些更适合异常；如何用 `const`、长度参数、`[[nodiscard]]` 和 RAII 减少误用；为什么很多线上问题本质上不是算法错，而是接口边界和失败边界没设计好。这样会更接近工程能力。

## 实战练习

1. 给一个现有 C 函数补上参数校验和明确错误码。
2. 把一个“失败时写半截结果”的接口改成“先校验、后提交”。
3. 为一个 C++ 类整理所有权边界，说明哪些方法失败时是否抛异常。
4. 给一个日志模块设计错误分层：参数错误、IO 失败、内部不变量失败。

## 关键要点

1. 好接口要把输入、输出、所有权和失败语义讲清楚。
2. 错误处理首先关心资源和状态是否仍然受控。
3. 返回值、日志、断言各自有分工，不应互相替代。
4. 接口设计应尽量让误用更难发生。
5. 独立做工程项目，接口能力和错误处理能力跟语法能力同样重要。
