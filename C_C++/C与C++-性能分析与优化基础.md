# C与C++-性能分析与优化基础

## 原始问题

为什么嵌入式代码经常"功能对了但性能不够"？为什么同样的算法，有人写得快有人写得慢？性能优化到底该从哪里入手，怎么测量，怎么验证，怎么避免"优化了半天反而更慢"？

## 先给结论

性能优化的核心不是"到处加 inline 和查表"，而是"先测量，再定位，再优化，再验证"：

1. 优化的前提是"有测量数据证明这里确实是瓶颈"，而不是"我觉得这里慢"。
2. 性能瓶颈通常集中在极少数代码路径，找到它们比盲目优化更有效。
3. 嵌入式里最常见的瓶颈不是算法复杂度，而是内存访问模式、缓存利用和中断延迟。
4. 优化后必须验证正确性，因为很多优化手段会改变代码语义。
5. 优化的收益要跟可维护性权衡，"快但看不懂"的代码长期成本更高。

如果只能背"用查表替代计算""加 volatile 防优化"，但讲不清测量方法、瓶颈定位和优化验证，就还没有真正掌握性能优化。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 代码功能正确但性能不达标，不知道瓶颈在哪里。
2. 凭感觉优化，改了半天没效果甚至更慢。
3. 不知道嵌入式里有哪些常见优化手段和各自的适用场景。
4. 优化后代码行为变了，引入了新 bug。
5. 面试时被问"你怎么做性能优化"，只能说"少用循环、多用查表"。

它在AI时代依然重要，因为AI生成代码时倾向于"可读性优先"，经常忽略嵌入式场景下的性能约束。你越理解性能分析和优化，越能判断AI给的代码是否满足实时性和资源约束，以及哪些地方需要手动优化。

## 核心概念 / 本质机制

### 1. 性能优化的正确顺序

```text
1. 先让代码正确
2. 再测量性能
3. 再定位瓶颈
4. 再针对性优化
5. 再验证优化效果和正确性
```

跳过任何一步都可能导致：

1. 优化了不需要优化的地方。
2. 优化引入了新 bug。
3. 优化后性能反而下降。

### 2. 性能测量的基本方法

#### 方法1：计时器测量

嵌入式里最直接的测量方式是用硬件定时器或系统时钟：

```c
#include <stdint.h>

uint32_t start = get_cycle_count();
function_to_measure();
uint32_t elapsed = get_cycle_count() - start;
```

注意事项：

1. 测量开销本身要小，否则影响结果。
2. 多次测量取中位数，排除异常值。
3. 关中断测量可以排除中断干扰，但会影响系统行为。

#### 方法2：性能计数器

很多 MCU 提供硬件性能计数器：

1. ARM Cortex-M 的 DWT（Data Watchpoint and Trace）可以计数周期。
2. 可以统计缓存未命中、分支预测失败等事件。
3. 比简单计时器提供更细粒度的信息。

```c
/* 启用 DWT 周期计数器 */
CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
DWT->CYCCNT = 0;
DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;

uint32_t start = DWT->CYCCNT;
function_to_measure();
uint32_t cycles = DWT->CYCCNT - start;
```

#### 方法3：逻辑分析仪 / 示波器

在引脚上翻转电平，用示波器测量时间：

```c
GPIO_SetBits(GPIOA, GPIO_Pin_0);  // 拉高
function_to_measure();
GPIO_ResetBits(GPIOA, GPIO_Pin_0);  // 拉低
```

优点：

1. 不占用 CPU 资源。
2. 可以精确到纳秒级。
3. 不影响被测代码的执行。

#### 方法4：主机端 Profiling

在开发机上用工具分析：

1. `perf`：Linux 下的性能分析工具。
2. `gprof`：GCC 自带的 profiling 工具。
3. `Valgrind / Callgrind`：详细的缓存和分支分析。
4. `perf stat`：统计硬件事件（缓存未命中、分支预测失败等）。

### 3. 常见性能瓶颈

#### 瓶颈1：内存访问模式

CPU 速度远快于内存，缓存未命中是最大的性能杀手：

1. 顺序访问比随机访问快（缓存预取）。
2. 连续内存布局比链式布局快（缓存行命中）。
3. 小数据结构比大数据结构快（一个缓存行装得下）。

#### 瓶颈2：分支预测失败

条件分支如果预测失败，CPU 需要刷新流水线：

1. `if-else` 链太长时，分支预测失败率高。
2. 数据依赖的分支（如 `if (arr[i] > threshold)`）比固定模式分支更难预测。
3. 在极端性能路径上，可以用无分支写法替代。

#### 瓶颈3：函数调用开销

函数调用本身有开销（保存寄存器、跳转、返回）：

1. 频繁调用小函数时，开销占比大。
2. `inline` 可以消除调用开销，但会增加代码体积。
3. 嵌入式里 `-Os`（优化代码体积）可能比 `-O2`（优化速度）更合适，因为缓存未命中的代价更大。

#### 瓶颈4：中断延迟

中断处理的开销包括：

1. 保存和恢复上下文。
2. 中断嵌套。
3. 中断里做了太多事情。

优化方向：

1. ISR 里只做最少工作（读数据、置标志）。
2. 主循环做复杂处理。
3. 用 DMA 替代中断驱动的数据搬运。

### 4. 嵌入式常见优化手段

#### 手段1：查表替代计算

把运行时计算替换为预计算好的查找表：

```c
// 计算方式
int factorial(int n) {
    int result = 1;
    for (int i = 2; i <= n; ++i) {
        result *= i;
    }
    return result;
}

// 查表方式
static const int factorial_table[] = {1, 1, 2, 6, 24, 120, 720, 5040};
int factorial_fast(int n) {
    if (n < 0 || n >= 8) return -1;
    return factorial_table[n];
}
```

适用场景：

1. 输入范围有限且已知。
2. 计算结果固定不变。
3. 计算量远大于一次内存访问。

代价：

1. 占用 Flash 空间。
2. 输入范围变化时需要更新表。

#### 手段2：减少分支

用算术运算替代条件分支：

```c
// 有分支
int clamp(int value, int min_val, int max_val) {
    if (value < min_val) return min_val;
    if (value > max_val) return max_val;
    return value;
}

// 无分支（利用条件移动或位运算）
int clamp_branchless(int value, int min_val, int max_val) {
    value = value < min_val ? min_val : value;
    value = value > max_val ? max_val : value;
    return value;
}
```

注意：现代编译器通常能自动做这种优化，手写不一定更快。关键是先测量，确认分支确实是瓶颈。

#### 手段3：内存对齐

确保数据结构按自然对齐访问：

```c
// 可能不对齐
typedef struct {
    uint8_t type;     // 1 字节
    uint32_t value;   // 4 字节，可能从偏移 1 开始
    uint8_t flag;     // 1 字节
} BadLayout;          // 可能有填充，大小不确定

// 显式对齐
typedef struct {
    uint32_t value;   // 4 字节，先放大字段
    uint8_t type;     // 1 字节
    uint8_t flag;     // 1 字节
    uint8_t _pad[2];  // 显式填充到 8 字节
} GoodLayout;
```

对齐的影响：

1. 不对齐的访问在某些架构上会触发异常。
2. 即使硬件支持不对齐访问，性能也会下降。
3. 合理排列结构体字段可以减少填充浪费。

#### 手段4：DMA 替代中断搬运

用 DMA 代替 CPU 中断搬运数据：

```c
// 中断方式：每字节一次中断
void UART_ISR(void) {
    rx_buffer[index++] = UART->DR;  // 每次中断搬 1 字节
}

// DMA 方式：CPU 不参与搬运
DMA_Config config = {
    .src = (uint32_t)&UART->DR,
    .dst = (uint32_t)rx_buffer,
    .count = BUFFER_SIZE,
    .src_inc = false,
    .dst_inc = true
};
DMA_Start(&config);
```

DMA 的优势：

1. CPU 完全不参与数据搬运。
2. 释放的 CPU 时间可以用来做计算。
3. 中断次数从 N 次减少到 1 次（传输完成中断）。

#### 手段5：循环优化

```c
// 普通循环
for (int i = 0; i < N; ++i) {
    result += data[i] * coeff[i];
}

// 循环展开（手动或编译器自动）
for (int i = 0; i < N; i += 4) {
    result += data[i] * coeff[i];
    result += data[i+1] * coeff[i+1];
    result += data[i+2] * coeff[i+2];
    result += data[i+3] * coeff[i+3];
}
```

注意：

1. 现代编译器在 `-O2` 或 `-O3` 下通常会自动展开。
2. 手动展开可能让代码更难维护。
3. 先测量，确认循环确实是瓶颈再手动优化。

#### 手段6：编译器优化选项

| 选项 | 含义 | 适用场景 |
| --- | --- | --- |
| `-O0` | 不优化 | 调试阶段 |
| `-O1` | 基本优化 | 调试与性能的平衡 |
| `-O2` | 充分优化 | 大多数发布版本 |
| `-O3` | 激进优化 | 性能关键路径（可能增大代码体积） |
| `-Os` | 优化代码体积 | Flash 受限的嵌入式 |
| `-Og` | 优化调试体验 | 需要调试的发布版本 |

嵌入式里常见选择：

1. 开发阶段用 `-O0` 或 `-Og`。
2. 发布版本用 `-Os`（代码体积优先）或 `-O2`（性能优先）。
3. `-O3` 要谨慎，可能引入意想不到的行为变化。

### 5. 优化后必须验证正确性

很多优化手段会改变代码语义：

1. 查表可能改变边界行为。
2. 无分支写法可能改变溢出行为。
3. 循环展开可能改变迭代次数。
4. 编译器优化可能移除"看起来多余"的代码（如 volatile 未加的硬件访问）。

验证方式：

1. 优化前后运行同一组单元测试。
2. 对比优化前后的输出结果。
3. 用 AddressSanitizer 和 UBSan 检查未定义行为。
4. 在目标板上做集成测试。

### 6. 空间换时间 vs 时间换空间

这是嵌入式里最常见的权衡：

**空间换时间**：

1. 查表替代计算。
2. 展开循环。
3. 缓存计算结果。
4. 使用更大的数据类型避免转换。

**时间换空间**：

1. 压缩数据，使用时解压。
2. 用位域替代整型。
3. 共享缓冲区替代独立缓冲区。
4. 延迟初始化。

选择依据：

1. Flash 和 RAM 哪个更紧张？
2. 实时性要求有多高？
3. 代码体积增量是否可接受？

## 数据流 / 控制流 / 时序关系

性能优化的典型主线：

```text
确定性能目标
-> 测量当前性能
-> 定位瓶颈（哪段代码、什么原因）
-> 选择优化手段
-> 实现优化
-> 测量优化后性能
-> 验证正确性
-> 如果不达标，回到定位瓶颈
```

最常见的错误是跳过"测量"和"定位"步骤，直接进入"优化"。

## 最小可运行示例

```c
#include <stdio.h>
#include <stdint.h>
#include <stddef.h>

#define DATA_SIZE 256

static int16_t data[DATA_SIZE];
static int16_t filtered[DATA_SIZE];

static void generate_signal(void) {
    for (size_t i = 0; i < DATA_SIZE; ++i) {
        data[i] = (int16_t)(100 * __builtin_sin(2.0 * 3.14159 * i / DATA_SIZE));
    }
}

static int32_t sum_abs_slow(const int16_t *arr, size_t len) {
    int32_t total = 0;
    for (size_t i = 0; i < len; ++i) {
        if (arr[i] < 0) {
            total -= arr[i];
        } else {
            total += arr[i];
        }
    }
    return total;
}

static int32_t sum_abs_fast(const int16_t *arr, size_t len) {
    int32_t total = 0;
    for (size_t i = 0; i < len; ++i) {
        int16_t val = arr[i];
        int16_t mask = val >> 15;
        total += (val ^ mask) - mask;
    }
    return total;
}

int main(void) {
    generate_signal();

    int32_t result_slow = sum_abs_slow(data, DATA_SIZE);
    int32_t result_fast = sum_abs_fast(data, DATA_SIZE);

    printf("slow result = %ld\n", (long)result_slow);
    printf("fast result = %ld\n", (long)result_fast);

    if (result_slow == result_fast) {
        printf("results match\n");
    } else {
        printf("MISMATCH!\n");
    }

    return 0;
}
```

编译和运行：

```bash
gcc -Wall -Wextra -std=c11 -O2 demo.c -lm -o demo
./demo
```

预期输出：

```text
slow result = 16200
fast result = 16200
results match
```

这个示例展示了：

1. 两种绝对值求和的实现：有分支版本和无分支版本。
2. 优化后必须验证结果一致性。
3. 实际性能差异需要用计时器或性能计数器测量。

## 代码解读

### 1. 为什么 `val >> 15` 能生成掩码

对于 16 位有符号整数，算术右移 15 位后：

1. 正数变成 `0x0000`（全0）。
2. 负数变成 `0xFFFF`（全1）。

这个掩码可以用来做无分支绝对值：

1. `val ^ mask`：正数不变，负数取反。
2. `- mask`：正数减0，负数加1（补码取反加1就是绝对值）。

### 2. 为什么无分支不一定更快

1. 现代编译器通常能识别 `if (x < 0) x = -x` 模式并生成条件移动指令。
2. 手写无分支代码可能让编译器无法做其他优化。
3. 必须实测才能确认哪个更快。

### 3. 为什么优化后必须对比结果

因为无分支写法和有分支写法在边界情况（如 `INT16_MIN`）可能行为不同。`INT16_MIN` 的绝对值无法用 `int16_t` 表示，两种写法可能给出不同结果。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 优化前提 | 先测量再优化 | 凭感觉优化 | 可能优化了不需要优化的地方 |
| 瓶颈定位 | 用工具找到热点 | 猜测哪里慢 | 猜测经常是错的 |
| 优化验证 | 对比优化前后结果和性能 | 只看性能不看正确性 | 优化可能引入 bug |
| 编译器优化 | 根据场景选 `-Os` 或 `-O2` | 一律 `-O3` | 代码体积膨胀可能导致缓存未命中增加 |
| 查表 | 输入范围有限且结果固定时用 | 到处查表 | Flash 不够用 |
| 内联 | 让编译器决定或用 profile-guided | 到处加 `inline` | 代码膨胀反而降低性能 |
| DMA | 批量数据搬运时用 | 所有数据都用中断搬运 | CPU 时间浪费在搬运上 |

## 边界条件与适用范围

1. 性能优化不是免费的，每一步优化都有可维护性代价。
2. 优化应该集中在性能不达标的关键路径，而不是全局优化。
3. 编译器优化选项不是万能的，有些优化编译器做不了（如算法替换）。
4. 嵌入式里的性能约束通常是"最坏情况"而不是"平均情况"。
5. 优化后如果代码变得更难理解，要考虑是否值得。
6. 有些优化是平台相关的，换一个 MCU 可能就不适用了。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 优化后性能没变 | 优化了非瓶颈代码 | 用 profiling 工具确认热点 |
| 优化后结果错误 | 优化改变了语义 | 对比优化前后输出 |
| 优化后更慢 | 代码膨胀导致缓存未命中 | 检查代码体积变化 |
| 编译器优化掉硬件访问 | 缺少 `volatile` | 查看汇编输出 |
| 不同编译器结果不同 | 依赖未定义行为 | 开 UBSan 检查 |
| 测量结果不稳定 | 中断干扰、缓存冷热 | 关中断测量或多跑取中位数 |

### 推荐排查顺序

1. 先确认性能目标是什么（延迟、吞吐量、代码体积）。
2. 再用工具测量当前性能，确认是否真的不达标。
3. 再定位瓶颈在哪段代码、什么原因。
4. 再选择合适的优化手段。
5. 最后验证优化效果和正确性。

### 常用验证方式

```bash
gcc -Wall -Wextra -std=c11 -O2 demo.c -o demo
gcc -fsanitize=address,undefined -g demo.c -o demo_sanitized
objdump -d demo > demo.asm
```

1. `-O2` 编译验证性能。
2. sanitizer 编译验证正确性。
3. `objdump` 查看汇编确认编译器是否按预期优化。

## 工程落地建议

### 1. 建立性能基线

在项目初期就测量关键路径的执行时间，建立基线。后续每次修改都可以跟基线对比，及时发现性能退化。

### 2. 把性能测试纳入持续集成

1. 自动运行关键路径的计时测试。
2. 性能退化超过阈值就报警。
3. 跟功能测试一样重要。

### 3. 优化前先确认约束

1. 是延迟不够还是吞吐量不够？
2. 是 CPU 不够还是内存不够？
3. 是平均性能不够还是最坏情况不够？

不同约束的优化方向完全不同。

### 4. 优先做"低成本高收益"的优化

1. 选择更好的算法（O(n) vs O(n²)）。
2. 改善内存访问模式（连续 vs 随机）。
3. 用 DMA 替代 CPU 搬运。
4. 减少中断频率。

这些通常比"手写汇编"或"到处 inline"更有效。

### 5. 保留优化前的代码

优化后的代码可能更难理解。保留优化前的版本（注释或版本控制），方便以后维护和审查。

## 性能、稳定性、可维护性影响

1. 合理优化能显著提升系统响应速度和资源利用率。
2. 不合理优化会降低可维护性，增加 bug 风险。
3. 过度优化会让代码变得平台相关，降低可移植性。
4. 真正好的优化，是让代码在满足性能目标的前提下仍然清晰可读。
5. 性能优化应该是"按需"的，不是"越多越好"的。

## 面试 / 问答怎么讲

### 30 秒版本

性能优化的正确顺序是：先测量、再定位瓶颈、再优化、再验证。嵌入式里最常见的瓶颈是内存访问模式和缓存利用，常见优化手段包括查表替代计算、减少分支、内存对齐、DMA 替代中断搬运。优化后必须验证正确性，因为很多优化会改变代码语义。

### 3 分钟版本

可以从"优化的正确顺序"讲起：先测量再优化，凭感觉优化经常是错的。然后说明嵌入式里常见的性能瓶颈：缓存未命中、分支预测失败、中断延迟。再举几个优化手段的例子：查表替代计算、DMA 替代中断搬运、内存对齐。最后强调优化后必须验证正确性，以及编译器优化选项的选择。

### 10 分钟版本

可以结合一个嵌入式项目展开：传感器数据处理系统里，先用 DWT 周期计数器测量各函数耗时，发现滤波函数是瓶颈。分析原因发现是随机内存访问导致缓存未命中。改用连续内存布局后性能提升 3 倍。再讨论编译器优化选项的选择：Flash 受限时用 `-Os`，性能关键路径用 `-O2`。最后说明如何建立性能基线、如何把性能测试纳入持续集成。这种讲法更接近真实工程能力。

## 实战练习

1. 用 DWT 周期计数器测量一个函数的执行时间，对比不同编译优化选项的差异。
2. 把一个链表遍历改成数组遍历，测量缓存命中率改善。
3. 用查表替代一个三角函数计算，对比性能和精度。
4. 用 DMA 替代中断搬运一段 UART 数据，测量 CPU 占用率变化。
5. 对一个结构体重新排列字段顺序，用 `sizeof` 对比优化前后的内存占用。

## 关键要点

1. 性能优化的正确顺序：先测量、再定位、再优化、再验证。
2. 嵌入式里最常见的瓶颈是内存访问模式和缓存利用，不是算法复杂度。
3. 常见优化手段：查表、减少分支、内存对齐、DMA、循环优化。
4. 编译器优化选项要根据场景选择：`-Os` 优化体积，`-O2` 优化速度。
5. 优化后必须验证正确性，很多优化会改变代码语义。
6. 空间换时间和时间换空间是嵌入式里最常见的权衡。
7. 真正好的优化，是让代码在满足性能目标的前提下仍然清晰可读。
