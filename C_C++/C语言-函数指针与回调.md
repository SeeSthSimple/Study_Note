# C语言-函数指针与回调

## 原始问题

为什么 C 里总会看到函数指针、回调和一堆 `void *ctx`？它们到底在解决什么问题？为什么驱动、协议栈、事件循环和状态机里这么常见？

## 先给结论

函数指针和回调的本质，是把“要做什么”从“什么时候做、谁来触发”里拆开：

1. 函数指针让代码可以在运行时选择调用哪个函数。
2. 回调让模块只负责触发时机，不负责具体业务。
3. `void *context` 常用来把调用需要的外部状态一起带进去。
4. 这种机制很适合驱动、协议解析、任务分发、状态机和插件式设计。

最重要的工程结论是：

1. 回调签名必须稳定，输入输出语义要明确。
2. 回调本身只是调度机制，不会替你解决上下文生命周期和线程安全问题。
3. 设计回调接口时，空指针、阻塞行为、重入和错误传播必须提前想清楚。

如果只能背“函数指针就是指向函数的指针”，但讲不清它为什么能解耦模块、为什么常配 `void *ctx`、为什么回调常常让 bug 更隐蔽，就还没有真正掌握这个主题。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 看驱动、协议或库代码时，经常被回调注册接口卡住。
2. 不知道为什么很多模块不直接调用业务函数，而要先“注册回调”。
3. 写代码时只会把逻辑硬编码进模块，导致复用性很差。
4. 面试时知道函数指针会考，但讲不出工程意义和风险边界。

它在 AI 时代依然重要，因为 AI 很擅长生成一层“看起来能用”的回调框架，但很容易忽略上下文生命周期、空回调保护和异步触发边界。真正稳的代码，关键不在语法，而在接口约束。

## 核心概念 / 本质机制

### 1. 函数指针是什么

函数指针保存的是某个函数入口地址，并且带有函数签名信息。

例如：

```c
typedef void (*event_cb_t)(void *ctx, int event);
```

### 2. 回调在工程里到底解决什么问题

回调的价值是解耦：

1. 底层模块只负责检测事件或完成时机。
2. 上层模块决定事件发生时要执行什么动作。

例如：

1. UART 接收到一帧数据后通知上层。
2. 定时器超时后通知业务逻辑。
3. 协议解析器解析出完整帧后交给用户处理。

### 3. 为什么总配 `void *ctx`

因为光有函数地址还不够，很多回调执行时还需要知道：

1. 当前处理的是哪个对象。
2. 哪个缓冲区或状态机实例。
3. 哪份用户上下文。

### 4. 回调为什么有时会让系统更复杂

因为控制流变得间接了：

1. 不是你显式调用某个业务函数。
2. 而是某个模块在将来某个时刻触发它。

这会带来三类常见风险：

1. 谁注册了它不清楚。
2. 什么时候触发不清楚。
3. `ctx` 在触发时是否还有效不清楚。

### 5. 函数指针表为什么常见

很多工程不会只放一个函数指针，而是放一组操作表：

1. 设备操作表
2. 协议处理表
3. 状态机动作表

本质上是在 C 里手工实现“基于接口选择行为”的能力。

## 数据流 / 控制流 / 时序关系

回调系统的典型主线可以理解成：

```text
调用方注册回调函数和上下文
-> 模块保存函数指针和 context
-> 某个事件发生
-> 模块检查回调是否存在
-> 按约定参数触发回调
-> 回调内部处理业务逻辑
```

真正容易出 bug 的地方通常不是“函数指针不会写”，而是：

1. 没注册就触发。
2. 注册了，但 `ctx` 已经失效。
3. 回调内部做了不该做的阻塞或重入操作。

## 最小可运行示例

```c
#include <stdio.h>

typedef void (*event_cb_t)(void *ctx, int event);

typedef struct {
    event_cb_t cb;
    void *ctx;
} EventDispatcher;

typedef struct {
    const char *name;
    int count;
} AppContext;

static void dispatcher_init(EventDispatcher *dispatcher, event_cb_t cb, void *ctx)
{
    if (dispatcher == NULL) {
        return;
    }

    dispatcher->cb = cb;
    dispatcher->ctx = ctx;
}

static void dispatcher_fire(EventDispatcher *dispatcher, int event)
{
    if (dispatcher == NULL || dispatcher->cb == NULL) {
        return;
    }

    dispatcher->cb(dispatcher->ctx, event);
}

static void on_event(void *ctx, int event)
{
    AppContext *app = (AppContext *)ctx;

    if (app == NULL) {
        return;
    }

    app->count++;
    printf("[%s] event=%d, count=%d\n", app->name, event, app->count);
}

int main(void)
{
    EventDispatcher dispatcher = {0};
    AppContext app = {"demo", 0};

    dispatcher_init(&dispatcher, on_event, &app);
    dispatcher_fire(&dispatcher, 100);
    dispatcher_fire(&dispatcher, 200);
    return 0;
}
```

预期输出：

```text
[demo] event=100, count=1
[demo] event=200, count=2
```

## 代码解读

### 1. 为什么 `EventDispatcher` 里同时保存 `cb` 和 `ctx`

只有函数地址不够，回调执行时往往还需要知道当前实例状态。`ctx` 就是把这个状态带进去。

### 2. 为什么触发前一定先判空

C 不会帮你阻止空函数指针调用。没有判空时，直接调用空回调通常会崩溃。

### 3. 为什么 `ctx` 的生命周期必须由设计保证

如果 `dispatcher` 保存的是一个已经失效的局部变量地址，后面再触发回调就会变成悬空指针访问。

### 4. 为什么这个例子很像驱动和协议代码

因为很多真实模块做的事情也是：

1. 注册回调
2. 保存上下文
3. 在某个中断、事件或解析完成点触发处理逻辑

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 回调注册 | 保存 `函数指针 + context` | 只保存函数，不传状态 | 复杂场景下无法关联实例 |
| 触发前检查 | 判空再调用 | 默认回调一定已注册 | 空指针调用会崩 |
| 上下文生命周期 | 保证 `ctx` 在触发时仍有效 | 传局部变量地址给异步回调 | 后续触发变悬空 |
| 签名设计 | 参数含义明确、类型稳定 | 随意改参数顺序和类型 | 调用方和实现方容易错配 |
| 回调行为 | 约束是否可阻塞、可重入 | 在 ISR 回调里做耗时阻塞 | 系统行为会失控 |

## 边界条件与适用范围

1. 回调适合解耦事件触发和处理逻辑，但不适合把所有控制流都改成过度间接。
2. 中断回调、线程回调、同步调用回调的约束完全不同，接口文档必须写清楚。
3. `void *ctx` 很灵活，但也最容易把类型边界和生命周期边界写乱。
4. 如果模块之间关系非常固定，直接函数调用有时比回调更简单、更清晰。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 一触发就崩 | 回调为空或 `ctx` 无效 | 看注册流程和触发前判空 |
| 业务处理错实例 | `ctx` 指错对象 | 打印对象地址和注册来源 |
| 系统卡死 | 回调里做了阻塞操作 | 查触发上下文是不是 ISR 或高优先级路径 |
| 结果偶发错乱 | 回调重入、共享状态无保护 | 梳理触发时序和共享数据 |

## 工程落地建议

### 1. 回调接口要写清三件事

至少说明：

1. 谁注册，谁触发
2. `ctx` 归谁管理
3. 回调里允不允许阻塞、加锁、调用其他接口

### 2. 优先把回调签名做稳定

不要今天传 `int`，明天传 `void *`，后天再加三个参数。宁可一开始就设计成结构化参数，也别频繁破坏接口。

### 3. 对异步回调特别重视生命周期

同步调用时问题还不明显，异步触发时最容易踩到：

1. `ctx` 失效
2. 模块已经销毁但回调还会来
3. 重入导致状态错乱

## 性能、稳定性、可维护性影响

1. 回调能显著提高复用性和模块解耦程度。
2. 但控制流间接后，调试复杂度会上升，所以注册关系和触发时序一定要清楚。
3. 回调设计得好，能让驱动和业务边界很干净；设计得差，会让系统像“到处偷偷跳转”。

## 面试 / 问答怎么讲

### 30 秒版本

函数指针让 C 代码可以在运行时选择要执行的函数，回调则把“事件触发”和“具体处理”解耦。它在驱动、协议和事件系统里很常见，通常会配一个 `void *ctx` 传上下文。工程里真正关键的是回调签名稳定、上下文生命周期清楚、触发上下文约束明确。

### 3 分钟版本

可以先举一个事件分发器例子：模块保存 `cb + ctx`，事件发生时触发回调。这样底层只负责发现事件，上层决定怎么处理。再补充为什么回调适合驱动和协议解析，以及为什么空回调、悬空 `ctx`、ISR 里阻塞是典型坑点。

### 10 分钟版本

可以进一步讲函数指针表如何在 C 里模拟接口抽象，例如不同设备驱动共用一套 `ops` 表；再结合异步回调说明生命周期和线程安全风险。这种讲法会更接近真实工程。

## 实战练习

1. 写一个简单定时器模块，超时后通过回调通知用户。
2. 写一个协议解析器，收到完整帧后调用回调分发。
3. 故意把局部变量地址传给异步回调，观察为什么危险。
4. 写一个 `ops` 表，让两种不同设备实现同一套接口。

## 关键要点

1. 函数指针解决“运行时选择行为”，回调解决“事件和处理解耦”。
2. `void *ctx` 的价值是把实例状态带进回调。
3. 回调设计真正的难点是生命周期、触发时机和错误边界。
4. 空回调、悬空上下文和不合适的阻塞行为是三类典型坑。
5. 函数指针表是 C 里实现接口抽象的重要手段。
