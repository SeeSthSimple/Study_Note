# C++-异常安全

## 原始问题

C++ 为什么总强调异常安全？异常一旦抛出来，到底会影响什么？为什么很多资源代码平时能跑，但一到异常路径就开始泄漏、状态错乱或半更新？

## 先给结论

异常安全的核心，不是“会不会写 try/catch”，而是先保证资源和状态在异常路径下仍然可控：

1. 资源释放交给 RAII，不依赖手工清理。
2. 析构函数通常不应抛异常。
3. 修改对象状态前，要先想清楚异常发生时对象应保持什么状态。
4. 优先写出至少满足 basic guarantee 的代码，重要场景争取 strong guarantee。

常见的三种异常安全保证：

1. Basic guarantee：出错后对象仍保持合法，但值可能改变。
2. Strong guarantee：出错后状态回滚，外部看起来像没发生过这次操作。
3. Nothrow guarantee：承诺不抛异常。

如果只会在函数外面套 `try/catch`，但讲不清为什么 RAII 能兜住异常路径、为什么构造失败和析构抛异常这么敏感，就还没有真正掌握 C++ 的异常安全。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 代码正常路径没问题，但一旦构造、分配、拷贝或容器操作抛异常，就开始泄漏或状态紊乱。
2. 不知道 `basic/strong/nothrow guarantee` 真正分别意味着什么。
3. 不理解为什么现代 C++ 这么强调 RAII、本地对象、智能指针和 `noexcept`。
4. 面试时知道异常安全重要，但讲不出落地方法。

它在 AI 时代依然重要，因为 AI 很容易生成只覆盖 happy path 的 C++ 代码，但对异常路径的资源收尾和状态一致性考虑不足。理解异常安全，你才能判断一段代码是“能跑”，还是“可在复杂控制流下稳定运行”。

## 核心概念 / 本质机制

### 1. 异常安全真正关心的是“失败时系统还能不能收得住”

函数可能在这些地方抛异常：

1. 内存分配。
2. 容器扩容。
3. 拷贝构造和移动构造。
4. 字符串拼接。
5. 显式 `throw`。

真正的问题不在“有没有异常”，而在异常后：

1. 资源有没有泄漏。
2. 对象是不是处于半初始化、半更新状态。
3. 外部观察者能不能继续安全使用对象。

### 2. RAII 是异常安全的基础设施

异常路径下最可靠的动作不是 catch 里手工补救，而是：

1. 已成功构造的对象在栈展开时自动析构。
2. 析构过程自动释放资源。
3. 这样你不用为每条异常路径都手写清理代码。

所以 RAII 不是“资源管理风格偏好”，而是异常安全的基础设施。

### 3. 三种异常安全保证怎么理解

#### Basic guarantee

保证：

1. 不泄漏资源。
2. 不破坏对象不变量。
3. 对象仍可继续使用或安全销毁。

但对象的值可能已经改变。

#### Strong guarantee

保证：

1. 操作要么全部成功。
2. 要么失败后完全回滚。
3. 外部看到的状态像没执行过这次操作。

这很适合配置更新、批量修改和需要事务感的逻辑。

#### Nothrow guarantee

保证：

1. 操作承诺不抛异常。
2. 常用于析构函数、交换函数、移动操作或底层清理路径。

### 4. 为什么析构函数通常不应该抛异常

因为析构经常发生在栈展开期间。如果这时候再抛异常：

1. 原本就有一个异常正在传播。
2. 再抛一个新的异常会导致程序直接终止。

所以工程里通常遵守：

1. 析构函数尽量 `noexcept`。
2. 析构中如果清理失败，改用日志、状态记录或显式关闭接口上报，而不是析构里直接抛。

### 5. Copy-and-swap 为什么常被用来做 strong guarantee

它的思想是：

1. 先在临时对象里完成可能失败的操作。
2. 全部成功后再和当前对象交换。
3. 交换通常设计为不抛异常或尽量低风险。

这样：

1. 临时对象构造失败，不影响原对象。
2. 构造成功后再提交，状态切换更像事务。

### 6. `noexcept` 为什么不仅是性能标记

`noexcept` 不只是“告诉编译器快一点”，它还影响：

1. 标准库是否愿意在容器重分配时优先使用移动操作。
2. 接口是否能作为某些异常安全路径的可靠工具。
3. 调用者能否把它当成稳定收尾步骤。

## 数据流 / 控制流 / 时序关系

异常安全的典型主线可以理解成：

```text
进入函数
-> 获取资源 / 构造临时对象
-> 执行业务逻辑
-> 中途某步可能抛异常
-> 已构造对象开始栈展开析构
-> 资源自动回收
-> 调用方决定捕获还是继续传播
```

这条链路说明两个关键点：

1. 真正稳的代码，不是靠每个 catch 补救，而是靠作用域和对象析构自然收尾。
2. 任何会修改共享状态的操作，都要提前设计“失败时状态停在哪”。

## 最小可运行示例

下面给一个用 copy-and-swap 思路做 strong guarantee 的最小示例。

```cpp
#include <iostream>
#include <string>
#include <utility>

class Config {
public:
    explicit Config(std::string value) : value_(std::move(value)) {}

    void update(std::string new_value) {
        Config temp(std::move(new_value));
        swap(temp);
    }

    void swap(Config& other) noexcept {
        value_.swap(other.value_);
    }

    const std::string& value() const {
        return value_;
    }

private:
    std::string value_;
};

int main()
{
    Config cfg("old");
    cfg.update("new");
    std::cout << cfg.value() << '\n';
    return 0;
}
```

编译和运行：

```bash
g++ -Wall -Wextra -Werror -std=c++17 demo.cpp -o demo
./demo
```

预期输出：

```text
new
```

这个例子的重点不是字符串本身，而是更新逻辑：

1. 先构造临时对象 `temp`。
2. 如果构造失败，原对象 `cfg` 完全不变。
3. 只有临时对象准备好了，才用 `swap` 提交。

这就是 strong guarantee 的典型思路。

## 代码解读

### 1. 为什么 `update` 不直接改 `value_`

如果直接在原对象上做复杂修改，中途一旦抛异常，就可能让对象停在半更新状态。先构造临时对象能把风险隔离开。

### 2. 为什么 `swap` 写成 `noexcept`

因为提交阶段越稳定，越容易实现 strong guarantee。`swap` 如果还可能抛异常，提交动作本身就变得不可靠。

### 3. 为什么这个例子也体现了 RAII

`temp` 是局部对象：

1. 构造成功才进入下一步。
2. 函数结束时自然析构。
3. 不需要写额外 cleanup。

### 4. 为什么“有 catch”不等于“异常安全”

如果 catch 里只打印日志，但资源已经泄漏、对象已经半损坏，那仍然不是异常安全代码。异常安全核心在于状态和资源的一致性，不在于 catch 本身。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 资源管理 | 用 RAII 对象自动收尾 | 手工 `new` 后寄希望于 catch 里补救 | 分支一复杂就容易漏清理 |
| 状态更新 | 先准备临时状态，再提交 | 直接在原对象上逐步修改 | 中途抛异常会留下半更新状态 |
| 析构函数 | 默认不抛异常 | 析构里抛异常 | 栈展开期间容易直接终止程序 |
| 移动/交换 | 重要基础操作尽量 `noexcept` | 不标 `noexcept` 或在其中做高风险操作 | 影响容器和异常安全策略 |
| 错误处理 | 先保证资源/状态正确，再考虑 catch | 以为加了 `try/catch` 就安全 | catch 不能自动修复资源边界问题 |

## 边界条件与适用范围

1. 不是所有函数都必须做到 strong guarantee，有时 basic guarantee 已足够。
2. 对性能敏感路径，是否为回滚复制一份完整状态，需要结合代价权衡。
3. 析构函数不抛异常是非常重要的工程约束，但这不代表清理失败不需要记录，只是不要在析构里继续抛。
4. 禁用异常的项目风格仍然存在，但那不等于可以忽视“失败路径资源一致性”这个本质问题。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 异常后一堆资源没释放 | 没用 RAII，手工清理路径漏了 | 检查资源是不是都绑在对象上 |
| 对象状态错乱 | 直接原地修改，失败时没回滚 | 看更新逻辑是否先构造临时状态 |
| 程序直接 terminate | 析构期间再次抛异常 | 检查析构函数和清理路径 |
| 容器表现不如预期 | 移动操作不 `noexcept` | 检查移动构造/赋值定义 |
| catch 后仍崩溃 | catch 只记录日志，没修正资源或状态 | 回查异常抛出前对象边界 |

### 推荐排查顺序

1. 先确认异常路径下资源会不会自动回收。
2. 再确认对象状态在失败后是否仍然合法。
3. 再看是 basic 还是 strong guarantee 场景。
4. 再检查析构和移动操作是否适合 `noexcept`。
5. 最后再优化性能和粒度。

## 工程落地建议

### 1. 默认用 RAII 承担清理工作

不要把清理责任留到 catch 里兜底，优先让对象析构自然回收资源。

### 2. 修改状态时先想“失败后要看到什么”

常用思路：

1. 失败后只要求对象仍合法，那就至少做到 basic guarantee。
2. 失败后要求对象值完全不变，就设计临时对象 + 提交流程。

### 3. 对基础资源类的要求更严格

这些函数通常更值得做稳：

1. 析构函数。
2. `swap`。
3. 移动构造和移动赋值。
4. 清理/关闭函数。

### 4. 和标准库配合时善用其现成异常安全语义

很多标准容器和标准类型已经帮你做了大量异常安全工作，越少绕开它们手写裸资源路径，代码通常越稳。

## 性能、稳定性、可维护性影响

1. 异常安全设计的最大收益通常是稳定性和维护性，而不是性能。
2. RAII + 明确状态提交策略，能显著降低“偶发失败后系统进入奇怪状态”的概率。
3. 强异常安全保证通常更稳，但代价可能更高；是否值得，要结合业务关键性判断。
4. 真正成熟的 C++ 代码，不是从不抛异常，而是即使失败也能保证系统边界不乱。

## 面试 / 问答怎么讲

### 30 秒版本

异常安全的核心不是 `try/catch`，而是资源和状态在失败路径下依然正确。RAII 解决资源回收，basic/strong/nothrow guarantee 解决状态一致性。现代 C++ 强调这些，是因为复杂控制流下手工清理和手工回滚太容易出错。

### 3 分钟版本

可以先讲三种保证：basic 保证对象仍合法但值可能变，strong 保证失败像没发生过，nothrow 保证不抛异常。然后说明 RAII 为什么是基础设施，因为异常路径下已构造对象会自动析构，资源不用手工收尾。再结合 copy-and-swap 说明如何实现 strong guarantee，这样就能把概念和工程实践串起来。

### 10 分钟版本

可以进一步结合一个配置更新或容器操作案例展开：先构造临时状态，如果成功再提交，否则原对象保持不变；析构函数不抛异常，移动和 swap 尽量 `noexcept`，这样整个系统在异常路径下依然可推理。这种讲法更像真实工程能力，而不只是术语背诵。

## 实战练习

1. 把一个“直接改原对象”的更新函数改成“临时对象 + 提交”版本。
2. 写一个带资源成员的类，验证异常抛出时资源是否能自动回收。
3. 故意写一个析构里抛异常的小例子，观察为什么危险。
4. 给一个类补上 `swap` 和 `noexcept` 移动操作，再分析它对容器行为的影响。

## 关键要点

1. 异常安全关心的是失败后资源和状态是否仍然受控。
2. RAII 是异常安全的基础设施。
3. basic、strong、nothrow guarantee 是不同层级的工程承诺。
4. 析构函数通常不应抛异常。
5. 先准备临时状态、再提交，是实现 strong guarantee 的常见思路。
