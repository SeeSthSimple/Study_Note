# 板级与启动-Bootloader启动流程

## 原始问题

板子上电之后到底发生了什么？Bootloader 为什么重要，它和 BootROM、内核、根文件系统分别是什么关系？真正做板级 bring-up 或启动排障时，应该沿着哪条主线去看，而不是只会说“卡在启动了”？

## 先给结论

Bootloader 的本质，是把系统从“刚上电、硬件还很原始”的状态，带到“足以加载并启动下一个阶段”的状态。

先记住下面几个结论：

1. 启动流程通常不是一步到位，而是分阶段推进，比如 `BootROM -> Bootloader -> Kernel / RTOS -> 用户空间或应用`。
2. Bootloader 的核心工作不是“打印几行启动日志”，而是初始化最基本的硬件环境并装载下一个阶段镜像。
3. 板子起不来时，不要笼统说“启动失败”，而要先判断卡在 BootROM、Bootloader、内核还是根文件系统阶段。
4. 启动排障最有效的方法不是盲猜，而是沿着日志、串口输出、启动介质、镜像地址、时钟复位和内存初始化这条链分段定位。
5. 学 Bootloader 的目标不是成为启动代码专家，而是建立一条稳定的 bring-up 主线，让你面对新板卡和启动问题时不慌。

如果只能背“U-Boot 是 Bootloader”，却讲不清它为什么存在、上电后先后做了什么、为什么有的板子连串口日志都没有、为什么内核镜像明明在但就是起不来，就说明这部分还没有真正掌握。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 不知道系统上电后 BootROM、Bootloader、Kernel 之间是怎样接力的。
2. 板子黑屏、无串口、卡 logo、卡 `Starting kernel...` 时，不知道问题在哪一层。
3. 面试或工作中经常需要解释启动流程，但只能说出名词，讲不清阶段职责。
4. 做板级 bring-up、烧录升级、恢复启动时，缺少稳定的分析和验证框架。

它在 AI 时代仍然重要，因为 AI 可以帮你拼出一份启动脚本或 U-Boot 命令，但它不知道你的 DDR 是否已经初始化成功，不知道存储介质分区地址是否正确，也不知道当前卡的是 BootROM 还是内核解压。启动链路越理解透，越能识别 AI 给出的建议到底是在正确阶段发力，还是在错误层面绕圈。

## 核心概念 / 本质机制

### 1. 为什么需要 Bootloader

芯片刚上电时，系统通常处于非常原始的状态：

1. 主频可能还没切到目标时钟。
2. DDR 可能还没初始化。
3. 外部存储还不能稳定访问。
4. 外设、串口、日志、显示等都还没准备好。

Bootloader 的价值就是把系统从这个“原始态”带到“可以装载下一阶段”的状态。

### 2. 启动链路通常如何分阶段

一个常见的嵌入式 Linux 启动主线可以先理解成：

1. `BootROM`：芯片内部固化代码，负责最早期启动入口和介质探测。
2. `Bootloader`：完成更完整的初始化，装载内核、设备树、initramfs 等。
3. `Kernel`：初始化内核子系统和驱动，挂载根文件系统。
4. `Userspace`：启动 `init`、服务和应用程序。

如果是 MCU 或无 Linux 场景，后半段可能变成：

1. `BootROM / startup code`
2. `Bootloader` 或直接用户应用
3. `RTOS / bare-metal application`

### 3. BootROM 负责什么

BootROM 通常是芯片厂商固化在片上的第一段代码。

它常做的事情包括：

1. 读取启动引脚或 eFuse 配置。
2. 选择启动介质，比如 NAND、eMMC、SD、SPI Flash、UART 下载模式。
3. 从固定位置加载第一阶段程序。

它通常做不了太多复杂事，因为：

1. 代码空间有限。
2. 硬件支持有限。
3. 功能被设计成最小可信启动入口。

### 4. Bootloader 的核心职责

Bootloader 往往承担这些关键工作：

1. 初始化更完整的时钟和内存环境。
2. 初始化串口，提供启动日志。
3. 初始化存储介质和必要外设。
4. 装载内核镜像、设备树和可选 rootfs/initramfs。
5. 设置启动参数并跳转到下一阶段。

有些系统还会在这里补：

1. 镜像校验。
2. 双分区升级。
3. 回滚策略。
4. 下载恢复模式。

### 5. 为什么启动排障一定要分阶段

因为不同阶段出问题，现象非常像，但根因完全不同。

例如：

1. 完全无串口输出，可能卡在 BootROM 或最早期串口初始化前。
2. 有 U-Boot 日志但进不了内核，问题可能在镜像地址、启动参数、设备树。
3. 内核起来了但挂根文件系统失败，根因已经不在 Bootloader。

所以“启动失败”不是一个问题，而是一类问题的统称。

### 6. 启动介质和镜像地址为什么经常出错

Bootloader 启动链常依赖这些关键事实：

1. 镜像确实写到了正确介质和偏移。
2. Bootloader 知道去哪里读。
3. 加载地址和执行地址是对的。
4. 设备树和内核镜像版本匹配。

只要这里任何一环错了，就可能出现：

1. 能读到数据但跳转后崩。
2. 看似成功加载但内核不启动。
3. 启动参数错，内核起来后找不到 rootfs。

## 数据流 / 控制流 / 时序关系

下面给一个典型嵌入式 Linux 启动链：

```text
上电
-> BootROM 根据启动配置选择 SPI Flash / eMMC / SD 等介质
-> BootROM 读取第一阶段启动程序
-> Bootloader 初始化时钟、DDR、串口、存储
-> Bootloader 加载 kernel image + dtb
-> Bootloader 设置 bootargs
-> 跳转到内核入口
-> Kernel 初始化子系统和驱动
-> 挂载根文件系统
-> 用户空间应用启动
```

这条链路里每一段都可能成为断点。

## 最小可运行示例

下面用一个典型 U-Boot 启动命令流程做最小示例：

```bash
setenv bootargs console=ttyS0,115200 root=/dev/mmcblk0p2 rw rootwait
load mmc 0:1 0x82000000 Image
load mmc 0:1 0x83000000 board.dtb
booti 0x82000000 - 0x83000000
```

这个流程表达的核心动作是：

1. 设置内核启动参数。
2. 从 `mmc 0:1` 分区加载内核镜像到内存地址 `0x82000000`。
3. 加载设备树到 `0x83000000`。
4. 通过 `booti` 跳转启动 64 位 ARM Linux 内核。

如果是其他架构或镜像格式，命令可能会换成：

1. `bootm`
2. `bootz`
3. 厂商私有启动命令

但主线不变：设置参数、加载镜像、加载设备树、跳转执行。

## 代码解读

### 1. 为什么 `bootargs` 很关键

`bootargs` 决定了内核启动时的重要行为，比如：

1. 串口控制台在哪。
2. 根文件系统在哪。
3. 是否只读或读写挂载。

如果这里错了，常见现象是：

1. 你以为内核没启动，其实只是串口没对。
2. 内核起来了，但根文件系统找不到。

### 2. 为什么加载地址要认真核对

内核、设备树、initramfs 的内存放置必须避免冲突。

如果地址配置不合理，可能会出现：

1. 解压覆盖。
2. 跳转异常。
3. 启动到某一步随机崩溃。

### 3. 为什么 Bootloader 日志非常重要

它通常是启动链里最早的可观测信息。

你至少可以借它判断：

1. Bootloader 有没有跑起来。
2. DDR 初始化是否成功。
3. 存储有没有识别到。
4. 内核镜像和设备树是否加载成功。

### 4. 为什么这只是最小闭环

真实项目里还会继续涉及：

1. 安全启动。
2. A/B 升级。
3. 环境变量持久化。
4. 网络启动。
5. 下载恢复模式。

但如果最小闭环都没打通，后面这些扩展都无从谈起。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 启动分析 | 先判断卡在哪个阶段 | 统一说“系统起不来” | 粒度太粗，无法定位 |
| 启动参数 | 明确核对 `bootargs` | 复制别人的参数直接用 | 串口、rootfs、内存布局可能不匹配 |
| 镜像加载 | 明确介质、分区和地址 | 只记命令不核对地址 | 可能加载了错误镜像或地址冲突 |
| Bring-up 过程 | 先串口、再日志、再介质、再镜像 | 没日志就开始盲猜 | 排障效率极低 |
| 恢复机制 | 保留下载 / 升级 / 回滚入口 | 一次烧坏就完全失联 | 工程风险高 |

## 边界条件与适用范围

1. 这篇笔记以嵌入式 Linux 常见启动链为主，但很多分阶段排障思路同样适用于 MCU 和 RTOS 项目。
2. 不同 SoC 厂商 BootROM、DDR 初始化和第一阶段启动细节差别很大，不能照搬命令和地址。
3. 某些 MCU 项目没有独立 Bootloader，但仍然可以借鉴这里的“分阶段理解和验证”方法。
4. 安全启动、可信启动和 OTA 回滚会让启动链更复杂，需要后续单独展开。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 完全无串口输出 | BootROM 阶段失败；串口配置错；最早期代码没跑到串口初始化 | 看启动模式、供电、时钟、串口硬件连接 |
| Bootloader 能起来但进不了内核 | 镜像没加载对；dtb 错；地址冲突； `bootargs` 错 | 看 U-Boot 日志、加载地址、镜像完整性 |
| 卡在 `Starting kernel...` | 内核早期异常；设备树错误；内存问题 | 开早期日志、核对 dtb 和内存配置 |
| 内核起来后找不到 rootfs | 启动参数错；分区错；存储驱动没起 | 看 `bootargs` 和内核日志 |
| 升级后设备变砖 | 镜像写错分区；没有回滚机制；环境变量被破坏 | 看分区布局、升级流程和恢复入口 |

### 推荐排查顺序

1. 先确认问题卡在 BootROM、Bootloader、Kernel 还是 Userspace。
2. 再确认串口和日志链路是否可靠。
3. 再确认启动介质、镜像文件和加载地址。
4. 再确认设备树和启动参数。
5. 最后再看更深的 DDR、时钟、电源和驱动初始化问题。

## 工程落地建议

### 1. 启动链每一阶段都要留观测点

例如：

1. Bootloader 早期串口打印。
2. 关键初始化步骤日志。
3. 镜像加载成功信息。
4. 进入内核前最后一条确认日志。

这样问题发生时，至少能知道断点在哪里。

### 2. 优先保证恢复能力

一个真正工程化的启动方案，至少应该考虑：

1. 固定下载模式。
2. 串口或 USB 恢复方式。
3. 升级失败时的回滚路径。

### 3. 板级 bring-up 时先追求最小启动闭环

推荐顺序：

1. 串口打印先起来。
2. 确认能稳定加载 Bootloader。
3. 再加载内核和设备树。
4. 再进入 rootfs 和应用层。

不要一上来同时尝试太多阶段。

## 性能、稳定性、可维护性影响

1. 启动链设计清晰，最大的收益通常不是性能，而是 bring-up 和恢复能力。
2. 启动参数、分区布局和日志设计混乱，会显著放大后续维护成本。
3. 一个有恢复入口和分阶段日志的系统，现场压力会比“出问题只能重刷、还不知道卡哪”小很多。

## 面试 / 问答怎么讲

### 30 秒版本

Bootloader 的作用是把系统从上电后的原始状态带到可以启动内核或应用的状态。典型启动链是 BootROM 选启动介质，Bootloader 初始化内存和外设、加载镜像和设备树，再跳转给内核。

### 3 分钟版本

可以从分阶段讲：BootROM 负责最早期启动入口，Bootloader 负责更完整的硬件初始化和镜像装载，Kernel 负责系统和驱动初始化，Userspace 再启动服务和应用。然后强调排障时必须先判断卡在哪一阶段，再沿着日志、介质、地址、设备树和启动参数去定位。

### 10 分钟版本

可以结合 U-Boot 的实际启动命令展开：先设置 `bootargs`，再加载内核和设备树到指定内存地址，最后执行 `booti`。然后说明为什么地址冲突、设备树错误、rootfs 参数错误都可能导致“看起来像启动失败”，以及 bring-up 时为什么要先把串口和最小启动闭环跑通。这种讲法更贴近真实项目。

## 实战练习

1. 画出你当前开发板的启动链，标出 BootROM、Bootloader、Kernel 和 Userspace 的边界。
2. 用一份真实 U-Boot 启动日志，标出时钟、DDR、存储、镜像加载和跳转的关键点。
3. 故意把 `bootargs` 里的 rootfs 参数改错一次，观察现象并总结排查路径。
4. 设计一个最小恢复方案，说明系统启动失败时如何重新进入下载模式。

## 关键要点

1. 启动排障的第一步永远是先判断卡在哪个阶段。
2. Bootloader 的核心职责是初始化基本环境并加载下一阶段。
3. 串口日志、启动介质、加载地址、设备树和启动参数是高频关键点。
4. 先打通最小启动闭环，再做升级、安全和恢复扩展。
