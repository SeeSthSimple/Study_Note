# Linux-platform总线与设备模型

## 原始问题

Linux 里的 platform 总线到底是什么？为什么设备树里的很多节点最后会变成 platform 设备，驱动又为什么经常叫 platform driver？如果不把设备模型这层想清楚，很多驱动匹配和排障问题为什么总会反复卡住？

## 先给结论

platform 总线的本质，是 Linux 为“板级固定存在、不能自动枚举的设备”提供的一套统一设备模型。

先记住下面几个结论：

1. platform 总线不是一条真实硬件总线，而是内核里的抽象组织方式。
2. 它解决的是“系统里有这个设备，但它不能像 PCIe、USB 那样自己枚举出来”这个问题。
3. 在设备树场景里，很多节点会先变成 `platform_device`，再由 `platform_driver` 来匹配和接管。
4. 不理解 platform 总线，驱动 `probe`、资源获取和设备树匹配都会显得零散。
5. AI 可以帮你写 `platform_driver` 骨架，但只有你理解设备模型，才能判断它为什么匹配不上、为什么资源拿不到。

## 这个知识解决什么问题

1. 不知道 platform 总线和真实硬件总线有什么区别。
2. 设备树、platform driver、platform device 之间关系串不起来。
3. 面试和工作中经常会被问到 Linux 设备模型，但只能背名词。

## 核心概念 / 本质机制

### 1. platform 总线为什么存在

Linux 里很多设备能靠枚举发现：

1. PCIe
2. USB
3. 某些网络设备

但 SoC 内建外设和板级固定设备通常不能自报家门。

这类设备需要平台层告诉内核：

1. 这里有个设备。
2. 它的资源是什么。
3. 该由谁来驱动。

### 2. platform bus 不是实体总线

它更像一个“固定设备集合的组织框架”。

它的价值在于把下面这些东西统一起来：

1. 设备对象。
2. 驱动对象。
3. 匹配机制。
4. 资源管理。

### 3. 设备树如何和 platform 模型接上

典型链路是：

1. 设备树描述节点。
2. 内核解析节点并创建设备对象。
3. 某些节点最终表现为 `platform_device`。
4. `platform_driver` 通过 `compatible` 匹配。
5. 匹配成功后进入 `probe`。

### 4. 设备模型真正帮你做了什么

至少做了这些事情：

1. 统一设备和驱动匹配。
2. 统一资源生命周期。
3. 统一 sysfs 表达。
4. 统一 suspend/resume、remove 等生命周期动作。

所以它不只是“概念层”，而是内核里很多行为的基础。

### 5. 为什么 platform 模型和设备树经常一起出现

因为它们刚好解决的是同一条链上的两层问题：

1. 设备树描述“板子上有什么”。
2. platform 模型组织“内核里怎么表示和接管这些设备”。

## 数据流 / 控制流 / 时序关系

```text
设备树节点存在
-> 内核解析节点
-> 创建 platform_device
-> platform_driver 注册
-> 匹配成功
-> probe 获取资源并初始化
-> 对外提供驱动能力
```

## 最小可运行示例

```c
static const struct of_device_id demo_of_match[] = {
    { .compatible = "demo,mydev" },
    { }
};

static struct platform_driver demo_driver = {
    .probe = demo_probe,
    .driver = {
        .name = "demo_mydev",
        .of_match_table = demo_of_match,
    },
};
```

这个示例虽然小，但体现了三件关键事情：

1. 驱动属于 platform 模型。
2. 匹配关键在 `of_match_table`。
3. 匹配成功后才会进入 `probe`。

## 代码解读

### 1. 为什么 `of_match_table` 比 `.name` 更关键

在设备树场景里，`compatible` 和 `of_match_table` 是主匹配路径。

`.name` 仍然有价值，但不是设备树匹配的核心。

### 2. 为什么 platform 模型特别适合 SoC 内建外设

因为它们通常：

1. 地址固定。
2. 中断固定。
3. 板级依赖固定。
4. 无法枚举。

这正是 platform 模型最擅长承载的对象。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 理解 platform | 把它看成固定设备模型 | 把它当成真实物理总线 | 容易混淆层次 |
| 设备树匹配 | 关注 `compatible` 和 `of_match_table` | 只盯 `.name` | 可能解释不了 `probe` 不进 |
| 排障路径 | 节点 -> 设备 -> 驱动 -> probe | 只盯驱动代码 | 容易漏掉设备出现链 |

## 边界条件与适用范围

1. 不是所有设备都属于 platform 模型，I2C、SPI、PCIe 等还有各自更具体的总线模型。
2. 某些 platform 设备并不来自设备树，也可能来自平台代码静态注册。
3. 理解 platform 模型并不等于已经掌握所有驱动细节，它只是进入驱动世界的关键入口。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| `probe` 不进 | 节点没生成设备；匹配失败 | 查运行中设备树和匹配表 |
| 设备存在但资源错 | 设备树资源描述错误 | 查 `reg`、`interrupts`、`clocks` |
| 驱动看起来对但系统没接上 | 设备模型链路没打通 | 查 bus、device、driver 三层关系 |

## 工程落地建议

1. 学驱动前先把设备模型主线想清楚。
2. 排障时先确认设备是否真的在内核里“出现”了，再看驱动逻辑。
3. 把 platform 模型、设备树和资源接口一起学，效率会高很多。

## 性能、稳定性、可维护性影响

1. 设备模型理解越清楚，驱动排障和复用能力越强。
2. 这部分主要提升的是结构理解和维护效率，而不是单点性能。

## 面试 / 问答怎么讲

### 30 秒版本

platform 总线不是实体总线，而是 Linux 为板级固定设备提供的统一设备模型。设备树描述硬件节点，内核把它们组织成 platform 设备，再由 platform 驱动匹配并进入 `probe`。

### 3 分钟版本

可以先讲为什么很多 SoC 内建设备不能枚举，所以需要 platform 模型。然后讲设备树如何把节点描述交给内核，内核如何创建 `platform_device`，驱动如何通过 `of_match_table` 匹配，最后进入 `probe` 获取资源并初始化。

### 10 分钟版本

可以再展开到驱动排障：节点在不在、设备对象有没有创建、匹配表是否一致、资源是否申请成功。这种讲法能把设备树、platform driver 和资源管理串成一条完整主线。

## 实战练习

1. 画出一个设备树节点到 platform 驱动 `probe` 的完整路径。
2. 对照一份真实驱动代码，找出它在平台模型中的设备、驱动和资源接口。
3. 故意把 `compatible` 改错一次，观察设备模型链路哪里断了。

## 关键要点

1. platform 总线是固定设备模型，不是实体总线。
2. 设备树和 platform 模型通常是一条链上的两层。
3. 驱动排障时，先看设备出现链，再看驱动初始化链。
4. 这部分理解是 Linux 驱动能力的重要地基。
