# Linux-核心基础

## 原始问题

Linux 到底该先掌握什么，才能在学习、工作、面试和排障里真正用起来，而不是只会背命令？

## 先给结论

Linux 入门最重要的不是死记硬背命令，而是先建立一条稳定主线：

1. 先理解 Linux 主要在管理什么：文件、权限、进程、输入输出、网络、服务。
2. 先打通一个最小闭环：创建文件、赋权、执行程序、查看进程、看日志、停止进程。
3. 命令要和现象绑定记忆，不能只记语法，必须知道“命令解决什么问题、为什么这样用、错了会出现什么现象、怎么验证”。
4. 真正能落地的 Linux 能力，通常来自排障链路：看到现象，提出怀疑，设计验证，确认根因，再修复和回归验证。

如果只能做到“知道 `ls`、`cd`、`ps`、`grep` 是什么”，但不会把它们串成排查路径，就还没有真正掌握 Linux。

## 这个知识解决什么问题

这篇笔记主要解决下面几类现实问题：

1. 刚接触 Linux，不知道应该先学什么，知识点很散。
2. 会几个命令，但遇到 `Permission denied`、服务起不来、端口占用、日志找不到时不会排查。
3. 面试时只能背定义，讲不清文件权限、进程、重定向、后台运行之间的关系。
4. 项目部署到 Linux 后，不能快速判断问题在脚本、权限、路径、环境变量、日志还是服务管理。

它在 AI 时代仍然重要，因为 AI 可以帮你生成命令，但不能替你确认环境、验证风险、判断根因。Linux 基础越扎实，你越能识别 AI 给出的命令是否危险、是否适配当前系统、是否真的解决问题。

## 核心概念 / 本质机制

### 1. Linux 本质上在管理“资源”和“访问方式”

Linux 可以先粗略理解成两层：

1. 内核态：管理 CPU、内存、文件系统、设备、网络、进程调度。
2. 用户态：Shell、编辑器、编译器、应用程序、服务进程都在这里运行。

用户平时输入的命令，大多数不是“直接操作硬件”，而是通过用户态程序向内核申请资源和操作权限。

### 2. 最核心的五个对象

1. 文件：普通文件、目录、设备、套接字、管道，在 Linux 里很多东西都能用“文件”抽象来理解。
2. 权限：决定谁能读、写、执行某个对象。
3. 进程：程序运行起来以后形成进程，系统调度和资源分配围绕进程展开。
4. 输入输出：标准输入 `stdin`、标准输出 `stdout`、标准错误 `stderr` 决定程序如何接收和输出内容。
5. 服务：长期运行的后台进程，通常由 `systemd` 管理。

### 3. 为什么文件、权限、进程必须一起理解

因为在真实场景里，一个问题通常不是孤立的：

1. 脚本跑不起来，可能不是脚本内容错，而是没有执行权限。
2. 程序启动失败，可能不是程序逻辑错，而是配置文件路径不对、日志目录无写权限。
3. 服务没有响应，可能不是服务没启动，而是端口没监听、进程已退出、标准错误被重定向后没人看。

所以 Linux 学习要从“命令表”升级到“资源关系图”。

## 数据流 / 控制流 / 时序关系

下面用一条典型命令说明 Linux 的主线：

```bash
./hello.sh > out.log 2> err.log &
```

这条命令背后的控制流可以这样理解：

1. Shell 先解析命令行，识别程序、参数、重定向和后台运行符号 `&`。
2. Shell 检查 `hello.sh` 是否存在、路径是否正确、当前用户是否有执行权限。
3. Shell 创建子进程，并在子进程里把标准输出重定向到 `out.log`，把标准错误重定向到 `err.log`。
4. 子进程通过 `exec` 执行脚本解释器和脚本内容。
5. 内核负责调度该进程运行，并处理文件打开、写日志、睡眠、退出等系统调用。
6. 因为使用了 `&`，Shell 不等待程序结束，而是立刻把控制权还给终端。

这条主线把多个知识点串起来了：

1. 路径问题决定程序能否找到。
2. 权限问题决定程序能否执行和写文件。
3. 重定向决定输出去哪。
4. 进程管理决定程序是否仍在运行。
5. 日志查看决定你能不能定位问题。

## 最小可运行示例

下面是一个最小 Linux 闭环：创建脚本、赋权、后台运行、查看日志、停止进程。

```bash
mkdir -p ~/linux-demo
cd ~/linux-demo

cat > hello.sh <<'EOF'
#!/usr/bin/env bash
echo "stdout: service started"
echo "stderr: something to inspect" >&2
sleep 60
EOF

chmod 755 hello.sh
./hello.sh > out.log 2> err.log &
echo $!
ps -fp <PID>
ls -l
cat out.log
cat err.log
kill <PID>
```

预期结果：

1. `hello.sh` 被成功创建。
2. `chmod 755` 后，脚本具备执行权限。
3. 后台启动后会打印一个进程号。
4. `out.log` 里看到标准输出内容。
5. `err.log` 里看到标准错误内容。
6. `kill <PID>` 后，进程结束。

如果这个最小闭环你能完整跑通并解释清楚，就已经开始真正理解 Linux 了。

## 代码解读

### 1. `mkdir -p ~/linux-demo`

作用是创建一个实验目录。`-p` 的价值是目录已存在时不报错，适合脚本化执行。

### 2. `cat > hello.sh <<'EOF'`

这是通过 here-document 直接生成脚本文件。这里的关键不是语法本身，而是理解“脚本本质上也是文件”。

### 3. `#!/usr/bin/env bash`

这行叫 shebang，告诉系统应当用哪个解释器执行脚本。如果这行错误，脚本可能报 `bad interpreter` 或无法按预期运行。

### 4. `echo "stderr: something to inspect" >&2`

这不是普通打印，而是明确写入标准错误。很多排障场景依赖把正常输出和错误输出分开看，否则日志会混在一起。

### 5. `chmod 755 hello.sh`

这一步不是“形式要求”，而是明确把文件权限改成可执行。没有执行位时，常见现象就是：

```bash
bash: ./hello.sh: Permission denied
```

### 6. `./hello.sh > out.log 2> err.log &`

这条命令同时体现了四个关键点：

1. `./hello.sh` 表示执行当前目录下的脚本。
2. `>` 把标准输出写到文件。
3. `2>` 把标准错误写到文件。
4. `&` 让命令在后台运行。

### 7. `ps -fp <PID>`

这是确认“进程是不是真的在跑”，而不是靠猜。排障里，验证比印象更重要。

### 8. `kill <PID>`

这是最基础的进程结束方法。重点不是会背 `kill`，而是知道它针对的是进程号，而不是文件名、服务名或端口号。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 执行当前目录脚本 | `./hello.sh` | `hello.sh` | 当前目录默认通常不在 `PATH`，直接写文件名可能提示 `command not found` |
| 赋执行权限 | `chmod 755 hello.sh` | 只写 `chmod 644 hello.sh` | `644` 没有执行位，脚本无法直接运行 |
| 区分输出和错误 | `cmd > out.log 2> err.log` | `cmd > all.log` | 错误信息混入普通输出，不利于排障 |
| 精确查看进程 | `ps -fp 1234` | `ps | grep app` 后直接下结论 | `grep` 方法容易误判、漏判，还可能匹配到自己 |
| 停止明确目标 | `kill 1234` | `kill -9` 随便用 | `-9` 会跳过正常清理流程，可能造成数据未刷盘或状态不一致 |
| 带空格路径 | `cat "my file.txt"` | `cat my file.txt` | Shell 会把空格分成多个参数 |

## 边界条件与适用范围

1. 不是所有 Linux 发行版都默认使用相同工具。比如有的系统主推 `systemd`，有的容器镜像非常精简，连 `ss`、`lsof`、`bash` 都不一定有。
2. `bash`、`sh`、`zsh` 行为不完全一样。脚本 shebang 写什么，就决定用什么解释器。
3. 权限不只看 `rwx`。线上环境还可能叠加 ACL、SELinux、AppArmor、容器挂载权限。
4. “能执行”不等于“能成功运行”。脚本可能有执行权限，但依赖的解释器、配置文件、动态库、环境变量仍然缺失。
5. Windows 编辑过的脚本复制到 Linux 后，可能因为 CRLF 换行导致执行异常，这类问题很常见。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证命令 |
| --- | --- | --- |
| `Permission denied` | 文件没有执行权限；目录无访问权限；挂载参数限制执行 | `ls -l` |
| `command not found` | 当前目录不在 `PATH`；命令未安装；拼写错误 | `echo $PATH`、`which <cmd>` |
| `No such file or directory` | 路径错；脚本解释器不存在；相对路径基准错 | `pwd`、`ls`、`head -1 script.sh` |
| 服务起不来 | 配置错误；端口被占用；依赖未启动；权限不足 | `systemctl status <service>`、`journalctl -u <service>` |
| 端口访问失败 | 进程未监听；监听地址不对；防火墙限制 | `ss -lntp` |
| 日志没有输出 | 输出被重定向；程序没真正执行到；写日志目录没权限 | `ps -fp <PID>`、`ls -l`、`tail -f` |

一个推荐的最小排查顺序：

1. 先确认进程是否存在。
2. 再确认配置和路径是否正确。
3. 再确认权限是否允许访问。
4. 再确认日志有没有错误输出。
5. 最后再看网络、依赖和资源瓶颈。

## 工程落地建议

### 1. 把 Linux 命令能力变成固定排障套路

最常用的一组组合拳通常是：

1. `pwd` / `ls -l`：先确认你在哪、文件是否真的在。
2. `cat` / `less` / `tail -f`：看配置和日志。
3. `ps -ef` / `pgrep`：看进程。
4. `ss -lntp`：看端口监听。
5. `systemctl status` / `journalctl`：看服务状态和日志。
6. `df -h` / `free -h` / `top`：看磁盘、内存、CPU 资源。

### 2. 脚本工程化时尽量遵守这些规则

1. 路径尽量写清楚，避免依赖“当前目录碰巧正确”。
2. 日志分开标准输出和标准错误，方便排障。
3. 重要脚本先做最小验证，再加后台运行、定时任务或服务托管。
4. 尽量避免在脚本里滥用 `sudo` 和 `kill -9`。
5. 线上改动前先确认回滚方式，尤其是权限、服务和防火墙类修改。

### 3. 典型项目场景

1. 部署程序后访问失败，先看进程、端口、日志，不要先怀疑网络库代码。
2. 定时任务没执行，先看脚本路径、执行权限、环境变量，而不是先怀疑业务逻辑。
3. 服务重启失败，先看 `systemctl status` 和 `journalctl`，不要盲目反复重启。

## 性能、稳定性、可维护性影响

1. 命令写得越清晰，排障成本越低。模糊脚本比错误脚本更难维护，因为它看起来能跑，实际边界非常脆弱。
2. 正确使用日志重定向，能显著提升定位速度；把所有输出混在一起，会放大排障成本。
3. 谨慎使用 `kill -9`、递归删除、全局权限放开这类“快速修复”，因为它们容易把局部问题变成系统级风险。
4. 用相对路径、依赖当前目录、依赖手工环境变量的脚本，通常在开发机能跑，到服务器就出问题，可维护性很差。
5. 形成固定验证动作，如“改完就看进程、端口、日志”，比记更多命令更能提高稳定性。

## 面试 / 问答怎么讲

### 30 秒版本

Linux 核心不是背命令，而是理解文件、权限、进程、输入输出和服务之间的关系。真正会 Linux，意味着能把启动、运行、日志、权限和排障串成一个闭环。

### 3 分钟版本

Linux 学习的主线可以从一个脚本启动流程展开。先创建文件，再赋执行权限，再通过 Shell 启动进程，再用重定向把标准输出和错误输出分开，最后用 `ps`、`ss`、`journalctl` 之类命令确认进程、端口和日志。这样学的好处是命令不再是孤立记忆，而是围绕真实问题组织。

### 10 分钟版本

可以进一步结合一次真实排障来讲：比如脚本执行失败，先区分是“找不到文件”“没有执行权限”“解释器不存在”“后台已退出但没看日志”“服务起来了但没监听端口”。然后说明每类现象分别用什么命令验证，为什么这样验证，修复后如何做回归确认。这种讲法比纯背命令更像真实工程能力。

## 实战练习

1. 自己写一个脚本，分别把正常输出和错误输出重定向到不同文件，再解释每条命令做了什么。
2. 故意把脚本权限改成 `644`，观察报错，再自己恢复并总结排查链路。
3. 启动一个简单服务或脚本，让它后台运行，然后用 `ps`、`ss`、`tail -f`、`kill` 完成一次完整观测和停止流程。
4. 故意把脚本里的相对路径写错，验证 `No such file or directory` 的表现，再修正为更稳妥的写法。

## 关键要点

1. Linux 学习不要从命令表开始，而要从资源关系开始。
2. 文件、权限、进程、输入输出、服务是最先必须打通的一条主线。
3. 最小闭环比知识点罗列更重要，先能完整跑通一个脚本生命周期。
4. 排障时优先验证，不靠猜测；先看进程、路径、权限、日志，再看网络和资源。
5. 会用 AI 生成命令不等于会 Linux，真正的价值在于你能不能判断命令是否安全、是否适配环境、是否解决了根因。
