# Linux-内核日志与排障

## 原始问题

板子启动后设备不工作时，为什么很多人只会反复看 `dmesg`，却还是定位不到问题？内核日志到底该怎么看，才能把设备树、platform 设备、驱动 `probe`、中断、资源申请这些线索串成一条稳定排障主线？

## 先给结论

内核日志的价值，不是“看到报错就结束”，而是把它当成 Linux 平台行为的时间线入口。

先记住下面几个结论：

1. `dmesg` 看到的是内核环形缓冲区，不等于全部系统日志，但它通常是嵌入式 Linux 排障的第一入口。
2. 真正有效的排障，不是只搜 `error`，而是把“日志时间线 + 设备树节点 + 驱动匹配 + 资源状态”一起看。
3. 驱动 `probe` 不进、资源申请失败、`-EPROBE_DEFER`、中断没触发、设备节点没创建，都会在内核日志里留下不同类型的线索。
4. `journalctl -k`、`/proc`、`/sys`、设备树内容和驱动日志必须联动使用，单看一处很容易误判。
5. AI 可以帮你生成筛日志命令，但真正决定定位效率的，是你能不能判断哪一条日志是根因，哪一条只是连锁反应。

如果你只是“看见报错就复制到搜索引擎”，却讲不清报错前发生了什么、设备有没有出现、驱动有没有匹配、资源有没有准备好，就还没有真正掌握内核日志排障。

## 这个知识解决什么问题

这篇笔记主要解决下面几类现实问题：

1. 设备树改了以后，设备还是不工作，不知道是节点没生效还是驱动没匹配。
2. 驱动 `probe` 打印了一句失败日志，但不知道前面的真正根因在哪里。
3. 设备节点存在，但中断、时钟、GPIO、regmap、DMA 这些资源是否真的准备好，排查没有主线。
4. 面试或工作交流里，经常会被问“你怎么定位 Linux 驱动初始化失败”，但只能回答“先看 `dmesg`”。

它在 AI 时代仍然重要，因为 AI 很容易给出“看起来像经验”的命令组合，但它并不知道你当前系统到底是 `systemd`、busybox，还是裁剪过的嵌入式发行版；也不知道日志里哪条是初始化早期错误、哪条是后续重试、哪条只是症状。日志排障能力，本质上是你校验 AI、约束 AI 和超越 AI 的工程判断力。

## 核心概念 / 本质机制

### 1. 内核日志本质上是一条“系统行为时间线”

内核通过 `printk()`、`dev_err()`、`dev_warn()`、`dev_info()` 等接口把关键事件写进内核日志缓冲区。

这些日志通常来自下面几类行为：

1. 启动阶段的硬件发现与初始化。
2. 设备树节点解析和驱动匹配。
3. `probe`、`remove`、suspend、resume 等生命周期动作。
4. 中断、时钟、GPIO、DMA、regulator、IOMMU 等资源申请。
5. 异常路径，例如超时、校验失败、访问非法地址、依赖未准备好。

所以日志不是孤立文本，而是“系统刚刚做了什么”的记录。

### 2. 为什么 `dmesg` 常常有用，但又经常不够

`dmesg` 读取的是内核环形缓冲区，优点是直接、快速、普适。

但它有几个天然限制：

1. 缓冲区是环形的，旧日志可能被新日志覆盖。
2. 它只看内核日志，不等于用户态服务日志。
3. 某些系统会限制普通用户读取 `dmesg`。
4. 如果你只看“当前时刻最后几行”，很容易错过更早的根因日志。

所以实际排障经常需要同时看：

1. `dmesg`：快速看最新内核事件。
2. `journalctl -k -b`：按本次启动完整回看内核日志。
3. `/proc`：看中断、内存映射、模块、cmdline 等运行时状态。
4. `/sys`：看设备、驱动、总线、属性和资源暴露。
5. 运行中的设备树：确认系统到底加载了什么硬件描述。

### 3. 内核日志里最常见的四类排障信号

#### 3.1 匹配和生命周期信号

例如：

1. 驱动注册了没有。
2. `probe` 有没有进入。
3. `remove` 有没有触发。
4. 设备是否因为 `deferred probe` 被延后。

这类日志决定你该先查“设备出现链”，还是先查“初始化细节”。

#### 3.2 资源申请信号

例如：

1. `clk` 获取失败。
2. regulator 没准备好。
3. GPIO 申请失败。
4. IRQ 号无效。
5. `ioremap` 或 `request_mem_region` 失败。

这类日志通常说明设备和驱动已经碰上了，但初始化依赖没打通。

#### 3.3 运行期异常信号

例如：

1. 超时。
2. DMA 错误。
3. 中断风暴。
4. 总线传输失败。
5. kernel warning 或 oops。

这类日志通常意味着 `probe` 已经过了，问题发生在运行阶段。

#### 3.4 噪声和连锁反应

很多日志看起来像报错，但其实不是根因：

1. 上层驱动报“设备不存在”，真正根因可能是下层 regulator 没起来。
2. 后续功能节点初始化失败，只是因为更早的 parent device 没 probe 成功。
3. 重复出现的报错，可能只是同一个失败路径被反复重试。

排障不能只看“最红的那条”，而要找第一条真正改变系统状态的失败点。

### 4. 为什么 `-EPROBE_DEFER` 必须单独理解

嵌入式 Linux 里，很多“看起来像失败”的日志，其实是“依赖还没准备好，请稍后再试”。

典型场景：

1. 驱动要拿时钟，但时钟提供者还没注册。
2. 驱动要拿 regulator，但电源驱动还没完成初始化。
3. 驱动要拿 GPIO controller，但对应控制器还没 probe 完。

这时常见返回值是 `-EPROBE_DEFER`。它不是最终失败，而是延迟探测。

如果把它误判成真正错误，就会把精力浪费在错误方向上。

### 5. 为什么 `/proc`、`/sys` 和日志必须联动

内核日志回答的是“发生了什么”，而 `/proc`、`/sys` 更偏向回答“当前状态是什么”。

例如：

1. 日志说 IRQ 注册成功，你可以去 `/proc/interrupts` 验证有没有计数增长。
2. 日志说 platform 设备 probe 了，你可以去 `/sys/bus/platform/devices` 看设备是否存在。
3. 日志说设备树节点有问题，你可以去 `/sys/firmware/devicetree/base` 确认运行中的属性值。
4. 日志说内存资源冲突，你可以去 `/proc/iomem` 对照地址范围。

排障效率高的人，通常不是日志看得更多，而是更会把“时间线”和“状态快照”对上。

## 数据流 / 控制流 / 时序关系

下面是一个典型嵌入式 Linux 设备初始化与排障主线：

```text
Bootloader 传入 dtb
-> 内核启动并解析设备树
-> 创建设备对象
-> 驱动注册并匹配
-> probe 开始
-> 申请 reg / irq / clk / gpio / regulator
-> 初始化硬件
-> 注册中断或字符设备
-> 用户态访问设备
-> 出现异常时在日志中留下线索
```

推荐把内核日志放在这条主线里理解：

1. 日志完全没有设备相关内容，先怀疑节点没生效或驱动没注册。
2. 有 `probe` 入口日志，但后面失败，先查资源申请链。
3. `probe` 成功但运行异常，先查中断、时序、超时和数据路径。
4. 运行异常只在用户态可见，内核日志干净，可能要转去查用户态日志或协议层。

## 最小可运行示例

下面给一个适合嵌入式 Linux 排障的最小闭环，目标是判断“某个 platform 设备到底卡在哪一层”。

### 1. 先完整抓本次启动的内核日志

```bash
journalctl -k -b --no-pager | tail -n 80
```

这一步的价值是：

1. 不只看最后几条，而是先建立最近一段时间线。
2. 比只执行一次 `dmesg | tail` 更不容易错过早期错误。

### 2. 只筛目标设备关键字

```bash
journalctl -k -b --no-pager | grep -Ei "mydev|probe|defer|clk|irq|gpio"
```

这一步不是为了“看到关键词就结束”，而是快速确认：

1. 有没有出现目标设备名字。
2. 有没有出现 `probe`、defer、资源失败类线索。

### 3. 确认设备对象是否真的出现

```bash
ls /sys/bus/platform/devices
ls /sys/bus/platform/drivers
```

如果设备树节点已经转成 platform 设备，通常能在对应目录下看到设备对象；如果根本没有，优先怀疑设备树或匹配链路。

### 4. 查看运行中的设备树内容

```bash
find /sys/firmware/devicetree/base -iname "*mydev*"
hexdump -C /sys/firmware/devicetree/base/soc/mydev@10000000/status
```

这一步解决的是“我改了 dts，但系统真的用了它吗”。

### 5. 验证中断和地址资源

```bash
cat /proc/interrupts
cat /proc/iomem | grep -i mydev
```

如果日志里说 IRQ 注册成功，但 `/proc/interrupts` 计数始终不变，就说明问题可能已经转到运行期触发链，而不是初始化链。

### 6. 结合一个最小驱动日志示例

```c
static int mydev_probe(struct platform_device *pdev)
{
    struct clk *clk;

    dev_info(&pdev->dev, "probe start\n");

    clk = devm_clk_get(&pdev->dev, NULL);
    if (IS_ERR(clk))
        return dev_err_probe(&pdev->dev, PTR_ERR(clk),
                             "failed to get clock\n");

    dev_info(&pdev->dev, "probe done\n");
    return 0;
}
```

对应日志可能是：

```text
mydev 10000000.mydev: probe start
mydev 10000000.mydev: failed to get clock: -517
```

这里的关键不是背 `-517`，而是知道它通常对应 `-EPROBE_DEFER`，说明要优先去查 clock provider，而不是先怀疑 `mydev` 自己的寄存器初始化代码。

## 代码解读

### 1. 为什么推荐用 `dev_err_probe()`

它适合资源获取失败场景，原因有三点：

1. 会把设备上下文带进日志，比裸 `pr_err()` 更容易定位是哪一个设备失败。
2. 能更自然地处理 `-EPROBE_DEFER` 这类返回值。
3. 能减少重复、分散、难 grep 的错误打印写法。

### 2. 为什么 `probe start` 和 `probe done` 这种边界日志有用

很多人觉得这类日志“太啰嗦”，但在板级排障里很有价值：

1. 只看到了 `probe start`，没看到 `probe done`，说明失败发生在中间。
2. 连 `probe start` 都没有，先怀疑匹配链没打通。
3. `probe done` 看到了但设备仍不工作，问题大概率已经转到运行阶段。

日志的作用不是堆数量，而是给初始化路径打边界。

### 3. 为什么 `pr_err()` 往往不如 `dev_err()`

错误写法常见是：

```c
pr_err("failed to get clock\n");
```

这样的问题在于：

1. 日志里没有设备名。
2. 多个同类设备时很难区分是谁失败。
3. grep 结果噪声更大。

更稳妥的写法通常是：

```c
dev_err(&pdev->dev, "failed to get clock\n");
```

或者在资源获取路径里直接用 `dev_err_probe()`。

### 4. 为什么日志只能告诉你入口，不能代替状态验证

例如日志打印“irq registered”并不等于中断真的能进：

1. 中断号可能注册了，但硬件根本没触发。
2. pinctrl 可能没切到中断功能。
3. 极性可能配反了。
4. 中断被屏蔽了。

这时必须继续去 `/proc/interrupts`、寄存器、波形或上层现象里验证。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 回看日志 | `journalctl -k -b` 先看本次启动全量时间线 | 只看 `dmesg | tail` | 容易错过更早根因 |
| 设备定位 | 结合设备名、总线名、`probe` 边界日志 grep | 只搜 `error`、`fail` | 很多关键线索不含这些词 |
| 驱动日志 | `dev_info/dev_warn/dev_err/dev_err_probe` | 大量裸 `printk/pr_err` | 缺少设备上下文，难排查 |
| defer 处理 | 识别 `-EPROBE_DEFER`，追依赖提供者 | 把 defer 当最终失败 | 方向会跑偏 |
| 状态验证 | 日志和 `/sys`、`/proc` 联动 | 只看日志文本下结论 | 容易误判“看起来成功” |
| 修复验证 | 重新启动后比对关键日志和状态 | 只看一次现象消失就结束 | 容易留下偶发问题 |

## 边界条件与适用范围

1. 并不是所有系统都有 `journalctl`，精简 rootfs 上可能只有 `dmesg` 和文件日志。
2. 某些生产环境会限制 `dmesg` 访问权限，需要 root 或调整 `kernel.dmesg_restrict`。
3. 控制台打印级别、动态调试、rate limit 会影响你能看到多少日志，没看到不一定等于没发生。
4. 日志是软件观察手段，不足以覆盖电气层问题；中断、电源、时钟异常时，往往还要结合示波器、逻辑分析仪或寄存器读写。
5. 某些严重故障会导致系统在日志刷出前就卡死或重启，这时要考虑串口控制台、pstore、ramoops、netconsole 等更早期手段。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 完全搜不到设备日志 | 节点没生效；驱动没编进内核；关键词不对 | 查运行中的设备树、`zcat /proc/config.gz`、驱动注册日志 |
| 看到 `probe failed` 就直接改驱动 | 真正根因是上游时钟、GPIO、regulator 依赖缺失 | 顺着失败资源继续查 provider |
| 日志显示 `probe done`，设备还是不能用 | 运行期中断、DMA、协议、时序问题 | 查 `/proc/interrupts`、运行期日志、上层错误码 |
| 改了 dts 但日志完全没变化 | 启动仍在用旧 dtb；bootloader 路径没改对 | 对照 `/sys/firmware/devicetree/base` 和启动日志 |
| 中断相关日志都正常，但设备一直超时 | 中断没有真正触发；极性错；pinmux 错 | 查 `/proc/interrupts`、GPIO/pinctrl、波形 |
| 只盯最后一条 oops 或 error | 根因在更早的 warning 或 timeout | 按时间线往前回看 |

### 推荐排查顺序

1. 先确认问题发生在哪个阶段：启动期、`probe` 期，还是运行期。
2. 再收集本次启动完整内核日志，不要只截最后几行。
3. 再确认运行中的设备树、设备对象和驱动对象是否存在。
4. 再根据失败资源去查 clock、GPIO、IRQ、regulator、DMA 等依赖。
5. 最后结合 `/proc`、`/sys` 和硬件观测手段验证修复。

### 一条稳定的排障口令

可以把这条主线练成固定动作：

```text
先定阶段 -> 再看完整日志 -> 再看设备是否出现 -> 再看资源是否齐 -> 最后验证运行时状态
```

## 工程落地建议

### 1. 驱动日志要服务排障，而不是服务情绪

建议遵守这些规则：

1. 入口和退出边界要清楚。
2. 资源申请失败要带资源名。
3. 关键设备上下文尽量用 `dev_*` 系列接口打印。
4. 不要在高频路径无节制打印，避免淹没关键日志。

### 2. 优先建立“可 grep 的日志结构”

例如：

1. 统一设备前缀。
2. 关键阶段统一用 `probe start`、`probe done`、`irq enabled` 这种稳定关键词。
3. 错误日志尽量体现资源类别，如 `clock`、`gpio`、`regulator`、`irq`。

这样做的价值是后续可以快速脚本化筛日志，而不是每次人工通读整屏输出。

### 3. 把日志和状态检查写进验证流程

真实项目里，修完问题后至少补两类验证：

1. 日志验证：关键报错是否消失，关键成功路径是否完整出现。
2. 状态验证：`/sys`、`/proc`、中断计数、设备节点、功能结果是否符合预期。

如果只验证“现象暂时消失”，后续很容易复发。

## 性能、稳定性、可维护性影响

1. 好的日志设计本身就是可维护性设计，它直接决定后续问题定位成本。
2. 过量、无上下文的日志会放大排障噪声，让真正根因更难找。
3. 合理区分 `info`、`warn`、`err`，能让日志既保留关键时间线，又不至于淹没重点。
4. 识别 `deferred probe`、资源依赖和运行期状态，能显著减少“改错地方”的概率，提升系统稳定性。
5. 在 AI 协助开发下，日志质量比以前更重要，因为你需要更快验证 AI 生成代码到底在哪一层出了问题。

## 面试 / 问答怎么讲

### 30 秒版本

Linux 内核日志排障的核心不是“会看 `dmesg`”，而是把日志当成系统行为时间线，再结合设备树、`/sys`、`/proc` 去判断设备有没有出现、驱动有没有匹配、资源有没有准备好、运行时状态是否正常。

### 3 分钟版本

可以从一次驱动初始化失败讲起：先用 `journalctl -k -b` 回看本次启动完整内核日志，确认目标设备有没有日志、`probe` 有没有进；如果没有，就先查设备树和匹配链。如果 `probe` 进了但失败，就沿着 `clk`、GPIO、IRQ、regulator 这些资源继续查；如果 `probe` 成功但设备还不工作，再去看 `/proc/interrupts`、运行期日志和上层现象。这样讲能体现你有分层排障主线，而不是只会搜报错。

### 10 分钟版本

可以再结合 `-EPROBE_DEFER` 展开：比如驱动打印 `failed to get clock: -517`，这不一定是最终失败，而可能是时钟 provider 还没准备好。这时应该顺着 provider 去查，而不是改业务驱动。然后说明修复后如何做回归：重新启动看关键日志、确认 `/sys` 下设备对象存在、确认 `/proc/interrupts` 有计数、再验证上层功能。这种讲法更接近真实项目里的 Linux 平台排障。

## 实战练习

1. 选一个真实开发板上的 UART、I2C 或 SPI 设备，完整走一遍“日志 -> 设备树 -> `/sys` -> `/proc/interrupts`”的排查链。
2. 在一个最小 platform 驱动里，分别模拟 `clk` 获取失败和 `-EPROBE_DEFER`，观察日志差异并总结判断依据。
3. 故意把设备树里的 `status` 改成 `"disabled"`，验证为什么日志里完全看不到 `probe start`。
4. 对比 `pr_err()` 和 `dev_err_probe()` 的输出差异，整理一套你自己的驱动日志规范。
5. 练习用一句话、三分钟、十分钟三种深度解释“为什么只看 `dmesg | tail` 不够”。

## 关键要点

1. 内核日志是系统行为时间线，不是孤立报错列表。
2. `dmesg` 适合快速入口，`journalctl -k -b` 更适合完整回看。
3. 排障要把日志、设备树、`/sys`、`/proc` 和硬件状态联动起来。
4. `-EPROBE_DEFER` 不是普通失败，通常意味着依赖链还没准备好。
5. 真正的根因常常在第一条改变系统状态的失败日志，而不是最后一条连锁报错。
6. 好的驱动日志设计，本身就是长期可维护性的组成部分。
