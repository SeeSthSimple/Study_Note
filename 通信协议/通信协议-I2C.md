# 通信协议-I2C

## 原始问题

为什么I2C总线能用两根线连接多个设备？地址冲突、时钟拉伸、多主仲裁到底是怎么回事？如何设计稳定的I2C总线系统，而不是只会"调HAL库读写寄存器"？

## 先给结论

I2C协议的核心价值，是用最少的线(SDA+SCL)实现多设备共享总线，并通过地址寻址、应答机制和开漏结构解决总线仲裁和冲突检测。

先记住下面几个结论：

1. I2C是主从同步半双工协议，主机产生时钟，从机响应地址。
2. I2C使用7位或10位地址寻址，同一总线上的设备地址不能冲突。
3. 开漏输出+上拉电阻实现线与逻辑，这是I2C多主仲裁和时钟拉伸的物理基础。
4. 应答机制(ACK/NACK)让主机知道从机是否正确接收数据。
5. 现场最常见的问题不是协议本身，而是地址冲突、上拉电阻不匹配、时序参数不满足和总线电容过大。

如果只会调用I2C库读写寄存器，却讲不清地址寻址原理、为什么需要应答、时钟拉伸如何工作、多主仲裁如何避免冲突，就说明这部分还没有真正掌握。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. I2C总线上挂多个设备时出现地址冲突或通信失败。
2. 不知道如何选择合适的上拉电阻和总线速率。
3. 面试或工作中经常被问到"I2C地址寻址""时钟拉伸""多主仲裁"。
4. 项目里出现I2C通信偶发失败、读回0xFF、设备不响应时，不知道从哪里排查。

它在AI时代仍然重要，因为AI可以很快生成I2C读写代码，但它不知道你的总线上是否有地址冲突、上拉电阻是否匹配总线电容、时序参数是否满足器件要求。I2C协议理解越扎实，你越能把AI生成的代码变成真正稳定的工程方案。

## 核心概念 / 本质机制

### 1. I2C的物理层：开漏+上拉

I2C总线有两根线：
- **SDA(Serial Data)**：双向数据线
- **SCL(Serial Clock)**：时钟线

关键特性：
1. **开漏输出**：设备只能主动拉低总线，不能主动拉高。
2. **上拉电阻**：总线空闲时被上拉电阻拉高。
3. **线与逻辑**：任何设备拉低总线，总线就是低电平。

这种设计的优势：
1. 多个设备可以共享总线，不会短路。
2. 实现多主仲裁：谁拉低总线谁赢。
3. 实现时钟拉伸：从机可以拉低SCL延长时钟周期。

### 2. I2C的协议层：地址寻址

I2C使用地址寻址区分总线上的不同设备。

**7位地址模式**（最常用）：
```text
起始条件 + 7位地址 + 1位读写位 + 应答位
```

地址范围：
- 0x00-0x7F（128个地址）
- 保留地址：0x00（广播）、0x01-0x07（特殊用途）、0x78-0x7F（10位地址扩展）
- 实际可用：0x08-0x77（112个地址）

**10位地址模式**（较少用）：
```text
起始条件 + 11110XX + R/W + ACK + 8位地址 + ACK
```

地址冲突：
- 同一总线上的设备地址不能重复
- 很多I2C器件地址是固定的或只能通过几个引脚配置
- 选型时必须检查地址冲突

### 3. I2C的时序：起始、数据、应答、停止

**起始条件(START)**：
- SCL为高时，SDA从高变低
- 表示通信开始

**停止条件(STOP)**：
- SCL为高时，SDA从低变高
- 表示通信结束

**数据传输**：
- SCL为低时，SDA可以变化（数据建立）
- SCL为高时，SDA必须稳定（数据采样）
- 高位在前(MSB first)

**应答机制(ACK/NACK)**：
- 每传输8位数据后，接收方发送1位应答
- ACK(应答)：SDA拉低，表示正确接收
- NACK(非应答)：SDA保持高，表示结束或错误

### 4. 时钟拉伸(Clock Stretching)

从机可以拉低SCL延长时钟周期，用于：
1. 从机处理数据需要更多时间
2. 从机缓冲区满，需要等待

主机必须检测SCL是否被拉低，等待从机释放。

注意：
- 不是所有I2C主机都支持时钟拉伸
- 某些快速模式下禁用时钟拉伸
- 如果主机不支持，从机拉伸会导致通信失败

### 5. 多主仲裁(Multi-Master Arbitration)

I2C支持多个主机共享总线，通过仲裁避免冲突。

仲裁规则：
1. 多个主机同时发送起始条件
2. 逐位比较SDA：谁发送0谁赢（线与逻辑）
3. 发送1但检测到0的主机立即退出
4. 仲裁失败的主机等待总线空闲后重试

仲裁发生在：
- 起始条件后的地址阶段
- 数据传输阶段

### 6. 重复起始条件(Repeated START)

不释放总线，直接发起新通信。

典型用途：
```text
START + 写地址 + 寄存器地址 + Repeated START + 读地址 + 读数据 + STOP
```

优势：
1. 原子操作，避免被其他主机打断
2. 减少总线开销

## 数据流 / 控制流 / 时序关系

### I2C写操作时序

```text
主机发送START
-> 主机发送7位从机地址 + 0(写)
-> 从机发送ACK
-> 主机发送寄存器地址
-> 从机发送ACK
-> 主机发送数据
-> 从机发送ACK
-> 主机发送STOP
```

### I2C读操作时序

```text
主机发送START
-> 主机发送7位从机地址 + 1(读)
-> 从机发送ACK
-> 从机发送数据
-> 主机发送ACK(继续读)或NACK(结束读)
-> 主机发送STOP
```

### I2C先写后读时序(Repeated START)

```text
主机发送START
-> 主机发送7位从机地址 + 0(写)
-> 从机发送ACK
-> 主机发送寄存器地址
-> 从机发送ACK
-> 主机发送Repeated START
-> 主机发送7位从机地址 + 1(读)
-> 从机发送ACK
-> 从机发送数据
-> 主机发送NACK
-> 主机发送STOP
```

## 最小可运行示例

### I2C地址扫描(STM32 HAL)

```c
/* 扫描I2C总线上的所有设备 */
void i2c_scan(I2C_HandleTypeDef *hi2c)
{
    uint8_t addr;
    HAL_StatusTypeDef ret;
    
    printf("Scanning I2C bus...\n");
    
    for (addr = 0x08; addr < 0x78; addr++) {
        /* 尝试发送地址，超时100ms */
        ret = HAL_I2C_IsDeviceReady(hi2c, addr << 1, 1, 100);
        
        if (ret == HAL_OK) {
            printf("Found device at 0x%02X\n", addr);
        }
    }
    
    printf("Scan complete\n");
}
```

### I2C读写寄存器(通用模式)

```c
/* 写单个寄存器 */
int i2c_write_reg(I2C_HandleTypeDef *hi2c, uint8_t dev_addr,
                  uint8_t reg_addr, uint8_t data)
{
    uint8_t buf[2];
    buf[0] = reg_addr;
    buf[1] = data;
    
    return HAL_I2C_Master_Transmit(hi2c, dev_addr << 1, buf, 2, 100);
}

/* 读单个寄存器 */
int i2c_read_reg(I2C_HandleTypeDef *hi2c, uint8_t dev_addr,
                 uint8_t reg_addr, uint8_t *data)
{
    HAL_StatusTypeDef ret;
    
    /* 先写寄存器地址 */
    ret = HAL_I2C_Master_Transmit(hi2c, dev_addr << 1, &reg_addr, 1, 100);
    if (ret != HAL_OK)
        return ret;
    
    /* 再读数据 */
    return HAL_I2C_Master_Receive(hi2c, dev_addr << 1, data, 1, 100);
}

/* 读多个寄存器(使用Repeated START) */
int i2c_read_regs(I2C_HandleTypeDef *hi2c, uint8_t dev_addr,
                  uint8_t reg_addr, uint8_t *data, uint16_t len)
{
    return HAL_I2C_Mem_Read(hi2c, dev_addr << 1, reg_addr,
                            I2C_MEMADD_SIZE_8BIT, data, len, 100);
}
```

### I2C从机地址配置示例

很多I2C器件通过硬件引脚配置地址：

```text
器件：MPU6050(加速度计+陀螺仪)
基地址：0x68
AD0引脚：
  - AD0=0 -> 地址0x68
  - AD0=1 -> 地址0x69

器件：EEPROM 24C02
基地址：0x50
A0/A1/A2引脚：
  - A2 A1 A0 = 000 -> 地址0x50
  - A2 A1 A0 = 001 -> 地址0x51
  - A2 A1 A0 = 111 -> 地址0x57
```

### 上拉电阻计算

上拉电阻选择公式：
```
R_min = (VDD - VOL_max) / IOL
R_max = tr / (0.8473 × Cb)

其中：
- VDD：总线电压(如3.3V或5V)
- VOL_max：最大低电平输出电压(如0.4V)
- IOL：低电平输出电流(如3mA)
- tr：上升时间要求(标准模式1000ns，快速模式300ns)
- Cb：总线电容(线缆+器件，典型10-400pF)
```

典型值：
- 标准模式(100kHz)：4.7kΩ - 10kΩ
- 快速模式(400kHz)：2.2kΩ - 4.7kΩ
- 快速模式+(1MHz)：1kΩ - 2.2kΩ

## 代码解读

### 1. 为什么地址要左移1位

I2C协议中，地址帧是7位地址+1位读写位，共8位。

HAL库的地址参数是8位的：
```c
dev_addr << 1        // 写操作：7位地址左移，最低位为0
dev_addr << 1 | 1    // 读操作：7位地址左移，最低位为1
```

例如：
- 器件地址0x68
- 写地址：0x68 << 1 = 0xD0
- 读地址：0x68 << 1 | 1 = 0xD1

### 2. 为什么读寄存器要先写后读

I2C从机通常有多个内部寄存器，主机必须先告诉从机要读哪个寄存器。

流程：
1. 写操作：发送寄存器地址
2. Repeated START：不释放总线
3. 读操作：从机返回该寄存器的数据

如果不用Repeated START，中间可能被其他主机打断。

### 3. 为什么最后一个字节要发送NACK

主机读取多个字节时：
- 中间字节：发送ACK，表示继续读
- 最后字节：发送NACK，表示结束读取

从机收到NACK后，知道主机不再需要数据，释放总线。

### 4. 为什么HAL_I2C_IsDeviceReady可以扫描设备

该函数只发送地址帧，不发送数据：
```text
START + 地址 + R/W + (等待ACK) + STOP
```

如果从机存在且地址匹配，会发送ACK；否则无响应。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 地址配置 | 检查器件手册，配置硬件引脚 | 直接用默认地址 | 地址冲突导致通信失败 |
| 上拉电阻 | 根据总线电容和速率计算 | 随便选4.7kΩ | 波形畸变或速率受限 |
| 读寄存器 | 先写地址，Repeated START，再读 | 分两次独立操作 | 可能被其他主机打断 |
| 多字节读 | 最后字节发NACK | 所有字节都发ACK | 从机不知道何时停止 |
| 时序参数 | 根据器件手册配置 | 用默认值 | 时序不满足导致通信失败 |
| 错误处理 | 检查返回值，超时重试 | 不检查返回值 | 错误无法发现和恢复 |

## 边界条件与适用范围

### I2C适用场景
1. 短距离(几十厘米内)低速通信
2. 多设备共享总线(传感器、EEPROM、RTC等)
3. 引脚资源有限的场景(只需2根线)
4. 对速率要求不高的场景(最高1MHz)

### I2C不适用场景
1. 长距离通信(超过1米)
2. 高速通信(超过1MHz)
3. 实时性要求极高的场景
4. 总线电容过大的场景(超过400pF)

### 速率与距离的权衡

| 模式 | 速率 | 典型距离 | 上拉电阻 |
| --- | --- | --- | --- |
| 标准模式 | 100kHz | 1-2米 | 4.7kΩ-10kΩ |
| 快速模式 | 400kHz | 0.5-1米 | 2.2kΩ-4.7kΩ |
| 快速模式+ | 1MHz | <0.5米 | 1kΩ-2.2kΩ |

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 扫描不到设备 | 地址错误；上拉电阻缺失；接线错误 | 示波器看波形；检查地址和接线 |
| 读回全是0xFF | 从机无响应；上拉电阻过大 | 检查从机供电；测量上拉电阻 |
| 偶发通信失败 | 总线电容过大；干扰；时序不满足 | 示波器看波形；缩短线缆 |
| 多设备冲突 | 地址冲突；上拉电阻过小 | 检查地址配置；增大上拉电阻 |
| 时钟拉伸失败 | 主机不支持时钟拉伸 | 检查主机配置；降低速率 |
| 波形畸变 | 上拉电阻不匹配；总线电容过大 | 示波器测波形；调整上拉电阻 |

### 推荐排查顺序

1. 先确认硬件连接：SDA/SCL是否接对，上拉电阻是否存在。
2. 再用示波器看波形，确认信号质量和时序参数。
3. 再扫描总线，确认设备地址是否正确。
4. 再检查时序配置，确认是否满足器件要求。
5. 最后检查协议层，确认读写流程和应答机制。

## 工程落地建议

### 1. 硬件设计检查清单

- [ ] 每根总线加一对上拉电阻(SDA和SCL各一个)
- [ ] 上拉电阻阻值根据总线电容和速率计算
- [ ] 检查所有设备地址，避免冲突
- [ ] 总线长度尽量短，避免过大电容
- [ ] 使用屏蔽线或双绞线，减少干扰
- [ ] 考虑总线隔离或电平转换(3.3V/5V混用)

### 2. 软件设计检查清单

- [ ] 配置正确的时钟频率和时序参数
- [ ] 使用Repeated START实现原子读写
- [ ] 检查所有I2C操作的返回值
- [ ] 实现超时和重试机制
- [ ] 多字节读取时最后字节发送NACK
- [ ] 记录通信错误日志，便于排查

### 3. 地址管理建议

建议为每个项目建立I2C地址映射表：

| 器件 | 型号 | 基地址 | 配置引脚 | 实际地址 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 加速度计 | MPU6050 | 0x68 | AD0=0 | 0x68 | 6轴传感器 |
| EEPROM | 24C02 | 0x50 | A0-A2=000 | 0x50 | 2Kbit存储 |
| RTC | DS1307 | 0x68 | 固定 | 0x68 | 冲突! |

发现冲突后的解决方案：
1. 修改硬件配置引脚
2. 更换器件型号
3. 使用I2C多路复用器(如TCA9548A)

### 4. 调试工具

推荐工具：
1. **逻辑分析仪**：抓取I2C时序，分析协议
2. **示波器**：测量波形质量，检查上升沿
3. **I2C扫描工具**：快速发现总线上的设备
4. **I2C调试器**：模拟主机或从机，测试通信

## 性能、稳定性、可维护性影响

1. I2C地址冲突会导致通信完全失败，选型时必须检查。
2. 上拉电阻不匹配会导致波形畸变、速率受限或通信不稳定。
3. 时序参数不满足器件要求会导致偶发通信失败，难以排查。
4. 总线电容过大会限制最大速率和传输距离。

## 面试 / 问答怎么讲

### 30秒版本

I2C是主从同步半双工协议，用两根线(SDA+SCL)连接多个设备。通过7位地址寻址，应答机制确认接收，开漏输出+上拉电阻实现线与逻辑。支持多主仲裁和时钟拉伸。关键是避免地址冲突，选择合适的上拉电阻，满足时序参数。

### 3分钟版本

可以先讲I2C的物理层：开漏输出+上拉电阻实现线与逻辑，这是多主仲裁和时钟拉伸的基础。然后讲协议层：7位地址寻址，应答机制(ACK/NACK)，起始/停止条件。再讲时序：SCL低时SDA变化，SCL高时SDA采样。最后讲工程要点：地址冲突检查，上拉电阻计算，Repeated START实现原子读写。

### 10分钟版本

可以进一步结合真实项目展开，比如I2C总线连接多个传感器。讲清地址寻址原理：7位地址+1位读写位，如何避免冲突。然后讲应答机制：每8位数据后接收方发送ACK/NACK，主机如何判断从机是否正确接收。再讲时钟拉伸：从机可以拉低SCL延长时钟周期，主机必须支持。接着讲多主仲裁：逐位比较SDA，谁发送0谁赢。最后讲一个实际排障案例，比如读回0xFF，如何通过示波器定位是上拉电阻问题还是从机无响应。这种讲法更像真实工程能力。

5. 上拉电阻选择、时序参数配置、地址冲突检查是工程中最容易出问题的地方。

1. I2C是嵌入式中最常用的总线协议，理解它能让你更好地对接各种传感器和外设。
2. AI可以生成I2C代码，但地址冲突、上拉电阻、时序参数需要你的工程判断。
3. 掌握I2C原理，能让你快速验证AI生成代码的正确性，避免现场踩坑。
4. I2C排障能力是AI无法替代的，因为它需要结合硬件、电气、协议的综合判断。
