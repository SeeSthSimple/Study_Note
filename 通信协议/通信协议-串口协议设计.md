# 通信协议-串口协议设计

## 原始问题

串口链路通了，为什么设备之间的数据交换还是经常出错？怎样设计一套真正适合嵌入式工作的串口协议，而不是只会“发一串字节试试看”？

## 先给结论

串口协议设计的核心，不是“能发出去”，而是让接收方在连续字节流里稳定地完成分帧、校验、恢复和扩展。

先记住下面几个结论：

1. UART 提供的是字节流能力，不天然提供消息边界，所以协议必须自己解决分帧问题。
2. 一套可用的串口协议通常至少要考虑：帧头、长度、类型、载荷、校验、超时和错误恢复。
3. 现场最怕的不是完全收不到，而是偶发错包、粘包、半包、版本不兼容和异常恢复差。
4. 协议解析必须按状态机思路实现，而不是假设“每次刚好收到一整帧”。
5. 好协议不是字段越多越好，而是边界清楚、调试方便、扩展成本低。

如果只能把几个字节拼起来发，却讲不清为什么要有长度字段、为什么要有校验、为什么接收端必须做状态机、为什么超时恢复很重要，就说明这部分还没有真正掌握。

## 这个知识解决什么问题

这篇笔记主要解决下面几类问题：

1. 两个设备之间串口能收发，但数据经常解析失败。
2. 不知道怎么设计一套可扩展、可调试、可恢复的简单协议。
3. 面试或工作中经常被问到“你怎么设计串口通信协议”“如何处理半包和错包”。
4. 项目里出现偶发通信错误时，不知道问题在链路、电气、解析器还是协议字段设计。

它在 AI 时代仍然重要，因为 AI 可以很快生成一份“看起来像协议”的结构体和发送代码，但它通常不会替你处理粘包、超时恢复、字段兼容和现场排障可观测性。协议设计能力越扎实，你越能把 AI 生成的草稿变成真正能在设备上长期稳定运行的方案。

## 核心概念 / 本质机制

### 1. 串口链路本身不等于协议

UART 只负责把字节按顺序发出去。

它并不保证：

1. 你一次 `send` 对方就一次 `recv`。
2. 你发的 1 帧，对方就自然知道边界。
3. 任何错误都能自动恢复。

所以协议层必须自己定义：

1. 一帧从哪里开始。
2. 一帧在哪里结束。
3. 这一帧是什么类型。
4. 有多少载荷。
5. 如何判断有没有损坏。

### 2. 为什么分帧是第一问题

因为接收方拿到的是连续字节流，而不是“结构体对象”。

常见分帧思路包括：

1. 固定长度帧。
2. 起始符 + 长度字段。
3. 起始符 + 结束符。
4. 特殊转义机制。

对嵌入式项目来说，最常见也最稳妥的一类是：

1. 固定帧头。
2. 长度字段。
3. 命令字或类型字段。
4. 载荷。
5. 校验字段。

因为它兼顾了：

1. 解析简单。
2. 扩展性较好。
3. 出错后较容易重新同步。

### 3. 为什么长度字段很重要

长度字段的作用不是“让协议显得完整”，而是让接收方知道：

1. 还需要继续收多少字节。
2. 当前是否已经收满一帧。
3. 异常时该从哪里重新开始恢复。

没有长度字段时，常见问题是：

1. 遇到可变长数据难以判断边界。
2. 遇到丢字节后接收方很难恢复。
3. 调试日志只能看到字节流，无法快速对齐字段。

### 4. 为什么校验不能省

串口链路经常看起来“挺稳定”，但现场干扰、接线问题、波特率不匹配、电平不稳时，偶发错误很常见。

校验常见选择包括：

1. 简单和校验。
2. 异或校验。
3. CRC8 / CRC16。

选择思路通常是：

1. 简单协议、短帧、资源有限时，可以从异或或简单和校验起步。
2. 工业环境、帧长较长、稳定性要求高时，更常用 CRC。

### 5. 为什么解析器必须做成状态机

接收数据时常见的真实情况是：

1. 一次中断只收到 1 个字节。
2. 一次 DMA 回调收到半帧。
3. 丢了几个字节后，后面数据还会继续来。
4. 某一帧校验错了，但链路并没有停止。

所以解析器不能假设“我手里永远是一整帧”，而应该按状态机逐字节推进：

1. 等帧头。
2. 收长度。
3. 收类型。
4. 收载荷。
5. 收校验。
6. 校验通过则产出消息，否则做恢复。

### 6. 超时恢复为什么重要

很多串口协议问题不是“全部错”，而是：

1. 发到一半中断了。
2. 接收方只收到了部分字节。
3. 上一帧没收完整，下一帧又已经开始。

如果没有超时恢复机制，解析器可能会长期卡在错误状态。

常见做法是：

1. 每次收到字节时刷新时间戳。
2. 如果超过一段时间还没收完整帧，就丢弃当前缓存并回到等帧头状态。

## 数据流 / 控制流 / 时序关系

下面给一条典型串口协议链路：

```text
发送方构造帧
-> 帧头 + 长度 + 类型 + 载荷 + 校验
-> UART 驱动按字节发送
-> 接收方中断 / DMA 收到字节流
-> 协议解析状态机逐字节推进
-> 长度满足后校验
-> 校验通过则分发给对应命令处理逻辑
-> 校验失败或超时则丢弃并重新同步
```

这条链路里常见问题包括：

1. 接收缓冲太小，导致丢字节。
2. 解析器假设一次收到整帧，结果半包解析失败。
3. 校验失败后没有重同步，后续帧全部被带歪。
4. 协议没有版本或类型区分，后续扩展困难。

## 最小可运行示例

下面给一个简单协议格式：

```text
SOF  LEN  CMD  PAYLOAD...  CHECKSUM
0xAA  N   1B   N bytes     1B
```

约定说明：

1. `SOF` 固定为 `0xAA`，表示帧开始。
2. `LEN` 表示 `CMD + PAYLOAD` 的总长度。
3. `CMD` 表示命令类型。
4. `CHECKSUM` 对 `LEN`、`CMD` 和 `PAYLOAD` 做异或校验。

下面是一个简化的逐字节解析状态机：

```c
enum parser_state {
    WAIT_SOF,
    WAIT_LEN,
    WAIT_DATA,
    WAIT_CHECKSUM,
};

struct parser {
    enum parser_state state;
    unsigned char len;
    unsigned char pos;
    unsigned char checksum;
    unsigned char data[64];
};

static void parser_reset(struct parser *p)
{
    p->state = WAIT_SOF;
    p->len = 0;
    p->pos = 0;
    p->checksum = 0;
}

static int parser_feed(struct parser *p, unsigned char ch)
{
    switch (p->state) {
    case WAIT_SOF:
        if (ch == 0xAA)
            p->state = WAIT_LEN;
        break;

    case WAIT_LEN:
        if (ch == 0 || ch > sizeof(p->data)) {
            parser_reset(p);
            break;
        }
        p->len = ch;
        p->checksum = ch;
        p->pos = 0;
        p->state = WAIT_DATA;
        break;

    case WAIT_DATA:
        p->data[p->pos++] = ch;
        p->checksum ^= ch;
        if (p->pos == p->len)
            p->state = WAIT_CHECKSUM;
        break;

    case WAIT_CHECKSUM:
        if (p->checksum == ch) {
            handle_packet(p->data[0], &p->data[1], p->len - 1);
            parser_reset(p);
            return 1;
        }
        parser_reset(p);
        break;
    }

    return 0;
}
```

这个示例虽然小，但已经包含了串口协议设计最核心的点：

1. 有明确帧头。
2. 有长度字段。
3. 有命令类型。
4. 有校验。
5. 解析器按状态机逐字节推进。

## 代码解读

### 1. 为什么 `LEN` 包含 `CMD`

因为 `CMD` 本质上也是当前帧数据的一部分。

这样做的好处是：

1. 接收方知道完整数据段长度。
2. 计算校验时更自然。
3. 协议扩展时字段边界更清楚。

### 2. 为什么先检查 `LEN`

如果长度字段明显非法，比如为 0 或超过缓冲区大小，就应该立刻丢弃当前帧。

否则很容易出现：

1. 缓冲区越界。
2. 状态机长期卡在错误状态。
3. 错误数据拖坏后续解析。

### 3. 为什么校验失败后直接 `reset`

因为一旦校验失败，就说明当前帧内容已经不可信。

这时更稳妥的做法不是“硬猜哪里错了”，而是：

1. 立刻丢弃当前帧。
2. 回到 `WAIT_SOF` 等待重新同步。

### 4. 为什么这个示例还不算完整工业协议

真实项目里通常还会继续补这些内容：

1. 序号。
2. 应答 / 重传机制。
3. 超时恢复。
4. 版本兼容字段。
5. 更强的 CRC 校验。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 分帧 | 帧头 + 长度 + 校验 | 只发原始数据不定义边界 | 接收端无法稳定解析 |
| 接收解析 | 按状态机逐字节推进 | 假设一次就收到完整帧 | 半包、粘包时极易出错 |
| 长度处理 | 先做合法性检查 | 收到长度就直接信任 | 容易越界或状态失控 |
| 错误恢复 | 校验错或超时后重同步 | 错误后继续沿用旧状态 | 后续帧会被持续带歪 |
| 扩展设计 | 保留 `CMD` / 类型字段 | 不区分命令和载荷 | 版本演进困难 |
| 调试性 | 协议字段清晰、日志可打印 | 字节拼得能跑就算 | 现场排障成本高 |

## 边界条件与适用范围

1. 这篇笔记适合 MCU、传感器、小设备之间的轻量串口协议设计。
2. 如果数据量更大、可靠性要求更高或网络拓扑更复杂，可能需要更成熟的总线协议或上层协议。
3. 串口协议设计不能替代底层电气稳定性，波特率、电平、接地和布线问题仍然要单独确认。
4. 如果使用 DMA、环形缓冲区或 RTOS，解析器仍然建议保持状态机思想，只是数据入口不同。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 偶发解析失败 | 丢字节；长度错；校验不一致 | 抓原始字节流，对照字段逐项检查 |
| 一次错包后后面全错 | 没有重同步机制 | 看状态机异常路径和 reset 时机 |
| 现场偶发乱码 | 波特率不一致；电平不稳；接地问题 | 示波器、逻辑分析仪、配置核对 |
| 某命令经常失败 | 长度计算错；命令字段定义不一致 | 打印发送帧和接收解析日志 |
| 大包容易丢 | 缓冲区太小；处理不及时 | 看中断频率、缓冲区大小和任务延迟 |

### 推荐排查顺序

1. 先确认链路层是否稳定，也就是波特率、电平和接线。
2. 再抓原始字节流，确认接收端到底看到了什么。
3. 再检查帧头、长度和校验是否一致。
4. 再检查状态机在异常帧后的恢复逻辑。
5. 最后再看任务调度、缓冲区和应用层处理是否拖慢解析。

## 工程落地建议

### 1. 协议字段要先为调试服务

一套好用的串口协议，现场调试时至少应该能快速回答：

1. 这帧是什么命令。
2. 长度对不对。
3. 校验对不对。
4. 失败后怎么恢复。

### 2. 收发两端都要有统一文档

建议明确写清：

1. 字段定义。
2. 字节序。
3. 校验范围。
4. 超时规则。
5. 应答规则。

否则最常见的问题不是代码写错，而是双方理解不一致。

### 3. 协议解析和业务处理要解耦

推荐思路：

1. 解析器只负责从字节流还原出合法帧。
2. 业务层再根据 `CMD` 分发处理。

这样协议和业务都更容易维护。

## 性能、稳定性、可维护性影响

1. 串口协议设计不稳，最先受影响的是现场稳定性和联调效率。
2. 状态机式解析虽然看起来比“直接 memcpy”麻烦，但在异常恢复和维护上收益很大。
3. 字段设计清晰、校验和日志完备，能显著降低后续兼容和排障成本。

## 面试 / 问答怎么讲

### 30 秒版本

串口协议设计的核心是把连续字节流稳定还原成消息，所以必须自己解决分帧、长度、校验和错误恢复。真正可靠的方案通常用帧头、长度、命令字、载荷和校验，再用状态机逐字节解析。

### 3 分钟版本

可以先说明 UART 只提供字节流，不提供消息边界，所以协议必须定义帧格式。然后讲一个简单结构：帧头、长度、命令、载荷、校验。接收端按状态机逐字节解析，遇到校验错或超时就重同步。这样既能处理半包和粘包，也便于后续扩展。

### 10 分钟版本

可以进一步结合一个真实项目展开，比如主控和从设备通过串口通信。发送端按协议组帧，接收端通过中断或 DMA 收字节流，状态机逐字节推进；校验成功后再把消息交给业务层。然后说明为什么长度字段和校验不能省，为什么错误恢复要回到等帧头状态，为什么解析器不能直接假设一次收到完整帧。这种讲法更像真实工程能力。

## 实战练习

1. 设计一套带帧头、长度、命令、载荷和 CRC 的简单串口协议。
2. 写一个逐字节状态机解析器，故意喂入半包、错包和乱序数据做测试。
3. 给协议增加应答和超时机制，说明什么时候重发、什么时候丢弃。
4. 用逻辑分析仪抓一次串口收发，把波形和协议字段对齐。

## 关键要点

1. UART 提供的是字节流，不是天然消息边界。
2. 串口协议至少要解决分帧、校验和错误恢复。
3. 解析器必须按状态机设计，不能假设每次都收到完整帧。
4. 一套好协议不仅要能跑，还要方便扩展和现场排障。
