# 通信协议-CRC与校验

## 原始问题

为什么很多协议都要带校验？简单和校验、异或校验、CRC 到底有什么区别，工程里应该怎么选，而不是只会机械地把“CRC16”抄进代码？

## 先给结论

校验的本质，是让接收方有能力判断“这一帧数据是否可能被传输或存储过程破坏了”。

先记住下面几个结论：

1. 校验不是为了让协议显得完整，而是为了发现错误。
2. 简单和校验、异或校验适合轻量场景，但检错能力有限。
3. CRC 的优势不是“更高级”，而是对多种常见错误模式检出能力更强。
4. 选校验算法时，不能只看计算量，还要看帧长、错误场景、资源和兼容性。
5. AI 可以给你生成 CRC 代码，但如果你不知道多项式、初值、反转和字节序，就很容易算出“看起来很像但双方不一致”的结果。

## 这个知识解决什么问题

1. 协议联调时双方都说自己 CRC 对，但结果就是不匹配。
2. 不知道什么时候简单异或就够，什么时候必须上 CRC。
3. 面试和工作中常被问到“为什么要做校验”“CRC 和普通校验有什么差别”。

## 核心概念 / 本质机制

### 1. 校验到底在解决什么问题

通信和存储过程中常见错误包括：

1. 单比特翻转。
2. 突发错误。
3. 多字节错位。
4. 干扰导致的随机错误。

校验无法自动修复数据，但能帮助你发现异常并决定：

1. 丢弃。
2. 重发。
3. 进入错误处理流程。

### 2. 常见校验方式各自适合什么

#### 简单和校验

特点：

1. 实现简单。
2. 计算代价低。
3. 对某些错误模式检出能力有限。

#### 异或校验

特点：

1. 实现更简单。
2. 对某些奇数位翻转更容易发现。
3. 对复杂错误模式并不强。

#### CRC

特点：

1. 对常见突发错误检出能力更强。
2. 工业协议中非常常见。
3. 参数更多，双方更容易在细节上不一致。

### 3. 为什么 CRC 经常“明明公式一样却对不上”

因为 CRC 不只是“一个名字”，它通常还包含这些参数：

1. 多项式。
2. 初值。
3. 输入是否反转。
4. 输出是否反转。
5. 最终异或值。
6. 字节顺序。

只要任何一个不一致，结果都会不同。

### 4. 为什么协议文档必须写清校验范围

高频问题不是算法错，而是双方算的字节范围不同。

比如：

1. 是否包含帧头。
2. 是否包含长度字段。
3. 是否包含校验字段本身。

这类问题现场特别常见。

## 数据流 / 控制流 / 时序关系

```text
发送方构造帧
-> 对约定字段范围计算校验
-> 把校验值附加到帧尾
-> 接收方收到整帧后按同样规则重算
-> 与帧中校验值比较
-> 一致则进入业务处理，不一致则丢弃或重发
```

## 最小可运行示例

### 1. 异或校验

```c
static unsigned char checksum_xor(const unsigned char *buf, unsigned int len)
{
    unsigned char sum = 0;
    unsigned int i;

    for (i = 0; i < len; ++i)
        sum ^= buf[i];

    return sum;
}
```

### 2. CRC16-CCITT 的简化实现

```c
static unsigned short crc16_ccitt(const unsigned char *buf, unsigned int len)
{
    unsigned short crc = 0xFFFF;
    unsigned int i;
    int bit;

    for (i = 0; i < len; ++i) {
        crc ^= (unsigned short)buf[i] << 8;
        for (bit = 0; bit < 8; ++bit) {
            if (crc & 0x8000)
                crc = (crc << 1) ^ 0x1021;
            else
                crc <<= 1;
        }
    }

    return crc;
}
```

## 代码解读

### 1. 为什么 CRC 示例先把字节左移 8 位

因为这里是按高位优先的 16 位 CRC 迭代方式，把新输入字节并入高位部分后再逐位推进。

### 2. 为什么校验代码最怕“抄对了实现，抄错了参数”

因为很多 CRC 名字看起来接近，但：

1. 初值不同。
2. 多项式不同。
3. 反转规则不同。

最后结果就完全不同。

## 正确写法 vs 常见错误写法

| 场景 | 正确写法 | 常见错误写法 | 为什么错 |
| --- | --- | --- | --- |
| 协议文档 | 写清算法、参数、字节范围 | 只写“CRC16” | 双方很可能理解不同 |
| 代码实现 | 先用标准测试向量验证 | 写完直接联调 | 出错时难定位 |
| 校验范围 | 明确哪些字段参与计算 | 双方默认理解 | 现场高频对不上 |
| 算法选择 | 根据错误模型和复杂度选 | 一律上最复杂算法 | 不一定划算 |

## 边界条件与适用范围

1. 校验是检错手段，不是安全加密手段。
2. 某些超短帧和低风险场景，简单校验已经够用。
3. 工业和现场环境更复杂时，CRC 往往更稳妥。

## 常见坑与排查

| 现象 | 常见根因 | 优先验证方法 |
| --- | --- | --- |
| 双方 CRC 不一致 | 参数不一致；字节范围不一致 | 用固定测试向量逐项比对 |
| 某些帧总过不去 | 长度字段理解不一致；大小端错 | 打印参与计算的原始字节 |
| 现场偶发校验错 | 链路干扰；缓冲区错位 | 抓原始帧、结合波形分析 |

## 工程落地建议

1. 协议文档里把校验参数写完整，不要只写简称。
2. 为每种校验实现保留标准测试向量。
3. 日志里必要时打印参与校验的原始字段和计算结果。

## 性能、稳定性、可维护性影响

1. 校验设计是否清楚，直接影响协议稳定性和联调效率。
2. 参数文档不完整，会显著放大后续维护成本。
3. 正确的校验不是可选装饰，而是可靠通信的重要基石。

## 面试 / 问答怎么讲

### 30 秒版本

校验的目的是发现数据是否在传输或存储过程中被破坏。简单校验实现简单但检错能力有限，CRC 对常见错误模式检出更强，但必须把多项式、初值、反转和字节范围写清楚，否则双方很容易对不上。

### 3 分钟版本

可以先讲为什么要校验，再区分和校验、异或校验和 CRC 的适用场景。然后强调协议联调最常见的问题不是代码不会写，而是双方对参数和计算范围理解不一致。最后补一个 CRC16-CCITT 的例子，会更完整。

### 10 分钟版本

可以进一步结合串口或 I2C 协议展开：发送方如何组帧并计算校验，接收方如何重算并决定丢弃或重发；再说明为什么固定测试向量、字节范围日志和参数文档能显著降低联调成本。这种讲法更贴近真实工程。

## 实战练习

1. 给一份简单协议分别实现异或校验和 CRC16。
2. 选一组标准输入，手工验证 CRC 结果。
3. 故意让发送方和接收方使用不同初值，观察联调现象并定位。

## 关键要点

1. 校验的价值在于检错。
2. CRC 名字一样不代表参数一样。
3. 参数、范围、字节序必须文档化。
4. 固定测试向量非常重要。
